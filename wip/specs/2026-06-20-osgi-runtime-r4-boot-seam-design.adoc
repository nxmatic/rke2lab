= OSGi runtime R4 — the boot seam: host bootstraps Felix, reads the registry
:toc: left
:toclevels: 3

[NOTE]
====
This is the design record for milestone R4 of the OSGi runtime migration — the architectural
lift where the host process actually *boots* an embedded Felix framework and consumes the
manifests-world services from its registry. It is the companion of
link:2026-06-18-osgi-runtime-migration-design.adoc[the migration design] (which gates R4 at
its §5); this doc captures the decisions taken while cartographing and coding R4 on the
worktree `feature/osgi-runtime-r4-boot-seam`. Where the two disagree, the carto in the project
memory (`osgi-runtime-r4-boot-seam-state`) is authoritative.
====

== 1. Overview — what R4 solves

R1–R3 proved, on an embedded Felix booted *by the test harness*, that bnd-annotated
`@Component` classes publish services and `@Reference` consumers bind. R4 moves that boot into
*production*: the seed-master exec-jar boots Felix itself, inside the Pulumi callback, and the
host seam reads the three manifests services from the live registry instead of via
`ServiceLoader`.

=== The knot

Two grounded facts made the R1–R3 install pattern *not* carry to the deployed process:

* The seed-master exec-jar *shades the osgi/ bundles FLAT* — the shade `ServicesResourceTransformer`
  fuses every `META-INF/services`, the `ManifestResourceTransformer` writes ONE manifest. The
  bundles' own `Service-Component` headers and per-bundle manifests are gone; `OSGI-INF/*.xml`
  classes are present but no longer a bundle *entity*.
* `Pulumi.yaml` launches ONE `binary:` jar (not a `-cp dir/*`). The Pulumi Java runtime runs a
  single jar.

So Felix-in-the-process cannot `installBundle()` a `manifests-core` bundle that no longer exists
as a discrete entity. *R4 must give the running process installable bundles.*

=== The decision in one line

Embed the OSGi-designed bundles *intact* inside the exec-jar (stop shading them flat), boot Felix
in the Pulumi callback, install them, and read their `@Component` services from the registry.
The environment supplies only configuration — one self-contained artifact.

== 2. The two worlds (C4 — Context)

The system is one process holding two classloader worlds. The host world is flat and holds gRPC
(invariant #1565: no gRPC type ever crosses into a bundle); the OSGi world holds the pure model
bundles Felix resolves.

The criterion is *designed-for-OSGi* (§5.2). AS SHIPPED, the minimal proven embedded set is exactly
five jars — `manifests-core` (the only module with `@Component` services) plus the boot stack
(`felix.scr`, `felix.resolver`, `pax-logging-api`, `pax-logging-logback`). Everything else stays FLAT
on the host classpath and is served to the bundles via `system.packages.extra`: the passive
OSGi-designed libs (`unitrepo-core`, `cdk8s-systemd`, `netplan-core`, jackson, snakeyaml,
commons-compress) AND the jsii jars never conceived as bundles (`org.cdk8s`, `software.constructs`).
The criterion still decides *eligibility* to be a bundle; the embed list is then the MINIMAL set with
active OSGi behaviour the seam actually needs — a passive lib is left flat until something requires it
to resolve as a bundle (e.g. `netplan-core` joins only when `netplan-cli` boots Felix).

`system.packages.extra` is DERIVED, not hand-listed: `OsgiRuntime` reads each embedded bundle's
bnd-computed `Import-Package` header and re-exports those packages from the system bundle. This
keeps the export set in lock-step with bnd and lets each exec entrypoint declare only ITS bundles.

== 5. Decisions

=== 5.1 Path 2 — provide the bundles to the framework

Rather than serve the whole model flat via system-export (path 1), the bundles are installed as
real bundles Felix resolves against each other. This preserves their OSGi behaviour (SCR
activation, capabilities, metatype, lifecycle) *by construction* and is robust to the future (a
`-core` that gains a `@Component` later just works).

=== 5.2 The criterion: designed-for-OSGi, not passive-vs-active

`system.packages.extra` ⟺ "a jar never conceived as a bundle". Everything designed for OSGi goes
into the bundle world. The one exception that would force OSGi-fying a third-party jar — our
bundles consuming a *Java service* (`ServiceLoader`) it provides — is verified INACTIVE: the only
`ServiceLoader.load` calls in osgi/ load our own SPIs, zero third-party SPI is consumed.

=== 5.3 Invariant: a system export carries classes, never behaviour

A package exported via `system.packages.extra` provides TYPE RESOLUTION only — no SCR activation,
no `Provide-Capability`, no metatype, no lifecycle (the bundle manifest is discarded). So only
designed-for-OSGi-but-passive *or* not-designed-for-OSGi packages may go there.

=== 5.4 Single exporter per package (the R1 split-package hazard)

Exactly one exporter per package, else two `Class` copies → the host's typed
`getService(X.class)` silently misses. Checked on the real manifest: manifests-core exports NO
`-port` package (it only imports them), so `OsgiRuntime` is the sole (versioned) exporter of the
`-port` packages on the typed seam path — safe.

=== 5.5 Order: B → A → C

Path 2 wants manifests-core to retire ENTIRELY into the bundle world, but the host still reached
into impl types — so the wrong-direction inversions (milestone B) must land BEFORE the boot
(milestone A). The realgraph fixture deletion (milestone C) then unblocks demoting manifests-core
from `compile` to `runtime` scope, machine-enforcing "host = ports only".

NOTE (as shipped): realgraph IS deleted (WI-C0), and the host already imports zero manifests impl
type (the B inversions hold), but the `compile`→`runtime` demotion was NOT applied — manifests-core
remains `compile` scope in `exec/seed-master/pom.xml`. The rule holds in fact (no impl leak) but is not
yet machine-enforced; the demotion is a small backlog follow-up, not a blocker.

== 6. Milestone B — the three wrong-direction inversions

The host was doing manifest *description* work, reaching into manifests-core impl types. Each leak
is re-sewn behind a `-port` service. (B introduced a transient dual-path `@Reference`-under-SCR /
`ServiceLoader`; AS SHIPPED, once A booted Felix the host seam was cut to a SINGLE registry path —
`awaitService`, fail-fast — so no host-side dual-path survives. The only remaining `ServiceLoader` on
our ports is in the un-migrated CLIs, see §10 / the resume-state dominoes.)

[cols="1,3,3"]
|===
| Couture | ❌ Before (host reaches into impl) | ✅ After (host depends on a port)

| 1 (B1+B2)
| `RuntimeEnvControlplaneOverlayWriter` builds+renders a ConfigMap via `ManifestYaml` and orders
  `NodeEnvContributorRegistry`
| `NodeEnvOverlayService` port; `DefaultNodeEnvOverlayService` `@Component` owns the synthesis; host
  passes only its resolved seed variables

| 2
| `CloudConfigSecretRenderer` parses manifest YAML via `ManifestYaml.mapper()`
| `ManifestDocumentService` port exposes the deterministic parse; `ManifestYaml` is 100% internal

| 3
| `SystemdTarget` `new`s `FloxRuntimeAssets` and reads its discovered environments
| `FloxRuntimeAssetService` port (write tree + `discoveredEnvironments`); host receives the service
|===

Outcome: seed-master MAIN imports ONLY `-port` types from the osgi world — zero impl leak.

== 7. The logging chain — Pax Logging onto the host's Logback

The host bootstraps the engine, so OSGi logs must converge on the host's Logback context — one
`LoggerContext`, not two. felix.scr *swallows* component-activation failures into the OSGi
LogService, so without draining it the host sees a silent `null`. Pax Logging unifies all three
sources onto the host's Logback:

[mermaid]
....
flowchart LR
  b["bundles (org.slf4j from pax-logging-api)"]:::osgi --> pls
  fw["framework + felix.scr (OSGi LogService)"]:::osgi --> pls
  hs["host seed-master (slf4j)"]:::host --> lc
  pls["PaxLoggingService<br/>(pax-logging-logback)"]:::osgi -->|"StaticLogbackContext=true"| lc["HOST LoggerContext<br/>(logback-classic)"]:::host

  classDef host fill:#fde,stroke:#a58;
  classDef osgi fill:#eef,stroke:#88a;
....

Mechanism, verified against pax source:

* `pax-logging-api` *replaces* `org.slf4j` for bundles (provides its own `StaticLoggerBinder`) — so
  `OsgiRuntime` must STOP system-exporting `org.slf4j` (pax provides it; two providers would split).
* `pax-logging-logback` registers `org.osgi.service.log.LogService` + `LoggerFactory` — framework/SCR
  logs route through it. Threshold via `org.ops4j.pax.logging.service.frameworkEventsLogLevel`.
* `org.ops4j.pax.logging.StaticLogbackContext=true` makes pax-logging-logback reuse
  `StaticLoggerBinder#defaultLoggerContext` — the HOST's logback context — instead of a private one.
* Install order: pax-logging FIRST (before felix.scr and the model bundles) so early LogService
  events are captured.

NOTE: this supersedes an earlier intent to bury Pax in favour of a hand-rolled
`LogService→slf4j` bridge. With `StaticLogbackContext`, Pax *realises* the "logs land in the host"
principle rather than contradicting it.

== 8. Anti-patterns

* ❌ *Shade the model bundles flat and reconstruct OSGI-INF* — fights the shade transformers, erodes
  isolation, not self-describing. ✅ Embed intact, install as bundles.
* ❌ *Move `ManifestYaml` into the `-port` contract* — pollutes the pure contract with jackson/
  snakeyaml and keeps a host static call. ✅ The manifests world owns YAML render+parse as a service.
* ❌ *System-export a package whose bundle has active behaviour* — its SCR/capability/metatype goes
  silently inert. ✅ Only designed-for-OSGi-passive or not-designed-for-OSGi packages.
* ❌ *Let two bundles export the same package* — two Class copies, typed lookup misses. ✅ One exporter.
* ❌ *Run pax-logging-logback with its private context while the host has Logback* — two log systems.
  ✅ `StaticLogbackContext=true`.

== 9. Validation

* Embedded-Felix host-scope test (`@Osgi`, permanent — not `@OsgiSpike`): `OsgiRuntime` boots Felix,
  installs manifests-core, the host resolves the three seam services + the three milestone-B
  services TYPED. A split or miswire fails loudly (null / ClassCastException).
* `pulumi preview` from the repo root (flox): boots Felix in the real Pulumi callback, no master
  mutation — the behavioural go/no-go. NEVER `-Plive up` (the user's optional gesture).
* Count surefire reports (a green build with no `Tests run:` is skipped, not passed).
