= Step 2 — the bundle/host contract, four OSGi planes, two axes, a static-to-dynamic roadmap
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN, grounded on the OSGi standard read off the real jars and proven by a resolution
spike. This spec freezes the architecture frame for Step 2 (decomposition + APIs) and the scope of its
first vertical slice. It lives in `wip/` and graduates into the durable docs (`docs/architecture/`,
notably `integration-atlas.adoc`) at merge.

This version SUPERSEDES the earlier "Model B" draft (config keys as a custom `unitrepo.config.key`
resolution namespace). An OSGi completeness review — grounded on the jars in
`~/.m2/repository/org/osgi/`, not memory — showed B conflated four planes the standard keeps separate.
The corrected model is below; B is recorded only as the rejected alternative in section 4.
====

== 1. Overview — what this is and why it exists

Step 1 retired the hand-rolled manifest dependency walker: the standalone Felix `UnitResolver` now
drives production manifest synthesis behind a type-state (`assembled → resolve() → coherent`), and
`resolve()` is the single coherence-rule coordinator. That shipped resolver is the *decomposition
oracle*: a candidate module boundary is expressed as each unit's Provide/Require, fed to `resolve()`,
and a missing requirement or incoherent closure makes the resolver REFUSE — the boundary is proven
wrong, not judged by hand.

Step 2 is the migration track: re-cut the reactor into role-based modules and define the APIs/SPIs
between them. Config is the *cas-zero of the generic bundle/host contract* — the first concrete
instance of a bundle declaring a need that the host, which talks to the Pulumi engine, satisfies.
Nailing config defines the contract every other bundle (the doctor, manifests…) reuses.

The central correction this spec records: *config is not one mechanism — it spreads across four OSGi
planes the standard separates.* Putting each config concern on the right plane is what the rejected
Model B got wrong, and what the rest of this document gets right.

== 2. How the boundary was found (bottom-up, then proven)

The decomposition was derived from the *real* class-dependency graph (jdeps over compiled bytecode,
the eight non-generated reactor modules: 284 coupled classes, 1099 edges, 26 host-marked classes that
import `com.pulumi`/`io.grpc`), not from the inherited Maven module borders. The graph was hardened
with objective metrics (strongly-connected components = dependency cycles; articulation points =
natural cut hinges) crossed with a manual reading. Three coupling galaxies emerged: a host-heavy
orchestration galaxy (`controlplane.*`, hub `IncusResourceBootstrap`, articulation degree 46), a pure
closed manifests galaxy (`manifests.*`, zero Pulumi), and a dense bridge from the diagnostic code to
the persistence substrate (`bdd → pulumi.automation`).

The config subsystem surfaced as the cas-zero when establishing the doctor frontier: the doctor's
dependency on configuration pointed at a record (`BootstrapConfig`) that is *pure* (no engine type)
but mislocated in a host package, and at a config-loading seam that is *inverted* (a pure record
depending on a host loader). Both are decomposition smells the cut must correct (section 6).

== 3. The four OSGi planes (the corrected model)

Config touches four distinct planes; the OSGi standard puts each concern on a different one. Read top
(static, what the resolver decides once) to bottom (dynamic, what the running framework does). All four
facts below were verified on the jars on disk, not from memory.

[mermaid]
....
flowchart TB
  subgraph "RESOLUTION — static, the oracle"
    r1["bundle Require osgi.extender"]
    r2["host Provide osgi.extender"]
    r1 -->|wired by resolve| r2
  end
  subgraph "DELIVERY — runtime, Config Admin"
    d1["values pushed by PID"]
    d2["Metatype describes the schema"]
    d2 --> d1
  end
  subgraph "ACTIVATION — DS"
    a1["configuration-policy require"]
    a2["no config so UNSATISFIED_CONFIGURATION"]
    a1 --> a2
  end
  subgraph "REGISTRY — runtime, dynamic"
    s1["services come and go"]
    s2["DS publishes and rebinds"]
    s2 --> s1
  end
  r2 -.->|extender then delivers| d1
  d1 -.->|values present then activates| a1
  a2 -.->|activated then registers| s2
....

*RESOLUTION* (static, the oracle applies). A bundle that needs its config delivered declares `Require
osgi.extender`; the host that runs that extender `Provide`s it. `osgi.extender` is a REAL resolution
namespace — `org.osgi.namespace.extender.ExtenderNamespace`, value `"osgi.extender"`, version attribute
`"version"` (verified on the 1.0.1 jar). This is the ONLY way config touches resolution: through the
DELIVERY MECHANISM (DS = `osgi.component`, Metatype = `osgi.metatype`), never per individual key. This
is the bridge Model B reached for with a custom namespace — the standard already provides it.

*DELIVERY* (runtime). Config Admin (`org.osgi.service.cm`) pushes config VALUES by PID
(`ManagedService.updated`) AFTER resolution — values are not a resolution concern. The value SCHEMA is
described by *Metatype* (`org.osgi.service.metatype`: `ObjectClassDefinition` + `AttributeDefinition` —
type, cardinality, required/optional, default). The current `InfraConfigFragment` plus `InfraDomain`'s
typed `contribute` keys REINVENT exactly this schema.

*ACTIVATION* (DS). `configuration-policy=require` makes a component refuse to activate without its
config — the component sits in state `UNSATISFIED_CONFIGURATION`. THIS is the "loud fail on missing
config" the design wanted, and it belongs at activation, not resolution. Model B forced this loudness
into the resolver; the standard already has the right level for it.

*REGISTRY* (runtime, dynamic). Beyond the three above sits the service registry:
`BundleContext.registerService` / `getServiceReference`, `ServiceListener`
(REGISTERED/MODIFIED/UNREGISTERING), service scopes (`service.scope` = singleton/bundle/prototype).
Services come and go *while* the framework runs — versus resolution, a static snapshot. DS bridges it
(`@Component` publishes, `@Reference` consumes + rebinds). This is the plane that carries the "living"
vision (recruit / restructure specialists and domains at runtime). `ServiceLoader` — what
`NodeEnvContributor` uses today — is the STATIC, poor cousin of the registry; the live trajectory goes
through the registry, not `ServiceLoader`.

== 4. The rejected alternative — Model B

Model B modelled each config key as a Provide/Require in a custom `unitrepo.config.key` resolution
namespace: a bundle declared `Require config-key=X`, the host provided `config-value=X` read from
Pulumi, and the resolver wired need to provider. A spike proved it works *mechanically* (the resolve
reached the host, a missing key threw `ResolutionException`).

It is rejected because it is INFIDÈLE to OSGi: it pulls config VALUES into the resolution closure, which
the standard deliberately keeps OUT (values are Config Admin delivery; schema is Metatype; the loud-fail
is DS activation). B reinvented three standard mechanisms as one custom namespace, and put a runtime
concern (values) on the static plane (resolution). The correct contract keeps resolution to the
*delivery mechanism* — `Require osgi.extender` — and lets the value/schema/activation concerns live on
their own planes. See the meta-lesson: check the OSGi standard on the real jars before modelling a
custom mechanism.

== 5. The two orthogonal classification axes

A Unit's place in the system is two independent coordinates, not one. Confusing them is what made the
attach question look like a purity question.

[mermaid]
....
flowchart LR
  subgraph "axis 1 — purity"
    p1["MODEL pure describes"]
    p2["HOST actualises over the engine"]
  end
  subgraph "axis 2 — attach mechanism"
    m1["CLOSED composition edit the centre — InfraDomain enum"]
    m2["FRAGMENT host-attach merge into a host — SystemdDropIn"]
    m3["EXTENDER discovery scanned and aggregated — NodeEnvContributor"]
  end
  m1 -.->|enum to SPI trajectory| m3
....

*Axis 1 — purity (WHO actualises).* A pure MODEL describes; a HOST actualises the description over the
Pulumi engine. The line the whole decomposition follows (`model-substrate-alignment`): pure models
describe, host code imports `com.pulumi` / `io.grpc`. This axis sorts the modules (doctor-core pure,
ledger-write host, manifests pure-closed, orchestration host).

*Axis 2 — attach mechanism (HOW a Unit joins).* Orthogonal to purity. Three mechanisms, each with a
prod exemplar already in the reactor:

* *Closed composition* (today's default): add a domain = EDIT the centre. Exemplar `InfraDomain` enum
  — `InfraConfigRegistry` loops `InfraDomain.values()`; a new domain is a new enum constant. No
  resolution footprint, central edit.
* *Fragment / host-attach* (`osgi.wiring.host`): a piece names a HOST and merges into it without
  modifying it. Exemplar `SystemdDropIn` (cdk8s-systemd, in prod): names `targetUnitName`, writes a
  separate `unit.d/x.conf`, systemd merges at runtime. For AUGMENTING an existing host. (Dug in
  section 7.)
* *Extender / discovery* (`osgi.extender`): a runtime SCANS autonomous contributors and aggregates.
  Exemplar `NodeEnvContributor` (manifests, in prod): `ServiceLoader.load` over `META-INF/services/`,
  six impls discovered, no central edit. For rendering a WHOLE NEW autonomous domain.

*The key finding:* `NodeEnvContributor` IS already the extender-form of `InfraDomain` — the same
concept ("a domain declares `domainId()` and contributes"), at two maturities (enum-closed vs
SPI-discovered). The enum→extender trajectory is therefore not hypothetical: both ends already exist in
the reactor. Migrating `InfraDomain` along this axis is three gestures — enum → interface
(`domainId()` + `contribute`), each constant → a class + a `META-INF/services` line, the domain bundle
`Require osgi.extender` — and it is ORTHOGONAL to the config-plane migration (two independent axes on
the same `InfraDomain` object).

== 6. The config subsystem today (the starting point)

The config package already half-codes a per-domain contribution model, and carries two structural
defects the cut must correct:

* `InfraDomain` is a closed enum; each constant `contribute(loader)` declares its needs (incus requires
  a config dir; image a shared folder; …) and the host loader satisfies them. This is the Metatype
  schema, reinvented inline.
* `InfraConfigFragment` is the per-domain contribution (sealed); `InfraConfigRegistry` aggregates the
  fragments keyed by domain id; `Rke2labConfig` exposes them typed. `ConfigLoader` is the only class
  that touches Pulumi config, already built around a pure SPI (`SectionReader`).

Two defects, both proven from the graph:

. *Mislocated pure data.* `BootstrapConfig` is a pure record derived from `Rke2labConfig` (Path/URI/
  Duration, zero Pulumi); its only outgoing dependency is `Rke2labConfig`; yet it lives in the host
  `controlplane.incus` package. It is not a host leak — it is config in the wrong package. Resolution:
  RELOCATE to the pure config layer next to `Rke2labConfig`.
+
NOTE: a fresh jdeps pass on current bytecode (correcting an earlier draft that said "eight
`bdd → incus` edges") shows `BootstrapConfig` is imported by *33 classes across 9 packages* —
`bdd` (10), `pipeline` + `pipeline.stages` (10), `resources` (5), `systemd` (3), `readiness` (2),
`config` (2), `incus` (+ `incus.image`) (2) — of which 6 main-scope importers sit in `bdd`. So the
relocate is a ~33-call-site mechanical move (a pure `import` rewrite, no logic change), not the small
8-edge flip the draft implied. SHIPPED as the first slice (see section 12).
. *Inverted seam.* The pure `Rke2labConfig` depends directly on the host `ConfigLoader`, short-circuiting
  the `SectionReader` SPI that already exists. The pure side depends on the host side — the wrong
  direction.

There is no bootstrap self-reference: the resolver consumes no configuration (verified — neither
`UnitResolver` nor `ManifestsUniverse` reads `Rke2labConfig`), so config can join the resolved closure
without an amorçage paradox.

Vocabulary defect: `InfraConfigFragment` is MISNAMED — an OSGi *fragment* is a host-attached bundle
(`Fragment-Host`, `osgi.wiring.host`), the section-5 attach mechanism, not a config DTO. What the class
actually is, is an `ObjectClassDefinition` (a Metatype schema). RENAME it as part of the config slice.

== 7. The FRAGMENT end of the attach axis (dug)

Of the three attach mechanisms, the fragment one is the least exercised: `SystemdDropIn` is its sole
prod instance (one site: `rke2lab-server-hooks` augmenting `rke2-server.service` in
`DefaultManifestSynthesisService`). The mechanism's shape, read off the code:

* A drop-in *names* its host (`targetUnitName`) and carries only its delta ([Unit]/[Service]
  directives). It does NOT reach into the host or know the host's other contributors.
* The host (`SystemdChart`) *collects* drop-ins (`registerDropIn`, called from the `SystemdDropIn`
  constructor) and merges them at synthesis time, each into `targetUnitName.d/<id>.conf`. systemd does
  the final runtime merge.

This is precisely `osgi.wiring.host`: a fragment names a `Fragment-Host`, the framework attaches it to
that host's class space without the host's cooperation or knowledge. The defining property — *augment
an existing host, don't introduce a new one* — is what separates fragment from extender:

* *Fragment* = "I add to THAT host" (a named, existing target; the contribution is meaningless alone).
  → `SystemdDropIn` adds hooks to a unit that must already exist.
* *Extender* = "I AM a new autonomous domain; scan and aggregate me" (no named target; stands alone).
  → `NodeEnvContributor` contributes a whole env-config domain discovered by `ServiceLoader`.

Where each fits in rke2lab going forward: the fragment mechanism is the right tool whenever a slice must
*decorate* a unit owned elsewhere (drop-in directives, an extra volume mount on an existing manifest, an
extra `After=` edge) without taking ownership of it. The extender mechanism is the right tool whenever a
slice introduces a *self-standing* domain (a new specialist, a new manifest domain) that the centre
should discover rather than enumerate. The closed-composition mechanism (`InfraDomain` enum) is the
right tool while the set is small, fixed, and benefits from reading top-to-bottom in one place — which
is exactly why stage 5 (enum→extender) is DEFERRED, not stage 1: the enum is not yet a pain.

== 8. The static-to-dynamic roadmap (6 stages, each additive)

Ordering principle (chosen): static → dynamic, fidelity to OSGi (resolve before activate before
service). Each stage is additive, rests on the prior, and risk grows left → right. Four planes
(section 3) × two axes (section 5).

[mermaid]
....
flowchart LR
  s1["1 STATIC decomposition role plus purity cut validated by the resolver oracle"]
  s2["2 CONFIG cas-zero Require osgi.extender schema is Metatype"]
  s3["3 DELIVERY Config Admin by PID invert ConfigLoader seam"]
  s4["4 ACTIVATION DS configuration-policy require loud fail on missing config"]
  s5["5 ATTACH opening InfraDomain enum to extender discovered domains"]
  s6["6 REGISTRY runtime living plane recruit and restructure hot swap"]
  s1 --> s2 --> s3 --> s4 --> s5 --> s6
....

. *STATIC decomposition* — role + purity cut, modules validated by the resolver ORACLE (resolution
  plane only). Lowest risk (the oracle shipped in Step 1). Includes the `BootstrapConfig` relocate, the
  manifests soldered-adapter staying one bundle, the doctor-core / ledger-read / ledger-write split.
. *CONFIG as cas-zero* — the bundle/host contract via `Require osgi.extender`; config schema = Metatype;
  RENAME `InfraConfigFragment`. Still resolution-plane (the extender requirement). Spike PROVEN.
. *DELIVERY* — Config Admin-style by PID; invert the `Rke2labConfig → ConfigLoader` seam behind
  `SectionReader`. Values leave resolution, arrive at runtime.
. *ACTIVATION* — DS `configuration-policy=require` — the loud-fail on missing config at the right level.
. *ATTACH-MECHANISM opening* — `InfraDomain` enum → extender (domains discovered, not enumerated), using
  `NodeEnvContributor` as the prod exemplar. Orthogonal migration to the config-plane one.
. *REGISTRY runtime* — the LIVING plane: recruit / restructure at runtime, hot-swap; specialists and
  composite cabinets become live services. Highest risk, gated.

Status: PROVEN/shipped = the Step-1 resolver, the config-extender spike
(`ConfigExtenderResolutionSpike`), the `SystemdDropIn` + `NodeEnvContributor` exemplars.
DESIGNED-not-built = stages 2–5 frontiers. SHIPPED = stage 1, slice 1 (the `BootstrapConfig`
relocate). DEFERRED v2 = stage 6.

[IMPORTANT]
====
*There is no OSGi framework runtime in production today.* Verified on the bytecode + poms: rke2lab
uses Felix only as a resolution ALGORITHM — `new ResolverImpl(...)` called directly inside
`UnitResolver`; the only OSGi artifact on the classpath is `org.apache.felix.resolver`. There is no
`BundleContext`, no framework launch, no Config Admin (`felix.cm`), no DS/SCR (`felix.scr`), no Metatype
runtime; `seed-master`'s entrypoint is a plain `main()` → Pulumi. This splits the roadmap by cost, not
just by risk:

* Stages 1–2 (RESOLUTION plane) ride the shipped resolver algorithm — cheap, oracle-backed.
* Stage 2's *Metatype* piece is just descriptive types (`ObjectClassDefinition` shape) + the
  `InfraConfigFragment` rename — pure modelling, no runtime needed.
* Stages 3–4 (DELIVERY = Config Admin push-by-PID; ACTIVATION = DS `configuration-policy`) are genuine
  *runtime* mechanisms with NO container to host them. They are a real architectural lift (stand up or
  emulate an OSGi runtime), NOT small increments — sequence them deliberately, after the static cut.
====

== 9. Proof — the spike

`ConfigExtenderResolutionSpike` (seed-master test scope) expresses the cas-zero at the corrected grain
against the real shipped resolver: a host unit `Provide`s the config-delivery extenders
(`osgi.extender` = `osgi.metatype` 1.4 + `osgi.component` 1.5); a config-bearing domain bundle
`Require`s both; the Felix resolver wires them. Two assertions, green (surefire-counted, full reactor
rebuilt with the build-cache disabled):

. *The contract holds.* Resolving the domain bundle reaches the host provider, and both required
  extenders wire (the wire count is asserted, not merely "it resolved").
. *Missing extender fails loudly.* With the host running only Metatype (not the component extender), the
  resolve throws `ResolutionException` — not a silent empty closure. This is the anti-cheat: the
  resolver discriminates a bad frontier.

The spike is throwaway; the kept artifacts are this spec and the verdict. It replaces the deleted
per-key `ConfigCapabilityResolutionSpike` of Model B.

== 11. Scope and deferrals

*In scope — the FIRST slice* (decided in section 12).

*Captured as a guarantee, not built:* the composite specialist model (independent → cabinet → clinic →
hospital as fractal Units aggregating their members' Provide/Require) — capturing it is what forces
one-specialist-one-Unit at the leaf; nothing composite is constructed in this slice. The doctor frontier
is an *instance* of the same contract, parked for a later slice.

*Deferred (v2):* live re-resolution / hot-swap (the REGISTRY plane, stage 6); the
attach-mechanism opening (stage 5) that turns the closed `InfraDomain` enum into discovered bundles.

== 12. The first shippable slice

SHIPPED scope = *the `BootstrapConfig` relocate, ALONE*, the lowest-risk oracle-backed cut. (An
earlier draft folded the doctor-core / ledger-read / ledger-write split into this same slice; a fresh
jdeps pass corrected that — see the note below — so the split is re-scoped to a later slice.) Rationale:

* It rests entirely on the resolution plane, which the shipped Step-1 oracle already validates — no new
  runtime mechanism (Config Admin, DS, the registry) is introduced.
* The `BootstrapConfig` relocate is a pure move with a single dependency (`Rke2labConfig`); it corrects
  a proven graph defect (config in a host package) with no logic change — a mechanical ~33-call-site
  `import` rewrite (section 6).
* It defers every concern that carries runtime risk (delivery values, activation policy, the living
  registry) and the orthogonal attach-mechanism opening, keeping the first slice on one plane and
  reviewable as a single static cut.

[IMPORTANT]
====
*The doctor-core / ledger-read / ledger-write "split" is NOT a relocate — it is boundary CREATION.*
Verified on current bytecode: there are no `doctor*` or `ledger*` packages today; the doctor record
model, the read-side and the host write-side are interleaved across `bdd` + `readiness` + `resources`.
So that slice must first MAP which class belongs to which new module (a cartography phase), then express
each as a Unit's Provide/Require for the oracle to validate — materially larger and riskier than the
relocate. It is therefore its own later slice, not part of slice 1. This is why slice 1 shipped as the
relocate alone.
====

NOTE: the exact module borders (which classes land in doctor-core vs ledger-read vs ledger-write, and
the precise `bdd → incus` edge count) are RE-DERIVED from a fresh jdeps run on current bytecode before
implementation — the `/tmp` analysis the design rested on is ephemeral, and a static cut of this size
deserves current data, not stale numbers.

The config-extender contract (stage 2) is PROVEN by the spike but need not ship in slice 1 — it can be
the second slice, once the static cut has landed and the module borders exist for the extender
requirement to sit on. This sequencing keeps each merge monotone against the atlas.
