= OSGi runtime migration — from resolution-algorithm to a launched framework
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN. This spec maps the surface of, and plans, the final OSGi push: rebuilding the
pre-OSGi services as NATIVE OSGi services *up to the runtime*, until `master` can be provisioned under a
real Felix framework. It is cartography + a sliced migration plan, NOT runtime code — no framework is
launched in `main()` by this document.

It lives in `wip/specs/` and graduates into the durable atlas
(`docs/architecture/integration-atlas.adoc`) and the manifests/config architecture docs when the first
runtime slice materialises.

*The cap decision is settled (not re-litigated here):* we go all the way to the OSGi runtime. The
objection "production mounts no framework today" — true, and recorded as corrected fact #3 of the Step-2
design (Felix is used only as a resolution *algorithm*, `new ResolverImpl(...)`, never a launched
framework) — describes the *transitional* state we are now deliberately leaving. The production *target*
IS an OSGi system.
====

== 1. Overview — what "up to the runtime" means

The Step-2 roadmap (`2026-06-17-config-bundle-host-contract-design.adoc`) froze four OSGi planes and a
six-stage static→dynamic sequence. Three things have shipped on the *resolution* plane: the standalone
`UnitResolver` drives production manifest synthesis (Step 1); the config-extender contract is
spike-proven (stage 2); and the bnd-annotations spike proved *Java annotations are the source of truth*
— bnd generates the manifest headers and `OSGI-INF` descriptors from `@Component` / `@Capability` /
`@ObjectClassDefinition`, no hand-written headers. The Maven re-layout into `osgi/` / `host/` / `exec/`
(steps 1–5) is done and merged.

What remains is the part the roadmap flagged as "a genuine architectural lift, not small increments":
stages 3–6, where config values are *delivered* at runtime, components *activate*, and services live in
a *registry* — none of which has a container to host it today. This spec is that lift. It is organised
around one distinction that governs everything:

* *Geste A — DECLARATION* (build-time, no runtime). An annotation (`@Component`, `@Capability`,
  `@ObjectClassDefinition`) that bnd reads to emit a manifest header or an `OSGI-INF/*.xml` descriptor.
  Proven on the bench; needs no framework.
* *Geste B — CONSUMPTION* (runtime). `@Reference` injection, a registry lookup, a component lifecycle.
  Requires Declarative Services (SCR) running inside a *launched* framework. This is the new capability
  this spec designs and sequences.

The whole migration is the disciplined crossing from A to B: declare first (cheap, additive, reversible),
then stand up the runtime that lets us consume the declarations, then move each consumption site across,
then delete the static mechanism.

.The governing distinction — geste A (declare, build-time) vs geste B (consume, runtime). The dashed line is the only thing this whole phase has to cross.

== 2. The migration surface (cartography, grounded on HEAD)

The surface is small and clean. Two mechanisms shadow standard OSGi services today
(`osgi-logging-and-cli-debt`), and only one of them is on the runtime path: `java.util.ServiceLoader` +
`META-INF/services/` standing in for the *service registry* + *Declarative Services*. (The logback Log
shadow is a separate exec/-relocation chore, not a runtime concern — out of scope here.)

=== 2.2 The two consumption shapes

* *Singleton-service* (four of the five): exactly one provider, looked up and called. `@Reference`
  with mandatory unary cardinality is the literal replacement; `singleSpiProvider`'s "throw if not
  exactly one" becomes SCR's `UNSATISFIED_REFERENCE`.
* *Aggregate-extender* (`NodeEnvContributor`): N providers discovered and ordered.
  `@Reference(cardinality=MULTIPLE)` on a `List<NodeEnvContributor>` is the replacement; this is the
  `osgi.extender` discovery shape named in the Step-2 attach axis, now realised at runtime. The hand
  ordering in `NodeEnvContributorRegistry.orderedContributors()` becomes a component property
  (`service.ranking`) or stays an explicit sort over the injected list — a slice decision.

== 3. What already exists toward the runtime (the short ladder)

The single most consequential cartography finding: *the runtime is almost entirely already wired in the
BOM.* The lift is far shorter than "stand up an OSGi runtime from scratch."

[cols="2,1,2",options="header"]
|===
| Artifact (in `bom/pom.xml`) | Present? | Role on the runtime path

| `org.apache.felix.framework` 7.0.5 | ✅ | the launchable framework itself
| `org.apache.felix.configadmin` 1.9.26 | ✅ | DELIVERY plane (Config Admin, stage 3)
| `org.apache.felix.metatype` 1.2.4 | ✅ | schema runtime (proven typed by P2 on the bench)
| `org.apache.felix.log` 1.3.0 | ✅ | OSGi Log service (the idiomatic Log shadow's target)
| `osgi.core` 8.0.0 + the three `*.annotations` | ✅ | API + the geste-A construction annotations
| `org.apache.felix.resolver` 2.0.4 | ✅ | the resolution algorithm (already in production use)
| *`org.apache.felix.scr`* | ❌ *MISSING* | *ACTIVATION plane (Declarative Services runtime) — the one gap*
|===

And the test harness already *launches a real framework*: `FelixFrameworkExtension`
(`osgi/osgi-bench/osgi-bench-testkit`) does `factory.newFramework(config).init().start()`, installs
bundles from the classpath, and resolves them — all as a plain JUnit5 extension that runs in surefire
*and* VSCode Test Explorer (`osgi-test-in-vscode-three-ways`). `MetatypeIntrospectionSpikeTest` already
does `felix.installFromClasspath("org.apache.felix.metatype").start()` then reads a typed service from
the registry. *The same gesture installs `org.apache.felix.scr` the moment it is in the BOM* — so every
runtime slice below is validated on a real Felix engine *without* `-Plive`. `-Plive` is reserved for the
one slice that actualises a real `master` over Pulumi.

This is the geste-A/geste-B boundary made concrete: geste A is proven (annotations → headers/descriptors,
the bnd spike); geste B is blocked by exactly two things — `felix.scr` absent from the BOM, and no
framework launched in `main()`. Slice 1 closes the first; slice 4 closes the second.

=== 4.1 Where Felix boots — Pulumi outer, Felix inner, gRPC flat

The governing constraint is already proven, not assumed: *gRPC must stay on the flat host classloader*
(`docrepo-dag-state` — issue #1565, gRPC transport discovery is a `ServiceLoader` keyed on the TCCL that
bundle isolation breaks; the `spike/osgi-grpc-host` test PASSED by pinning the TCCL in a host-side
mediation seam). `seed-master` IS the Pulumi program: `main()` → `ApplicationPipeline.run()` →
`Pulumi.run(ctx → body)` when `PULUMI_MONITOR` is set, else standalone (`ApplicationPipeline:39`).
`Pulumi.run` takes over the lifecycle; the SDK opens gRPC channels back to the engine.

Therefore the framework is *not* the outermost shell.

.C4 L2 — components inside the seed-master process at runtime. The nesting (Pulumi callback wraps the framework) and the seam (host reads the registry, gRPC never crosses into a bundle) are the two things to get right.

Felix is embedded as a *host-owned service*, started by the composition root *inside* the Pulumi
callback. The pure `osgi/` bundles (manifests, netplan, the future doctor-core) run in the bundle world;
the host, holding gRPC on its flat loader, consumes their *descriptions* from the registry across the
yellow seam and actualises them — exactly the "OSGi models describe, the host actualises over the engine"
line (`model-substrate-alignment`), now made runtime rather than build-time. No gRPC type ever crosses
into a bundle, so #1565 cannot occur by construction. The seam reads the service *typed* (no reflection)
because `system.packages.extra` exports the API package from the system bundle so host and bundle share
one copy of the interface — the bench's proven trick (`osgi-test-in-vscode-three-ways`).

=== 4.2 SCR vs the bare registry — recommend SCR

Two ways to publish/consume services once a framework runs:

* *Bare registry*: the host calls `BundleContext.registerService(...)` for each provider and
  `getServiceReference(...)` to consume. No new artifact. But this is `ServiceLoader`-with-extra-steps —
  the wiring stays imperative and hand-written, betraying the bnd-annotations decision that *the Java
  `@Component` is the source of truth*.
* *Declarative Services (SCR)*: `@Component` classes auto-publish at activation; `@Reference` auto-wires
  and rebinds. Idiomatic, declarative, and the direct continuation of the proven annotation work. Costs
  one BOM line (`org.apache.felix.scr`) and a framework that runs the SCR extender.

*Recommendation: SCR.* The bnd-annotations spike already committed to annotations-as-source-of-truth and
already emits the `Require osgi.extender=osgi.component` headers; choosing the bare registry now would
make those headers decorative. "Fully integrated OSGi up to the runtime" means Declarative Services. The
bare registry survives only as the mechanism the *host seam* uses to read a service it consumes from
outside the bundle world (the host is not itself a DS component) — see §4.3.

=== 4.3 The consume seam — bundles use `@Reference`, the host uses the registry API

A subtlety the cartography forces: consumption splits by who is consuming.

* *Inside the bundle world* (e.g. `NodeEnvContributorRegistry` consuming the 6 contributors, or
  `DefaultManifestUpdateGate` consuming the synthesis service): the consumer is itself a bundle class →
  it becomes a `@Component` with `@Reference`. Fully declarative.
* *At the host seam* (`IncusResourceBootstrap`, `EntryGatePolicyEnforcer` in `exec/seed-master`): the
  host is *not* a bundle and must not become one (it holds gRPC). It consumes the pure-model services
  via the plain registry API (`getServiceReference` / `getService`) — the same typed-access pattern the
  bench proved with `system.packages.extra` exporting the API package from the system bundle so the host
  and the bundle share one copy of the interface (`osgi-test-in-vscode-three-ways`). This is the only
  place the "bare registry" survives, and it is correct there: it is the hexagonal *adapter* reading a
  *port*.

|===
| Phase | Mechanism | Plane / geste

| *declare* | bnd reads `@Component` → emits `OSGI-INF/<c>.xml` + `Service-Component` + `Require

`UNSATISFIED_CONFIGURATION` until Config Admin delivers it — the "loud fail on missing config" at the
right level. Config Admin (already in the BOM) is the DELIVERY half; it is sequenced as its own slice
after the service migration proves SCR works.

== 6. What is deliberately NOT in this phase

* No runtime code — this is the cartography + plan; the first code is slice R1 on a fresh branch.
* No Log-service migration — the logback shadow is an `exec/`-relocation chore
  (`osgi-logging-and-cli-debt`), not on the runtime path; `felix.log` is in the BOM for when it is taken
  up.
* No doctor-core / ledger split — that is the Step-2 static-decomposition cartography slice
  (`config-bundle-host-contract-design` §12), orthogonal to and sequenced independently of the runtime
  lift.
* No federation transport / distributed OSGi services — the v2 north-star
  (`docrepo-dag-state`), gated far beyond this phase.

=== Verdict — does it hold?

. *The additive beat (R1–R4) is monotone: yes.* Diagram G→H erases no built box. The 5 SPIs, their
  providers, and `UnitResolver` (Felix-as-algorithm) are unchanged. The `ServiceLoader` box survives
  through R4 — both paths coexist while each consumption site is walked across. The green additions
  (`felix.scr`, the `@Component` annotations on the *same* provider classes, the registry, the
  `@Reference`/seam consumers) are NEW, beside the old path, not rewrites of it.

. *One honest edit, named:* R3/R4 change the *consumers* — `DefaultManifestUpdateGate` and
  `NodeEnvContributorRegistry` become `@Component`s, the host sites read the registry instead of
