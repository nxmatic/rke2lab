= Runbook & Doctor — Layer 3 Plan (write side: serialize the diagnostic layer)
:toc: left

> *For agentic workers:* implement task-by-task; steps use `- [ ]` for tracking. Builds/tests are
> runnable by Claude (compile/test/`pulumi preview` are dry-runs — CLAUDE.md). Single-dev,
> sequential, NO compat shims: when a path is superseded, delete it and update all call sites in the
> same change. *Docs convention:* this plan describes behaviour in prose + diagrams, NOT Java
> snippets — the executor has codebase context; the design lives in
> link:layer3-medical-record-design.adoc[layer3-medical-record-design.adoc].

*Goal:* make the stack state self-describing — each checkpoint `ComponentResource` carries its own
serialized consultation report (diagnostic layer only), and the cluster→systemd edge becomes a real
persisted `dependsOn`, behind a single-source `Checkpoint` enum join key.

*Architecture:* Pulumi state holds the graph, update history holds the time; we serialize ONLY the
diagnostic layer (`Symptom`/`Dossier`/`RemediationPlan`), per node, additively. The stack's
top-level outputs (`OutputBuilder`) are *untouched* — the Stage-B contract stays byte-identical.

*Tech stack:* Java 25 (flox toolchain), Pulumi-java `ComponentResource`, JGiven (render), JUnit5 +
Mockito (test). Build: `flox activate -- ./mvnw … -pl :seed-master -am`.

*Scope — this plan is the WRITE side only.* The post-hoc reconstruction tool (parse `pulumi stack
export` → rebuild DAG → graft → render) and the "our model = source" renderer flip
(`RunbookRenderingTest` assertion) are a SEPARATE follow-up plan. Reason: you cannot reconstruct what
is not yet written; the write side is independently valuable (state becomes queryable via `pulumi
stack output`) and the runtime runbook already renders from the in-memory model, unchanged.

== Hard guard (do not break)

Top-level stack outputs (everything `OutputBuilder.buildOutputs(...)` emits) stay *byte-identical*:
`handoffReady`→`nextStep`, `bootstrapStatus`, the 7 `cluster*` keys, the systemd-adapter flat keys.
The new diagnostic data lives ONLY *under* each checkpoint `ComponentResource` (via
`registerOutputs`), never at top level. `ClusterReadinessProjectionTest` is the pin and must stay
green unchanged.

== Task 1: `Checkpoint` enum — the single-source join key

Replaces the two hand-aligned literal pairs (`"cluster-readiness"` ↔ `"seed-cluster-readiness"`,
`"systemd-adapter"` ↔ `"seed-systemd-adapter"`) with one source. *Identity ONLY — never the edge*
(the dependency lives on the resource, Task 2). Shape: see the UML class diagram in the design doc.

*Files:*

* Create: `seed-master/src/main/java/io/nxmatic/rke2lab/controlplane/bdd/Checkpoint.java`
* Test: `seed-master/src/test/java/io/nxmatic/rke2lab/controlplane/bdd/CheckpointTest.java`
* Modify: `…/pipeline/stages/ClusterReadinessStage.java:38`, `…/pipeline/stages/SystemdAdapterStage.java:40`, `…/resources/ResourceCreationPipeline.java:118,129`

*Steps:*

- [ ] *Step 1 — write the failing test.* `CheckpointTest` asserts the two constants expose the right
  identity: `CLUSTER_READINESS.slug()` = `"cluster-readiness"` and `.resourceName()` =
  `"seed-cluster-readiness"`; `SYSTEMD_ADAPTER.slug()` = `"systemd-adapter"` and `.resourceName()` =
  `"seed-systemd-adapter"`. This pins that the resource name is derived from the slug.
- [ ] *Step 2 — run it, verify it fails.*
  `flox activate -- ./mvnw test -Dmaven.build.cache.skipCache=false -pl :seed-master -am -DskipTests=false -Dtest=CheckpointTest`
  → FAIL (`Checkpoint` does not exist, compilation error).
- [ ] *Step 3 — create the enum.* Two constants (`SYSTEMD_ADAPTER`, `CLUSTER_READINESS`) each holding
  a kebab `slug`; `slug()` returns it; `resourceName()` returns `"seed-" + slug`. Javadoc states the
  invariant: identity only, never topology (the edge is on the resource `dependsOn`), and the
  single-source rationale (the clusterApi/cluster-api pattern).
- [ ] *Step 4 — run the test, verify it passes.* Same command as Step 2 → PASS.
- [ ] *Step 5 — wire the two stages.* In both `ClusterReadinessStage` and `SystemdAdapterStage`,
  replace the `private static final String SCENARIO_ID = "<literal>"` with the enum's `slug()`
  (`Checkpoint.CLUSTER_READINESS.slug()` / `Checkpoint.SYSTEMD_ADAPTER.slug()`); add the import.
  Everything else (the `ConsultationReport(SCENARIO_ID, …)` calls) is unchanged.
- [ ] *Step 6 — wire the two resource names.* In `ResourceCreationPipeline`, replace the
  `"seed-systemd-adapter"` and `"seed-cluster-readiness"` literals (lines 118, 129) with the enum's
  `resourceName()`; add the import.
- [ ] *Step 7 — full build, all green.*
  `flox activate -- ./mvnw package -Dmaven.build.cache.skipCache=false -pl :seed-master -am -DskipTests=false`
  → BUILD SUCCESS, `Tests run:` present, all green (33+).
- [ ] *Step 8 — commit.* `feat(doctor): Checkpoint enum — single-source join key for the medical record`
  (the enum, its test, the two stages, the pipeline).

== Task 2: the single-source edge — cluster resource really `dependsOn` systemd resource

Today both resources are siblings under `readinessDependency()`; the cluster→systemd edge lives only
in the BDD nesting (see the design's before/after diagram). Move it to where the state persists it.
No unit-test seam for the resource graph (no Pulumi mock-test precedent) → verified by compile +
`pulumi preview`.

*Files:* Modify `…/resources/ResourceCreationPipeline.java` (`withReadiness()`, ~lines 124-132).

*Steps:*

- [ ] *Step 1 — repoint the dependency.* In `PulumiResourceBuilder.withReadiness()`, change the
  `ClusterReadinessResource`'s dependency argument from `bootstrapResult.readinessDependency()` to
  `this.systemdAdapter` (the real business dependency). `withSystemdAdapter()` runs before
  `withReadiness()` in the builder chain, so `this.systemdAdapter` is set. The eager scenario play is
  ordered by the builder, NOT by `dependsOn`, so this changes only the persisted graph (design review
  verified this safe). The standalone path builds no `ClusterReadinessResource`, so it is unaffected.
- [ ] *Step 2 — compile + existing tests green.*
  `flox activate -- ./mvnw package -Dmaven.build.cache.skipCache=false -pl :seed-master -am -DskipTests=false`
  → BUILD SUCCESS, all green (no test asserts the resource graph; graph-only change).
- [ ] *Step 3 — verify the persisted edge via preview.*
  `flox activate -- pulumi preview --cwd seed-master --diff 2>&1 | grep -iA2 "cluster-readiness\|ClusterReadiness"`
  → the `seed-cluster-readiness` component shows its dependency on `seed-systemd-adapter` (no longer
  only the common `readinessDependency`). If preview cannot run here (provisioning blocked on the
  dbus probe per memory), record that and defer to a user-run preview — Step 2's compile is the
  blocking gate.
- [ ] *Step 4 — commit.* `feat(doctor): persist the cluster→systemd-adapter edge on the resource (single source)`.

== Task 4: per-node `registerOutputs` — graft the report onto each resource

Each checkpoint resource registers its OWN consultation report (when present) as an additive output,
joined from the shared `ConsultationLog` by `Checkpoint.slug()` at construction time. Top-level
outputs untouched.

The write-time join — why ordering is safe (the scenario plays, recording into the shared log,
*before* the resource is built, so the report is already there to graft):

[mermaid]
....
sequenceDiagram
  participant B as PulumiResourceBuilder
  participant Log as ConsultationLog (shared)
  participant Res as Checkpoint resource

  Note over B: withSystemdAdapter() then withReadiness()
  B->>B: playClusterReadiness(true) / systemd already played
  B->>Log: stage records ConsultationReport(slug, …) on a symptom
  B->>B: consultationFor(checkpoint) — filter log by slug
  B->>Res: new …Resource(name, result, Optional<report>, dependsOn)
  Res->>Res: registerOutputs(… + consultationReport when present)
....

*Files:* Modify `…/systemd/SystemdAdapterResource.java`, `…/readiness/ClusterReadinessResource.java`,
`…/resources/ResourceCreationPipeline.java` (`withSystemdAdapter()`, `withReadiness()`).
Construction sites verified: these two resources are built ONLY in `ResourceCreationPipeline` (no
test instantiates them), so the constructor-signature change has a single call-site each.

*Steps:*

- [ ] *Step 1 — `SystemdAdapterResource` takes and registers an optional report.* Add an
  `Optional<ConsultationReport>` constructor parameter; in the output-map builder, when it is
  present, put one additive key `consultationReport` = `report.toOutputMap()`. The existing summary
  keys are unchanged.
- [ ] *Step 2 — `ClusterReadinessResource` takes and registers an optional report.* Same: add the
  `Optional<ConsultationReport>` parameter and the single additive `consultationReport` key. The 9
  existing `cluster*`/`handoffReady`/`bootstrapStatus` keys do NOT move — that preserves the guard.
- [ ] *Step 3 — add the write-time join helper in `ResourceCreationPipeline`.* A private
  `consultationFor(Checkpoint)` returning `Optional<ConsultationReport>`: null-safe on a missing log,
  otherwise the first report in `consultations.consultations()` whose `checkpointId()` equals the
  checkpoint's `slug()`.
- [ ] *Step 4 — pass the reports at construction.* `withSystemdAdapter()` passes
  `consultationFor(Checkpoint.SYSTEMD_ADAPTER)`; `withReadiness()` plays the scenario first (so the
  cluster report is already logged), then passes `consultationFor(Checkpoint.CLUSTER_READINESS)`.
- [ ] *Step 5 — full build, all green (guard held; outputs additive only).*
  `flox activate -- ./mvnw package -Dmaven.build.cache.skipCache=false -pl :seed-master -am -DskipTests=false`
  → BUILD SUCCESS, all green; in particular `ClusterReadinessProjectionTest` unchanged (top-level
  handoff keys did not move).
- [ ] *Step 6 — verify the diagnostic output appears only on a simulated failure.*
  `flox activate -- pulumi preview --cwd seed-master -c rke2lab:policy.preview.simulate.systemd-adapter=connection-refused 2>&1 | grep -i "consultationReport\|systemd-adapter"`
  → under `seed-systemd-adapter`, a `consultationReport` output appears (the simulated incident
  raised a symptom → report recorded → serialized). A healthy preview (no simulate) shows NO
  `consultationReport` key (reactive model). If preview cannot run here, defer to a user-run preview
  and rely on Step 5's build + Task 3's serialization test.
- [ ] *Step 7 — commit.* `feat(doctor): register the per-node consultation report into the checkpoint resource state`.
