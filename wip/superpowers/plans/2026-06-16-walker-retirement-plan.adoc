*No-Java-in-docs convention* ([[docs-diagrams-not-java]]): this plan describes each
TDD step's *behaviour* in prose, with diagrams for tricky interactions. Exact file
paths and shell commands are kept (they aid execution). The implementer has the
codebase in context, so prose suffices — do NOT expect Java snippets here.
====

*Goal:* Make the merged Felix `UnitResolver` drive production manifest synthesis,
retiring the hand-rolled ordering trio, behind a type-state (`AssembledRegistry` →
`resolve` → `CoherentRegistry`) so the constructor only builds and `resolve` is the
single coherence gate.

*Architecture:* The fine-layer `UnitResource` universe (domains + units) is built
from the *already-assembled, policy-applied* `ManifestsDomainRegistry` by a promoted
`ManifestsUniverse` adapter; `resolve` runs `UnitResolver`, topo-sorts the `require`
edges (excluding `requireAll` containment), and returns a `CoherentRegistry` carrying
the visit order; `DefaultManifestSynthesisService` drives the unchanged visitor over
that order.

*Tech Stack:* Java 25 (flox toolchain), Maven reactor (`-am`, never `install`),
Apache Felix Resolver 2.0.4 + `org.osgi:osgi.core:8.0.0` (already in `unitrepo-core`),
JUnit 5.

*Spec:* `wip/superpowers/specs/2026-06-16-walker-retirement-design.adoc`.

== The key production difference — registry-as-input

[IMPORTANT]
====
The seed-master *test* `ManifestsUniverse` builds its OWN registry via a private
`buildRealRegistry()` with an all-enabled policy. *Production must not do that.* In
production the registry already exists and is *policy-filtered*
(`DefaultManifestSynthesisService` builds it via `buildDomainRegistry` then
`applyManifestDomainPolicy`). So the promoted adapter takes an existing
`ManifestsDomainRegistry` as a constructor parameter and reads its `domains()` /
`manifestUnits()` / `requireDomainIdForManifestsUnit()` — it never builds its own.
This is the faithful production form of the test adapter, not a new decision.
====

== Task 3: `ManifestsVisitOrder` — topo-sort the `require` edges into a visit order

*Files:*

* Create: `manifests/src/main/java/io/nxmatic/rke2lab/unitrepo/ManifestsVisitOrder.java`
* Test: `manifests/src/test/java/io/nxmatic/rke2lab/unitrepo/ManifestsVisitOrderTest.java`

Given a resolved wiring (`Map<Resource, List<Wire>>` from `UnitResolver.resolve`) and
the universe's `byId` map, produce the *manifest-unit* visit order: a topological
order over the `require` edges only, excluding `requireAll` containment edges.

*Behaviour:* build a dependency graph whose nodes are the manifest-units in the
closure and whose edges are the `require` wires whose capability namespace is
`unitrepo.unit` (the real `dependsOnManifestsUnitIds` edges); ignore wires on the
`unitrepo.manifest.domain` containment namespace and any `requireAll`-sourced wire;
topologically sort so a unit appears after all units it requires; return the ordered
`List<ManifestsUnit>` (or ordered unit ids the caller maps back). A cycle (no valid
linearization) throws a diagnosable exception naming the offending units.

[mermaid]
....
flowchart LR
  WIRING["resolved wiring"]
  PICK["pick require wires on unitrepo.unit"]
  DROP["drop requireAll containment wires"]
  GRAPH["dependency graph units"]
  TOPO["topological sort"]
  ORDER["unit visit order"]
  WIRING --> PICK
  PICK --> GRAPH
  WIRING --> DROP
  GRAPH --> TOPO
  TOPO --> ORDER
....

- [ ] *Step 1: Write the failing tests.* Create `ManifestsVisitOrderTest` with three
  behaviours, each driven against a small hand-made universe resolved by `UnitResolver`:
  (a) *order validity* — for a real depends-on chain (A requires B requires C), the
  order places C before B before A, and a domain before a domain that depends on it;
  (b) *containment excluded* — two sibling units in the same domain with no
  depends-on between them are not forced into a relative order by their shared domain
  membership (assert both present, no spurious ordering constraint); (c) *cycle fails*
  — a unit-level cycle makes the sort throw a diagnosable exception.

- [ ] *Step 2: Run; verify it fails to compile* (`ManifestsVisitOrder` missing). Same
  `-Dtest=ManifestsVisitOrderTest` command shape as Task 2 Step 2.

- [ ] *Step 3: Implement `ManifestsVisitOrder`* per the behaviour above (filter
  `require` wires on the unit namespace, build the graph, Kahn or DFS topo-sort with
  cycle detection). Keep it a pure function of (wiring, byId) — no synthesis side
  effects.

== Task 5: Introduce the type-state and rewire synthesis; delete the trio + validation

*Files:*

* Create: `manifests/src/main/java/io/nxmatic/rke2lab/manifests/CoherentManifestsDomainRegistry.java`
* Modify: `manifests/src/main/java/io/nxmatic/rke2lab/manifests/ManifestsDomainRegistry.java`
* Modify: `manifests/src/main/java/io/nxmatic/rke2lab/manifests/DefaultManifestSynthesisService.java`
* Delete: `manifests/src/main/java/io/nxmatic/rke2lab/manifests/ManifestsUnitDependencyApplier.java`
* Test: `manifests/src/test/java/io/nxmatic/rke2lab/manifests/RegistryResolveTest.java`

This is the integration task: it makes `ManifestsDomainRegistry` the *assembled*
state, adds the `resolve` transition returning a `CoherentManifestsDomainRegistry`
that carries the visit order, rewires the synthesis loop to that order, and deletes
the trio and the constructor validation in the same change.

[mermaid]
....
flowchart TB
  ASM["ManifestsDomainRegistry assembled build only"]
  RESOLVE["resolve build universe run resolver topo-sort"]
  COH["CoherentManifestsDomainRegistry visit order"]
  SYNTH["DefaultManifestSynthesisService drive visitor"]
  VISITOR["manifestUnitVisitor UNCHANGED"]
  ASM --> RESOLVE
  RESOLVE --> COH
  COH --> SYNTH
  SYNTH --> VISITOR
....

*Behaviour:*

* `ManifestsDomainRegistry` constructor: keep the index building
  (`domainsById`, `manifestUnits`, `domainIdByManifestsUnitId`); *remove* the two
  `validate*` calls. It must never throw on a malformed graph — only on the existing
  structural guards (duplicate domain id, duplicate unit assignment, empty domains),
  which are construction invariants, not coherence checks.
* Add `resolve()` on `ManifestsDomainRegistry`: builds the fine-layer universe
  (`ManifestsUniverse`), resolves it with `UnitResolver` from a synthesis root that
  `requireAll`s every domain, derives the order via `ManifestsVisitOrder`, and returns
  a `CoherentManifestsDomainRegistry` holding the ordered `List<ManifestsUnit>` (and
  whatever the visitor loop needs). Incoherence (cycle, unsatisfiable, cross-domain
  per Task 4) surfaces here as a thrown exception.
* `CoherentManifestsDomainRegistry`: exposes the visit order (e.g. `visitOrder()`
  returning `List<ManifestsUnit>`) and the model accessors the synthesis still needs
  (`requireDomainIdForManifestsUnit`, delegating to the assembled registry). It does
  NOT expose a way to re-resolve. This is the only type with an order.
* Delete `ManifestsUnitDependencyApplier` entirely, and delete from
  `ManifestsDomainRegistry`: `applyManifestsUnitWithDomainDependencies`,
  `applyDomainWithDependencies`, `validateDomainDependencies`,
  `validateManifestsUnitDependencies`, `dependsOnDomainTransitively`,
  `validateManifestsUnitAcyclic`.
* `DefaultManifestSynthesisService.buildAndApplyUnits` (the inner `DomainRegistryStage`):
  replace the per-unit loop that called `applyManifestsUnitWithDomainDependencies`
  with: call `registry.resolve()` once, then iterate `coherent.visitOrder()` calling
  `manifestUnitVisitor.visit(unit, context)` per unit, building the same
  `ManifestsUnitContext(chart, domainId, manifestUnitId, resolver)` it builds today.
  Drop the `ManifestsUnitDependencyApplier` and `ManifestsUnitRegistry` instantiation
  if they become unused (verify `ManifestsUnitRegistry` has no other consumer; if it
  does, leave it).

- [ ] *Step 1: Write the failing tests* in `RegistryResolveTest`: (a) *construction
  never throws* — building a `ManifestsDomainRegistry` over a graph that the old
  validation would have rejected (e.g. an acyclic but cross-domain-irregular graph)
  succeeds at construction; (b) *type-state* — there is no visit order on the
  assembled registry; `resolve()` returns a `CoherentManifestsDomainRegistry` that
  exposes `visitOrder()`; (c) *cycle throws at resolve* — a unit cycle makes
  `resolve()` throw, not the constructor. (The "no order on assembled" check is an
  API-shape assertion: the assembled type simply has no `visitOrder` method.)

- [ ] *Step 2: Run; verify failure* (`CoherentManifestsDomainRegistry` / `resolve`
  missing). `-Dtest=RegistryResolveTest`.

- [ ] *Step 3: Implement* the type-state (`resolve` + `CoherentManifestsDomainRegistry`),
  remove the constructor validation calls, delete the six registry methods, and delete
  the `ManifestsUnitDependencyApplier` file. Rewire
  `DefaultManifestSynthesisService.buildAndApplyUnits` to the resolve + visit-order
  loop. Update all call sites in the same change (no compatibility branch).

- [ ] *Step 4: Run the manifests + seed-master tests; count.*
