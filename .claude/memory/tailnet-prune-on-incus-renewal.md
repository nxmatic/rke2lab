**Tailnet stale-device GC — the deterministic trigger FOUND (design converged 2026-09-02, NOT coded).**

**Problem** (render-loop backlog item 4, see [[manifests-publish-in-cluster-render]]): on a cold-start / re-grow the incus master is deleted+recreated, but its tailscale devices (headscale/tailscale, incl. the PaC `pac-webhook` device via the tailscale operator) linger in the tailnet → the new node's devices get a `-N` suffix (`pac-webhook-2.mammoth-skate.ts.net`) → the GitHub App webhook (pointed at `pac-webhook…`) delivers to the dead device → PaC never fires the render. The open question was always the DETERMINISTic TRIGGER (the operator has no ephemeral knob; a steady-state re-grow doesn't touch it).

**★ The trigger = incus instance renewal.** In `host/pulumi/incus-ingress/.../InstanceGrow.java` `createInstance()`, the `Instance "seed-instance"` has `deleteBeforeReplace(true)` + `replaceOnChanges(["config","config.*"])`; a cold-start/rebuild changes `user.rke2lab.imageBuildChecksum` / `imageFingerprint` → delete+recreate. That IS the exact moment the old node's devices go stale.

**Design (user-driven):** a `com.pulumi.command.local.Command` (NEW dep `com.pulumi:command` — no Command usage exists host-side yet) in InstanceGrow, `triggers=[imageFingerprint]` (re-fires on instance replacement), `create` = `sleep <delay>; manage-tailnet --prune-stale-devices --stale-after <threshold> --yes`.
- **Delay is REQUIRED** (user's point): tailscale doesn't mark a device offline instantly, and `--prune-stale-devices --stale-after <t>` only deletes devices offline LONGER than t. So `sleep` (a few s → ~15-30s) lets Tailscale register the just-deleted node offline + exceed the threshold. `--stale-after` short enough to catch the fresh-offline node; single-node cluster → only the master's devices are tagged → low prune risk. `--yes` needed (dry-run by default).
- **The binary** = ndh flake output `inputs.ndh.apps.${system}.manage-tailnet` (type app; darwin, built via `ndhStoreApiDarwin`). rke2lab ALREADY has `ndh.url="github:seedmatic/ndh/develop"` as a flake input → reachable, NO ndh checkout needed for the binary. Src: `ndh:modules/.common.d/manage-tailnet.d/manage-tailnet.sh`.
- **The auth** = the Tailscale SaaS API (`api.tailscale.com/api/v2`), OAuth client-secret → short-lived token. `manage-tailnet` currently HARDCODES reading its OWN `.secrets` via sops (`[tailnet][tailscale][client]`, requires cwd=ndh repo root + `[ -f .secrets ]` guard + sops age key). To use from rke2lab WITHOUT the ndh checkout/sops → **parameterize manage-tailnet to accept the OAuth client_secret via env/arg on the prune path** (ndh change).
- **Creds source** = rke2lab's own tailscale OAuth. `.secrets` (rke2lab) has `kubernetes.…tailscale = {name: operator-oauth, replicateTo: [mesh-system]}` (the REPLICATION POINTER only) + `TailscaleManifestsUnit` renders `Secret operator-oauth {client_id, client_secret}` (replicated from source). Same tailnet (mammoth-skate), operator OAuth has device-write scope → has delete for prune. **KEY MODE FACT (user):** in STANDALONE/dev the worktree `.secrets` is CLEAR (`.gitattributes: .secrets filter=sops-yaml` smudges it on checkout — verified 0 `ENC[`, no `sops:` block); IN-CLUSTER the git sops filter is NOT configured → `.secrets` stays encrypted. Instance-renewal is a standalone/dev op (the user runs the cold-start `pulumi up`) → the Command runs where `.secrets` is clear → read the OAuth directly, no `sops -d`. **OPEN detail to pin at impl: the RAW operator-oauth client_secret VALUE is NOT in `.secrets` (that block is only the replication config) — it comes from the seal's revealed `ReplicatorSourceSecretsMaterial`; locate its exact path/reveal before wiring the Command's env.**

**What refinement CHANGED vs the earlier draft:**
- **AUTH — the code forced PARAMETERIZE (not checkout, not clear-.secrets).** manage-tailnet's preflight REFUSES a non-encrypted `.secrets` and `authenticate()` always `sops -d`s its OWN `.secrets` (schema `tailnet.tailscale.client`). So pointing it at rke2lab's clear `.secrets` was IMPOSSIBLE. → ndh change: `--client-secret-file <path>` bypasses the `.secrets` preflight + sops read (reads the bare `tskey-client-…` scalar); incompatible with `--rotate-auth-key` (which writes `.secrets`). **KILLED the "locate the raw operator-oauth seal value" open item:** rke2lab holds NO tailscale creds — the `.secrets` block (line 70) is only the REPLICATION POINTER (`name: operator-oauth → mesh-system`). The real OAuth is ndh's, user-mirrored on the operator host at `~/.local/share/ndh/tailnet.tailscale.client` = `TailscaleOauthClientGateway.NDH_CLIENT_PATH` (host-runtime). The Command feeds THAT path. **Single-mode, not both:** the incus GROW is standalone-only (the user's `pulumi up` on the operator host) → the mirror file always resolves; no in-cluster path needed.
- **DELAY/`--stale-after` — grounded in Tailscale code, NOT guessed (user: "on devrait le définir en fonction du code dans tailscale … j'aime pas attendre pour rien").** headscale (open, mirrors the Tailscale protocol) `hscontrol/poll.go`: `keepAliveInterval = 50 * time.Second` + ~10s offline grace. So a LIVE connected device's `lastSeen` can be up to ~50s old between keepalives → a threshold < 50s FALSE-PRUNES a live device (this REVERSED the user's initial "aggressive 30s" pick). **Final: `--stale-after 90s`, ZERO sleep.** 90s > 50s+grace never false-prunes a live device; `deleteBeforeReplace` kills the old node FIRST → it's offline for the whole new-instance boot (minutes) → already well past 90s when the Command runs → no wait. Pathological sub-90s boot: prune missed that run, self-heals next grow.

**★★ SEPARATE BLOCKER — RESOLVED (2026-09-03, rke2lab `388d85f8c`).** `nix run .#deploy -- dev up` failed `NoClassDefFoundError: clusterpki/contract/AdminCredentials` at jGiven stage construction (`ClusterSeedScenario$When`, before the grow). NOT the tailnet change.

ROOT CAUSE (a real staging-extension timing bug): the shade-exclude injection encodes the dual-realm FLAT-keep — a per-assembly demand (`DualRealmFlatDemand`) read from the exec module's OWN compiled classes. `StagingExecutionStrategy.reconfigureStaging` computed it BEFORE `delegate().execute()`, i.e. **before compile** → `target/classes` empty → a `type=dual-realm` carrier consumed ONLY by the exec's own host code (`ClusterSeedScenario`→`clusterpki.contract`) registered NO demand → folded OSGi-only → flat copy vanished → runtime NoClassDef. incus-ingress-contract / seed-broker-codec stayed flat only because a DEPENDENCY jar consumes them (seen pre-compile). The `REALM_BOUNDARY` gate (post-compile) considered it flat-reachable → the gate and the shade DISAGREED. Decisive proof: a clean build (`-Dmaven.build.cache.enabled=false`, ANY lane) gave 0 flat clusterpki — the "standalone works" nxmatic jar (9 flat) was a STALE-incremental artifact (target/classes populated by a prior build). So "make nix == standalone" was INVERTED: nix was correct, standalone stale.

FIX (user chose "compute demand AFTER compile"): split the two injection faces in `StagingExecutionStrategy.execute` — STAGING artifact-items (demand-independent) injected up front as before; SHADE excludes injected by a **wrapped `MojoExecutionRunner`** the instant before the shade mojo runs (compile has populated target/classes by then). Single delegation (build-cache decorator preserved); mutation still lands before `getConfiguredMojo`. Aligns the demand switch with the gate (already post-compile). PROVEN end-to-end on a clean build (cache dropped): jar has 9 clusterpki flat + AdminCredentials + staged bundle; log `[osgi-staging] seed-master: +48 shade excludes (post-compile dual-realm flat demand)`; all 10 staging-extension test classes green. The extension is a RELEASE (v1.0.0) installed to `~/.m2` (shared) via the bootstrap `mvn -f maven-embed-staging-ext/pom.xml -pl :staging-extension -am install` — must be reinstalled for the fix to take effect (the user did). This unblocks the cold-start `nix run .#deploy`. See [[manifests-publish-in-cluster-render]].
