= Systemd Resource Provisioning
:toc:
:toc-placement: preamble

== Overview

Systemd units and scripts follow a cross-module build pattern where the **manifests module** is the single source of truth, and **seed-master** consumes them via Maven dependency unpacking.

=== Component Ownership

[cols="1,2,3"]
|===
| Component | Owner | Purpose

| Systemd units (`.service`)
| manifests module
| Service definitions, oneshot units, dependencies

| Systemd scripts (`.sh`)
| manifests module
| Executable scripts invoked by units

| Classpath loading
| seed-master (`SystemdTarget.java`)
| Reads from `META-INF/.../incus/manifests/systemd/` via `ClasspathTreeCopier`

| Host materialization
| seed-master
| Copies from classpath to `/srv/host/systemd-{units,scripts}.d/`
|===

**Key Points**:
- `ClasspathTreeCopier` walks the classpath resource tree (not filesystem)
- Writes to staging directory during Pulumi apply (host-state preparation)
- `HostAssetRootLifecycle.syncStagingToFinal()` rsyncs to `/srv/host/`
- Incus pushes `/srv/host/` to control node via `incus file push -r`

=== Build Flow

[mermaid]
....
graph LR
    A[manifests/src/main/resources/systemd/] -->|Maven JAR| B[manifests-0.1.0-SNAPSHOT.jar]
    B -->|Maven assembly| C[manifests-0.1.0-SNAPSHOT-manifests-d.zip]
    C -->|dependency:unpack| D[seed-master/target/generated-resources/META-INF/.../incus/manifests/systemd/]
    D -->|Maven resources| E[seed-master JAR classpath]
    E -->|ClasspathTreeCopier| F[/srv/host/systemd-units.d/]
    E -->|ClasspathTreeCopier| G[/srv/host/systemd-scripts.d/]
....

**Step-by-step**:

1. **manifests module** packages `src/main/resources/systemd/` into its JAR
2. **manifests module** creates `manifests-d.zip` classifier artifact (via `maven-assembly-plugin`)
3. **seed-master** unpacks `manifests-d.zip` during `generate-resources` phase into `target/generated-resources/META-INF/io.nxmatic/rk2lab/controlplane/incus/manifests/`
4. **seed-master** includes generated-resources in its JAR classpath
5. **SystemdTarget** reads from classpath `META-INF/.../incus/manifests/systemd/` via `ClasspathTreeCopier`
6. **SystemdTarget.materialize()** copies to staging paths, which sync to `/srv/host/`

== Adding New Systemd Resources

**IMPORTANT**: Always add systemd files to the **manifests module**, never directly to seed-master.

=== Correct Location

```
manifests/src/main/resources/systemd/systemd-scripts/your-script.sh
manifests/src/main/resources/systemd/systemd-units/your-unit.service
```

=== Incorrect Location (Anti-pattern)

❌ **DO NOT** create files in:
```
seed-master/src/main/resources/io/nxmatic/.../systemd/...
seed-master/src/main/resources/incus/manifests/systemd/...
```

These locations bypass the manifests-d artifact and won't be included in the build.

=== Example: Adding a Post-Cluster Resource Unit

**Step 1**: Create the script in manifests module

```bash
cat > manifests/src/main/resources/systemd/systemd-scripts/rke2lab-my-resource-apply.sh <<'EOF'
#!/usr/bin/env -S bash -exu -o pipefail
source <(flox activate --dir /var/lib/rancher/rke2)
kubectl apply -f /srv/host/manifests/my-layer/staged/my-resource.yaml
EOF
chmod +x manifests/src/main/resources/systemd/systemd-scripts/rke2lab-my-resource-apply.sh
```

**Step 2**: Create the unit in manifests module

```bash
cat > manifests/src/main/resources/systemd/systemd-units/rke2lab-my-resource-apply.service <<'EOF'
[Unit]
Description=Apply staged my-resource manifest
After=rke2-server.service
ConditionPathExists=/srv/host/manifests/my-layer/staged/my-resource.yaml

[Service]
Type=oneshot
ExecStart=/srv/host/systemd-scripts.d/rke2lab-my-resource-apply.sh
RemainAfterExit=true
Restart=on-failure
RestartSec=10s

[Install]
WantedBy=multi-user.target
EOF
```

**Step 3**: Rebuild

```bash
./mvnw clean package -pl :manifests,:seed-master
```

**Step 4**: Verify unpacking

```bash
ls seed-master/target/generated-resources/META-INF/io.nxmatic/rk2lab/controlplane/incus/manifests/systemd/systemd-scripts/rke2lab-my-resource-apply.sh
ls seed-master/target/generated-resources/META-INF/io.nxmatic/rk2lab/controlplane/incus/manifests/systemd/systemd-units/rke2lab-my-resource-apply.service
```

**Step 5**: Deploy

```bash
pulumi up
```

The new files will be materialized to `/srv/host/systemd-{units,scripts}.d/` during host-state preparation.

== Maven Configuration Reference

=== manifests/pom.xml

**Resource inclusion** (standard):
```xml
<resources>
  <resource>
    <directory>${project.basedir}/src/main/resources</directory>
  </resource>
</resources>
```

**Assembly plugin** (creates `manifests-d.zip`):
```xml
<plugin>
  <artifactId>maven-assembly-plugin</artifactId>
  <executions>
    <execution>
      <id>manifests-d</id>
      <phase>package</phase>
      <goals><goal>single</goal></goals>
      <configuration>
        <descriptors>
          <descriptor>src/assembly/manifests-d.xml</descriptor>
        </descriptors>
      </configuration>
    </execution>
  </executions>
</plugin>
```

=== seed-master/pom.xml

**Dependency plugin** (unpacks `manifests-d.zip`):
```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-dependency-plugin</artifactId>
  <executions>
    <execution>
      <id>unpack-manifests-bundle</id>
      <phase>generate-resources</phase>
      <goals><goal>unpack</goal></goals>
      <configuration>
        <artifactItems>
          <artifactItem>
            <groupId>io.nxmatic.rke2lab</groupId>
            <artifactId>manifests</artifactId>
            <classifier>manifests-d</classifier>
            <type>zip</type>
            <outputDirectory>
              ${project.build.directory}/generated-resources/META-INF/io.nxmatic/rk2lab/controlplane/incus/manifests
            </outputDirectory>
          </artifactItem>
        </artifactItems>
      </configuration>
    </execution>
  </executions>
</plugin>
```

**Resources inclusion** (includes generated-resources):
```xml
<resources>
  <resource>
    <directory>${project.basedir}/src/main/resources</directory>
  </resource>
  <resource>
    <directory>${project.build.directory}/generated-resources</directory>
  </resource>
</resources>
```

== Classpath Loading in seed-master

**SystemdTarget.java**:
```java
private static final String CLASSPATH_ROOT = "META-INF/io.nxmatic/rk2lab/controlplane";
private static final String CLASSPATH_SYSTEMD_SCRIPTS_ROOT =
    CLASSPATH_ROOT + "/incus/manifests/systemd/systemd-scripts";
private static final String CLASSPATH_SYSTEMD_UNITS_ROOT =
    CLASSPATH_ROOT + "/incus/manifests/systemd/systemd-units";

@Override
public void materialize(BootstrapPaths paths) throws IOException {
  ClasspathTreeCopier.copy(CLASSPATH_SYSTEMD_SCRIPTS_ROOT, paths.scriptsRoot(), true);
  ClasspathTreeCopier.copy(CLASSPATH_SYSTEMD_UNITS_ROOT, paths.systemdRoot(), false);
  // ...
}
```

`ClasspathTreeCopier` walks the classpath resource tree and copies to the target directory. The files end up at:
- `/srv/host/systemd-scripts.d/rke2lab-*.sh`
- `/srv/host/systemd-units.d/rke2lab-*.service`

== Troubleshooting

=== Files not appearing in /srv/host/

**Symptom**: Added a systemd file but it's not in `/srv/host/systemd-{units,scripts}.d/` after `pulumi up`.

**Check 1**: Is the file in the manifests module?
```bash
ls manifests/src/main/resources/systemd/systemd-scripts/your-file.sh
```

**Check 2**: Was manifests rebuilt?
```bash
unzip -l manifests/target/manifests-0.1.0-SNAPSHOT-manifests-d.zip | grep your-file
```

**Check 3**: Did seed-master unpack it?
```bash
ls seed-master/target/generated-resources/META-INF/io.nxmatic/rk2lab/controlplane/incus/manifests/systemd/systemd-scripts/your-file.sh
```

**Check 4**: Is it in the seed-master JAR?
```bash
jar tf seed-master/target/seed-master-0.1.0-SNAPSHOT.jar | grep your-file
```

**Fix**: Rebuild both modules:
```bash
./mvnw clean package -pl :manifests,:seed-master
```

=== Files in wrong module

**Symptom**: Created files in `seed-master/src/main/resources/` but they don't appear.

**Why**: The manifests-d artifact is the only source for systemd resources. Files added directly to seed-master are ignored by `SystemdTarget`.

**Fix**: Move files to manifests module and rebuild:
```bash
git mv seed-master/src/main/resources/.../your-file.sh \
        manifests/src/main/resources/systemd/systemd-scripts/
./mvnw clean package -pl :manifests,:seed-master
```

== Design Rationale

**Why manifests module owns systemd resources**:

1. **Single source of truth**: Systemd units are infrastructure-as-code, co-located with Kubernetes manifests and other runtime resources
2. **Reusability**: Multiple provisioning targets (seed-master, future workers) can consume the same artifact
3. **Versioning**: The manifests-d artifact is versioned alongside manifest layers, ensuring consistency
4. **Build caching**: Maven reactor can cache manifests-d.zip, avoiding unnecessary rebuilds of seed-master
5. **Separation of concerns**: manifests module knows WHAT to deploy, seed-master knows WHERE to deploy it

**Why not generate at runtime**:

- Systemd units are static declarations, not dynamic config (unlike Kubernetes manifests that vary by cluster)
- Pre-packaging them simplifies seed-master's runtime (no template engine, no file I/O beyond copying)
- Build-time validation: syntax errors caught by linters during Maven build, not at Pulumi apply time
