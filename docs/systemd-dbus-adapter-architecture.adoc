This document defines the architecture for the new `systemd-adapter` module and intentionally splits diagrams into small reviewable units.

IMPORTANT: current implementation is shell-backed (`systemctl` via `ShellSystemdStatusSnapshotProvider`).
Native D-Bus client integration is a follow-up evolution, not the current runtime path.

== Why split this architecture set

The adapter spans multiple concerns:

* bootstrap/runtime monitoring contract
* systemd state probing
* HTTP status surface consumed by operators and Pulumi
* deployment/runtime ownership boundaries

To keep reviews focused, each concern is diagrammed separately with one primary question per diagram.

=== 4) Sequence view — how does one status request flow?

Review question: does runtime behavior and error handling match expectations?

[plantuml,systemd-adapter-status-sequence,svg]
----
@startuml
skinparam shadowing false

title Systemd Adapter - /status/systemd sequence

actor Caller
participant "SystemdStatusController" as Controller
participant "ShellSystemdStatusSnapshotProvider" as Provider
participant "systemctl show/list-jobs/--failed" as Systemctl

Caller -> Controller : GET /status/systemd
Controller -> Provider : currentSnapshot()

Provider -> Systemctl : show ActiveState of mandatory target
Systemctl --> Provider : target state

Provider -> Systemctl : list-jobs --no-legend
Systemctl --> Provider : tabular jobs

Provider -> Systemctl : failed-units --no-legend
Systemctl --> Provider : failed units listing

Provider --> Controller : SystemdStatusSnapshot
Controller --> Caller : 200 + JSON snapshot
@enduml
----

== Review and evolution policy

For large updates, prefer one PR per diagram concern:

. Context/container boundary updates
. Component ownership updates
. Sequence/runtime behavior updates

This keeps architectural reviews short and allows faster approval cycles.
