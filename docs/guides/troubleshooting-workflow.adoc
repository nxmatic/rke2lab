= Troubleshooting Workflow
:toc: left
:toclevels: 3

This note captures the preferred workflow for live troubleshooting in this repository.

It exists so operational debugging does not depend on chat history, terminal scrollback, or one-off ad hoc commands.

== Purpose

The troubleshooting workflow should:

* make the intended runtime or operational mode explicit before diagnostics begin
* keep temporary operational helpers reproducible
* separate quick shared-space experiments from permanent repository code
* preserve useful scripts by promoting them into the codebase when they prove durable

== Core rule

Before starting live troubleshooting, create or update a short troubleshooting note that states the exact operation mode being exercised.

Examples of operation modes include:

* `master-guest`
* `daemonset-host-assets`
* `master-hotfix`
* `pod-materialization`
* `host-reexec`

The important rule is not the exact vocabulary.
The important rule is that the operator and the code reviewer can tell which execution surface is being inspected.

== Preferred execution flow

The intended workflow is:

. State the target operation mode in a troubleshooting note.
. Author any helper scripts first in `.local.d/share`.
. Execute those scripts through the shared host path contract.
. Observe the results and refine the helper if needed.
. If a helper script becomes important beyond the current session, reverse-promote it into the repository.

This keeps troubleshooting fast without losing useful operational knowledge.

== Shared script staging area

For live diagnostics, author reusable helper scripts under:

* `.local.d/share`

These scripts are staging artifacts for troubleshooting.
They are allowed to move faster than repository-owned assets, but they should still be readable, explicit, and reusable.

The corresponding host-side shared directory contract is:

* `RKE2LAB_SHARED_DIR`

When troubleshooting requires execution on the live node or guest, prefer executing authored scripts through that shared directory contract rather than building long inline remote command strings.

== Terminal usage rule

The PTY/terminal bridge is useful for execution, but it is often noisy for script authoring.

Therefore:

* prefer writing troubleshooting scripts to disk first
* use the terminal primarily to execute those scripts remotely
* avoid treating terminal history as the source of truth for operational logic

In short:

* file authoring first
* remote execution second

== Promotion rule

A troubleshooting helper should remain in `.local.d/share` only while it is still provisional.

If it becomes:

* repeatedly useful
* structurally important
* part of the expected runtime/debugging toolkit
* necessary to understand or operate the system correctly

then it should be promoted into the codebase.

That promotion should preserve a single canonical implementation rather than leaving a long-lived split between:

* repository-owned scripts
* operational scratch scripts

== Relationship to runtime debugging

This workflow is especially important for daemonset and host-mutating runtime flows where multiple execution surfaces can be confused with each other.

Examples include:

* pod-mode installer execution
* host-mode re-exec execution
* master guest diagnostics
* shared host asset inspection
* live hotfix or validation scripts

A troubleshooting note should always make that distinction explicit.

== Minimal troubleshooting note template

A minimal note can be as small as:

[listing]
----
# Troubleshoot note

## Operation mode
- target mode: <mode>

## Goal
- <what we are trying to verify>

## Scripts
- .local.d/share/<script-name>.sh

## Promotion decision
- keep in share only / promote into repo later
----

== Summary

The canonical troubleshooting workflow for this repository is:

* declare the operation mode first
* author helper scripts in `.local.d/share`
* execute them through `RKE2LAB_SHARED_DIR`
* promote durable helpers into the repository so they are not lost
