=== Two-phase operating model

Retain the strict split:

* Stage A: external/bootstrap provisioning (outside cluster)
* Stage B: in-cluster lifecycle reconciliation (CAPI/CAPRKE2/CAPN)

=== Stage A minimalism

Retain the principle that Stage A must stay narrow:

* bootstrap only what is needed for management API readiness
* emit deterministic handoff outputs for Stage B
* avoid becoming a long-running general reconciler

=== Canonical infrastructure ownership

Retain the model where foundational Incus host resources are treated as canonical platform inputs (project/network/profile/image), while Stage A manages bootstrap-specific resources (for now: seed instance lifecycle).

=== Phase 2 GitOps scope

=== Next-stage migration note

For upcoming stages, progressively migrate host-mutating `host/systemd-units` workflows into Kubernetes init-container flows that execute via `nsenter` on host namespaces/filesystems.

Constraints to preserve during this migration:

* keep one canonical owner per workflow (no parallel systemd+init implementations)
* keep behavior idempotent and deterministic across reruns
* avoid introducing backward-compatibility aliases unless explicitly requested

=== Node setup StatefulSet/Job migration plan baseline (current repository state)

This note captures the migration baseline after runtime shim packaging and checksum-driven seed renewal updates.

Current implementation facts to preserve:

* host bootstrap scripts and units are still sourced from `manifests/src/main/resources/host/systemd-{scripts,units}` and materialized by `controlplane/incus`
* runtime host mutation already has a proven Kubernetes pattern in `runtime/flox-containerd-shim` using init-container + `nsenter`
* seed replacement is currently tied to Stage A provisioning checksum (`user.rke2lab.provisioningChecksum`) and image build checksum (`user.rke2lab.imageBuildChecksum`)

Phased migration intent:

. introduce a dedicated node-setup Kubernetes workload (start as DaemonSet/Job with init-container `nsenter` execution)
. migrate low-risk/idempotent scripts first (readiness/diagnostics and non-critical one-shot setup)
. migrate ordering-sensitive manifest install flows with explicit Kubernetes ordering and readiness gates
. only after parity, remove corresponding host systemd unit ownership and materialization

Guardrails:

* keep Stage A deterministic and avoid adding compatibility aliases
* maintain one canonical implementation per migrated workflow
* ensure each migrated step has explicit idempotency markers and observable logs

First implementation slice recommendation:

* create a `node-setup` layer with one small, verifiable host-operation script executed through init-container `nsenter`
* validate on `bioskop` with Flox active by compiling `manifests` + `controlplane`, applying generated manifests, and confirming idempotent rerun behavior

=== Runtime shim source model update (worktree-first)

Adopt a worktree-first model for runtime shim package builds:

* avoid hardcoded `git+file://...` source URLs for shim package inputs
* resolve package sources from a local worktree path (`path:` inputs)
* prefer a subtree layout when externalizing shim sources, so node provisioning remains self-contained from `rke2lab` ownership

Canonical execution modes for shim builder:

* `guest`: run directly from repository-owned resources during local iteration (default when omitted)
* `host`: run from `/srv/host/flox-shim.d` during node provisioning
* mode selection is explicit when passed as builder argument, not auto-detected

Guardrail:

* maintain one canonical path contract for both modes (`networking/kdns/src` preferred for subtree mode, optional explicit override via environment variable when needed)

=== Runtime shim rootfs sync mount-mode deferral

For the current Flox shim wrapper evolution, keep `bundle/.flox -> rootfs/.flox` synchronization in copy mode and explicitly defer bind-mount mode.

Reason for deferral:

* a bind mount created from the host view is not guaranteed to be visible inside the eventual container mount namespace; visibility depends on namespace timing and propagation
* the current wrapper model `exec`s into the real shim, so it does not naturally retain a post-exec cleanup phase for deterministic unmount-before-bundle-deletion behavior
* copy mode is less elegant but remains deterministic, namespace-agnostic, and free of mount-lifecycle cleanup hazards while the Go wrapper is still being introduced

Future revisit criteria:

* implement bind mode only as an explicit, opt-in path
* make it namespace-aware rather than assuming host-namespace mount visibility
* pair it with deterministic cleanup semantics (either namespace-scoped teardown or dedicated cleanup helper/supervisor)

Until those conditions are met, `copy` remains the canonical synchronization behavior and `bind` is tracked as a future optimization rather than an active migration target.

=== Deferred ConfigMap simplification note (serialized-asset pattern)

For a later cleanup pass, reuse the Flox shim wrapper packaging pattern for selected mesh/runtime ConfigMaps that are currently assembled inline in Java.

Initial candidate:

* `mesh/headplane` Flox environment payloads (for example, the Headplane Flox env ConfigMap) should eventually move toward a serialized asset/archive model rather than remaining as hand-built inline map literals

Intent of the follow-up:

* keep layer Java focused on object wiring and dependency structure
* move larger or more mechanical payload construction into deterministic serialized assets, similar to the shim-wrapper archive + manifest flow
* make future payload updates easier to diff, validate, and reuse across layers

Guardrails for that later refactor:

* do not change runtime behavior while introducing the packaging cleanup
* keep one canonical owner for each emitted asset/config payload
* prefer deterministic archive/manifest generation over ad-hoc string assembly when payload complexity justifies it

This is explicitly deferred work and not required for the current mesh-system / runtime-namespace refactor.

=== Working note: current robustness review (Stage A policy/runtime path)

This section is a living working document for robustness findings discovered while iterating on the Stage A refactor.
It is intentionally pragmatic: record what already feels solid, what still looks fragile, and what we are explicitly deferring.

Current framing:

* the Pulumi + cdk8s direction looks correct and is helping requirements emerge cleanly
* the current review focus is robustness of the existing Stage A feature set, not broad test expansion yet
* systematic test coverage is intentionally deferred until the Stage A refactor settles enough that we are not freezing transitional seams

What currently looks good:

* policy naming is now much more coherent (`policy.*`, `RKE2LAB_POLICY_*`)
* manifest domain identity is shared instead of re-declared ad hoc across layers
* controlplane policy is now first-class rather than hidden inside bootstrap config booleans
* optional manifest-domain policy is visible in the synthesis model through an explicit interface
* synthesis policy filtering respects dependency closure rather than naïvely dropping dependent domains
* current builds are compiling cleanly under the Flox/JDK 25 path

Current robustness gaps worth improving next:

==== 1. Reduce default drift across layers

The same effective defaults are still expressed in several places:

* `Pulumi.dev.yaml`
* `ControlplanePolicy.defaults()`
* `ControlplanePolicy.from(...)` default values
* shell-side fallback defaults in host install scripts

Risk:

* future changes may update one layer but leave another unchanged, causing subtle behavioral drift

Desired follow-up:

* converge on a smaller number of canonical Stage A default sources
* reduce shell-side fallback duplication where controlplane-injected env is sufficient

==== 2. Keep synthesis policy and live-link policy clearly distinct

We now have two valid but different concepts:

* synthesis policy: what manifest domains are included in cdk8s synthesis
* Stage A link policy: what serialized host manifests are linked live into the RKE2 manifests directory

Risk:

* the code is now capable of representing both, but the semantic distinction could blur again in future changes

Desired follow-up:

* keep this distinction explicit in naming, docs, and future refactors
* avoid treating “policy” as if it always means only one operational phase

==== 3. The policy-aware synthesis path is present but not yet central to live operation

The new synthesis-policy path exists and is structurally correct, but it is still mostly an available capability rather than a routine Stage A path.

Current state:

* `ManifestSynthesisRequest` can carry manifest-domain policy
* `DefaultManifestSynthesisService` can filter domains with dependency closure
* current Stage A behavior still effectively follows “synthesize everything, link selectively”

Desired follow-up:

* document the intended operational story clearly
* decide later whether Stage A should pass policy directly into synthesis, or intentionally keep full synthesis as the canonical behavior

==== 4. Host-side policy behavior is still more stringly than the Java model

The host scripts are workable and much improved, but policy semantics are still partially represented in shell:

* env var name construction
* boolean parsing
* domain-to-path mapping
* local shell fallbacks

Risk:

* policy semantics are easier to drift in bash than in typed Java models

Desired follow-up:

* progressively reduce shell-only policy knowledge
* prefer explicit mapping tables or generated machine-readable inputs where the complexity justifies it

==== 5. We do not yet have drift guards across Pulumi, controlplane, manifests, and host runtime

Policy now spans multiple layers cleanly, but there is still no automated guard against naming or semantic drift between:

* Pulumi config keys
* controlplane policy objects
* exported outputs
* runtime env overlays
* host scripts
* manifests-domain policy/synthesis handling

Risk:

* future changes could silently desynchronize one layer from the others

Desired follow-up:

* once Stage A shape is more stable, add focused consistency checks around names, enabled domains, and exported/runtime policy surfaces

==== 6. Documentation for the new synthesis-policy input is still thin

The property exists:

* `rk2lab.manifests.policy.enabledDomains`

But today it is mostly discoverable only by reading code.

Desired follow-up:

* document valid domain IDs
* document that dependencies are auto-included
* document whether this is intended mainly for local synthesis use, future Stage A use, or both

==== Recommended sequencing and dependency order

Point 1 is the immediate must-do item.

Reason:

* default drift is the broadest source of subtle behavior changes because it affects Pulumi, controlplane, host scripts, and operator expectations at once
* if defaults are still duplicated, later cleanup work can easily harden the wrong layer or document behavior that is not actually canonical

Recommended sequence:

. *First: reduce default drift across layers* (Point 1)
* make one smaller canonical source of Stage A defaults
* reduce repeated shell fallbacks where controlplane-injected env should be the source of truth
* this gives a stable behavioral baseline for all later work

. *Second: keep synthesis policy and live-link policy clearly distinct* (Point 2)
* once defaults are clearer, tighten the semantics of the two policy concepts
* this avoids future refactors accidentally collapsing two different concerns back into one

. *Third: decide the intended role of policy-aware synthesis in live operation* (Point 3)
* after defaults and semantics are clarified, decide whether Stage A should keep “synthesize all, link selectively” as canonical behavior or start passing policy directly into synthesis
* this decision should be taken only after Points 1 and 2, otherwise the decision will rest on moving assumptions

. *Fourth: reduce shell-side stringly policy knowledge* (Point 4)
* once the canonical defaults and policy semantics are settled, simplify or constrain the shell layer so it is consuming policy rather than partially redefining it
* doing this earlier would risk moving bash logic before the canonical model is stable enough

. *Fifth: add drift guards across layers* (Point 5)
* only after the previous items are clearer should we add strong consistency checks
* otherwise we risk baking transitional state into guardrails that will need to be relaxed or rewritten soon after

. *Sixth: document the synthesis-policy input and the final intended operational story* (Point 6)
* documentation should follow the semantic decisions above, not race ahead of them
* small interim notes are fine, but the durable documentation pass should happen once the behavior is the one we intend to keep

. *Seventh: begin the broader test-coverage phase after Stage A refactor stabilization* (Point 7)
* this remains intentionally deferred
* targeted consistency tests can start once the policy/default/semantic shape has stopped moving enough to be worth protecting

Relationship summary:

* Point 1 stabilizes behavior
* Point 2 stabilizes meaning
* Point 3 stabilizes operational intent
* Point 4 stabilizes implementation boundaries
* Point 5 stabilizes cross-layer guarantees
* Point 6 stabilizes communication/documentation
* Point 7 stabilizes protection through tests

Practical takeaway for the next iteration:

* treat Point 1 as the first concrete robustness hardening task
* use Points 2 and 3 to decide what should remain canonical in Stage A
* only after that should we spend energy on stronger guardrails and broader coverage

==== 7. Full test coverage is deferred intentionally, not forgotten

Current decision:

* do not begin the serious codebase-wide test coverage phase until the Stage A refactor reaches a more settled implementation state

Reason:

* otherwise we would spend effort stabilizing and updating tests around transitional seams and temporary model shapes

What we should do meanwhile:

* continue hardening semantics, defaults, naming, validation, observability, and deterministic runtime behavior

What should happen after Stage A settles:

* add targeted unit coverage for policy objects and parsing
* add synthesis-policy filtering tests
* add a small set of consistency/drift checks across layers
* then broaden from there as the architecture stops moving underfoot

Working conclusion for now:

* the main current weakness is not that features are conceptually wrong
* the main weakness is cross-layer drift risk while the model is still being consolidated
* the right next robustness work is to harden defaults, semantics, documentation, and policy boundary clarity before starting the broader test-coverage phase

=== Working note: Flox shim problem-solving summary

This section is a living working document dedicated to the actual Flox shim problem path.
It complements the robustness review above: the goal here is not broad architecture review, but to record what is already in place for the shim, what still remains uncertain, and the most sensible order for debugging and closing the remaining gap.

Current assessment:

* we now appear to have the main architectural prerequisites in place to return to the Flox shim problem directly
* the remaining work should be much less about policy/config plumbing and much more about validating actual build/install/runtime behavior end to end

What now seems to be in place:

* policy-controlled debug selection for both KDNS and the Flox shim wrapper
* canonical policy propagation from Pulumi -> controlplane -> runtime env overlay -> host scripts
* debug package selection logic in `shim-build.sh`
* debug wrapper package selection logic in `shim-installer-host.sh`
* host install path that resolves and installs:
** the real shim binary (`containerd-shim-flox-v2.real`)
** the selected wrapper package binary (`containerd-shim-flox-v2`)
** the rootfs sync helper (`flox-rootfs-sync.sh`)
* containerd config mutation that points the `flox` runtime to `/usr/local/bin/containerd-shim-flox-v2`
* explicit prior decision that rootfs sync remains in `copy` mode for now, with bind mode deferred intentionally

What this changes compared to earlier stages:

* we are no longer blocked on creating the policy knobs or propagating them
* we are no longer blocked on naming ambiguity between controlplane and manifests policy surfaces
* we are now in a much better position to investigate the true shim runtime behavior with fewer architectural distractions

What still remains uncertain:

* whether the original shim failure mode has already been eliminated, or is still present but now easier to isolate
* whether the correct wrapper variant is not only selected logically, but also installed and executed as intended on host
* whether the runtime binary layout under `/usr/local/bin` and `/usr/local/libexec/rke2lab/flox-shim-wrapper` is exactly what containerd expects at execution time
* whether containerd-facing runtime behavior remains correct after the wrapper delegates to the real shim
* whether the copy-mode rootfs sync is sufficient for the concrete workload/runtime case we are actually trying to support

Important framing:

* at this stage, the likely remaining problems are operational/runtime problems, not missing-configuration problems
* this means the next work should bias toward runtime inspection, artifact verification, and reproduction of the original symptom

Recommended investigation order:

. *First: restate the exact original shim symptom we are trying to eliminate*
* keep this precise (install failure, runtime launch failure, missing env, rootfs-sync issue, wrong wrapper variant, containerd integration issue, etc.)
* without this, later checks risk proving only that the plumbing exists, not that the original problem is solved

. *Second: verify selected build/install artifacts on host*
* confirm which wrapper package variant was selected (`flox-shim-wrapper` vs `delve-sidecar`)
* confirm the expected files exist and are executable:
** `/usr/local/bin/containerd-shim-flox-v2`
** `/usr/local/libexec/rke2lab/flox-shim-wrapper/containerd-shim-flox-v2.real`
** `/usr/local/libexec/rke2lab/flox-shim-wrapper/flox-rootfs-sync.sh`
* confirm symlink targets and wrapper package paths are what we expect

. *Third: verify containerd integration shape*
* confirm containerd config points to the wrapper entrypoint we intend
* confirm the runtime name/path/options are correct after config rewrite
* ensure we are not proving only installation while runtime configuration still points elsewhere

. *Fourth: verify wrapper -> real shim delegation path*
* inspect how the installed wrapper calls the real shim
* confirm the real shim path the wrapper expects actually matches what the installer places on disk
* confirm helper paths used by the wrapper also match installed layout

. *Fifth: verify rootfs/environment behavior in the exact runtime case*
* confirm the chosen copy-mode sync still provides the runtime visibility we need
* inspect whether the relevant Flox environment/rootfs content actually lands where the shim expects it
* only revisit mount-mode/bind-mode ideas if the real runtime symptom specifically points back there

. *Sixth: rerun against the original failing scenario and capture evidence*
* at that point, verify whether the original symptom is gone, changed, or still present
* if still present, classify whether the remaining problem is:
** packaging/build-time
** install/layout-time
** containerd configuration-time
** runtime wrapper delegation-time
** rootfs/environment-time

Practical near-term takeaway:

* we should now return to the Flox shim work as a focused runtime problem
* we should resist reopening broad architecture changes unless the runtime investigation proves a real missing seam
* the best next debugging pass is probably artifact-first and containerd-integration-first, because those are easiest to verify and most likely to narrow the remaining problem quickly

Working conclusion for now:

* the Flox shim path now looks sufficiently scaffolded to tackle directly
* the likely next gains will come from end-to-end runtime verification rather than more policy plumbing
* if the original issue still exists, it should now be much easier to classify and fix precisely

Guardrails for this track:
