= Post-Bootstrap In-Cluster Ownership Plan
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

This note replaces the earlier operator-centered next-plan note with the current intended in-cluster ownership model.

It keeps one canonical owner per concern and records earlier wrong assumptions only as footnotes, not as the active design.

== Current intent

The active plan after Stage A is:

* keep `controlplane` as the external bootstrap authority for the seed management cluster
* hand off non-seed machine lifecycle to CAPI + CAPN + CAPRKE2 inside the management cluster
* install GitOps controllers for declarative cluster add-on reconciliation
* install a workflow/pipeline controller inside the cluster for build, promotion, and delivery workflows
* move long-lived host-local runtime mutation out of staged bootstrap/systemd flows and into node-local reconcilers

This means the target in-cluster control plane is not “Pulumi Operator plus everything else”.footnote:[Earlier planning treated the Pulumi Operator as the likely in-cluster provisioning brain after bootstrap. That assumption is no longer the active plan because it overlaps too broadly with the already-declared Stage B ownership of CAPI/CAPN/CAPRKE2 for ongoing machine lifecycle.] It is a split of specialized controllers with clearly separated ownership.

== Concrete environment anchors

The current intended environment is not purely abstract; two named Darwin environments matter to the plan:

* `bioskop` — the Darwin bare-metal host on the home network (`mac-mini m4 pro`)
** runs the NixOS Tart/VZ VM that hosts the Incus server used for Stage A seed bootstrap
** is the place where `controlplane` bootstraps the seed management cluster
** owns the seed management cluster bootstrap path
* the Hyland enterprise MacBook Pro bare-metal host — the enterprise-managed Darwin laptop (`macos m4 pro`)
** remains a separate Darwin host boundary outside the managed-cluster guest
** runs the Tart/VZ guest named `nikopol`
* `nikopol` — the isolated NixOS Tart/VZ guest running inside the enterprise-managed Darwin MacBook Pro host
** provides the required Incus server inside that guest boundary
** is intended to host a managed cluster whose lifecycle is owned by the management cluster bootstrapped from `bioskop`

In other words:

* `bioskop` is the concrete Stage A bootstrap site for the seed management cluster
* the enterprise-managed MacBook Pro is a separate Darwin host boundary and should not be conflated with the guest
* `nikopol` is the concrete downstream NixOS guest site that should be reconciled by the in-cluster control plane after handoff

== Worktree distribution path

The `rke2lab` Git worktree is also part of the concrete system shape.

Current intent:

* `bioskop` holds an `rke2lab` worktree on the Darwin host side
* the enterprise-managed MacBook Pro also holds an `rke2lab` worktree on the Darwin host side
* each Darwin host projects that worktree into its NixOS Tart/VZ guest via NFS
* the NixOS guests consume that projected worktree as a source input rather than as a generated runtime asset
* Incus instances and cluster nodes then receive access to selected worktree folders through bind mounts sourced from the projected worktree inside the NixOS guest

That gives the system a layered path:

. Darwin host worktree
. NFS-mounted worktree inside the NixOS Tart/VZ guest
. bind-mounted worktree folders inside Incus instances or nodes

This matters because the worktree is neither a cluster-owned runtime output nor a daemonset host-asset root. It is an upstream source input projected across multiple boundaries.

== Canonical ownership split

[cols="1,3",options="header"]
|===
| Concern | Canonical owner

| Seed bootstrap and handoff outputs
| `controlplane` outside cluster

| Non-seed machine lifecycle (scale, replacement, rollout, remediation)
| CAPI + CAPN + CAPRKE2

| Declarative in-cluster add-ons and desired cluster services
| GitOps controllers

| Build, promotion, delivery, and workflow orchestration
| workflow/pipeline controller

| Ongoing host-local runtime mutation and node drift correction
| node-local controller / privileged DaemonSet patterns
|===

This is the core design rule:

* CAPI owns machine lifecycle.
* GitOps owns declarative add-ons.
* The workflow/pipeline controller owns build and delivery workflows.
* Node-local reconcilers own host mutation on already-running nodes.

That split is deliberate because CAPI is not the natural owner of ongoing host-local runtime mutationfootnote:[A second wrong assumption was that CAPI might absorb the host-local runtime mutation currently expressed through staged systemd services and daemonset host workflows. CAPI can bootstrap machines, but the active plan treats ongoing host-runtime reconciliation as a node-local controller concern, not as generic machine lifecycle.] and the workflow/pipeline controller is not the natural owner of either node lifecycle or host drift correction.footnote:[A third wrong assumption was that the workflow/pipeline controller might become a general post-bootstrap orchestrator. The corrected plan keeps it focused on build, promotion, delivery, and workflow execution, not node reconciliation or bootstrap authority.]

== Role of the workflow/pipeline controller

The workflow/pipeline controller is part of the real plan, but its role is intentionally narrow.

It should own:

* build/test/package workflows
* promotion workflows across environments or artifact states
* delivery workflows that prepare artifacts or manifests for GitOps consumption
* explicit multi-step operational workflows that are reviewable as pipelines

It should not own:

* machine lifecycle already owned by CAPI
* declarative steady-state reconciliation already owned by GitOps
* long-lived host-local reconciliation already owned by node-local controllers
* seed bootstrap authority already owned by `controlplane`

The workflow/pipeline controller sits in the flow as the system that produces or promotes deployable outputs; GitOps consumes those outputs to reconcile cluster state.

== Bootstrap-to-handoff flow

The active sequence is:

. `controlplane` provisions the seed management cluster and emits the Stage A -> Stage B handoff assets.
. The cluster becomes healthy enough to host in-cluster controllers.
. CAPI + CAPN + CAPRKE2 are installed and become the only owners of non-seed machine lifecycle.
. GitOps controllers are installed and become the owners of declarative add-on state.
. The workflow/pipeline controller is installed and becomes the owner of build/promotion/delivery workflows.
. Node-local reconcilers gradually replace staged systemd/bootstrap host mutation for long-lived runtime concerns.

The bootstrap layer should become smaller over time; it should not remain the permanent owner of everything.

== Design guardrails

The following guardrails remain strict:

* no overlapping controller ownership for the same concern
* no backward-compatibility orchestration aliases just to bridge old assumptions
* one canonical owner per lifecycle surface
* systemd is a current bootstrap backend, not the long-term architecture concept
* node-local reconciliation should replace durable host-mutation shell flows once the cluster can host that control loop

The dynamic view is intentionally simple: bootstrap the seed on `bioskop` first, project the `rke2lab` worktree into the NixOS guests via NFS, hand off ongoing lifecycle to in-cluster controllers, then let downstream Incus nodes consume selected worktree folders through bind mounts while the Darwin hosts remain the source-of-truth worktree owners.

== Summary

The real plan is now:

* external `controlplane` for seed bootstrap only
* CAPI + CAPN + CAPRKE2 for non-seed machine lifecycle
* GitOps for declarative cluster add-ons
* workflow/pipeline controller for build, promotion, and delivery workflows
* node-local reconcilers for ongoing host-local runtime mutation

The earlier Pulumi-operator-centered idea remains only as historical context in footnotes, not as the active architecture.
