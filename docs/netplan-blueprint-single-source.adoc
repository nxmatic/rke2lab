= Netplan Blueprint as Cross-Repo Single Source of Truth
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

== Overview

The cluster network underlay — cluster/node IDs, MAC derivation scheme, IP
addressing — is defined once in rke2lab's Java `ClusterNetworkBlueprint` and must
be consumed identically by two parties:

* *rke2lab itself* (the netplan/bootstrap code that provisions guests), and
* *nix-darwin-home* (which configures host routes, dbus, and incus on the NixOS
  hosts that run the guests).

This design re-establishes nix-darwin-home's consumption of that blueprint as a
proper flake edge, so there is a single source of truth. rke2lab's flake builds
and runs the netplan jar to produce the blueprint and exposes it as
`lib.networkBlueprint`; nix-darwin-home adds rke2lab as a flake input and consumes
`deriveMacs` instead of hand-copying the values.

== Background: how the link broke and why it matters

The reverse edge (nix-darwin-home consuming rke2lab's blueprint) was removed.
nix-darwin-home's `catalog/default.nix` now *hand-inlines* the MAC/IP values
(`mac = "10:66:6a:4c:00:00"`, ...) while its comments still declare
`Source of truth: rke2lab/netplan (ClusterNetworkBlueprint semantics)`. The
intent says "linked"; the mechanism is a manual copy. If the Java blueprint
changes a MAC/IP, the copy silently diverges. rke2lab's `flake.nix`
`lib.networkBlueprint` / `deriveMacs` export — built to feed this link — is
consumed by nobody (orphaned).

== The non-cycle invariant

The two repos depend on each other in *different scopes*, so there is no
flake-eval cycle:

* `nix-darwin-home -> rke2lab`: BUILD/eval time (imports the blueprint).
* `rke2lab -> nix-darwin-home`: RUNTIME only (rke2lab's incus instances run on
  the NixOS host nix-darwin-home provisions). This edge is invisible to nix eval.

rke2lab's flake imports only `flake-commons` + its own `flox-runtime` sub-flake —
never nix-darwin-home. A guard comment at rke2lab's `inputs` block records this
invariant so a future edit cannot accidentally close the loop.

[mermaid]
....
flowchart LR
  ndh["nix-darwin-home flake"]:::b -->|build/eval: imports blueprint| rl["rke2lab flake"]:::b
  rl -->|build/eval| fc["flake-commons"]:::b
  rlrun["rke2lab incus instances"]:::r -.->|RUNTIME only: run on| host["bioskop-nixos (provisioned by ndh)"]:::r
  classDef b fill:#dae8fc,stroke:#6c8ebf
  classDef r fill:#ffe6cc,stroke:#d79b00
....

The blue (build) edges form an acyclic graph; the orange (runtime) edge does not
participate in eval.

== Design: the flake runs the jar (IFD), exposes a flat lib

The blueprint is a *pure output* of the Java: `BlueprintExportCommand` generates
it from hardcoded cluster/node maps and reads no input file. So there is no
chicken-and-egg — the jar takes no blueprint in, it emits one. rke2lab's flake
already builds the jar and runs `yamlExport` to produce the blueprint
(`networkBlueprintYaml` -> `networkBlueprintData`); we keep that and expose
`lib.networkBlueprint` for nix-darwin-home to consume.

[cols="1,3",options="header"]
|===
| Element | Role

| `ClusterNetworkBlueprint` (Java) | the single source of truth
| `netplan.jar yamlExport` | generator: emits the blueprint as YAML (no input)
| rke2lab `flake.nix` (`networkBlueprintYaml` -> `networkBlueprintData`) | builds + runs the jar at eval (IFD), parses the YAML
| `lib.networkBlueprint` (`deriveMacs` + data) | the consumable export
| nix-darwin-home flake input `rke2lab` | consumes `rke2lab.lib.networkBlueprint.deriveMacs`
|===

The YAML carries the full contract (from `BlueprintExportCommand`): `clusters`,
`nodes`, `macPatterns`, `nodeTypes`, and per-node `addressing` (macs/ips/leases).
`deriveMacs cluster node` resolves a `{lan, wan}` pair from the cluster/node IDs.

=== The IFD tradeoff (accepted)

Consuming `lib.networkBlueprint` triggers import-from-derivation: nix builds the
netplan jar via Maven-in-nix and runs it during eval. So a `nixos-rebuild` on
bioskop-nixos that touches the catalog will Maven-build rke2lab's netplan module
the first time (then cache).

This cost is *accepted* in favor of simplicity. The alternatives were weighed and
rejected:

* *Committed YAML projection* (commit `yamlExport` output as a lock-like file,
  read it purely, guard against drift): removes the IFD cost but adds a committed
  artifact, a regeneration discipline, and a sync guard. Over-engineered for a
  single-developer lab where the build caches and rebuilds are infrequent.
  IMPORTANT placement note if ever reconsidered: the YAML must NOT live as a
  netplan-module Maven *resource* (`src/main/resources/...`) — that would package
  it into the very jar that generates it, creating a real chicken-and-egg. It
  would have to be a top-level, lock-like file outside the module's input path.
* *Pure-Nix data file*: would require the Java to read the same Nix data (or
  duplicate it), a larger refactor with its own drift surface.

If the IFD cost ever proves painful in practice (cold `nixos-rebuild` latency on
the NixOS hosts), revisit the committed-projection option with the placement
caveat above.

== The blueprint is OS-independent

The blueprint data + `deriveMacs` logic have no genuine system dependency: the
underlying values (cluster/node IDs, MAC patterns, addressing) are pure literals
from the Java, identical on every system. The jar that generates the YAML does
need a build platform (jdk/maven), but the *resulting data* does not.

Practical consequence: expose `lib.networkBlueprint` as flat and
system-independent where feasible, so consumers use
`rke2lab.lib.networkBlueprint.deriveMacs` rather than a per-system
`rke2lab.lib.${system}.networkBlueprint...`. (The generating derivation is
per-system because it builds the jar; the exposed *data* need not be — parse once
and surface flat.)

== Implementation plan

*rke2lab side (do first):*

. Keep `networkBlueprintYaml` (the jar-running derivation) and `netplanJar` — they
  produce the blueprint. No committed YAML, no sync guard.
. Surface `lib.networkBlueprint` as flat/system-independent (parse the YAML once,
  expose the data + `deriveMacs` outside the per-system split where practical), so
  consumers don't need `lib.${system}`.
. Keep the no-nix-darwin-home-input guard comment (already added).

*nix-darwin-home side (follow-up):*

. Add `rke2lab` as a flake input (url = the rke2lab repo).
. In `catalog/default.nix`, replace the hand-inlined MAC/IP literals with
  `rke2lab.lib.networkBlueprint.deriveMacs <cluster> <node>` (and the
  IP/addressing fields from the same blueprint).
. The "source of truth: rke2lab" comments become true rather than aspirational.

== Open questions

. *`lib` flattening mechanics*: how to expose the parsed blueprint data flat while
  the generating derivation stays per-system (e.g. parse under one system, surface
  under top-level `lib`). Confirm this evaluates without forcing a build on the
  wrong platform.
. *Input pinning*: nix-darwin-home pins rke2lab via flake.lock; decide the ref
  (branch vs rev) and the lock-bump cadence.
. *IFD platform*: nix-darwin-home eval on bioskop-nixos (aarch64-linux) builds the
  netplan jar for that system; confirm jdk25 + maven are substitutable/cached so
  the first `nixos-rebuild` isn't a cold full build.
