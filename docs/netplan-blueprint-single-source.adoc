= Netplan Blueprint as Cross-Repo Single Source of Truth
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

== Overview

The cluster network underlay — cluster/node IDs, MAC derivation scheme, IP
addressing — is defined once in rke2lab's Java `ClusterNetworkBlueprint` and must
be consumed identically by two parties:

* *rke2lab itself* (the netplan/bootstrap code that provisions guests), and
* *nix-darwin-home* (which configures host routes, dbus, and incus on the NixOS
  hosts that run the guests).

This design re-establishes nix-darwin-home's consumption of that blueprint as a
proper flake edge, so there is a single source of truth, while avoiding the
import-from-derivation (IFD) cost that made the previous link untenable. The
mechanism mirrors the project's flox-lock pattern: a *committed projection* of
the Java source, regenerated by a build step, guarded against drift.

== Background: how the link broke and why it matters

The reverse edge (nix-darwin-home consuming rke2lab's blueprint) was removed.
nix-darwin-home's `catalog/default.nix` now *hand-inlines* the MAC/IP values
(`mac = "10:66:6a:4c:00:00"`, ...) while its comments still declare
`Source of truth: rke2lab/netplan (ClusterNetworkBlueprint semantics)`. The
intent says "linked"; the mechanism is a manual copy. If the Java blueprint
changes a MAC/IP, the copy silently diverges. rke2lab's `flake.nix`
`lib.networkBlueprint` / `deriveMacs` export — built to feed this link — is
consumed by nobody (orphaned).

== The non-cycle invariant

The two repos depend on each other in *different scopes*, so there is no
flake-eval cycle:

* `nix-darwin-home -> rke2lab`: BUILD/eval time (imports the blueprint).
* `rke2lab -> nix-darwin-home`: RUNTIME only (rke2lab's incus instances run on
  the NixOS host nix-darwin-home provisions). This edge is invisible to nix eval.

rke2lab's flake imports only `flake-commons` + its own `flox-runtime` sub-flake —
never nix-darwin-home. A guard comment at rke2lab's `inputs` block records this
invariant so a future edit cannot accidentally close the loop.

[mermaid]
....
flowchart LR
  ndh["nix-darwin-home flake"]:::b -->|build/eval: imports blueprint| rl["rke2lab flake"]:::b
  rl -->|build/eval| fc["flake-commons"]:::b
  rlrun["rke2lab incus instances"]:::r -.->|RUNTIME only: run on| host["bioskop-nixos (provisioned by ndh)"]:::r
  classDef b fill:#dae8fc,stroke:#6c8ebf
  classDef r fill:#ffe6cc,stroke:#d79b00
....

The blue (build) edges form an acyclic graph; the orange (runtime) edge does not
participate in eval.

== The IFD problem this avoids

rke2lab's `networkBlueprintData` currently does
`builtins.fromJSON (builtins.readFile (runCommand … yq … networkBlueprintYaml))`,
where `networkBlueprintYaml` is a *Maven-in-nix derivation* that runs
`java -jar netplan.jar yamlExport`. Consuming `deriveMacs` therefore triggers
*building and running the netplan jar at eval time*. If nix-darwin-home consumed
this directly, every `nixos-rebuild` touching the catalog would Maven-build
rke2lab's netplan module. That eval-time cost is why the naive re-link is wrong.

== Design: committed projection + sync guard

Source of truth stays the Java `ClusterNetworkBlueprint`. We add a *committed
YAML projection* of it and make both the rke2lab flake and nix-darwin-home read
that pure file — no jar at eval.

[cols="1,3",options="header"]
|===
| Element | Role

| `ClusterNetworkBlueprint` (Java) | the source of truth (unchanged)
| `netplan.jar yamlExport` | generator: emits the blueprint as YAML
| `netplan/src/main/resources/network-blueprint.yaml` (committed) | the projection — a checked-in artifact, like a flox lock
| rke2lab `flake.nix` `networkBlueprintData` | reads the COMMITTED yaml (pure), no IFD
| nix-darwin-home flake input `rke2lab` | consumes `rke2lab.lib.${system}.networkBlueprint.deriveMacs`
| sync guard | fails the build if the committed yaml != `yamlExport` output
|===

The YAML carries the full contract (from `BlueprintExportCommand`): `clusters`,
`nodes`, `macPatterns`, `nodeTypes`, and per-node `addressing` (macs/ips/leases).
`deriveMacs cluster node` resolves a `{lan, wan}` pair from the cluster/node IDs.

=== Why a committed projection (not IFD, not pure-Nix data)

* *Committed projection (chosen)*: pure read on both sides, no Maven at eval. The
  Java stays the single source; the YAML is its checked-in shadow. Matches the
  established flox-lock model (commit the lock, regenerate on input change, guard
  coherence). Cost: the YAML must be regenerated + committed when the blueprint
  Java changes — enforced by the guard.
* *IFD (rejected)*: truest single-source but builds the jar on every consuming
  eval; unacceptable for `nixos-rebuild`.
* *Pure-Nix data file (rejected)*: would require the Java to read the same Nix
  data (or duplicate it), a larger refactor with its own drift surface.

=== Sync guard — never drift

A coherence check ensures the committed YAML matches the Java output, mirroring
the existing `EntryGatePolicyEnforcer.enforceFlakeLockCoherence` pattern (which
guards committed flake locks against `flake.nix` changes). Two viable homes:

* a Maven `verify`-phase goal in `netplan/` (it already has `exec-maven-plugin`)
  that runs `yamlExport` to a temp file and `diff`s it against the committed
  resource — failing the build on mismatch; or
* an entry-gate enforcer in seed-master (like `enforceFlakeLockCoherence`) run at
  `pulumi up` time.

The Maven `verify` home is preferred: it catches drift at build time, the same
moment the Java changed, before anything ships.

=== Regeneration workflow

When `ClusterNetworkBlueprint` changes:

. `mvn -pl :netplan ...` regenerates `network-blueprint.yaml` (a generate-resources
  goal, or a documented `yamlExport > resources/...` step).
. Commit the regenerated YAML alongside the Java change (one commit, like a lock
  bump).
. The sync guard passes; rke2lab's flake and nix-darwin-home both read the new
  values purely.

== Implementation plan

*rke2lab side (do first — make the export pure + stable):*

. Add a netplan build step that writes `network-blueprint.yaml` into committed
  resources (regenerate-and-commit, not generate-at-eval).
. Repoint `flake.nix` `networkBlueprintData` to `builtins.readFile` the committed
  YAML — removing the `runCommand`/jar IFD. `lib.${system}.networkBlueprint` +
  `deriveMacs` become pure.
. Add the sync guard (Maven `verify` goal).
. Keep the no-nix-darwin-home-input guard comment (already added).

*nix-darwin-home side (follow-up):*

. Add `rke2lab` as a flake input (url = the rke2lab repo).
. In `catalog/default.nix`, replace the hand-inlined MAC/IP literals with
  `rke2lab.lib.${system}.networkBlueprint.deriveMacs <cluster> <node>` (and the
  IP/addressing fields from the same blueprint).
. Drop the "source of truth: rke2lab" comments' implied-but-broken claim — it
  becomes true.

== Open questions

. *`lib` namespacing*: the export is under `eachDefaultSystem` so it is
  `lib.${system}.networkBlueprint`. Confirm nix-darwin-home accesses it per-system
  (or lift the blueprint to a system-independent `lib` since the data is
  system-agnostic — it is pure YAML, no `pkgs` dependency once de-IFD'd).
. *Generator goal wiring*: whether `yamlExport` runs as `generate-resources`
  (regenerates into the source tree — careful with reproducibility) or as a
  `verify` diff-only guard with manual regeneration. The guard-only approach
  keeps the build pure; regeneration stays an explicit developer action.
. *Input pinning*: nix-darwin-home pins rke2lab via flake.lock; decide the ref
  (branch vs rev) and the lock-bump cadence.
