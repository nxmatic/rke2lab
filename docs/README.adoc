=== Doctor & Runbook (BDD diagnostic model)

The doctor is the diagnosis engine the bootstrap checkpoints consult on failure; the runbook is the
living-doc the medical record materializes. Increments A–D and Increment E (layers 2 + 3) are
implemented; the medical-model extensions are Design Only. All docs live in `architecture/doctor/`.

* link:architecture/doctor/integration-atlas.adoc[Integration Atlas — do the models hold together?] (🗺️ **living integration view**) - Lists every doctor model and proves each new one is *additive* via monotone before/after figures; reopened at the start of every doctor design activity
* link:architecture/doctor/glossary.adoc[Doctor Glossary — clinical vocabulary] (📖 **vocabulary source of truth**) - Every term, its Pulumi mapping, and the 2026-06-10 rename map (Dossier→Observation, SpecialistDomain→Specialty, Complaint→ChiefComplaint, SymptomCorrelation→Comorbidity, DiagnosisReader→ConsultationReportReader)
* link:architecture/doctor/runbook-doctor.adoc[Runbook & Doctor — Design] (📐 **START HERE** for the doctor) - The full medical model: checkpoints as patients, Generalist/Specialist, Symptom/Observation/Prescription, the three increments, and the AI-augmentation seam
* link:architecture/doctor/pulumi-doctor-integration.adoc[Pulumi Entity Model & Doctor Integration] (✅ Resolved) - Why the doctor is app logic, not a Pulumi resource; the report carried as ComponentResource outputs (Option A)
* link:architecture/doctor/layer3-medical-record-design.adoc[Layer 3 — Medical Record (write-side)] (✅ Implemented) - Per-node diagnostic serialization, the single-source Checkpoint edge, phantom-diff dissolution
* link:architecture/doctor/layer3-readside-runtime-enrichment-design.adoc[Layer 3 — Read-side, part 1] (✅ Implemented) - Injecting the diagnosis into the JGiven runbook node via `extendedDescription`
* link:architecture/doctor/medical-record-query-api-design.adoc[Medical Record — Query API reconstructed from Pulumi] (✅ Implemented) - The four clinical questions (`chiefComplaint`/`historyOf`/`efficacyOf`/`comorbiditiesWith`) reconstructed on-demand from Pulumi state+history; the `pulumi-automation-ext` module; the layered error contract; deployment-instant (not version) ordering
* link:architecture/doctor/vocabulary-and-live-record-design.adoc[Vocabulary + Live-Record Wiring — Design] (✅ Implemented) - The clinical-vocabulary refactor (Dossier→Observation et al.) + wiring the live doctor to retrieve the patient's record (held registry, latent/wire-only). Companion: link:architecture/doctor/vocabulary-and-live-record-plan.adoc[the executed plan]
* link:architecture/doctor/healthsystem-access-control-design.adoc[HealthSystem — Access-Control + Correlation] (✅ Implemented) - The per-run keystone holding the registry + grant policy, employing clinicians (by `ClinicianId`), admitting the patient; gated access by `(ClinicianId, Patient)` grant via a credentialed `ClinicalAccess`; consent-bounded cross-patient correlation; shared by identity, not by a stack. Shipped on `feature/healthsystem-keystone`; referral-derived grants deferred to step 2
* link:architecture/doctor/cohort-correlation-proof.adoc[Cross-patient Cohort Correlation — Proof Record] (✅ Proof) - The empirical evidence (Phase 1 unit + Phase 2 live `pulumi preview`) that the read half of cross-patient correlation works; motivated the keystone, kept as the proof record
* link:architecture/doctor/rules-engine-checkpoint-topology-exploration.adoc[Rules Engine? — Diagnosis-layer Redundancy] (⚠️ Design Only) - Three options mapped; ② self-declaring specialists adopted, ① Checkpoint-topology a planner prerequisite, ③ Drools-substrate rejected
* link:architecture/doctor/drools-network-specialist-prototype.adoc[Drools behind the Specialist Seam] (⚠️ Design Only) - ②′ a contained Drools `NetworkSpecialist` (multi-condition), fed by the patient record
* link:architecture/doctor/preview-whatif-replay-exploration.adoc[Preview as Counterfactual Replay (what-if)] (⚠️ Design Only) - The closed-loop planner + the self-referential `medicalRecord` accumulator

== Contributing

When adding new documentation:

1. **Use AsciiDoc format** (`.adoc`) for consistency
2. **Include Mermaid diagrams** for architecture visualization
3. **Add cross-references** - link to related docs AND code in both directions
4. **Update this index** - add your document to the appropriate section
5. **Follow the pattern**: Overview → Architecture → Usage → Troubleshooting
6. **Add package-info.java** for domain-level architecture co-located with code

=== Cross-Reference Checklist

When you document a new concept:

- [ ] Add forward links FROM your doc TO related docs
- [ ] Add backward links FROM related docs TO your doc
- [ ] **Add links FROM docs TO code** (interfaces, implementations, package-info)
