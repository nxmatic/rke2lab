= Flake as Authoritative Build Entry Point
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

== Overview

This design makes the top-level `flake.nix` the authoritative *deploy/release*
build entry point for rke2lab, with Maven kept as the *developer inner loop*.
The deployable artifacts — the seed-master bootstrap jar, the manifests jar, and
the flox NRI plugin — become flake outputs built into `/nix/store`, so what runs
is content-addressed, reproducible, and identical across machines.

It resolves a concrete defect: the flox NRI plugin (an `aarch64-linux` Go binary)
is currently built *only at runtime* on the node by the installer. A broken
plugin is therefore discovered hours later on a cluster node rather than at build
time on the dev machine. Surfacing it as a flake output cross-built via the
configured linux-builder moves that failure left.

=== Scope and non-goals

* *In scope*: flake outputs for `seed-master`, `manifests`, `flox-nri-plugin`
  (+`-debug`); Pulumi binary resolution from a store-built artifact; the
  developer-vs-deploy role split.
* *Out of scope*: relocating where the bootstrap *runs*. Pulumi continues to run
  on the operator's darwin machine; only the *build location* of linux artifacts
  moves (to the linux-builder). The bootstrap jar still executes on the dev
  machine, from a store path instead of `target/`.

== Background: what already exists

The top-level `flake.nix` already proves the pattern. `netplanJar` runs
`mvn clean package` *inside* a nix derivation and surfaces the jar as a flake
output (`nix eval .#netplanJar.name` -> `"rke2lab-netplan"`). `networkBlueprintYaml`
then runs that jar to generate YAML consumed by nix-darwin-home. So "Maven runs
inside nix, artifact comes from the store" is established here, not novel.

Current outputs: `[ incus-client, netplanJar, networkBlueprintYaml ]`.

Two enabling facts are already true:

* The dev machine's nix is configured with a linux remote builder
  (`/etc/nix/machines`: `ssh-ng://builder@linux-builder aarch64-linux ...`), so
  `nix build .#flox-nri-plugin` for `aarch64-linux` routes there. The
  cross-compile prerequisite is satisfied.
* The runtime flox flake (`manifests/.../runtime/flox/flake.nix`) already builds
  `flox-nri-plugin` + `flox-nri-plugin-debug` via `buildGoModule` over
  `eachSystem [aarch64-darwin aarch64-linux]`.

== The core constraint: cross-compilation

The Maven build runs on *aarch64-darwin* (dev machine). The NRI plugin must be
*aarch64-linux* (runs in containers on cluster nodes). Darwin cannot emit a Linux
binary directly. Therefore "build the plugin as part of the build" can only mean
*nix builds it, routing the Linux build to the linux-builder* — never "Maven
compiles Go on darwin". This is why the flake (which understands remote builders)
is the right entry point and a raw Maven goal is not.

== The two roles, made explicit

[cols="1,2,2",options="header"]
|===
| Concern | Maven (developer inner loop) | Flake (deploy / release)

| Iteration speed | fast, incremental, IDE-integrated | slow — full build in a fresh sandbox
| Reproducibility | "works on my machine" risk | pinned, content-addressed
| Cross-compile plugin | impossible on darwin | natural (routes to linux-builder)
| Deploy artifact | `target/*.jar` (mutable, can be stale) | store path (immutable, is-what-ran)
| Entry command | `./mvnw -pl :seed-master` | `nix build .#seed-master`
|===

The split mirrors what netplan already does: `./mvnw -pl :netplan` for dev,
`.#netplanJar` for consumption. This design extends the same discipline to the
deployable artifacts.

== Target flake outputs

[cols="1,2,2",options="header"]
|===
| Output | What | How built

| `.#netplanJar` | netplan jar | exists (Maven-in-nix)
| `.#manifests` | manifests exec jar | *new* — Maven-in-nix (reactor build)
| `.#seed-master` | bootstrap exec jar | *new* — Maven-in-nix (reactor build)
| `.#flox-nri-plugin` (+`-debug`) | NRI plugin, aarch64-linux | *new* — re-export from runtime flake; cross-built via linux-builder
|===

=== seed-master / manifests: build the reactor, not the module

`seed-master` depends on `manifests`, `netplan`, `systemd-contract`; `manifests`
depends on others in turn. Rather than `netplanJar`'s piecewise
`install-file` + per-module build, the seed-master/manifests outputs should run
the *whole reactor* once from the parent pom:

[source,nix]
----
seedMaster = pkgs.stdenv.mkDerivation {
  name = "rke2lab-seed-master";
  src = ./.;                                   # full repo: parent pom + all modules
  nativeBuildInputs = [ pkgs.maven pkgs.jdk25 ];
  buildPhase = ''
    mkdir -p $TMPDIR/.m2
    mvn -Dmaven.repo.local=$TMPDIR/.m2/repository -o? clean package -DskipTests
  '';                                          # offline (-o) once deps are vendored; see open questions
  installPhase = ''
    mkdir -p $out/share/java
    cp seed-master/target/seed-master-*-exec.jar $out/share/java/seed-master.jar
  '';
};
----

The hard part is Maven dependency resolution inside the pure nix sandbox (no
network). `netplanJar` sidesteps it for a single module; the full reactor pulls a
much larger third-party tree. See open questions.

=== flox-nri-plugin: re-export, do not duplicate

The runtime flake already defines the plugin. The top-level flake should *import*
that flake and re-export its `flox-nri-plugin` / `flox-nri-plugin-debug` outputs,
so there is a single Go build definition. `nix build .#flox-nri-plugin --system
aarch64-linux` cross-builds via the linux-builder.

== Pulumi binary resolution

`Pulumi.yaml` currently hardcodes `binary: seed-master/target/seed-master-0.1.0-SNAPSHOT-exec.jar`.
A store path is content-addressed (changes every build), so it cannot be
hardcoded. The clean seam is a stable `result` symlink produced by `nix build`:

[source,yaml]
----
runtime:
  name: java
  options:
    binary: result/share/java/seed-master.jar   # nix build .#seed-master -> ./result
----

`result` is gitignored. The deploy flow becomes:
`nix build .#seed-master && pulumi up`. The jar Pulumi runs is then exactly the
store-built artifact, not a possibly-stale `target/`.

The node's installer already GC-roots and `readlink`s the plugin store path (and,
since the store-resolved-env work, the env store paths the same way). So the node
side changes from "build then gcroot" to "consume the pre-built path then gcroot"
— a natural fit with the existing model.

=== Store distribution to the node (verified)

The node (`master`) is an incus instance with its *own* rootfs-resident nix store
(~8272 paths), independent of `bioskop-nixos` (~2790) and the darwin dev machine.
A build-time store path therefore must be *distributed* into master's store. The
topology, verified live:

----
bioskop (darwin dev machine = this host)   nix build here; also the NFS source
  └─ bioskop-nixos (NixOS aarch64)          own store; sshd:22; reachable as `nxmatic`
       └─ master (incus instance)            own store; sshd:22; runs the flox containers
----

The proven mechanism — no ssh keys, no substituter, no shared mount, over the
incus control channel that already exists:

[source,sh]
----
# on bioskop-nixos (or proxied from the dev machine):
nix-store --export $(nix-store --query --requisites "$STOREPATH") \
  | incus exec master --project rke2lab -- nix-store --import
----

Verified by copying `nixpkgs#hello` (absent in master) into master's store:
the path and its full closure landed (RESULT=PRESENT). This corrects the earlier
framing that distribution would go "dev -> node over the nix-store ssh identity":
the dev machine *is* bioskop (local, not a remote peer), the hardened
`nix-store.<peer>` alias only targets nikopol (inventory filters out self), and
the real consumer is `master`, one hop deeper than `bioskop-nixos`.
`nix copy --to ssh-ng://master` is also viable (sshd is up) but needs auth wiring;
export|import needs none.

== Coupling to the remote nix builder

The plugin's build-time cross-build and the container remote-builder feature
(link:flox-store-resolved-runtime-and-builder.adoc[Flox Store-Resolved Runtime +
Remote Nix Builder]) use the *same* linux-builder. They are siblings: both are
"let nix route Linux builds to the Linux host". Settling this build-entry-point
design first gives the builder feature a clean, store-resolved world to build on.

== Open questions

. *Maven offline resolution in the nix sandbox*: the reactor's third-party
  dependency tree must be available without network during a pure build. Options:
  a vendored `.m2` derivation (fixed-output, hash-pinned), `maven2nix`-style
  dependency fetching, or running the build impure (`--option sandbox false`)
  like the runtime flake's prebuild does. `netplanJar` currently relies on the
  ambient environment; the full reactor will expose this.
. *Incremental dev story*: confirm the Maven inner loop stays untouched (it does —
  `./mvnw` is unchanged); document when to use which entry point.
. *`result` symlink vs wrapper*: whether Pulumi reads `result/...jar` directly or
  via a tiny wrapper that `nix build`s on demand. Direct symlink is simpler;
  wrapper auto-builds but hides the step.
. *CI*: where `nix build .#seed-master .#flox-nri-plugin` runs (the linux-builder
  must be reachable from CI, not just the dev machine).
