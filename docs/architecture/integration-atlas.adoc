== Why this atlas exists

The atlas's *function* — prove the specification models hold together via a monotone-before/after
additivity test, reopened at every design activity — is **cross-subsystem, not subsystem-specific**.
This placement (`docs/architecture/integration-atlas.adoc`) reflects that transverse structure. The
content today is **doctor-only** (the first per-subsystem view below); honest caveat: transverse in
structure, doctor-only in content until a second subsystem adopts the ritual.

Each new model risks silently contradicting or duplicating the others. This atlas is the antidote: a
single view that lists every model, draws how they connect, and — when a model is added — *proves it
is additive* by a simple visual test.

*The test of "additive" is MONOTONE before/after.* Draw the model constellation without the new
model (before), then with it (after). Additive means: *no box erased, no arrow rewired, only
additions.* If "after" cannot be drawn without rubbing out a line of "before", the model is not
additive — and the figure says so out loud. This operationalizes the project principle that *a
well-integrated spec is itself the proof we are on the right path.*

Legend used throughout: thin/blue = IMPLEMENTED (built); thick/green = the model under design;
dashed/amber = EXPLORATION (not built, future); grey = cross-cutting foundation.

== The two spaces — OSGi and host

Every model on this atlas sits in one of two spaces, and the line between them is the application's
deepest seam. This framing is the *purity axis* made structural: it is the backdrop each per-subsystem
view is read against.

* *OSGi space* — pure models that *describe*: the resolution oracle (`UnitResolver`), the
  manifests universe, the doctor record model, the config records. No `com.pulumi`, no `io.grpc`.
* *Host space* — code that *actualises* the description over the Pulumi engine: orchestration, the
  ledger write-side, `ConfigLoader`. This is where the engine imports live.

The only edge that legitimately crosses is the *bundle/host contract*: a bundle declares a need
(`Require osgi.extender`), the host satisfies it (`Provide` + the `SectionReader` SPI for values). A
pure model reaching directly into host code — as `Rke2labConfig → ConfigLoader` does today — is a
crossing in the WRONG direction, a decomposition defect to invert.

==== Verdict — does it hold?

An honest reading of the three figures:

. *Monotone: yes.* No blue box or arrow is erased or rewired from A to B, or within C. Every change
  is an addition. The HealthSystem model is additive against the whole constellation.

. *Two honest edits (changes, not deletions):*
.. `Generalist` gains a held `ClinicalAccess` (it held registry + patient before). That is a *changed
   collaborator*, but the read core it ultimately calls is unchanged — the wrap is real, not a
   rewrite.
.. `LiveMedicalRecordRegistry.cohortFor` loses its `@Spike` marker on promotion. A marker strip, not
   a logic change.

. *The explorations gain seams, lose nothing:* the what-if planner now has a concrete patient-record
  provider (the HealthSystem), and the rules-engine / referral work has the named grant seam to plug
  into. The keystone does not merely sit beside the explorations — it makes them more buildable.

. *The one not-yet-proven edge* is the amber dashed "grant seam awaits referrals". It is proven only
  when step 2 plugs referral-derived grants into the GrantPolicy. Everything else is solid today.

Conclusion: the constellation holds, and HealthSystem is additive.

=== Additivity proof: Referral round-trip (shipped 2026-06-13)

The referral round-trip flips the diagnosis seam from `diagnose(Symptom, Observation) →
Optional<Prescription>` (the why drops on `Optional.empty()`) to `diagnose(Referral) →
ReferralReply` (the why — an `Assessment` — ALWAYS survives, prescription or not). Four new types
(`Referral`, `ReferralReply`, `Assessment`, `SchemaRef`) plus a persisted-shape change
(`RemediationPlan` carries `List<ReferralReply>` not `List<Prescription>`, with `prescriptions()` as
a derived view). The changed collaborator (`Prescription.humanHint` shrinks to action-only; the
reasoning migrates into `Assessment`). Two exemplar specialists (`NetworkSpecialist`,
`ClusterSpecialist`) co-consult.

==== Verdict — does it hold?

An honest reading:

. *Monotone at the persisted-shape level: yes.* `RemediationPlan` carries a new collection (`replies`)
  and a derived view (`prescriptions()`) — the old `prescriptions` field is gone, BUT the persisted
  output map gains a `replies` key (additive) and loses nothing (the doctor predates any persisted
  remediation plan in the dev stack, so no real data is rewritten). `ConsultationReport` gains the
  `assessment` key under each reply in `plan.replies`, additive. The negative check: no other
  shipped box or serialized shape was rewritten; `Observation`, `Symptom`, `ConsultationReport`
  envelope, and all read/write paths for them are untouched.

. *One honest changed collaborator:* `Prescription.humanHint` shrinks from "reasoning + action" to
  "action only" — the reasoning migrates into the reply's `Assessment`. This is a changed
  collaborator, not an erased one. The `Prescription` box itself remains; only its content shifts.

. *The seam method signature changed* (`diagnose(Symptom, Observation)` → `diagnose(Referral)`), but
  both the `Specialist` box and all its existing collaborators (`Patient`, `Observation`, `Symptom`,
  `MedicalRecord`, `HealthSystem`) remain — the flip adds a request/response envelope, rewires
  nothing downstream.

. *Two fake exemplar specialists added* (`NetworkSpecialist`, `ClusterSpecialist`) to show the
  integration seams (treatment vs decline-with-why). These are NEW boxes, not rewrites.

Conclusion: the referral round-trip is additive. The seam flip is monotone; the one changed
collaborator (`Prescription.humanHint` shrink) is honest and isolated.

=== The ritual — how this atlas stays alive

Reopen this atlas at the START of every design activity (doctor or another subsystem), before
writing a new model's spec:

. *Add the new model* as a green box in a fresh before/after pair (or extend Diagrams A–C).
. *Prove monotone:* confirm no existing box or arrow is erased or rewired. If you must erase one,
  STOP — the new model is not additive; rework the seam until it is, or record explicitly why a
  breaking change is justified.
. *List honest edits:* any changed collaborator (not just additions) is named in the verdict, as
  the two edits above are.
. *Flip green→blue* when a model ships, and update its inventory status.
. *Update the inventory table* with the new model and its links.

This keeps "a well-integrated spec is the proof we are on the right path" a standing practice, not a
one-time exercise.

== Config subsystem — per-subsystem view

Step 2's second subsystem to adopt the ritual. The OSGi bench (four modules under `osgi-bench/`)
proved, on the real Felix framework, the *schema/resolution* half of the crossing contract: the
`Require osgi.extender` contract (P1) and an introspectable Metatype `ObjectClassDefinition`
retrieved by PID (P2). The *value/`SectionReader`* half (inverting `Rke2labConfig → ConfigLoader`)
stays stage 3, and Config Admin delivery / DS activation are stages 3–4, gated.

The bench is disposable scaffolding — it proved the principles without touching production config
code (`InfraDomain`, `InfraConfigRegistry`, `Rke2labConfig` all unchanged). Real config will adopt
these patterns by MOVE in later increments, never by duplication.

=== Verdict — does it hold?

An honest reading:

. *Monotone: yes.* No built box erased or rewired from BEFORE to AFTER. The three boxes
  (`InfraDomain` loop, `InfraConfigRegistry`, `Rke2labConfig`) are unchanged because the bench is
  separate scaffolding — it proved the contract without touching production. The three green
  additions (the Require/Provide extender pair + the Metatype OCD) are NEW, not rewrites.

. *Honest scope:* only the *schema/resolution* half is proven here. The `Require osgi.extender` +
  `Provide osgi.extender` contract is resolved by the REAL Felix framework (P1:
  `ExtenderContractSpikeTest`), and the Metatype `ObjectClassDefinition` is introspectable by PID
  (P2: `MetatypeIntrospectionSpikeTest`). The *value* channel (`SectionReader`, inverting
  `Rke2labConfig → ConfigLoader`) is stage 3, and Config Admin delivery / DS activation are stages
  3–4, deferred.

. *The proof is on the REAL engine, not asserted.* Both tests run on the real embedded Felix
  framework (via `FelixFrameworkExtension`, a JUnit5 extension), installing real bundles built by
  `bnd-maven-plugin`. P1 proved the framework refuses to resolve when the host is absent
  (`BundleException`). P2 proved typed access (no reflection) by having the framework export
  `org.osgi.service.metatype` from the system bundle (`system.packages.extra`) so the test and
  felix.metatype share one API copy.

. *Metatype is a NEW box.* The atlas previously defined the crossing contract as `Require
  osgi.extender` + `SectionReader` (value channel); Metatype (schema) is the new addition this slice
  introduced. Its additivity is proven above: it connects to the existing `InfraConfigRegistry` by
  describing its shape, but does not rewrite any existing box.

Conclusion: the config constellation holds, and the extender + Metatype additions are monotone. The
bench is disposable scaffolding that graduates these principles to the durable atlas.
