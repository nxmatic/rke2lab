= Architecture Diagrams: Flox NRI Plugin
:toc: left
:toclevels: 3

[IMPORTANT]
====
*Two-tier delivery (substrate alignment, 2026-08-25).* The plugin is delivered in
*two tiers* and these diagrams span both — read the tier tag on each section:

* *FOUNDATION (baked, LIVE)* — the plugin binary is a flake output of
  `github:seedmatic/flox-nri-plugin` (a fork), baked into the node-base image by
  `nixos/containerd.nix` (symlinked to `/opt/nri/plugins/10-flox`, NRI enabled via
  `90-nri.toml`). No DaemonSet, no `/srv/host`, no ConfigMap trampoline. This is
  Section 1 below.
* *EXTENSION (retained, post-boot)* — the DaemonSet installer/reconciler + the
  remote nix builder that contribute *new/unknown* binaries and node configuration
  at runtime. RETAINED in the codebase for future use, but no longer the primary
  path; the stale `/srv/host` hostPath is dissolved (→ store-resolved / ConfigMap /
  rendered-branch source). Sections 2, 3, 6 and the deployment diagram describe this
  tier — treat their `/srv/host/...` paths as the pre-substrate form.

* *ENV delivery moved to runtime (2026-08-27).* The plugin stays BAKED (foundation),
  but the flox *envs* it injects no longer live in the node's baked `/nix/store` —
  they live in a runtime ZFS-PVC nix store written by a *reconciler DaemonSet*, and
  the plugin overlays THAT store. Where a diagram or the resolution section shows the
  env GC-root/store on the baked host store, read it as the LIVE interim; the target
  populator is the reconciler (design doc §Runtime env delivery).

See link:patterns/flox-store-resolved-runtime-and-builder.adoc[Flox Store-Resolved
Runtime + Remote Nix Builder] for the full two-tier design and the extraction.
====

The foundation is a pure bake: the fork flake's binary is symlinked in by
`nixos/containerd.nix`, containerd launches it, and it injects envs — no FloxHub
round-trip, no runtime installer. The env *store* it overlays is, in the target, the

delivery); the baked `/nix/store` env is the LIVE interim.

== Key Flow Points

=== Pod Structure (DaemonSet on each node)

The `flox-runtime-installer` pod has two containers:

. *Init Container* (`runtime-installer`):
** *Purpose*: One-time setup and configuration
** *Pod Mode*: Copies assets from ConfigMap to host filesystem
** *Host Mode*: Pre-activates flox environments, configures containerd
** *Lifecycle*: Runs once, exits when complete
** *Output*: Prepares host filesystem and configures containerd for NRI

. *Main Container* (`nri-plugin`):
** *Purpose*: Runs the NRI plugin process continuously
** *Execution*: Runs `/opt/nri/plugins/flox-nri-plugin` binary
** *Lifecycle*: Long-running, restarts if crashes
** *Communication*: Bidirectional with containerd via NRI API (Unix socket)
** *Function*: Intercepts container creation, injects flox environment mounts

=== Installation (Init Container → Host)

. *Pod Mode* (`installer::pod:run`):
** ConfigMap mounted at `/.sh/build-assets`
** Materializes scripts and debug tools to host filesystem
** Extracts NRI plugin tarball

. *Environment Setup* (`installer::flox:install_environments` in pod mode):
** Traverses mounted directory structure: `/.sh/build-assets/{category}/{name}/.flox/`
** Copies flox env files to host: `json`, `flake.nix`, `manifest.toml`, `manifest.lock`
** *⚠️ Does NOT activate* (pod has no access to /nix/store)

. *Trampoline*: `nsenter --target 1` to host namespace

. *Host Mode* (`installer::host:run`):
** Initialize tooling, validate assets

. *Pre-activation* (`installer::host:flox:activate_environments` in host mode):
** Rediscovers environments from host filesystem
** For each environment: `cd {env_dir} && flox activate`
** Generates `flake.lock` files
** Builds packages and populates `/nix/store`

. *Containerd Configuration*:
** Updates `config.toml` to enable NRI (`disable = false`, plugin paths)
** Restarts containerd if config changed
** Containerd discovers plugins in `/opt/nri/plugins/`
** NRI plugin (`flox-nri-plugin`) self-registers with containerd via NRI API

=== Runtime (Container Creation)

. *Annotation Detection*: NRI plugin checks `flox.dev/environment`
. *Environment Resolution*: Maps `networking/kdns` → `/srv/host/.../networking/kdns`
. *Mount Construction*: Builds bind mounts for .flox + overlay for /nix
. *Hook Creation*: Prestart hook to fix ownership (chown)
. *Injection*: Returns ContainerAdjustment to containerd
. *Activation*: Container starts with flox environment auto-discovered

=== Overlayfs Strategy

* *Lower*: `/nix-store-ro` (read-only bind of /nix/store)
* *Upper*: `/nix-overlay-upper` (tmpfs, writable, ephemeral)
* *Work*: `/nix-overlay-work` (tmpfs, overlay metadata)
* *Mount*: `/nix` (merged view)
* *Benefit*: Protects host store, allows builds in container

== Annotations Reference

=== Supported Annotations

[cols="1,1,1,1",options="header"]
|===
| Annotation | Required | Description | Example
| `flox.dev/environment` | Yes | Flox environment name | `networking/kdns`
| `flox.dev/home` | No | Override HOME directory | `/home/app`
| `flox.dev/uid` | No | Container UID (for chown) | `1000`
| `flox.dev/gid` | No | Container GID (for chown) | `1000`
| `flox.dev/debug` | No | Enable debug mode | `true`
| `flox.dev/debug-port` | No | Delve debugger port | `2345`
|===

=== Environment Path Resolution

* Format: `{category}/{name}` or just `{name}` (defaults to `networking/`)
* *Store-resolved (the contract, stable):* `{category}/{name}` → readlink the
  GC-root `/nix/var/nix/gcroots/flox-runtime/env/{category}/{name}` → the env store
  path. The GC-root contract is INVARIANT; only its populator + backing store move —
  TARGET = the runtime ZFS-PVC store written by the reconciler DaemonSet; INTERIM
  (LIVE) = baked into the node `/nix/store` by `nixos/flox-runtime.nix`. The env
  catalog lives in rke2lab's `runtime/flox` flake; the shim (fork) never holds it.
* *Extension (pre-substrate, legacy):* mapped to
  `/srv/host/k8s-daemonset.d/runtime/flox-runtime/{category}/{name}` by the
  DaemonSet installer — dissolved by the substrate, repointed to the store path.
