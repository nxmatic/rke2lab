= bbox-edge — the router-reconciliation contact, put in its place
:toc: left

[NOTE]
====
*Status:* IN PROGRESS (2026-07-07). The sixth external edge, second extraction of the
control-plane→OSGi sweep (after link:incus-edge-spec.adoc[incus-edge]). Unlike incus (a bare
`ProcessBuilder`), the bbox contact rides an external library, `java-bbox-api-client` — so this edge
also proves the *library-backed* edge shape: the library is made an OSGi bundle and IMPORTED (not
embedded), and no library type crosses the contract boundary.
====

== The contact today — inlined, duplicated, library types on the host

The bbox contact (open a session to the Bouygues Bbox router, diff+apply DHCP reservations) lived in
`seed-master`, duplicated across two paths: `BboxReconcilerComponent.reconcileStandalone` and the
Pulumi `BboxReservationsResource`. Both did `BboxApiClient.open` + `ReservationReconciler.apply(row,
mode)`. Five host files imported `io.nxmatic.bbox.*` — the library's `Action`/`RowOutcome`/
`DesiredReservation` types were spread across the host, including into the Pulumi resource graph
(`BboxReservationResource` built its `Output`s from a library `RowOutcome`).

== Resolution — a `bbox-edge` `@Component` and a home-vocabulary `bbox-core`

* *java-bbox-api-client* becomes an OSGi bundle (bnd manifest, `0.2.1`): `Bundle-SymbolicName
  io.nxmatic.bbox.api.client`, exports its two API packages, imports `com.google.gson` (itself a
  bundle). No embedding — the edge imports it, and the staging closure stages it (and gson) as
  carriers because an edge imports their packages.
* *bbox-core* (`type=model`): `BboxReconciler` — `reconcile(baseUri, password, dryRun,
  List<BboxReservationRequest>) → List<BboxRowOutcome>` — over a HOME vocabulary
  (`BboxReservationRequest`, `BboxRowOutcome`, `BboxAction` mirroring the library enum). No
  `io.nxmatic.bbox.*` type crosses the contract boundary.
* *bbox-edge* (`type=edge`, `@Component`): `LiveBboxReconciler` opens the session, rebuilds the
  library `DesiredReservation` from each request, applies, and maps the library `RowOutcome`/`Action`
  back to the home records. The single door — the library resolves only in this bundle's realm.
* *seed-master* (host): purified off `io.nxmatic.bbox.*` — it builds `BboxReservationRequest`s from
  the blueprint, calls the reconciler resolved from the registry, and projects `BboxRowOutcome`s into
  its counts and Pulumi resource graph. The library types no longer live host-side.

== The bbox SCION scenario (target — the metier definition)

In the ClusterSeed vision (link:../bdd/bdd.adoc#clusterseed-scenario-map[the scenario map]) bbox is a
graft-caller: the host step "the network reservations are settled" sows THIS scenario in-container and
grafts its scion. The host speaks gardening; this scenario speaks the bbox metier (reservation · diff ·
outcome). It is the `bbox-bdd` bundle (first extraction of the two host-side scions, 2026-07-11), on the
`cluster-bdd` reference shape: a `BboxReconciliationScenario` (jGiven `Given/When/Then`) + a
`BboxBddScenarios.run()` front-door the launcher plays in-container, and a
`BboxReconciliationScenarioInContainerTest` (`@OsgiWorld`) that boots Felix and registers the mock
collaborators. `BlueprintRowEnumerator` (pure — `bbox-core` + `netplan-contract`, zero Pulumi) lives in
`bbox-core` (its home vocabulary), consumed by the scion. The host `BboxStage` +
`BboxReconciliationOrchestrator` are the DEFERRED "avant", deleted when the host runbook grafts this scion.

[listing]
----
SCENARIO: the desired reservations are reconciled against the router
  GIVEN the desired (mac, ip, hostname) reservations for the run
    AND the BboxReconciler contact (edge) + the RunGate — both resolved from the registry
  WHEN the scion asks the RunGate whether to cultivate, derives dryRun = !cultivating()
    AND the edge opens one session, fetches the router's reservation table once, diffs each desired row
  THEN every desired row has a BboxRowOutcome — present-already / created / corrected (BboxAction)
    AND a row that could not be reconciled is SURFACED, never silently dropped
----

*Preview inertness — the SCION consults the RunGate (A2), not the edge.* The scion resolves `RunGate`
from its own `BundleContext` and derives `dryRun = !gate.cultivating()`, passed to the existing
`BboxReconciler.reconcile(..., dryRun, ...)` — under a closed gate the edge diffs but does not write
(native DRY_RUN mode → `WOULD_CREATE`/`WOULD_UPDATE`), so the scion plays honestly without touching the
router (no separate fake). The port + edge are untouched. *On a refused row* the domain MAY consult the
doctor itself (a symptom), the same transversal-consult pattern as systemd/cluster — the host never sees
it.

The scion grafts back under the host step; its `@Scion("fruit")`/`@Scion("sowing")` roles (if it consults)
project through the neutral port exactly as the doctor's do (see
link:seed-broker-spec.adoc[the seed-broker spec]).
