= The engine lifecycles — framework, launcher, runbook, on the JUnit substrate
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN (converged 2026-07-04), not built. This is the SOCLE (foundation) of the
BDD-as-engine migration — increment 1, which must land before the ClusterSeed vertical
(link:pipeline-spec.adoc[pipeline-spec]) consumes it.

One spec for one subject: *how the stacked engine lifecycles are held at runtime* — the OSGi
framework, the embedded JUnit Platform launcher, and the jGiven runbook — and how the SAME model
serves both a real test and a live seed run, differing only by scope, never by branch.

*Why this exists:* the BDD-as-engine turn makes the seeding a tree of jGiven scenarios played by an
embedded JUnit launcher inside Felix. That launcher, that framework, and that runbook each have a
lifecycle — and today all three are held *lexically / per-scenario* (a fresh `newFramework()` per
`launch()`, a throwaway `LauncherFactory.create()` per run, a `new ReportModel()` per scenario). That
is fine for a test that may fall after each case; it is WRONG for a live seed, where the world must
survive across the scenarios that compose the run. This spec fixes the ownership and the scoping.
====

[TIP]
.TL;DR — read this, skim the rest
====
* *Substrate:* JUnit is the single lifecycle substrate. It already discovers and creates the OSGi
  framework; it also carries scope demarcation (`LauncherSession` root > class > method) via
  `ExtensionContext.Store` + callbacks. Nothing home-grown doubles it.
* *Framework lifecycle:* held by a JUnit scope's `Store`; undone when THAT scope closes. Test vs
  runtime = *where the root lives* (test run / seed run), same code. Connection = `OsgiConnection`:
  `embedded()` realised (`close()` stops Felix), `remote()` a named extension point (`close()`
  detaches — the world survives).
* *The lever:* the OSGi *start level*, a SINGLE global cursor, driven by the depth of the JUnit
  scope. Descent stops bundles `STOP_TRANSIENT` (async → wait for `STARTLEVEL_CHANGED`); re-ascent
  re-lights them from the persistent autostart. The `BootPlanner` stays the sole role→level source.
* *Two composable dimensions* a scope declares: *depth* (start level) × *domain* (`DiscoveryPolicy`
  — which bundles are installed).
* *Discipline by role, declared by an rke2lab annotation* (meta-`@ExtendWith` → extension → shared
  base + teardown strategy): *isolation* (a real test — the method scope descends/re-ascends, each
  case starts clean) vs *stationary* (a runtime pipeline — climbs once, NEVER descends between
  pipelines, the world survives). Extensible: a 3rd discipline = a 3rd annotation.
* *The runbook is the DELIVERABLE.* It is owned by the launcher / the seed OPERATION (bounded by
  `pulumi up`), NOT by the framework — the framework only CONTRIBUTES `ScenarioModel`s to it.
* *YAGNI:* no per-bundle activation model (the test case does that in plain JUnit), no scenario-level
  start-level (a scenario activates no bundle of its own — fixtures are fragments), no transaction
  engine (the "lease" is a lifetime analogy, not ACID), no framework-serves-N-operations (there is
  no client version of the framework yet).
====

== The subject — three stacked lifecycles, held lexically today

The BDD-as-engine model (link:pipeline-spec.adoc[pipeline-spec]) plays the seeding as jGiven
scenarios on an embedded JUnit launcher, inside Felix. Three engines stack, each with a lifecycle:

[cols="1,2,2",options="header"]
|===
| Engine | Held TODAY (lexical / per-scenario) | Problem at runtime
| OSGi framework | `FrameworkLauncher.launch()` does `factory.newFramework()` — a FRESH framework per
  call; `BootedFramework.close()` = full `framework.stop()`, all-or-nothing | a live seed is ONE long
  run whose scenarios must share ONE surviving world, not a framework per scenario
| JUnit launcher | `LauncherFactory.create()` per run, thrown away; no `LauncherSession` | no root
  scope survives the individual scenario
| jGiven runbook | `new ReportModel()` per scenario (`ClusterReadinessTopic`: `runbook.orElseGet(new)`) |
  the operator needs ONE runbook for the whole seed, not a throwaway per scenario
|===

The common defect: all three are scoped to the *scenario / test case*, which is acceptable when a
test may fall after each case, and WRONG at runtime where the world must survive the run. This spec
re-homes each lifecycle to the scope that matches its true lifetime.

== The substrate — JUnit carries the lifecycles, nothing home-grown doubles it

*Lead: JUnit already discovers and creates the OSGi framework (`InContainerJUnitRunner` /
`JGivenTestkit.felix()`); it also owns nested scope demarcation. So it carries the framework, launcher
and runbook lifecycles too. A new policy is a contributed JUnit extension — never a home-grown
registry.*

The realisation (2026-07-04): we already make JUnit carry the two hard parts — discovering the
framework's install set and creating the framework in-container. Making it also carry *when* the
framework, launcher and runbook live and die is not new surface — it is the same substrate, one cran
further. This is the dogfooding rule (link:pipeline-spec.adoc[pipeline-spec] § "Why embed JUnit +
jGiven at runtime") applied to lifecycle: we extend JUnit, we do not reinvent it beside itself.

The native mechanism, used as-is:

* *`ExtensionContext.Store`, nested by scope* — `LauncherSession` (root) > Engine > Class
  (`@BeforeAll`/`@AfterAll`) > Method (`@BeforeEach`/`@AfterEach`). A `CloseableResource` in a Store
  is closed when THAT scope ends — not before.
* *Lifecycle callbacks* — `BeforeXxxCallback` (the entry hook a discipline needs to capture / raise)
  + `AfterXxxCallback` / `close()` (the exit hook to release / lower).
* *The launcher* — the extracted `JUnitLauncherCore` (see § <<the-launcher>>), driven from a
  `main()` at runtime and from surefire/IDE in test.

[NOTE]
.Anti-pattern — a home-grown FrameworkRegistry
====
❌ A process/run-global registry that we write (first-connect bootstraps, caches, later ones attach),
independent of the JUnit `Store`. It re-invents a scope JUnit already gives, and it *re-decouples*
what we want coupled (the framework's life and the scenario's scope tree). ✅ The framework lives in
the `Store` of the scope whose lifetime it should share; the SCOPE is the coupling.
====

== The framework lifecycle — held by the connection's scope

*Lead: the framework lives in a JUnit scope's `Store` and is undone when that scope closes. Test vs
runtime is only WHERE the root scope lives; the code is identical. Connecting is an abstraction:
embedded bootstraps and owns the close; remote attaches and closes nothing.*

The framework is not a JVM singleton and not a lexical `try` — it is a `CloseableResource` in the
`Store` of a chosen scope. The same teardown mechanism ("close at the end of the scope") serves both
worlds; only the *location of the root* differs:

[cols="1,2,2",options="header"]
|===
| | Real test | Live seed (runtime)
| Root scope | the test run (the class / the surefire session) | the seed run (bounded by `pulumi up`)
| Framework falls | at the end of the test — acceptable | at the end of the seed run
| Same code? | yes — only the root's lifetime differs | yes
|===

*Connecting is `OsgiConnection`* — an abstraction over "how do I reach the OSGi world", with explicit
ownership of lifecycle:

[source,java]
----
interface OsgiConnection extends AutoCloseable {
  BootedFramework world();
  boolean ownsLifecycle();          // true iff THIS connection bootstrapped the world
  @Override void close();           // owns → stop; attached → detach (world survives)

  static OsgiConnection embedded();       // bootstraps Felix in-process; owns the close — REALISED
  static OsgiConnection remote(String endpoint);  // attaches; closes = detach — NAMED, not built
}
----

*Embedded* (`FrameworkLaunchPipeline.embedded()`, the only realisation today) bootstraps Felix and
owns its `close()`. *Remote* is the named extension point: the world runs detached, `close()` detaches
without stopping it. Only `embedded()` is built in this increment; `remote()` throws
`UnsupportedOperationException` until a real client-framework case arrives (see § <<yagni>>). This is
the same detached-by-design frame the pipeline-spec already grave — here applied to the *first step*
of the seed scenario ("the OSGi world is connected").

[[the-lever]]
== The lever — the start level, driven by the depth of the JUnit scope

*Lead: the OSGi start level is a SINGLE global cursor. Each JUnit scope targets a level; because the
scopes nest, the cursor moves up on entry and down on teardown, ordered in time — NOT stacked in
parallel. The `BootPlanner` stays the sole role→level authority.*

The `BootPlanner` already assigns each bundle a start level by its ROLE, in named layers
(link:osgi-boot-decomposition-spec.adoc[OSGi boot decomposition]):

[cols="1,2",options="header"]
|===
| Level | Role
| `START_LEVEL_PASSIVE` (1) | DS-API spec jars — resolve only, no activator
| `START_LEVEL_LOGGING` (2) | pax-logging
| `START_LEVEL_FRAMEWORK_RUNTIME` (3) | felix.scr, resolver
| `START_LEVEL_BUNDLES` (4) | model/edge domain bundles — activate LAST
|===

`beginningStartLevel()` is the highest a bundle sits at (4) — the framework climbs to it, so all
installed bundles are active when the boot hands over.

*The cursor is single and global.* The framework is AT level N — never "at 4 for this scope and 3 for
that one". So there is no parallel stack of levels. What DOES nest is the JUnit scope tree, and it
maps to *ordered moves of the one cursor in time*:

[source]
----
openSession    → setStartLevel(0)   nothing active
  @BeforeAll   → setStartLevel(3)   framework-runtime (felix.scr, resolver)
    @BeforeEach → setStartLevel(4)  domain bundles active for THIS method
    @AfterEach  → setStartLevel(3)  descend: STOP_TRANSIENT on the domain bundles
  @AfterAll    → setStartLevel(0)
closeSession
----

*Descent and re-ascent, per the OSGi R8 spec* (`osgi.core` 8.0.0, verified against
`FrameworkStartLevel.setStartLevel`):

* Lowering the active start level *stops* bundles above the new level using `Bundle.STOP_TRANSIENT` —
  which arrests them WITHOUT touching their persistent autostart setting.
* The call is *asynchronous*: it returns immediately, the work runs on another thread, a
  `FrameworkEvent.STARTLEVEL_CHANGED` fires on completion. **Therefore a scope's teardown that lowers
  the level MUST wait for that event** (with a timeout, as `BootedFramework.close()` already waits on
  `waitForStop`) — otherwise the next scope sees a half-torn-down world.
* Because the descent was `STOP_TRANSIENT`, re-ascending the level *re-lights* those bundles
  automatically from their unchanged autostart setting.

NOTE: R8 guarantees per-level ordering (higher levels stop before lower) but does not explicitly
mandate an order *within* a level; the layer design already separates roles across levels, so this
does not bite. The dependency-safe order is the level order.

== The two dimensions — depth × domain

*Lead: a scope declares TWO composable things — its DEPTH (start level, the role layer active) and its
DOMAIN (which bundles are installed). They are orthogonal levers, both dimensions of "what I want
active to play".*

[cols="1,2,2",options="header"]
|===
| Dimension | Grain | Lever
| *depth* | role layer (1→4), system-wide | the start level (this spec's lever)
| *domain* | which domain / which bundles installed | `DiscoveryPolicy` (`only` / `onlyMatching(ldap)`
  / fixtures) — link:osgi-boot-decomposition-spec.adoc[boot decomposition]
|===

The start level is COARSE: level 4 activates *all* installed domain bundles together — it cannot say
"doctor but not manifests". Domain selection is the `DiscoveryPolicy`'s job (already a `sealed`
interface with `all`/`allExcept`/`only`/`onlyMatching`). A scope composes both: *"install this domain
subset (policy) AND play at this depth (level)"*. The `BootPlanner` remains the single authority that
maps role→level and computes the install set; the scope only *requests* a level, it reorders nothing.

[[discipline-by-role]]
== The discipline — chosen by role, declared by an rke2lab annotation

*Lead: the mapping scope→level is not fixed — it is a DISCIPLINE the scope's ROLE chooses. A real test
wants isolation (the method scope descends/re-ascends, each case clean); a runtime pipeline wants
stationary (climb once, never descend between pipelines, the world survives). Opposite mappings, one
mechanism.*

The asymmetry is the same test-vs-runtime divergence, seen through the level lever:

[cols="1,2,2",options="header"]
|===
| | *isolation* (a real test) | *stationary* (a runtime pipeline)
| level mapping | method scope descends at teardown, re-ascends for the next | climbs to 4 once, NEVER
  descends between pipelines
| effect | each test case re-starts the domain bundles → starts clean | the live world survives across
  the scenarios of the run
| why | isolate each case, repartir propre | the seed is one long run; do not rebuild the world
|===

A fixed mapping would break one side: `session=0/class=3/method=4` breaks pipelines (they must not
descend); `always 4` breaks test isolation. So *the role of the scope selects its discipline* — the
concrete form of "each level chooses its discipline by its role" that runs through the whole design.

*The role is DECLARED, not detected — by an rke2lab annotation, meta-annotated `@ExtendWith`.* The
annotation is the readable intent; the extension is the mechanism it pulls; the extensions share a
common base (connect + start-level piloting) and differ only in their teardown strategy (the
discipline):

[source,java]
----
@Target(TYPE) @Retention(RUNTIME)
@ExtendWith(/* the extension incarnating the discipline */)
public @interface /* SeedRuntime | IsolatedWorld — exact form decided at spec authoring */ {}
----

* An *isolation* annotation → an extension whose method-scope teardown lowers the level.
* A *stationary* annotation → an extension that climbs once and holds; teardown at the ROOT only.

Choosing the annotation IS choosing the role. Extensible: a 3rd discipline = a 3rd annotation pulling
its strategy, no change to the core — the JUnit extension model, "comme jGiven". This honours the
single-source-of-truth-for-identifiers discipline (CLAUDE.md): the role is a named rke2lab type, not a
hand-wired extension repeated at each call site.

NOTE: whether it is one annotation per discipline (`@SeedRuntime`, `@IsolatedWorld`) or one
parameterised annotation (`@SeedWorld(mode=…)`) — and the exact verbs of the lease — is decided at
authoring time, where the reading is judged. The PRINCIPLE (annotation → extension → shared base +
strategy) is fixed here.

== The runbook — the deliverable, owned by the operation, contributed by the framework

*Lead: the runbook is the whole POINT (the operator's read-AND-act view). It is owned by the launcher
/ the seed OPERATION, bounded by `pulumi up`. The framework does NOT hold a runbook — it CONTRIBUTES
`ScenarioModel`s to the one the operation owns.*

The runbook (`ReportModel`) is the benefit of all this machinery — miss it and we would have specced
the plumbing without its purpose. Ownership, decided:

* *The launcher / the operation owns it.* `SeedLauncher` opens ONE `ReportModel` at the start of the
  seed, the scenarios graft their trees into it (E5 nested-step, E10 cross-world graft), and it is
  rendered at the end of `pulumi up`. One runbook for the whole seed run.
* *The framework does not hold it — it contributes.* An OSGi world consulted across the gateway
  returns a serialized `ScenarioModel` (the `Document` seam); it stores no report. The calling world
  (host / launcher) aggregates. Consistent with the two-spaces invariant: no live report object
  crosses the gateway.
* *Scenarios stay distinguishable within one runbook.* `ReportModel.scenarios` is a
  `List<ScenarioModel>` where each keeps its `className` + description; `RunbookRenderer` already
  selects a scenario by identity (`scenarioFor(model, checkpoint)`). So the seed-cluster scenario is
  identifiable among the others. (E4 caveat: the list is FLAT + sorted by description — the *tree*
  lives only in `nestedSteps`; "distinguish by identity" yes, "hierarchy between scenarios" only via
  nesting.)

The runbook's scope is the OPERATION, not the framework's life. In embedded they coincide (the
framework falls with the operation). The framework is a participant consulted, never a repository.

[[yagni]]
== What the socle deliberately does NOT do (YAGNI, confirmed by the code)

Each exclusion was checked against the codebase, not assumed:

* *No per-bundle activation model.* Once the framework is connected and injected, a test case
  activates/deactivates ITS bundles with plain JUnit hooks (`@BeforeEach`…) + the `BundleContext` —
  its own affair, with its own knowledge. The socle acts on the FRAMEWORK (the start level), never on
  an individual domain bundle. `START_TRANSIENT`/`STOP_TRANSIENT` per bundle is the test case's
  domain, not the socle's.
* *No scenario-level start level (no level 5).* Cartography: a scenario activates NO bundle of its own
  — what a test case adds is a *fixture*, and a fixture is a FRAGMENT (`Fragment-Host: …`), which has
  no lifecycle (calling `start()` on it throws). A scenario consumes services already active at level
  4 (`awaitService`), it starts nothing. A `START_LEVEL_SCENARIO` above 4 would be empty of meaning.
* *No transaction engine.* The "lease" (bail) is a *lifetime analogy* — begin/hold/release scoped by
  the JUnit tree — NOT an ACID contract. It is bounded to bundle activation; there is no atomicity /
  isolation / resource rollback. The seed is strictly sequential (no concurrent runs), so isolation
  has no referent here. A different name than "transaction" is used on purpose to avoid the ACID
  confusion.
* *No framework-serves-N-operations.* There is no client version of the framework yet. `remote()` is
  a NAMED extension point (the framework *could* survive an operation), but "one long-lived framework
  serving a series of runbooks" is not designed in this socle. It is out of scope until a real client
  case arrives.

== The authority of the lease — bound to the initiator

*Lead: only the scope that INITIATED a mutation of the framework (posed the lease) holds — or
delegates — the authority to keep or undo it. No ambient authority.*

The lease that raises the start level for a scope confers its authority on that scope's initiator.
The initiator may delegate it, but no other scope may keep or undo a mutation it did not initiate (or
receive by delegation). This is why the discipline is a *choice of the scope*, not a global rule: the
role is defined by who holds the authority at that level. Practically, in this socle the authority is
carried by the extension the annotation pulls — the extension that raised the level at its scope's
entry is the one that lowers it at teardown; a nested scope that wants a different depth declares its
own annotation (its own extension, its own authority, undone at its own teardown).

== Increment boundary — this socle is increment 1

This spec is the foundation the ClusterSeed-vertical migration rests on. It ships as *increment 1*
(the launcher-core extraction + the connection/lifecycle model), integrated BEFORE the ClusterSeed
migration (*increment 2*) consumes it:

* *Increment 1 (this socle):* extract `JUnitLauncherCore` into `osgi/runtime/launcher` (the launcher
  the runtime OWNS, the test CONSUMES); the `OsgiConnection` abstraction (embedded realised, remote
  named); the discipline annotations (isolation / stationary) and the start-level piloting. Its plan:
  `docs/superpowers/plans/2026-07-04-launcher-core-extraction.md`.
* *Increment 2 (ClusterSeed):* the seed as a jGiven scenario whose first step connects to the OSGi
  world, consuming this socle. Its plan: `docs/superpowers/plans/2026-07-04-clusterseed-bdd-migration.md`.

[[the-launcher]]
== Related — the launcher core it rests on

The launcher is `JUnitLauncherCore`, extracted from `InContainerJUnitRunner` (the runtime owns it,
the test consumes it — the sound dependency direction, and the dogfooding promotion of JUnit to
runtime scope). It runs a JUnit Platform `Launcher` inside Felix on a dedicated host-bound thread,
engine registered explicitly, the three OSGi crossings handled; discovery + harvest are injected
strategies so both the test envelope (`*Test` + PASS/FAIL) and the seed (a named scenario +
`ReportModel`) reuse one core. Full task breakdown in the increment-1 plan.
