:toc: left

*Status:* DESIGN, not built (2026-07-01, extended 2026-07-02). One spec for one subject: what the
pipeline *is*, who owns it, how it rests on jgiven, and the two boundaries it decides to cross.

*Ownership (DECIDED 2026-07-02):* the pipeline — grammar, engine, AND the bootstrap *reasoning* — is
owned by the *OSGi world*. The grammar primitives already live there
(`osgi/foundation/pipeline/pipeline-port`: `FluentTopicRunner`/`OnFailure`/`TopicFailure`, pure,
*dual-consumable*), and jgiven is already an OSGi bundle (`jgiven-wrap`). The *host* (`exec/seed-master`
+ `pulumi-edge`) is a *consumer*: it boots the framework, injects the launch context (`RunMode`, the
Pulumi output sink), and renders/writes what the OSGi world produces. The reasoning that is *today*
stranded in `exec/seed-master/.../controlplane/pipeline` is *target-state OSGi*. This spec describes
that target; the "today" notes mark what still lives host-side and must migrate.

This document folds in — and *replaces* — the earlier parked exploration
`dsl-unification-exploration.adoc` ("JGiven as Shared Engine", 2026-06-07). That exploration framed
"one engine, two layers" and left two questions open (the state model; the narration depth). This
session closed both, so the exploration is deleted, not linked: its living content lives here.

It also subsumes the original "two gates" design (living gate + output gate). The gates are two
*mechanisms* derived from a single named launch concept (`RunMode`) — and, being intrinsically Pulumi,
they sit at the *host edge*, fed by / feeding the OSGi reasoning across the seam. The authoring surface
is the shared link:../patterns/fluent-pipeline-grammar.adoc[fluent pipeline grammar]; this spec is the
substrate + reasoning underneath it.

== The compass — the runbook is the operator's view, read AND act

*Lead: the runbook renders what the OPERATOR needs to understand and act on the whole system — not what
the pipeline does. Inclusion is judged by operator-need, not by "is it a topic".*

The reason any of this matters. The runbook does not exist to *narrate the pipeline*. seed-master is
only one piece — the cluster bootstrap — of a larger system the operator runs. The runbook is the
projection of *the operator's mental model of the whole system*, and the inclusion criterion for what
it renders is not "is it a pipeline topic?" but *"does the operator need it to understand and act on
the system?"*

Scope is *read AND act*: the runbook is the medium through which the operator both understands (state,
health, why — the doctor, symptoms, drift) and acts (replay a checkpoint, apply a remedy, relaunch a
phase). The doctor / symptoms / drift / remedies are not isolated features; they are pieces of this
actionable operator-view.

This compass judges the "depth" question the parked exploration left open (see
<<closed-questions>>): a topic narrates through the runbook *iff the operator needs it*, not because
it happens to be a pipeline step. bbox reconciliation is the first verdict — IN, because the operator
needs the reservation state — even though it is an action topic that narrates nothing today.

The mechanics below (two pipelines, the vocabulary, `RunMode`, the two gates, probe⟺step) are the
*means*; this operator-view is the *end*.

== Ownership and the seam — OSGi reasons, the host feeds and renders

*Lead: OSGi owns grammar + engine + reasoning (they already live there); the host injects `RunMode` +
Pulumi context and renders/writes back. A domain never reads the global flag — the seam carries it.*

The pipeline is *owned by the OSGi world*; the host is a consumer. Two facts of the code already put
it there: the grammar primitives live in `osgi/foundation/pipeline/pipeline-port` (pure, dual-consumable
— a real bundle at build time, exported from the system bundle for the flat host classloader at
runtime), and jgiven is already an OSGi bundle (`jgiven-wrap`, with an in-container testkit). The
bootstrap reasoning — the topics, the scenarios, the doctor consult, the readiness verification, the
runbook — is *target-state OSGi*; it is only *stranded* in `exec/seed-master` today.

[cols="1,2,2",options="header"]
|===
| | *OSGi world* (owner) | *host* (`exec/seed-master` + `pulumi-edge`, consumer)
| role | the brain — reasons about the bootstrap | thin launcher + the Pulumi edge
| holds | the topics, the jgiven session + engine, the doctor, readiness, the `ReportModel` runbook |
  framework boot (already OSGi via `BootPipeline`), the *source* of `RunMode`, the stack *sink*
| jgiven engine | *here* (`jgiven-wrap`) | —
| the seam | *produces* the runbook + the output contributions | *injects* `RunMode` + Pulumi context,
  *renders* the runbook, *assembles + writes* the stack
|===

The seam keeps the discipline this spec is built on: *a domain never reaches for the global flag.*
`RunMode` (which only the host can know — it derives from `Deployment.isDryRun()`) is *injected* into
the OSGi world as a value; the OSGi world reasons; the host renders and writes. The founding constraint
travels intact: probes-as-steps and the runbook are produced OSGi-side; the host only renders/exports.
The seam is *remote-first* (the OSGi world is detached by design; embedded exec merely folds it
in-process — see the next section); the output gate probably splits *contributors OSGi-side* (each
domain contributes a pure `Map`, no Pulumi dependency crosses the seam) from *assembly + write
host-side* (`pulumi-edge`). Not yet decided — that seam is the next brainstorm.

== The OSGi world is detached by design — embedded exec is a special case

*Lead: the general case is a detached OSGi world (remote); seed-master's embedded exec merely folds the
seam in-process. The amorce paradox + Pulumi belong to the embedded/bootstrap host only, not the world.*

The correcting frame (user, 2026-07-02): *the OSGi world is designed to live detached from the
embedded executable and be accessed remotely.* The general case is a standalone OSGi world running as
a service — it *amorces itself* (no external actor needs to bring it into being), and the host is a
*remote client* that connects, injects `RunMode` + the Pulumi context, and pulls back the runbook and
the output contributions across the remote frontier.

The embedded exec (`BootPipeline.embedded()`) is therefore *one particular case* — the degenerate one
where the host co-locates and boots OSGi in-process. The `embedded` in the preset's name already said
so: it is a preset, not the pipeline. The chicken-and-egg amorce ("what starts OSGi cannot run inside
OSGi") is *real only in the embedded case*; detached, the OSGi world has its own internal amorce and
there is no paradox. The amorce is the hardest part — but it is a property of *co-location*, not of the
architecture.

*Which use case is which* (user, 2026-07-02): the two modes are not a theoretical symmetry — they are
two real seed use cases:

[cols="1,2,2",options="header"]
|===
| | *seed-master (bootstrap)* | *seed in-cluster (other uses)*
| mode | *embedded exec* — boots OSGi in-process | *detached workloads* — OSGi as a separate workload, remote
| why this mode | it *precedes* the cluster: there is no cluster yet to deploy a workload into, so it
  must embed and amorce OSGi itself — *this* is why it owns the amorce paradox | the cluster already
  exists; the OSGi world runs as a workload, accessed remotely — nothing needs to amorce it in-process
| Pulumi edge (`RunMode`, stack sink) | *yes* — seed-master *creates* the infra via Pulumi, so
  `Deployment.isDryRun()` is a fact only here | *no* — a workload runs *inside* the already-created
  cluster; it has no `RunMode`
|===

This lands the Pulumi coupling precisely: it is *not* a property of the OSGi world — it is a property
of the *bootstrap's embedded host*. The detached OSGi world knows nothing of Pulumi. Which confirms, by
a second route, that the two gates live at the *host edge* (`pulumi-edge`), never in the OSGi
reasoning.

So the hierarchy is not "host → amorce → OSGi". It is *one OSGi world, one seam, two ways the seam is
realised*:

memories (the atlas-first reflex applied) shows there are *three* levels of pipeline, each already

== Two engines, not one — the grammar rests on jgiven, does not merge with it

*Lead: `FluentTopicRunner` (type-state, our grammar) and jgiven (narration+report) are orthogonal, not
redundant. One engine (jgiven) as substrate, two layers; `during/then` stays the authoring surface.*

Within the reasoning pipeline, the root defect this spec addresses is that *two independent engines are
tangled* (in the topics still stranded host-side) and mistaken for one. They are orthogonal, not
redundant:

[cols="1,2,1",options="header"]
|===
| Engine | What it does | Size
| `FluentTopicRunner` (`osgi/foundation/pipeline/pipeline-port`, shared) | type-state ordering
  (compile-time) + enter/leave logging + wrap a throwable as `TopicFailure(label, cause)` |
  ~33 LOC, *zero jgiven import*
| JGiven (`jgiven-wrap`, OSGi bundle) | `ReportModel` (→ living-doc AsciiDoc), given/when/then
  narration, thread-local scenario state | a library
|===

`FluentTopicRunner` does not do narration; jgiven does not do type-state ordering. Neither duplicates
the other. Note the runner *already speaks the target vocabulary* — `FluentTopicRunner`, `TopicFailure`,
`runDuring(topic, …)` — so the `*Stage → *Topic` rename below merely *aligns the stranded host classes
onto the shared word*; it invents nothing. The landing direction — settled in the June exploration and
unchanged — is:

> *One engine (JGiven), two layers. The fluent `during/then` grammar stays the authoring surface;
> JGiven is the runtime substrate underneath it.*

Not "one merged language" (rejected: forces every action topic into a `When`), and not "re-code the
BDD layer on a hand-rolled engine" (rejected: jgiven already *is* a narration+report engine). The
type-state worry dissolves: `during/then` stays the authoring surface (compile-time), jgiven is only
the runtime substrate (narration + report); they sit at different altitudes and never compete.

The three layers (structure unchanged, re-labelled to the vocabulary below):

[source]
----
Layer 1: ApplicationPipeline   during("environment").then().during("bootstrap").then().during("outputs")
Layer 2: BootstrapPipeline     during("preflight").then()…during("bootstrap resources")   (topics)
Layer 3: verification topics   a topic plays a JGiven scenario (given/when/then + doctor consult)
----

The shared-report seam already exists in germ: the pipeline carries a caller-owned `ReportModel`, and
the two checkpoint topics `setModel(reportModel)` so both scenarios write into *one* report. "Shared
engine" is already real for two topics; generalising it — to the topics the operator needs — is the
work.

== The vocabulary — separate our words from jgiven's

`Stage` and `State` are jgiven words (`Given/When/Then extends Stage`, `@ScenarioState`); our classes
borrowed them and *caused the tangle*. The reset:

[cols="1,1,2",options="header"]
|===
| concept | jgiven (theirs) | ours (DECIDED)
| unit of work | `Stage` | *`*Topic`* (`BootstrapStage`→`BootstrapTopic`,
  `ClusterReadinessStage`→`ClusterReadinessTopic`, `SystemdAdapterStage`→`SystemdAdapterTopic`)
| executor | `ScenarioExecutor` | `FluentTopicRunner` (already ours)
| the whole | `Scenario` | the pipeline (`during`.`then`)
| read context | `@ScenarioState` | *`TopicContext`* — immutable: config, policy, `RunMode`, runbook,
  consultations, doctor, recordedAt, resolved ports
| accumulated results | — | *`TopicOutcomes`* — mutable: bboxResult, bootstrapResult,
  systemdAdapterLaunchSummary, resourceResult
| living doc | `ReportModel` | produced VIA the jgiven session, held by the provider
|===

`PipelineState` (today) splits into `TopicContext` (read) + `TopicOutcomes` (mutable). A topic today
recopies ~7 identical params (config/policy/runbook/consultations/doctor/recordedAt/gate); after, a
topic takes `(TopicContext, its probe, its sink)` — ~10 params collapse to ~3. `RunMode` becomes a
*field of `TopicContext`*, read by reference — no longer threaded as a per-topic param (that was the
"gate mal placée" realization).

== The jgiven provider — one topic furnishes the session, the rest consume it

`BootstrapStage` (→ `BootstrapTopic`) is *already* the de-facto jgiven provider: it `new ReportModel()`
and renders it (`RunbookRenderer`) in a `finally`. Make it the full provider: it owns the jgiven
session lifecycle (create the model, render it). The other topics *consume* the session — they write
their scenario into the shared report — and never configure jgiven. In port/edge terms: the provider
*furnishes* the BDD session; topics consume it.

== `RunMode` — the named launch concept the two gates derive from

*Lead: separate the preview CAPABILITY (dry-run the reasoning → jgiven PENDING, living gate closed —
OSGi-native) from its TRIGGER (`Deployment.isDryRun()` in bootstrap; an operator command / CRD field
detached). `RunMode` is INJECTED, not read. Only the stack axis is Pulumi-bound; the preview axis
survives detached.*

[IMPORTANT]
.The trap I nearly wrote: preview is NOT Pulumi-only (user, 2026-07-02)
====
Preview would seem lost in-cluster ("no Pulumi → no dry-run"). It is not — that conflates two things:

* *The preview CAPABILITY* — play the reasoning WITHOUT touching the real system: the jgiven session in
  dry-run (steps render PENDING, bodies don't run) + the living gate closed. jgiven is an OSGi bundle,
  so *this capability is OSGi-native* and works detached, remote, anywhere.
* *The TRIGGER* — what puts the world in preview. In the embedded/bootstrap host it is
  `Deployment.isDryRun()` (a Pulumi fact). Detached in-cluster it is something else — an operator
  command, a CRD field, a flag (OPEN — the detached trigger is not yet designed; ties to the
  `RunMode → OSGi → runbook` seam and the doctor what-if, `preview-whatif-replay-exploration`).

So `RunMode` is *injected* into the OSGi world as a value, never read from `Deployment`. This fits the
compass (the runbook is read AND ACT — an operator asking for a preview in-cluster is an action they
drive). What IS Pulumi-only is the *output/stack axis* (write the stack) — it vanishes detached; the
*probe/preview axis* does not. The three-mode table below is the bootstrap host's incarnation; detached
keeps the preview axis under a different trigger, loses the stack axis.

*Consequence (design, not built): promote the AXES, not the enum.* `RunMode {STANDALONE, PREVIEW,
APPLY}` is *host launch vocabulary* — STANDALONE already means "the host runs the exec without Pulumi",
a host fact. None of the three means anything if the pipeline is not launched in the host world — and
*that is correct*: the OSGi world must never see "STANDALONE". What it reads is the abstract *probe
axis* (live / deferred). So:

* the OSGi-native PORT speaks in *axes* (probe: live/deferred), not in `RunMode`;
* `RunMode` is the host's *projection* — it maps a launch mode to axis values
  (`STANDALONE`→probe-live+no-stack, `PREVIEW`→probe-deferred+stack-ro, `APPLY`→probe-live+stack-rw);
* detached in-cluster, a *different edge* (operator command / CRD field) feeds the SAME probe axis
  without ever saying "standalone"; the stack axis simply has no in-cluster edge.

So we ACCEPT that STANDALONE/PREVIEW/APPLY are host-only words with no detached meaning — that is the
proof the port is the axis, not the enum. (This corrects an earlier framing that spoke of "promoting
`RunMode` into OSGi": it is the axes that are OSGi-native; the enum stays host.) NOT built; recorded so
it is not re-derived.
====

*The mode is RESOLVED; the context is INJECTED — complementary, not competing (user, 2026-07-02).* An
OSGi capability is found by an LDAP filter, so the preview axis becomes a *resolution* axis: resolve the
pipeline/topic service under `(probe=deferred)` and Felix wires the variant that never touches the real
system — the living gate stops being an `if`, it becomes a `Require` the resolver satisfies (this is the
"gates become resolution edges" of `orchestration-purity-benefit`, applied to the mode). Changing mode
is then a *re-resolution* event — natural in bootstrap (each launch resolves its mode once) and
in-cluster (the operator commanding preview re-resolves, read+ACT).

But resolution chooses only the *form* — it carries no run data. The *matter* of a run (the patient, the
resolved config, the outputs sink, the recorded instant) still enters through *`TopicContext`*, injected
as an instance (instance-passing discipline). So:

* *resolution (LDAP)* answers *which variant* — `(probe=deferred)` → the preview variant;
* *`TopicContext` (injected)* answers *with what data this run* — patient, config, sink.

The host `RunMode` then projects to *both*: it supplies the resolution filter (probe live/deferred) AND
feeds the data part of `TopicContext` (e.g. the stack sink). One host axis, two destinations by nature —
structural facts resolve, data is passed. *Rule: the mode resolves, the context injects.* NOT built.

*How the host gets this — transpose the ROLE, not the MECHANISM (user, 2026-07-02).* Resolution is an
OSGi-native mechanism (the Felix resolver, `getServiceReferences(type, filter)`); the host has no
resolver, and re-coding one would be the "re-code OSGi host-side" trap. The host does not need to
*resolve* — it needs to *ask for the right variant*. Today the host looks up services by TYPE only
(`awaitService(Class)`), not by filter. So the transposition is a *port that carries the mode INTENTION*,
and OSGi resolves it:

* *port-factory (chosen):* the host calls e.g. `PipelineProvider.forMode(probe=deferred)`; the OSGi
  world resolves the variant internally (LDAP filter stays OSGi-side) and returns it. The host knows
  only the INTENTION, never the capability vocabulary.
* *why not `awaitService(Class, filter)`:* it would teach the host the LDAP vocabulary AND it breaks
  detached — a remote host has no local registry to filter. The port-factory carries an intention, so
  it works embedded (folds onto `awaitService`) and detached (remote call) alike — the remote-first
  seam.

So: the host TRANSPOSES the role (ask the intention), OSGi keeps the mechanism (resolve). `RunMode`
becomes the host's producer of that intention (`STANDALONE/PREVIEW/APPLY` → a `(probe=…)` intention it
sends), never a resolver itself. The port-factory's exact shape is decided at chantier S3. NOT built.

There are three launch modes *in the embedded/bootstrap host*, three coordinates in a *two-axis* space
(probe × stack), not one binary. A single `RunMode` enum names the input; both gates are projections of
it. Topics read `RunMode` off `TopicContext`; none reaches for `Deployment.getInstance()`.

[cols="1,1,1",options="header"]
|===
| `RunMode` | probe axis (living gate) | stack axis (output gate)
| `STANDALONE` | live | none (print — `pulumiContext == null`)
| `PREVIEW` (`pulumi preview`) | *dry-run (deferred)* | read-only (Pulumi engine)
| `APPLY` (`pulumi up`) | live | read-write (Pulumi engine)
|===

KEY: `PREVIEW` is the *only* mode with a dry-run probe — `STANDALONE` and `APPLY` both probe live. The
trap to avoid is *fusing* the two axes: "standalone = dry-run" is wrong — standalone probes the live
system, it merely writes no stack. The axes are orthogonal, each binary in our code:

* *probe axis*: live vs deferred → deferred *only* in `PREVIEW` (`pulumiMode && isDryRun()`).
* *stack axis*: our code sees only `pulumiContext != null` (export) vs null (print) — the
  read-only/read-write split is *internal to Pulumi* (`OutputsStage.exportOrPrint` makes the same
  `context.export` call; the engine simply does not apply in preview). We do not pilot ro/rw.

`RunMode` is resolved once at launch (the one place the dry-run flag is read) and lives on
`TopicContext`. The `LiveGate` type built today (`LiveGate.forRun(pulumiMode)`, `isOpen()`,
`through(live, deferred)`) is the *transitional projection* of the probe axis — on implement it
becomes `runMode.probesLive()` and the combinator stays.

== The living gate — what may touch the real system

=== Problem — the pipeline crosses the living boundary without checking it

In `pulumi preview` the pipeline must not touch the live system: no systemd probe, no kubeconfig wait.
Today domains gate themselves inline, and one reads it wrong:

* *systemd* — `ResourceCreationPipeline.withSystemdRuntimeStatus` branches on `isDryRun()` and calls
  `deferredPreview(config)` in preview. Correct, but inline and global.
* *k8s / cluster readiness* — `ClusterReadinessStage` computes `preview` but uses it only AFTER
  playing the scenario. The scenario's step bodies (`ClusterReadinessScenario.checking`) call
  `phaseProbe.probe(...)` unconditionally, so the live probe still runs:
  `waitForBootstrapPreconditions` then `waitForKubeconfigPublished` — a wait that times out after one
  minute in every preview. The stage sets `System.setProperty(JGIVEN_DRY_RUN)` believing it skips the
  step bodies — but that property does nothing on our execution path (see <<dead-dry-run>>).

The living boundary was crossed before the gate was consulted. The output said "deferred"; the side
effect had already happened.

| Site | What it reads globally
| `SystemdAdapterStage:124` | `pulumiMode && Deployment.getInstance().isDryRun()`
| `ClusterReadinessStage:95` | `pulumiMode && Deployment.getInstance().isDryRun()`
| `ResourceCreationPipeline:207` | `Deployment.getInstance().isDryRun()`

[[founding-constraint]]
=== The founding constraint — probes ARE jgiven scenario steps

*Every probe must be a jgiven scenario step, or there is no runbook.* The runbook exists only because
each probe is played as a step (it records into the `ReportModel`). A probe that is not a step produces
no runbook entry. So probe ⟺ scenario-step is the *raison d'être* of the pipeline↔jgiven coupling, not
an incidental detail — and it is the deepest justification for making jgiven the substrate: the
operator-model deserves to be rendered and acted upon.

This constraint *disqualifies a tempting-but-wrong fix.* Injecting a canned "deferred" probe that
*returns a value* makes the step *execute* and render *PASSED (fake green)* — the exact dishonesty to
avoid. The honest `PREVIEW` rendering is jgiven's native dry-run: `disableMethodExecution()` +
`setDefaultInvocationMode(PENDING)` → step bodies do not run, steps render *PENDING* ("to do"). The
body never executes, so it never touches the real system, and the runbook shell renders honestly. So
the probe axis in `PREVIEW` is not "inject another probe" — it is "put the jgiven session in dry-run",
and because probes *are* steps, they all become PENDING at once. The living gate acts *through* the
jgiven session, not beside it — which fits the provider decision (`BootstrapTopic` owns the session, so
it flips the session to dry-run in `PREVIEW`, derived from `RunMode`).

[[dead-dry-run]]
=== The blocker — jgiven's dry-run is dead on our execution path

Verified in jgiven-core 2.0.3 sources: `Config.dryRun()` reads
`System.getProperty("jgiven.report.dry-run")`, *but* `disableMethodExecution()` is triggered only in
`ScenarioExecutor.startScenario(Class, Method, List<NamedArgument>)` — the JUnit path. Our topics call
`startScenario(String)` (the 1-arg overload), which never consults `Config.dryRun()`. So the
`System.setProperty(JGIVEN_DRY_RUN, "true")` in both `SystemdAdapterStage` and `ClusterReadinessStage`
is *dead code* — dry-run never activates on our path. There is no public Java API to enable it (only
the system property + the JUnit entry we do not use).

Consequence: the honest PENDING rendering requires making our scenario execution *honor* jgiven's
dry-run without the JUnit entry — the open design work below. Until then the dead `System.setProperty`
lines must be *deleted* from both topics (they encode a false belief), and the transitional mechanism
is the living gate deferring the probe.

[IMPORTANT]
====
*Open design question (resume):* how to trigger `disableMethodExecution` without the JUnit
`startScenario(Class, Method, args)` entry. Candidates: drive `ScenarioExecutor`/its interceptor
directly, or add a jgiven-wrap helper in the `pipeline-jgiven` module. The currently-built
`SimulatedClusterReadinessProbe.deferred()` + the `checking()` symptom tweak are a *wrong direction to
unwind* (they render fake-green), kept only until the honest PENDING path exists.
====

=== Resolution — the living gate as a projection of `RunMode`

The pipeline holds the gate and calls `through(...)` at each gated action; the domain provides both
branches and reads `isDryRun()` nowhere.

[source,java]
----
interface LiveGate {                                       // transitional; becomes runMode.probesLive()
  boolean isOpen();                                        // APPLY/STANDALONE → true, PREVIEW → false
  <T> T through(Supplier<T> live, Supplier<T> deferred);   // open → live.get(), closed → deferred.get()
}
----

== The output gate — what is written to the stack

=== Problem — an omniscient builder pulls each output by name, over raw maps

`OutputBuilder` knows every output by name and pulls each (`resourceResult.registrySummary()`,
`.systemdRuntimeStatusSummary()`, …). Every new output edits this class; nothing prevents a duplicate
key (silent overwrite) or a value that flattened too early. The systemd case is the last one: its
producer flattens `SystemdStatusSnapshot` to a `Map` at production time, and the map then travels
internally to `SeedNodeBootstrapWatcher`, which re-parses it (the null lived here). The three sibling
summaries (`registrySummary`/`imageBuildSummary`/`manifestSynthSummary`) already stay structured until
the edge. The convention exists (`policy.toOutputMap()`, `bbox.summaryMap()` are named projections); it
is simply not enforced.

=== Resolution — `PulumiOutputContributor` (SPI) + `PulumiOutputRegistry` (guaranteed assembly)

The pipeline collects contributors and the registry assembles them, guaranteeing what the omniscient
hub could not: no key collision (a duplicate is a named failure, not a silent overwrite) and a
deterministic order. `contribute()` is the single flatten point — called once, by the registry, never
by an internal consumer.

[source,java]
----
interface PulumiOutputContributor {
  String namespace();                 // identity for diagnostics (names the offender on collision)
  Map<String,Object> contribute();    // the flat projection — computed here and nowhere else
}

final class PulumiOutputRegistry {
  PulumiOutputRegistry add(PulumiOutputContributor c);   // fluent
  Map<String,Object> assemble();                          // unique keys, deterministic order
}
----

Both types live in `host/pulumi/pulumi-edge` (pure: `String` + `Map`, zero seed-master type), beside
`StackHandle` — an output projection is a Pulumi-edge concept. `pulumi-edge` is already `@NullMarked`
and depends on `com.pulumi:pulumi`, so the living gate lives there too. The stateful implementations
(`SystemdRuntimeStatusReport`, and the registry/image/manifest contributors, which hold
`bootstrapResult`) stay in `controlplane` and depend on the edge SPI — the dependency direction
`seed-master → pulumi-edge` already holds, no cycle.

=== The structured type behind the systemd contribution — `SystemdRuntimeStatusReport`

The systemd runtime status stays a domain-pure record all the way in, and projects to the K8s envelope
only at the edge. The `deferred-preview` case is NOT a runtime status — it is the living gate being
closed — so it is not a value of the report's `Status`; the report models the two outcomes of a *real*
probe, and the deferred envelope is produced by the contributor when the living gate is closed.

[source,java]
----
record SystemdRuntimeStatusReport(
    Status status,                              // OK | EXECUTION_ERROR (a real probe's two outcomes)
    Optional<SystemdStatusSnapshot> snapshot,   // present on OK, empty on error
    String summary) {
  enum Status { OK, EXECUTION_ERROR }
}
----

`SeedSystemdAdapterRuntimeStatusSnapshot.snapshot()` returns the report (no map). The watcher reads
`report.snapshot()` typed — the three converter helpers and the `@Nullable Object` params are deleted
at the source. The K8s envelope (`apiVersion`/`kind`/`status`/`source`/`probeMode`) and the deferred
case live in the systemd contributor's `contribute()`, gated by the living gate.

== Work plan (high level) — two orthogonal threads

The spec describes a target; this is the map of what it takes to get there. There are *two orthogonal
threads*, and they must not be braided into one chantier:

* *Thread R — reliability* (tactical, the arc that started this): non-null → pulumi-outputs → jgiven →
  pipeline, fixed in reverse. Detailed in "Build order" below. Independent of the restructuring.
* *Thread S — structure* (strategic, the three levels): the pipeline moves toward OSGi ownership. Each
  step is its own chantier + worktree; none is started here.

== Build order — thread R (reliability), fixed in reverse

The defects were discovered symptom-to-root along the thread *non-null → pulumi-outputs → jgiven →
pipeline*; they are fixed in reverse (pipeline first), each link green before the next:

1. *pipeline* — split `PipelineState`→`TopicContext`+`TopicOutcomes`; rename `*Stage`→`*Topic`;
   `RunMode` on `TopicContext`; `BootstrapTopic` as the jgiven provider.
2. *jgiven* — resolve the honest-PENDING question (drive dry-run without the JUnit entry), or keep the
   gate-deferred probe transitionally; delete the dead `System.setProperty(JGIVEN_DRY_RUN)`; unwind the
   fake-green `SimulatedClusterReadinessProbe.deferred()` + `checking()` tweak. `pulumi preview` proves
   the kubeconfig hang is gone and the shell renders honestly.
3. *pulumi-outputs* — `SystemdRuntimeStatusReport`; producer returns it; watcher reads it typed
   (helpers/`@Nullable` deleted); `PulumiOutputContributor`/`PulumiOutputRegistry`; migrate the four
   summaries to contributors; `ResourceCreationResult` drops raw maps; `OutputBuilder` melts.
4. *non-null* — the watcher's converter helpers and `@Nullable Object` params fall out; sweep the
   remaining `isDryRun()` sites onto `RunMode` (Incus/image/bbox).

Build `-Pall-worlds` (never `,nxmatic`); measure NullAway with `clean package -DskipTests=true`.
