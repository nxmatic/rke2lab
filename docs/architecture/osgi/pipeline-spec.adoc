== Why embed JUnit + jGiven at runtime — the dogfooding rationale

*Lead: we embed the JUnit Platform launcher and jGiven into our RUNTIME scope — not just our test
scope — because no alternative offers as rich a MODEL, and because re-entering proven tools we already
depend on beats reinventing an engine. This is our re-entrance / dogfooding rule applied.*

The seeding needs three things at once: an *orchestration substrate* (order phases, express temporal
loops and gates, compose sub-scenarios), a *narration + report model* (the runbook the operator reads
and acts through), and a *value-DAG* between phases. Two frameworks already give all three, richly:

* *The JUnit Platform launcher* — an engine-agnostic orchestration substrate with a mature extension
  SPI (`TestTemplateInvocationContextProvider`, `ExecutionCondition`, `ExtensionContext.Store`). Those
  hooks are exactly the missing dynamics (temporal poll, live/preview gate, ambient + fan-in), and an
  extension IS a contribution — the same paradigm as DS `@Component`.
* *jGiven* — a narration + report engine (`ReportModel` → living-doc), with a state model
  (`@Provided/ExpectedScenarioState`) that carries the value-DAG, nested-step composition, and a clean
  separation of *model / execution / rendering* that let every adaptation we needed (E5, E8, E9) be a
  *public-API extension* — no fork, no dirty reflection.

Both are *battle-proven*: each has shown, over years and across ecosystems, robustness and the
flexibility to adapt to real use cases — precisely the properties a runtime engine for the bootstrap
must have. Building a bespoke orchestrator + BDD engine of comparable richness would be a large,
under-tested reinvention of exactly what these two already do (the "home-grown BDD engine" and "Spock"
alternatives were rejected for this reason — see link:bdd-pipeline-poc-design.adoc[the POC record]).

*The re-entrance / dogfooding rule.* We already run both frameworks — jGiven as an OSGi bundle
(`pipeline-jgiven`), the JUnit launcher in-container (`InContainerJUnitRunner`) — to *test* rke2lab.
Promoting them from the test scope into the runtime scope is a *re-entrant* use of tools we already
trust and maintain: the seeding engine is the same machinery that verifies the seeding. We eat our own
dog food — the runtime consumes the very frameworks our testing depends on. That closes the loop
(a bug in the engine surfaces in both test and runtime, one toolchain to master) and it means the
runtime engine inherits, for free, the maturity these frameworks earned. Given no richer alternative
exists at the model level, this choice is fully justified.

*The honest objection — and why it turns into a strength.* One could object: *you should not test with
the very framework you want to test* — the circularity worry, that a self-validating loop (engine and
test harness being one framework) could mask the framework's own faults. It is a fair objection. But
using the same framework at *two different levels* — as the runtime engine AND as the test harness that
exercises it — pushes it across a far wider span of use cases, including the edge cases a
normal-test-scope usage never reaches. That is precisely how you *discover* the real problems a
framework can pose, rather than hide them. The POC is the evidence: pushing jGiven beyond its ordinary
test usage is exactly what surfaced E1 (dry-run is incompatible with state-DAG enforcement), E9 (jGiven
couples rendering to execution, so a naive dry-run renders blind), and the nested-scope-swallow gotcha
— real limitations we now design around, found *because* we ran the framework at the limit, not
despite it. The circularity is not a blind spot here; it is a stress test.

== The compass — the runbook is the operator's view, read AND act

*Lead: the runbook renders what the OPERATOR needs to understand and act on the whole system — not what
the pipeline does. Inclusion is judged by operator-need, not by "is it a phase". This survives the
turn unchanged — it is why the seeding must narrate at all.*

The reason any of this matters. The runbook does not exist to *narrate the pipeline*. seed-master is
only one piece — the cluster bootstrap — of a larger system the operator runs. The runbook is the
projection of *the operator's mental model of the whole system*, and the inclusion criterion for what
it renders is not "is it a pipeline phase?" but *"does the operator need it to understand and act on
the system?"*

Scope is *read AND act*: the runbook is the medium through which the operator both understands (state,
health, why — the doctor, symptoms, drift) and acts (replay a checkpoint, apply a remedy, relaunch a
phase). The doctor / symptoms / drift / remedies are not isolated features; they are pieces of this
actionable operator-view.

This compass judges the "depth" question: a phase narrates through the runbook *iff the operator needs
it*, not because it happens to be an execution step. bbox reconciliation is the first verdict — IN,
because the operator needs the reservation state — even though it is an action phase that narrates
nothing visible today. In the BDD-as-engine model this is native: every phase IS a scenario, so every
phase already produces its runbook node; the compass decides only what to `@Hidden`.

[[founding-constraint]]
== The founding constraint — a probe IS a jGiven scenario step

*Lead: every probe must be a jGiven scenario step, or there is no runbook. In the former model this was
a discipline bolted onto a fluent grammar; in the BDD-as-engine model it IS the model — which is the
deepest reason the turn is not a rewrite but a realization.*

The runbook exists only because each probe is played as a step (it records into the `ReportModel`). A
probe that is not a step produces no runbook entry. So probe ⟺ scenario-step is the *raison d'être* of
the seeding↔jGiven coupling, not an incidental detail. The former spec already recognized this — two
topics (`ClusterReadinessTopic`, `SystemdAdapterTopic`) drove jGiven scenarios by hand, and the
"provider" pattern generalized it. The turn removes the "by hand": *every* phase is a scenario, so the
coupling is total and uniform, not confined to two topics.

This constraint disqualifies a tempting-but-wrong preview fix. Injecting a canned "deferred" probe that
*returns a value* makes the step *execute* and render *PASSED (fake green)* — the exact dishonesty to
avoid. The honest preview rendering is a step marked *PENDING* ("to do") whose body never ran, so it
never touched the real system, and the runbook shell renders honestly. The POC proved this is
achievable *richly* (a full nested plan, every step PENDING, zero traversal) by decoupling rendering
from execution — see § <<runmode-preview>> (E9). What one bouchons is the *probe* (the runtime seam),
never the *edge* (the produced state) — E2: a faked probe injected in the step body makes the body run
and produce the edge honestly from a stubbed output, so the runbook never lies.

[[the-model]]
== The model — scenarios ARE the execution engine

*Lead: the seeding is not "described by" scenarios; it IS a tree of jGiven scenarios, run by the
embedded JUnit Platform launcher. jGiven is the engine, the launcher is the orchestration substrate,
Jupiter extensions contribute the dynamics JUnit does not ship. Every piece already exists in the
codebase — the turn composes them, it does not invent an engine.*

Five decisions, taken together (2026-07-04), fix the model:

. *jGiven scenarios are the EXECUTION ENGINE of the seeding*, not a description layer. Each phase = a
  scenario. This is the founding constraint (above) promoted to the model: probes ARE steps because
  the whole seeding IS scenarios.
. *Engine = jGiven* — already an OSGi bundle (`pipeline-jgiven`); its programmatic API is already used
  outside JUnit in `ClusterReadinessTopic`.
. *Orchestration substrate = the JUnit Platform launcher, embedded at runtime.* Not a gamble:
  `InContainerJUnitRunner` (osgi/runtime/junit-testkit) *already* drives `LauncherFactory.create(...)`
  with an explicit engine, a listener and a discovery request, *inside* OSGi. The launcher is engine-
  agnostic (Jupiter carries jgiven-junit5, already used: `DoctorScenarioTest extends ScenarioTest`).
. *The fluent `during`/`then` grammar dissolves ENTIRELY — the boot included* — jGiven composes
  everything. Order and dependencies are expressed by nested steps (`@NestedSteps` — already in
  production: `ClusterReadinessScenario` replays `SystemdAdapterScenario`). No mince scheduler survives
  (the POC confirmed the launcher + `@NestedSteps` carry all the ordering; there was nothing left for a
  grammar to do). *This reaches the boot too:* `FrameworkLaunchPipeline` is a `Topic.Execution` of
  effect already chained first inside seed (`ClusterSeedTopic.seedCluster()` runs
  `FrameworkLaunchPipeline.embedded().during(framework -> seedClusterWithinFramework(...))`). It becomes
  the *first jGiven step of the seed scenario* — "when the framework is launched" — a plain effect step
  (bouchonné-probe pattern E2, no runbook value folded). There is no amorce paradox: the JUnit launcher
  runs on the HOST flat classpath, OUTSIDE Felix (`SeedLauncherMain` — `main()` creates it), so
  launching Felix is a narrated step the launcher plays, not a pre-amorce that must precede it. So the
  fluent grammar has NO surviving user once seed migrates — `pipeline-port` stops exporting it, and only
  then do its types leave the specs (the `SPEC_COVERAGE` code-first ratchet).
. *The value-DAG is carried by the jGiven state annotations*, not lost:
+
--
** `@ProvidedScenarioState(guaranteed=true)` = the outgoing edge (this stage produces this value);
** `@ExpectedScenarioState(required=true)` = the incoming edge (this stage requires this value);
** a `required` with no upstream `guaranteed` = a mis-wired DAG, detectable *at build time* by a new
   ASM gate (§ <<dag-gate>>).
** *The trade accepted:* the compile-time safety of the former type-state `State<I,B>` becomes a
   *declared runtime state + a build-time gate*. Not a flat bag — a typed, annotated model with a
   topological gate. The POC judged this cran acceptable (E1 named the one incompatibility: DAG
   enforcement XOR dry-run — resolved by the `PreviewExecutor`, § <<runmode-preview>>).
--

*The missing dynamics = contributed Jupiter extensions.* JUnit does not ship the temporal/DAG/gate
primitives, but it exposes the SPI to *build* them — and an extension IS a contribution (same paradigm
as DS `@Component`: a node registered, discovered, composed). Three carrying hooks, each proven on the
bench:

=== The scenario tree — a phase opens a nested scenario (the pièce maîtresse)

The mechanism that makes "phase = scenario" compose into ONE runbook tree is E5: a step CAN open onto a
nested scenario. "A step is a nested scenario" does not exist in the jGiven model (`StepModel` does not
point to a `ScenarioModel`) — but a scenario is just a `Given/When/Then` of steps, and the intro-words
`given()/when()/then()` *render inside a `@NestedSteps` block*. So a phase, as it establishes, grafts
its G/W/T under the step of its parent phase → one arborescent runbook where each phase is a real
scenario at its place:

[listing]
----
   Given the pipeline starts
    When the cluster-readiness checkpoint runs          ← parent step (a phase)
           Given a reachable systemd adapter "..."      ← child scenario, nested
           When the kubeconfig is published
           And the api is ready
           Then the cluster is ready
    Then the seed is ready
----

The orchestration relays that sequence the phases are `@Hidden @NestedSteps` (E8): `@Hidden` removes
the relay from the render (no double title), `@NestedSteps` promotes the phase's content one level — so
each phase is a single visible node carrying its rich `@As` (`the incus instance "bioskop-master" is
provisioned`), not the relay's bare method name. Rule: the orchestrator is transparent, the phase is
the visible node.

=== Fan-in — several upstream outputs into one phase, in one scenario

A late phase reads several upstream outputs (Resources reads both a network plan and a storage plan).
The candidate blocker was "jGiven state is per-scenario, would break fan-in if each phase were its own
scenario". It dissolved under the stacked model: because all phases compose into ONE scenario, the
scenario-state scopes by the stage/step hierarchy, so a phase reads every `@ExpectedScenarioState` its
upstream siblings `@ProvidedScenarioState`-produced. `FanInStatusSpikeTest` runs a real two-input
fan-in and renders both fanned-in values on the one node.

=== Fail-fast — the halt is read off the model, not a thrown exception

jGiven defers a failing step's propagation to `scenario.finished()`: it records the step `failed`,
marks the chained downstream steps SKIPPED (the fail-fast), and only propagates at `finished()` (E7).
Two consequences the model relies on: the diagnostic runbook is naturally targeted (the operator sees
the broken step and everything not reached), and the halt signal MUST be read off
`ScenarioModel.getExecutionStatus()` (FAILED) — not off a per-node SKIPPED marker, because under a
`@Hidden @NestedSteps` relay a fail-fast-skipped consumer node does not even materialize
(`FanInStatusSpikeTest`, refinement 1).

== Ownership and the seam — OSGi reasons, the host feeds and renders

*Lead: OSGi owns the scenarios + engine + reasoning (they already live there); the host injects the
`RunMode` fact + Pulumi context and renders/writes back. The cross-world edge crosses as a serialized
`ScenarioModel`, grafted into the host runbook — the live jGiven object never crosses.*

The pipeline is *owned by the OSGi world*; the host is a consumer. Two facts of the code already put it
there: jGiven is already an OSGi bundle (`pipeline-jgiven`, with an in-container testkit), and the JUnit
launcher already runs inside embedded Felix (`InContainerJUnitRunner` drives `LauncherFactory` under
the testkit). The bootstrap reasoning — the scenarios, the doctor consult, the readiness verification,
the runbook — is *target-state OSGi*; it is only *stranded* in `exec/seed-master` today.

[cols="1,2,2",options="header"]
|===
| | *OSGi world* (owner) | *host* (`exec/seed-master` + `pulumi-edge`, consumer)
| role | the brain — reasons about the bootstrap | thin launcher + the Pulumi edge
| holds | the scenarios, the jGiven session + engine, the launcher, the doctor, readiness, the
  `ReportModel` runbook | framework boot (already OSGi via `BootPipeline`), the *source* of `RunMode`,
  the stack *sink*
| jGiven engine + launcher | *here* (`pipeline-jgiven` + `junit-testkit`) | —
| the seam | *produces* the runbook + the output contributions | *injects* `RunMode` + Pulumi context,
  *renders* the runbook, *assembles + writes* the stack
|===

The seam keeps the discipline this spec is built on: *a domain never reaches for the global flag.*
`RunMode` (which only the host can know — it derives from `Deployment.isDryRun()`) is *injected* into
the OSGi world as a value; the OSGi world reasons; the host renders and writes. The founding constraint
travels intact: probes-as-steps and the runbook are produced OSGi-side; the host only renders/exports.

*The cross-world edge = a grafted `ScenarioModel` (E10).* A `@NestedSteps` composes within ONE world
(one jGiven engine, one `ReportModel`). A dependency that crosses the world-gateway cannot be a nested
step — two engines, two `ReportModel`s. It becomes a *gateway step*: the caller world sends a
`Document`, the remote world plays its scenario in ITS `ReportModel`, and returns the *serialized
`ScenarioModel`* (JSON String — the seam carries no live jackson type). The caller *grafts* the remote
steps as the gateway step's `nestedSteps` (`StepModel.addNestedStep`) → the operator reads ONE
continuous tree, from the seed down to the OSGi root. And the verdict travels IN the model:
`remoteScenario.getExecutionStatus()` — if the remote is FAILED, the graft marks the gateway step
FAILED and the host's downstream steps SKIPPED (the local fail-fast, reproduced across the frontier).
*One Document suffices* — the `ScenarioModel` carries both the narration (steps → the sub-tree) and the
verdict (`executionStatus` → the propagation). This is proven *in isolation* on the bench (a
`URLClassLoader` realm stand-in, an in-JVM JSON round-trip); wiring it to the real embedded Felix
(`ClusterSeedTopic.seedCluster()`) is the migration increment, not re-proof.

== The OSGi world is detached by design — embedded exec is a special case

*Lead: the general case is a detached OSGi world (remote); seed-master's embedded exec merely folds the
seam in-process. The launcher is one more consumer of the R4 boot seam. Pulumi belongs to the
embedded/bootstrap host only, not the world.*

The general case is a standalone OSGi world running as a service — it *amorces itself*, and the host is
a *remote client* that connects, injects `RunMode` + the Pulumi context, and pulls back the runbook and
the output contributions across the remote frontier. The embedded exec (`FrameworkLaunchPipeline.
embedded()`) is *one particular case* — the degenerate one where the host co-locates and boots OSGi
in-process. The chicken-and-egg amorce ("what starts OSGi cannot run inside OSGi") is *real only in the
embedded case*; detached, the OSGi world has its own internal amorce.

*This does NOT bar the boot from being a jGiven step* (§ <<the-model>>). The thing that "starts OSGi"
is the JUnit launcher + its `main()`, which run on the HOST flat classpath, OUTSIDE Felix — so they do
not run *inside* OSGi, and the paradox does not touch them. The launcher plays the seed scenario whose
*first step* is the boot effect (launch Felix); every later step reasons within the framework that
first step opened. "What starts OSGi" (host launcher) and "what runs inside OSGi" (the reasoning
steps) are different threads/classpaths — the frontier is exactly the gateway (Figure 2).

The launcher does not change this — it is one more consumer of the R4 boot seam (Felix in `Pulumi.run`).
`InContainerJUnitRunner` already drives a JUnit launcher *inside* Felix; `JGivenTestkit.felix()` proves
the jGiven runtime (byte-buddy proxy, `ScenarioExecutor`, `ValueInjector`) boots in-container — the
coupling that gives the state-DAG + the execution nesting. The live boot seam already exists:
`ClusterSeedTopic.seedCluster()` boots embedded Felix synchronously on the `Pulumi.run` lambda thread
today.

*Which use case is which* (two real seed use cases, not a theoretical symmetry):

[cols="1,2,2",options="header"]
|===
| | *seed-master (bootstrap)* | *seed in-cluster (other uses)*
| mode | *embedded exec* — boots OSGi in-process | *detached workloads* — OSGi as a separate workload, remote
| why this mode | it *precedes* the cluster: there is no cluster yet to deploy a workload into, so it
  must embed and amorce OSGi itself — *this* is why it owns the amorce paradox | the cluster already
  exists; the OSGi world runs as a workload, accessed remotely — nothing needs to amorce it in-process
| Pulumi edge (`RunMode`, stack sink) | *yes* — seed-master *creates* the infra via Pulumi, so
  `Deployment.isDryRun()` is a fact only here | *no* — a workload runs *inside* the already-created
  cluster; it has no `RunMode`
|===

This lands the Pulumi coupling precisely: it is *not* a property of the OSGi world — it is a property
of the *bootstrap's embedded host*. The detached OSGi world knows nothing of Pulumi. Which confirms, by
a second route, that the preview trigger and the stack sink live at the *host edge* (`pulumi-edge`),
never in the OSGi reasoning.

The concern was that `context.export` is synchronous on the `Pulumi.run` lambda thread while the test
harness runs the launcher on a dedicated TCCL thread. It conflated the harness with the production
path: host-world scenarios run on the lambda thread (no OSGi realm → launcher inline, export
synchronous); OSGi-world scenarios run inside Felix on ITS own thread — the host never drives that
thread, it consults via `consult(Document) → Document` and grafts the returned model. *The thread/TCCL

[[runmode-preview]]
== RunMode re-posed — an ExecutionCondition + a PreviewExecutor (LiveGate erased)

*Lead: preview is NOT a Pulumi-only capability, and it is NOT jGiven's naive dry-run (which renders
blind). It is the launcher-native `ExecutionCondition` selecting a `PreviewExecutor` that decouples
RENDERING from EXECUTION — a rich PENDING plan. `RunMode` produces the condition; `LiveGate` is erased.*

The former model had two gates (a `LiveGate` state + an output gate) derived from a `RunMode` enum. The
turn dissolves the living gate into the launcher's own vocabulary:

* *The preview CAPABILITY* — play the reasoning WITHOUT touching the real system — is OSGi-native
  (jGiven is a bundle) and works detached, remote, anywhere.
* *The TRIGGER* — what puts the world in preview. In the embedded/bootstrap host it is
  `Deployment.isDryRun()` (a Pulumi fact). Detached in-cluster it is an operator command / CRD field
  (OPEN — the detached trigger ties to the doctor what-if, `preview-whatif-replay-exploration`).

So `RunMode` becomes an `ExecutionCondition`: the launcher reads the injected `RunMode` fact and selects
the execution mode. It is *injected*, never read from `Deployment` inside a phase (E3 confirmed the mode
is piloted from OUTSIDE the scenario — a context decision, never a scenario property).

*The trap the POC avoided — naive dry-run renders BLIND (E1 + E9).* jGiven couples rendering to
execution: `doIntercept` returns early WITHOUT `proceed()` as soon as the invocation mode is SKIPPED or
PENDING. So any mechanism that skips step bodies (the `jgiven.report.dry-run` property, a
`disableMethodExecution()`, a `setDefaultInvocationMode(PENDING)`) also skips *building the tree* — a
`@NestedSteps` whose body does not run never builds its sub-tree, the plan comes out EMPTY (and with the
E8 `@Hidden` relays, entirely empty). Worse, E1: dry-run skips the step bodies, so a `guaranteed` state
stays `null` → the DAG enforcement throws. *DAG enforcement XOR dry-run — not both.*

*The resolution, proven (E9):* a `PreviewExecutor` decorates the `ScenarioListener` the executor
installs. The interceptor keeps its local mode NORMAL — so it `proceed()`s, the entire tree builds
against inert (bouchonné) probes — but the mode that REACHES the model is rewritten `NORMAL → PENDING`.
Result: the full plan (all phases, the nested G/W/T, every reservation), each step `(pending)`, zero
traversal. Preview is not the weak point it seemed — a rich preview is reachable by rebranching the
render without touching execution. Bonus seam `FailFastPreviewExecutor` (overrides
`ScenarioExecutor.failed` to re-enable execution so a fail-fast-skipped downstream plan still renders)
is loquacity polish, not on the critical path.

*The output/stack axis* (write the stack) is the genuinely Pulumi-only part — it vanishes detached. It
stays at the host edge as a `PulumiOutputContributor` (SPI) + `PulumiOutputRegistry` (guaranteed
assembly): each domain contributes a pure `Map` (no Pulumi dependency crosses the seam), the registry
assembles them with unique-key + deterministic-order guarantees, host-side. This is orthogonal to the
scenario model and unchanged by the turn — see link:../atlas/host-pipeline.adoc[host-pipeline L1] for
the contributor/registry design and the `SystemdRuntimeStatusReport` typed record.

[[dag-gate]]
== The DAG gate — build-time topological safety (replaces PIPELINE_PATTERN)

*Lead: the compile-time DAG safety of the former type-state survives the turn as a build-time ASM gate.
It reads the `@Provided/ExpectedScenarioState` annotations and proves TOPOLOGICAL order (guaranteed
BEFORE required), not mere presence — a `StagingGate` sibling of the retired `PIPELINE_PATTERN`.*

Moving the value-DAG from type-state to runtime scenario-state would lose the compile-time guarantee if
nothing replaced it. The gate replaces it at build time: it recovers the phase call ORDER from the
composing method body via asm-tree `MethodInsnNode` iteration (mirroring `ReferencedTypes` /
`PipelinePattern`), then walks it maintaining a produced-so-far set, and REJECTS a pipeline whose
consumer precedes its producers — a fault a presence-only check accepts. `DagGateSpikeTest` proves the
difference is genuinely topological, on test-classpath bytecode; confirming it on real staged bytecode
is part of the migration.

This is one more `StagingGate` (ASM over staged bytecode, reached from `ResolvedBundle`, governable per
package via `@GovernedBy`) — see link:staging-gates-governance-spec.adoc[staging-gates governance]. It
supersedes `PIPELINE_PATTERN` (which policed the former Topic/Sink shape).

== Migration — legibility first, then ClusterSeed-vertical

*The method: the spec runs ahead (avant/après) with the atlas up to date; only then the plan and the
worktree scheduling — integration obliges the worktrees, the spec does not.*

. *Legibility cleanup of the spec network — FIRST, this pass.* Make the BDD-as-engine model the primary
  readable content across the network (this spec, host-pipeline, the atlas satellites); demote the
  former model to the avant reference above. Do not build the migration on docs nobody can read. (This
  is the pass you are reading the result of.)
. *ClusterSeed-vertical migration — one pipeline at a time.* Migrate ONLY `ClusterSeedPipeline` first
  (the POC transposed it) end-to-end into `seed-master` (real Felix, not the `URLClassLoader` stand-in):
  the seven proven mechanisms wired live. The other six pipelines STAY on the former model meanwhile —
  assumed coexistence, NOT a legacy variant to hide. Each subsequent pipeline is its own increment.

(`git show spike/bdd-pipeline-poc:<path>`): `SeedLauncherMain` (the launcher from a bare `main()`),
