*One domain, one bundle pair, two contacts.* An Incus instance needs an Incus image — reachability
and image-build are the same concern (talking to an Incus host), so they share `incus-contract` /
`incus-edge` rather than splitting into a second module pair. The instance-reachability contact was
the *first* sweep extraction (it validated the working unit); the image-build contact was the *last*
and heaviest. Both landed here.

The working unit each time: *one external contact, extracted atomically* — the port, the edge, AND
the re-wiring of the consumer, in one change. The criterion: a type migrates to a bundle only if a
bundle `@Component` contacts an external system (→ edge) or rides its verb (→ port). "Pulumi-free" is
not enough, and neither is "lives in the incus package".

== Contact 1 — instance reachability

=== The contact today — inlined in the host readiness gate

`SeedSystemdAdapterEndpointGate` (seed-master) waited on two axes: the dbus runtime status (already an
OSGi service, `SystemdRuntimeProbe`) and *instance reachability* — running `ssh … incus exec <node> --
true` to check a launched Incus instance answers. The second was still host I/O: a `ProcessBuilder`
inlined in the gate, marked `@Transitional(to="incus-edge")` precisely because it awaited this
extraction. The gate's retry loop, deadline, adaptive intervals, and the `ObservationView`/`SymptomKind`
projection are host orchestration that genuinely stays.

=== Resolution

* *incus-contract* declares `IncusInstanceContact` — the verb `isReachable(IncusExecRequest) →
  Optional<String>` (empty = reachable, else the failure summary); and `IncusExecRequest`, the flat
  contract record (`sshHost`, `incusProject`, `nodeName`) the host projects out of its config at the call
  site.
* *incus-edge* provides `ProcessBuilderIncusInstanceContact` (`@Component`) — shells `ssh … incus
  exec` and nothing else.
* *seed-master* keeps the orchestration; `SystemdAdapterStage.liveProbe()` resolves
  `IncusInstanceContact` from the registry (`connection.awaitService`) and passes it to
  `SeedSystemdAdapterEndpointGate.live`.

== Contact 2 — seed image build

=== The contact today — inlined in the host image provider

`PulumiIncusImageProvider` (seed-master) ensures the seed image exists. Most of it is host
orchestration that stays: the `getImagePlain` reuse lookup, the `com.pulumi.incus.Image` resource it
schedules, the artifact-directory resolution across NFS mirror candidates, the `.image.checksum.sha256`
cache marker, and the NixOS path translation. (The distrobuilder-config materialisation is NO LONGER
host — the config is an edge bundle resource the edge materialises itself; see § the recipe is
edge-owned.)

Buried inside was one external contact — *building the artifacts*: probe `PATH` for `distrobuilder`,
run `distrobuilder build-incus` (under `sudo` if not root), or, failing a local binary, stream a
`remote-build-incus-image.sh` recipe over `ssh` to the builder host. All `ProcessBuilder`, plus the
recipe script as a classpath resource.

=== Resolution

* *incus-contract* declares `ImageBuilder` — `build(ImageBuildRequest)` (produce the artifacts, throwing
  `ImageBuildException` on failure) and `recipeDigest()` (a stable digest of the edge-owned recipe).
  `ImageBuildRequest` is the flat contract record: the builder binary, and two path families — `local*`
  (drive a local build) and `remote*` (NixOS-translated by the host, drive the ssh recipe). The
  distrobuilder CONFIG is NOT a field — the edge owns it (see below), so only artifact/workspace
  placement crosses.
* *incus-edge* provides `DistrobuilderImageBuilder` (`@Component`) — owns the local-vs-remote decision
  (`tryResolveExecutable`), the local `distrobuilder build-incus` (+ sudo), and the ssh recipe stream.
  BOTH recipe resources moved here as *bundle resources* (this edge is their single source): the
  `remote-build-incus-image.sh` driver AND the `incus-distrobuilder.yaml` distrobuilder config.
* *seed-master* keeps the Pulumi `Image` resource, the reuse lookup, the cache marker, and the path
  translation. `PulumiIncusImageProvider` resolves `ImageBuilder` from the registry (`singleSpiProvider`
  on the held `BootedFramework`) and calls `build` only when a rebuild is needed.

==== The recipe is edge-owned end to end (2026-07-17)

The distrobuilder config `incus-distrobuilder.yaml` used to live as a seed-master classpath resource
handed to the edge by PATH — while the driver script travelled over ssh/stdin. Two resources of the
SAME recipe delivered by two channels (NFS path vs ssh stream): incoherent, and it forked the recipe's
ownership. Voie B unifies it: the yaml joins the edge as a bundle resource beside the driver, and the
edge delivers BOTH over the one ssh channel — a local build materialises the yaml to a temp file, a
remote build streams both as base64 heredocs into a throwaway dir (`ssh … sh -s`), no NFS hand-off.

`recipeDigest()` now folds BOTH resources' bytes (script `\n` config), so a change to EITHER invalidates
the host's image cache. The host still holds only the digest, never the recipe — it folds
`recipeDigest()` into its `buildChecksum` exactly where the script bytes used to go. The scion composes
`buildChecksum` from `recipeDigest` + `imageAlias` + `builderBinary` + `builderHost` (all it holds via
the image amendment); the config bytes it never sees are already covered by the digest. One owner, one
channel, behaviour preserved.

== The incus SCION scenarios (target — the metier definition)

In the ClusterSeed vision (link:../bdd/bdd.adoc#clusterseed-scenario-map[the scenario map]) the incus
WHEN splits into THREE beats, ordered by the mount (settled 2026-07-15, see
link:../bootstrap/provisioning-slice-architecture.adoc[provisioning-slice] § the crux): PREPARE (scion) →
GROW (pure-host) → VERIFY (scion). *The incus domain owns TWO of the three — prepare and verify; the GROW
between them is pure-host `com.pulumi` and is NOT a scion* (a scion has no Pulumi engine around it; the
control flow cannot enter Felix — shape (A)). The host speaks gardening; these scenarios speak the incus
metier (image · host-tree · exec).

*Why the instance-creation is NOT here.* An earlier draft of this section had a single scenario whose
`WHEN … the instance is created from that image (IncusInstanceContact)` — that was WRONG on two counts:
`IncusInstanceContact.isReachable` only PROBES, it never creates; and the creation is the Pulumi graph
(`Project/Network/Profile/Image/Instance`), host-side, deleted with `IncusResourceBootstrap`
(`342b7c327`) and restored as the pure-host GROW beat, not a scion step. The scion prepares the material
and probes the result; the host grows the VM between the two.

The scenario skeleton below tracks the codebase (2026-07-16). Step names are the jGiven methods where
they exist; `[CODED]`/`[VISION]` mark what ships vs what is designed-not-yet-coded. It will eventually
be superseded by a rendered runbook (more faithful), but stays the readable target meanwhile.

*Preview inertness:* under a closed `RunGate` the edges do not ssh/build/promote — each scion narrates the
plan (PENDING, E9) without touching the Incus host. *The recipe-digest subtlety* (see above) is metier
detail owned here, not host-visible. Each scion grafts back under its host step; on failure the transversal
doctor-consult follows the same pattern as the other scions.

*Migration note (2026-07-17).* PREPARE's materialisations are CODED: `IncusProvisionScenario` ships
image-build + manifests-sub-sow + nocloud-unwrap (#2) + secrets (#10) + IncusHarvest/HostStaging stores.
The two materialisations are WHEN steps (they FABRICATE material — § bdd.adoc, the G/W/T phase rule),
delegating to incus-core instances (`NocloudSeedWriter`, `LaunchSecretsWriter`); the stores are the
THEN bookend. The PROMOTE is NO LONGER a PREPARE step — it is its own landed scenario
`IncusReconcileScenario` (`IncusScenario.RECONCILE`, a distinct root WHEN).

*The GROW enablement:* PREPARE has `the_network_and_identity_are_resolved` (WHEN)
+ `the_instance_grow_plan_is_published` (THEN) — the scion resolves `NetplanSynthesisService`, computes
`buildChecksum` OSGi-side, and assembles ONE immutable `InstanceGrowPlan` (network view + image view +
identity view) it stores at `INSTANCE_GROW_PLAN`. The plan is a flat record in a NEW `type=dual-realm`
dual-realm module `incus-ingress-contract` (the host face of the incus contract — flat value records only,
no logic; the first `type=dual-realm` of a domain). The contract also carries `IngressConfig` — the flat
config the host fills to actualise (incus project/remote + node/profile/bridge names) — so the actualiser
reads ONE authoritative vocabulary and names no seed-master type. The GROW between reconcile and verify is
pure-host (`com.pulumi` + provider invokes only — it fetches the plan and actualises, computes nothing of
the domain), NOT a scion; the import-lookup it keeps is a provider invoke, not ssh. Its actualiser
(`InstanceGrow` + `IncusProviderContext` + `IncusImportLookup`) lives in the host module `incus-ingress`
(`host/pulumi/`, package `io.seedmatic.rke2lab.controlplane.incus`): the run fetches the plan and DELEGATES
the grow to it, filling an `IngressConfig` from its `BootstrapConfig` — no `com.pulumi.incus` in
seed-master itself. The probe pulls out to a VERIFY beat (post-grow). See link:host-cellar-realisation-spec.adoc#the-grow-anatomy[host-cellar §
the-grow-anatomy] (the scion-projects/host-actualises rule + the plan) and
link:../bootstrap/provisioning-slice-architecture.adoc[provisioning-slice] §deltas.
