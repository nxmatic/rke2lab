= dbus-systemd-edge — the systemd contact, put back in its place
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN (2026-06-23). The third external edge of the
link:../patterns/frontier-playability-model.adoc[frontier-playability model], after
link:pulumi-edge-handoff.adoc[pulumi-edge] and link:ssh-to-age-edge-handoff.adoc[ssh-to-age-edge].

This is a *before / after* document. Tracing the systemd-status flow end to end uncovered a handful
of distinct problems — a stranded edge, an overloaded word, a misplaced specialist, a relationship
hidden in a string. Each section states one problem, shows it as a figure, and shows the resolution
as a figure. The model is read from the code, not imposed on it.
====

== The system in one picture

The systemd contact is a single class today, `DbusSystemdProbe`, the only file in the reactor that
imports `de.thjom.java.systemd` / `org.freedesktop.dbus`. Everything else *consumes a port*. Here is
what the whole flow is meant to be — the reference the rest of the document repairs toward.

Each node carries its *domain* (systemd / doctor / manifests / control-plane / external) and its
*role* by color (edge blue, port pink, domain-core green, control-plane/host green-outline, external
grey). `seed-master` is a *control-plane application* — that is its nature, not a module; it
orchestrates and *consults* the doctor domain, it is not itself a domain.

== The keystone — the mediator is the control-node, not a domain

[NOTE]
====
*Superseded (2026-06-23) on the central claim.* This section's conclusion — "the control-node is the
mediator; mediation between facets is a property of the executable, never a domain" — was *reversed* by
the cluster work. Mediation is *distributed, peer-to-peer*: a domain that intrinsically spans peers
relates them itself, in a *contribution* it owns, and the registry resolves the wiring. The executable
keeps only control of *time* (boot, retry, preview), not of *meaning*. See
link:../patterns/port-edge-domain-ownership.adoc#the-contribution-role[the contribution role and the
peer-to-peer mediation section]. The *upward-ignorance* premise below still holds; only the "therefore
the executable mediates" step is withdrawn.
====

One frame holds all the problems below together. *Knowledge runs strictly downward, never up.* Each
domain is pure in its *upward ignorance*: Pulumi does not know it provisions RKE2; the doctor does not
know it lives in a provisioning system; systemd does not know a doctor auscultates it. None of them
knows it belongs to a control-node. The dependency graph proves it — `seed-master` depends on every
domain (`doctor-*`, `systemd-port`, `manifests-*`, `pulumi-edge`, …); *no domain depends on
`seed-master`*.

So the one place that knows *both* `doctor` and `systemd` is the *control-node* (`seed-master`) — and
that is exactly why it, and only it, can mediate between facets. But it mediates *through their ports*
(it knows them all), *never through their internals* (it reasons in none). `DoctorAssembly` is the
proof: it wires impls onto ports, it diagnoses nothing and speaks no dbus.

[mermaid]
....
flowchart TB
  node["control-node — seed-master<br/>knows ALL facets, mediates by PORTS"]
  doctor["doctor domain — pure, upward-blind"]
  systemd["systemd domain — pure, upward-blind"]
  manifests["manifests domain — pure, upward-blind"]
  pulumi["pulumi target — external"]
  node -->|knows + wires| doctor
  node -->|knows + wires| systemd
  node -->|knows + wires| manifests
  node -->|drives| pulumi
  classDef n fill:#dfd,stroke:#2a2,stroke-width:2px;
  classDef d fill:#fde,stroke:#a58,stroke-width:1px;
  classDef w fill:#eee,stroke:#999,stroke-width:1px;
  class node n;
  class doctor,systemd,manifests d;
  class pulumi w;
....

This is the same shape as "doctors do not open doors" (Problem 4) seen from the top: the control-node
makes the systemd domain speak (edge → `systemd-port`), translates the fact into an `Observation`
(`doctor-port`), and consults the doctor domain. The mediation between facets is the control-node's
role — *a property of the executable that materializes the system, never a responsibility of a
domain*.

== Problem 1 — the edge is stranded, and wrongly called host

`DbusSystemdProbe` lives in `seed-master/controlplane/readiness`. The dbus contact is therefore
*invisible as an edge*, and an import of `BootstrapConfig` nails it to the host world. The frontier
doc even labels dbus "irreducibly host (native deps, ServiceLoader)".

That label is wrong for our usage: the native deps are the *unix-socket* transport; we use
*TCP only*, which is plain sockets — playable in OSGi. The only real obstacle is that
`dbus-java-transport-tcp` discovers its `TcpTransportProvider` by `ServiceLoader`.

  probe -->|imports| sport
  classDef bad fill:#fdd,stroke:#a22,stroke-width:2px;
  classDef ok fill:#fde,stroke:#a58,stroke-width:1px;

  class sport ok;

.After — an OSGi edge that embeds dbus-java, reached through the port
[mermaid]
....

  sport["systemd domain — PORT<br/>systemd-port, SystemdRuntimeProbe seam"]

The jars are plain Maven jars used *only* by this edge, so the bundle *embeds* them on its private
classpath. Then the `ServiceLoader` call and the `TcpTransportProvider` live in one bundle
classloader and discovery resolves — no SPI-Fly, no leak onto the system bundle. dbus-systemd-edge is
thus the first edge *extracted and migrated into OSGi* in one move; only Pulumi stays irreducibly host.

== Problem 3 — whose is the probe? the cardiologist and the ECG

A tempting error: "the specialist knows systemd, so the probe is his." The medical metaphor the code
already uses settles it. A cardiologist *knows the heart* — but he *reasons* over it (reads the ECG,
prescribes); he does not *build the ECG machine* nor *place the electrodes*. "Knowing systemd"
diagnostically is not the same as *talking to systemd over dbus*.

The probe interface is a *port* (the order "produce a status"); only its impl that fetches the live
world is the *edge*. The specialist owns the reasoning, never the contact.

== Problem 4 — doctors do not open doors; they consume facts from the stacks

The deepest correction, and the one that reframes everything. From the code: `Observation`'s javadoc
says "the snapshot _is_ the Status/Conditions — the specialist *reads* the observation"; the
`MedicalRecord` is reconstructed from the *stack timeline* via `SnapshotSource`. So the doctor opens
*no door*. The flow is *two decoupled times*: the edge measures and the fact is written to the stack;
later, the doctor reads facts back from the stack and reasons.

== Problem 5 — there is no dbus-systemd-port; the edge is one door both ways

Two clarifications the model keeps having to re-state.

*Ownership.* A port belongs to the *consumer that calls outward*, never the edge. `SystemdStatusSnapshot`
is systemd-shaped, but it is the readiness consumer's port specialized for systemd — exactly as
`InterventionLedgerWriter` is doctor's port specialized for Pulumi. So we *extend systemd-port*; we
never create a port named after the edge. And *produce is not own*: the edge is the only producer of
the snapshot, but the port owns the type.

*Direction.* One edge = one target = one door, not directional. `DbusSystemdProbe` already holds the
`systemd1.Manager`; today it calls only read methods (ingress). The same `Manager` exposes
`RestartUnit` — a latent *egress* face.

== Problem 6 — a magic string is a relationship in disguise

Checking the flow against the *import graph* is the real test of placement: if everyone is in their
right place, the flow should read back from the imports, without prose. It almost does — except for
one break that placement alone cannot fix.

The unit name `"rke2lab-dbus-tcp-system-bus.service"` is a literal duplicated in `manifests`
(`StorageStage`, the producer), in the specialist (the consumer), and in ~6 tests. The producer and
the specialist *must agree* on it — they are related — but the relationship lives in a string, so
neither the compiler nor the import graph can see it. The relation exists in the world and *nowhere
in the model*.

.Before — the relationship as DATA: two literals agreeing by coincidence, no edge in the graph

  stage -.-> note
  spec -.-> note
  classDef bad fill:#fdd,stroke:#a22,stroke-width:2px;
  class stage,spec bad;
....

.After — the relationship as TYPE: one shared identifier; importing it draws the edge
[mermaid]
....

  stage["manifests domain — producer<br/>StorageStage"]
  id["systemd domain — PORT<br/>one typed unit identifier in systemd-port"]

  stage -->|imports| id

  classDef ok fill:#dfd,stroke:#2a2,stroke-width:2px;

The fix is to *promote the relationship from data to type*: one typed identifier in a shared module
that both sides import — the act of importing draws the edge in the graph. This is the project's
single-source-of-truth discipline, whose real purpose is the *traceability of relationships*, not
avoiding typos. It is not routed through the probe: the specialist never reaches systemd; it simply
names a unit, and that name becomes a shared type. *That shared module is `systemd-port`* (decided
below): systemd is one of our domains, so the unit vocabulary is its internal face — `manifests`
(producer) and `doctor` (consumer) both import it cross-domain.

== Decided — what `systemd-port` is

systemd is *one of our domains* (it owns `systemd-port` and `cdk8s-systemd`), not merely an external
target. So `systemd-port` is the *internal face of the systemd domain*: it owns both the readiness
seam (`SystemdRuntimeProbe` + `SystemdStatusSnapshot`) and the systemd-unit vocabulary (the typed
identifier of Problem 6). The doctor reads it *cross-domain*; the edge implements it. Nothing migrates
to `doctor-port`.

This is a *legitimate asymmetry* with pulumi, not an inconsistency: pulumi is *not* a domain of ours
(it has no model, only an external backend), so its read seam `SnapshotSource` is owned by the
*consumer* (`doctor-port`). systemd *is* a domain, so its seam is owned by the *systemd domain*. The
"align on pulumi when unsure" rule is a safety net for the undecided; here the domain question has a
real answer, so the net does not apply. (`systemd-port`'s stale module description — "shared by
cdk8s-systemd and the synthesis layer" — should be corrected to name the runtime-status + unit-vocab
role; nobody but seed-master readiness imports it today.)

== What stays open (a choice, not a problem)

* *Packaging shape* — pulumi-edge is grouped with a testkit under `host/pulumi/`; ssh-to-age-edge is
  flat under `osgi/`; `osgi/systemd/` already exists. Where dbus-systemd-edge lands (likely
  `osgi/systemd/dbus-systemd-edge`, beside the port it implements), and whether to reconcile the
  existing edges' shapes, is held open.
