= The seed — orchestration architecture (host↔OSGi ownership, the embedded seam)
:toc: left
:toclevels: 3

[NOTE]
====
The design of the SEED subsystem — the orchestration that provisions the management cluster (the
`seed-master` program, whose `controlplane` package is being redistributed into sub-modules). This spec
carries the seed's ARCHITECTURE in prose: who owns what across the host↔OSGi seam, why the OSGi world is
detached-by-design with the embedded exec as a special case, and the migration roadmap. Its sibling
documents: link:../bdd/bdd.adoc[the BDD-as-engine pattern] (the engine the seed is expressed on — a
transverse pattern, not seed-specific) and link:../atlas/seed.adoc[the seed atlas L1 view] (the
figures + verdicts). This file is the seed's *design*; those are the *pattern* and the *view*.
====

== Ownership and the seam — OSGi reasons, the host feeds and renders

*Lead: OSGi owns the scenarios + engine + reasoning (they already live there); the host injects the
`RunMode` fact + Pulumi context and renders/writes back. The cross-world edge crosses as a serialized
`ScenarioModel`, grafted into the host runbook — the live jGiven object never crosses.*

The pipeline is *owned by the OSGi world*; the host is a consumer. Two facts of the code already put it
there: jGiven is already an OSGi bundle (`pipeline-jgiven`, with an in-container testkit), and the JUnit
launcher already runs inside embedded Felix (`InContainerJUnitRunner` drives `LauncherFactory` under
the testkit). The bootstrap reasoning — the scenarios, the doctor consult, the readiness verification,
the runbook — is *target-state OSGi*; it is only *stranded* in `exec/seed-master` today.

[cols="1,2,2",options="header"]
|===
| | *OSGi world* (owner) | *host* (`exec/seed-master` + `pulumi-edge`, consumer)
| role | the brain — reasons about the bootstrap | thin launcher + the Pulumi edge
| holds | the scenarios, the jGiven session + engine, the launcher, the doctor, readiness, the
  `ReportModel` runbook | framework boot (already OSGi via `BootPipeline`), the *source* of `RunMode`,
  the stack *sink*
| jGiven engine + launcher | *here* (`pipeline-jgiven` + `junit-testkit`) | —
| the seam | *produces* the runbook + the output contributions | *injects* `RunMode` + Pulumi context,
  *renders* the runbook, *assembles + writes* the stack
|===

The seam keeps the discipline this spec is built on: *a domain never reaches for the global flag.*
`RunMode` (which only the host can know — it derives from `Deployment.isDryRun()`) is *injected* into
the OSGi world as a value; the OSGi world reasons; the host renders and writes. The founding constraint
travels intact: probes-as-steps and the runbook are produced OSGi-side; the host only renders/exports.

*The cross-world edge = a grafted `ScenarioModel` (E10).* A `@NestedSteps` composes within ONE world
(one jGiven engine, one `ReportModel`). A dependency that crosses the world-gateway cannot be a nested
step — two engines, two `ReportModel`s. It becomes a *gateway step*: the caller world sends a
`Document`, the remote world plays its scenario in ITS `ReportModel`, and returns the *serialized
`ScenarioModel`* (JSON String — the seam carries no live jackson type). The caller *grafts* the remote
steps as the gateway step's `nestedSteps` (`StepModel.addNestedStep`) → the operator reads ONE
continuous tree, from the seed down to the OSGi root. And the verdict travels IN the model:
`remoteScenario.getExecutionStatus()` — if the remote is FAILED, the graft marks the gateway step
FAILED and the host's downstream steps SKIPPED (the local fail-fast, reproduced across the frontier).
*One Document suffices* — the `ScenarioModel` carries both the narration (steps → the sub-tree) and the
verdict (`executionStatus` → the propagation). This is proven *in isolation* on the bench (a
`URLClassLoader` realm stand-in, an in-JVM JSON round-trip); wiring it to the real embedded Felix
(`ClusterSeedTopic.seedCluster()`) is the migration increment, not re-proof. The conceived form of this
seam — one broker door instead of N service verbs — is link:world-gateway-spec.adoc[the seed-broker
design].

== The OSGi world is detached by design — embedded exec is a special case

*Lead: the general case is a detached OSGi world (remote); seed-master's embedded exec merely folds the
seam in-process. The launcher is one more consumer of the R4 boot seam. Pulumi belongs to the
embedded/bootstrap host only, not the world.*

The general case is a standalone OSGi world running as a service — it *amorces itself*, and the host is
a *remote client* that connects, injects `RunMode` + the Pulumi context, and pulls back the runbook and
the output contributions across the remote frontier. The embedded exec (`FrameworkLaunchPipeline.
embedded()`) is *one particular case* — the degenerate one where the host co-locates and boots OSGi
in-process. The chicken-and-egg amorce ("what starts OSGi cannot run inside OSGi") is *real only in the
embedded case*; detached, the OSGi world has its own internal amorce.

*This does NOT bar the boot from being a jGiven step* (see link:../bdd/bdd.adoc#the-model[the model]).
The thing that "starts OSGi" is the JUnit launcher + its `main()`, which run on the HOST flat classpath,
OUTSIDE Felix — so they do not run *inside* OSGi, and the paradox does not touch them. The launcher
plays the seed scenario whose *first step* is the boot effect (launch Felix); every later step reasons
within the framework that first step opened. "What starts OSGi" (host launcher) and "what runs inside
OSGi" (the reasoning steps) are different threads/classpaths — the frontier is exactly the gateway
(Figure 2).

The launcher does not change this — it is one more consumer of the R4 boot seam (Felix in `Pulumi.run`).
`InContainerJUnitRunner` already drives a JUnit launcher *inside* Felix; `JGivenTestkit.felix()` proves
the jGiven runtime (byte-buddy proxy, `ScenarioExecutor`, `ValueInjector`) boots in-container — the
coupling that gives the state-DAG + the execution nesting. The live boot seam already exists:
`ClusterSeedTopic.seedCluster()` boots embedded Felix synchronously on the `Pulumi.run` lambda thread
today.

*Which use case is which* (two real seed use cases, not a theoretical symmetry):

[cols="1,2,2",options="header"]
|===
| | *seed-master (bootstrap)* | *seed in-cluster (other uses)*
| mode | *embedded exec* — boots OSGi in-process | *detached workloads* — OSGi as a separate workload, remote
| why this mode | it *precedes* the cluster: there is no cluster yet to deploy a workload into, so it
  must embed and amorce OSGi itself — *this* is why it owns the amorce paradox | the cluster already
  exists; the OSGi world runs as a workload, accessed remotely — nothing needs to amorce it in-process
| Pulumi edge (`RunMode`, stack sink) | *yes* — seed-master *creates* the infra via Pulumi, so
  `Deployment.isDryRun()` is a fact only here | *no* — a workload runs *inside* the already-created
  cluster; it has no `RunMode`
|===

This lands the Pulumi coupling precisely: it is *not* a property of the OSGi world — it is a property
of the *bootstrap's embedded host*. The detached OSGi world knows nothing of Pulumi. Which confirms, by
a second route, that the preview trigger and the stack sink live at the *host edge* (`pulumi-edge`),
never in the OSGi reasoning.

The concern was that `context.export` is synchronous on the `Pulumi.run` lambda thread while the test
harness runs the launcher on a dedicated TCCL thread. It conflated the harness with the production
path: host-world scenarios run on the lambda thread (no OSGi realm → launcher inline, export
synchronous); OSGi-world scenarios run inside Felix on ITS own thread — the host never drives that
thread, it consults via `consult(Document) → Document` and grafts the returned model. *The thread/TCCL
frontier IS the gateway* — no live jGiven object ever sits on the export thread.

[[migration]]
== Migration — legibility first, then ClusterSeed-vertical

*The method: the spec runs ahead (avant/après) with the atlas up to date; only then the plan and the
worktree scheduling — integration obliges the worktrees, the spec does not.*

. *Legibility cleanup of the spec network — DONE.* The BDD-as-engine model is the primary readable
  content across the network (link:../bdd/bdd.adoc[the pattern], this seed spec, the atlas satellites);
  the former model is the avant reference in the pattern spec. (Closed before the socle landed.)
. *Engine-lifecycle socle — increment 1, SHIPPED (2026-07-05).* The launcher, connection, lever and
  disciplines are live in `osgi/runtime/scenario-engine`; see
  link:engine-lifecycle-spec.adoc[engine-lifecycle-spec]. This is the substrate the vertical rests on —
  no longer a bench stand-in.
. *ClusterSeed-vertical migration — increment 2, one pipeline at a time.* Migrate ONLY
  `ClusterSeedPipeline` first, end-to-end into `seed-master` on the shipped socle (real embedded Felix):
  the phases become `@ScenarioStage`s, the two live jGiven islands (`SystemdAdapterTopic`,
  `ClusterReadinessTopic`) fold in as phases, the value-DAG replaces `StateBuilder`, outputs return as
  `SeedRun(runbook, outputs)`. The other six pipelines STAY on the former model meanwhile — assumed
  coexistence, NOT a legacy variant to hide. Each subsequent pipeline is its own increment.
. *Closing task — the `SCENARIO_STATE_DAG` gate.* Once the phases carry `@Provided/ExpectedScenarioState`,
  add the sixth `StagingGate` (the topological check, on the existing ASM+`@GovernedBy` mould), born
  WARN then flipped WARN→ERROR — the REALM_BOUNDARY ritual, the static safety the former type-state gave.

The three mechanisms not yet productionised (the `PreviewExecutor`, the `SCENARIO_STATE_DAG` gate, the
cross-world `ScenarioModel` graft) have their reference sketch pinned at tag `spike/bdd-pipeline-poc`
(`git show spike/bdd-pipeline-poc:<path>`): `PollUntilReadyExtension` (adaptive poll — though its live
form is `SeedSystemdAdapterEndpointGate`), `DagGateSpikeTest` (the topological gate), and
`CrossWorldGraftSpikeTest` (the E10 graft). The rest shipped with the socle.
