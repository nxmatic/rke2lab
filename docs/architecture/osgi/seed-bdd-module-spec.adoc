= seed-bdd — the common gardening spine every seed exec rebuilds on
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN, ready to implement (2026-07-12). `seed-bdd` is the FOUNDATION module holding the
gardening spine common to every seed exec — the host runbook stages spoken in the gardening register
(`Cellar` fetch/store, the sow-and-graft caller, the world opening, the harness). An exec (`seed-master`,
and the seed execs after it) adds only its OWN root composition: which scions, in what order. It realises
the host half of link:../bdd/bdd.adoc#clusterseed-scenario-map[the ClusterSeed scenario map] atop
link:gardening-model-spec.adoc[the gardening model].
====

== Why a module — common spine vs per-exec composition

The target host runbook is uniform: every root step is EITHER pure-host gardening (`Cellar` fetch/store,
preflight) OR a *sow-and-graft caller* (sow a domain scenario toward the gardening, graft its scion). The
STAGES that speak these gestures are the same for every seed exec; only the COMPOSITION — the phase order,
which scion each step sows — is exec-specific. So the stages are common (`seed-bdd`), the composition is
the exec's (`seed-master` writes its `ClusterSeedScenario`, a later exec writes its own).

[cols="1,2",options="header"]
|===
| layer | contents · home
| *common* | the gardening stages (`Cellar` fetch/store, the sow-and-graft caller, preflight, the world
opening + the seeding harness) — **`osgi/foundation/seed-bdd`**
| *per-exec* | `Main` + the concrete root scenario (the phase chain: preflight → … → outputs) — the exec
module (**`seed-master`**, …)
|===

== Placement and consumption — under osgi/, consumed FLAT by the host

`seed-bdd` lives in `osgi/foundation/` (beside `seed-broker-port`, whose BDD counterpart it is), yet the
host consumes it as a *flat jar*. Location and realm are independent axes — the precedent is
`scenario-engine` (`osgi/runtime/`): *a bundle is a superset of a plain jar*, and the split is by PACKAGE,
not by module.

* *One artifact, one BSN* (`io.nxmatic.rke2lab.osgi.foundation.seed.bdd`), both a bundle and a plain jar.
* *The host-side spine is NOT exported* — the sow-and-graft caller, the world opening, the harness sit in
  a base package the host reads on the flat classpath, never wired in-container. Exporting them would let
  a bundle load a second copy of a seam class (the `DUPLICATE_REALM_CLASS` collision the engine's bnd
  guards against).
* *Only in-realm halves are exported* (if any) — what an in-container scion could one day want.
* *Host-only imports are `resolution:=optional`* (`jgiven.report.*`, framework-launch, …) — exactly as
  `scenario-engine`, so the bundle still RESOLVES when installed in-container for its exported packages.

This is NOT the codec's dual-realm (staged bundle + shaded flat, two copies). It is one jar whose
non-exported base package the host uses flat, and whose exported packages a bundle *may* install —
superset, not duplication. If a scion later needs the spine in-realm, that is the moment to reconsider —
reversibly, per package, never by inflating the seam.

== Dependencies — leans on seed-port + engine, never inflates seed-port

`seed-bdd` DEPENDS on `seed-broker-port` (it consumes `Cellar`, `SeedEnvelope`, `Parcel`, `SeedBroker`,
`RunGate`) and on the neutral half of `scenario-engine` (the sow-and-graft mechanics). The arrow runs
FROM `seed-bdd` TO `seed-port` — depending on the seam is not entering it. `seed-port` stays the minimal
membrane; the gardening stages are a consumer, not a seam inhabitant.

== Who speaks gardening — the stages, not the engine

The engine stays at the FLIRT level: `ScenarioGraft` names the horticultural gesture (*graft*) but its
signatures are mechanical (`rebuild(String)`, `graftUnder(ReportModel, …)`). `seed-bdd`'s stages SPEAK
gardening in their step titles ("I go to the cellar for the parcel's state", "I sow X and graft its
scion", "I store the harvest") and COMPOSE the neutral mechanics underneath. The engine gains no
gardening type; the vocabulary lives in `seed-bdd`'s stages, which call the engine's neutral mechanics.

The sow-and-graft caller composes the two halves of the crossing (link:seed-broker-spec.adoc#playing-a-scenario-is-a-sow[the
runbook handler]): the SOW half is `broker.sow(new RunbookCoordinate(soil), trigger)` — the host holds
only a soil NAME (a `String`) and reaps the runbook as JSON, never naming a `*Coordinate` enum nor
reaching a `*BddScenarios` front-door (that reflection lives INSIDE the domain's runbook handler, on its
own loader). `RunbookCoordinate` is a neutral value-coordinate in `seed-broker-port` (the twin of
`SplitCoordinate`), so the seam names nothing a domain owns. The GRAFT half is
`ScenarioGraft.rebuild(payload)` + `graftUnder(hostTree, step)`, host-side. One gesture — one door out,
one graft home — four times in the root scenario. `seed-bdd` therefore depends on `seed-broker-port`
(the `SeedBroker` door + `RunbookCoordinate`) and the neutral `ScenarioGraft`, never on a domain's
`*BddScenarios` or `*Coordinate`.

== The root scenario — a per-exec composition on the common stages

`seed-master`'s `ClusterSeedScenario` is the concrete instance: pure-host `Cellar.fetch` opening (read the
parcel's state — where we start from), four sow-and-graft callers (bbox · incus · systemd · cluster, the
dependency chain whose terminal fruit is *the cluster answers ready*), pure-host `Cellar.store` closing
(the harvest filed to its parcel). The cellar at both ends — `fetch` opens, `store` closes; between them
everything is cultivated fresh (no scion reads the cellar; the manifests graft is grown fresh, not cached).
