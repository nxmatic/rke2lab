= jGiven-in-OSGi testkit — host handoff
:toc: left
:toclevels: 3

[NOTE]
====
Test-scope infrastructure only — no production bundle imports jGiven. jGiven wraps clean as an OSGi
bundle at a LOCAL cost — one `bootdelegation=sun.misc`, one forced fragment import, no
`DynamicImport-Package: *` — not viral. A non-regression guard (`JGivenTestkitGuardTest`, palier 2 +
palier 3) runs on a real embedded Felix 7.0.5.
====

== What this is

A reusable kit that lets a host bundle run jGiven BDD scenarios *in-container* — inside the real OSGi
framework, through the host's own classloader — so a scenario sees the host's `internal` /
package-private types *white-box*, exactly as the host's own code does. It is the execution
substrate for the test-fragment model: the in-framework twin of package-private.

jGiven is a *BDD* concern, not a JUnit one: its scenarios run through the host classloader, not
through JUnit. So the kit lives under `osgi/jgiven/`, depends on the generic JUnit testkit
(`osgi/testkit`), and is *not owned by it*.

The kit exists because testing OSGi-world code from the bare-JVM flat classpath is a
world-incoherence (it is what produced the doctor `ReferralReplies` Maven cycle). A test *fragment*
restores coherence: the test *is* its host (shared classloader), so a shared fixture is visible with
no reverse module edge — no cycle.

== The modules

[cols="1,3",options="header"]
|===
| Module | Role

| `osgi/jgiven/jgiven-wrap`
| jGiven (`jgiven-core` + `jgiven-junit5` 2.0.3) wrapped as a first-class OSGi bundle. The bnd
  recipe stamps OSGi headers onto the only two header-less jars and imports the rest (guava, gson,
  paranamer, jansi, jakarta.annotation, byte-buddy — all already bundles) as stock bundles. No
  shade, no relocation, no embed. Test-scope.

| `osgi/jgiven/jgiven-testkit`
| The reusable assets. **(1)** `src/main/resources/jgiven-fragment.bnd` — the shared bnd include
  carrying the one forced `Import-Package` bnd cannot compute. **(2)** `JGivenTestkit.felix()` — a
  `OutOfContainerFrameworkExtension.Builder` pre-loaded with the jGiven boot closure. Its own `src/test`
  carries the palier-2/3 guard. A plain jar, not a bundle.

| `osgi/jgiven/jgiven-probe`
| The guard's host bundle: a pure POJO (`Vault`) with a package-private field and ZERO test
  dependencies — it stands in for a real host like `doctor-core`.

| `osgi/jgiven/jgiven-probe-test`
| The guard's `-test` fragment, attached to `jgiven-probe`. **This module is the template a real
  host copies**: its bnd writes only `Fragment-Host` + a one-line `-include`, and it authors a
  `Stage` + runner in the host's package. Running it in-container is what the guard asserts.
|===

== How a host consumes the kit

Two artefacts, two halves of the model: a *build-time* include and a *test-time* boot helper.

=== 1. The host's `-test` fragment bnd — two lines

The fragment's `bnd.bnd` writes only what is host-specific; everything else comes from the shared
include. bnd's `${.}` expands to the directory of the including bnd file (a true cross-jar classpath
include is a bndtools-workspace feature, absent in plain `bnd-maven-plugin`), so the `-include` is a
reactor-relative path to the shared file:

[source]
----
Bundle-SymbolicName: io.nxmatic.rke2lab.doctor.core.test
Fragment-Host: io.nxmatic.rke2lab.doctor.core
-include: ${.}/../../jgiven/jgiven-testkit/src/main/resources/jgiven-fragment.bnd
----

The include contributes the single forced import bnd cannot see — `com.tngtech.jgiven.impl.intercept`
(implemented by the runtime-generated stage proxy, never named in scenario bytecode) — plus the
`com.tngtech.jgiven.*` wildcard tail and `-noimportjava: true`. byte-buddy packages need NO forcing:
bnd computes them from the `Stage` bytecode, and they resolve against the `jgiven-wrap` bundle.

=== 2. The host's harness — one builder call

[source,java]
----
@RegisterExtension
static final OutOfContainerFrameworkExtension felix =
    JGivenTestkit.felix()                 // jGiven boot closure baked in
        .installBundles("doctor-core")    // + the host bundle under test
        .build();
----

`JGivenTestkit.felix()` pre-loads `bootDelegation("sun.misc")`, the jGiven dependency bundles
(`failureaccess`, `guava`, `gson`, `paranamer`, `jansi`, `jakarta.annotation`, `byte-buddy`),
`jgiven-wrap`, and the host slf4j/junit packages the wrap imports. The host adds only its own bundle.
The host test module must put `jgiven-wrap`, `jgiven-testkit`, the host bundle, its `-test` fragment,
and `byte-buddy` on its test classpath so the testkit locates them by classpath substring.

=== 3. Running a scenario in-container

The `-test` fragment authors a `Stage` in the host's package (so it reaches package-private members
white-box) and a runner that drives the scenario standalone:

[source,java]
----
// in the fragment, in the HOST's package — sees package-private members white-box
public final class ConsultScenarioRunner {
  public static String run() {
    Scenario<ConsultStage, ConsultStage, ConsultStage> s = Scenario.create(ConsultStage.class);
    s.setModel(new ReportModel());   // standalone embedding: JUnit would otherwise inject this
    s.startScenario("...");
    s.given()...; s.when()...; s.then()...;
    s.finished();
    return "OK";
  }
}
----

The harness installs host + fragment, resolves the host (attaching the fragment), starts it, and
invokes the runner *through the host classloader* — so the returned value is a plain `String` and no
jGiven type ever crosses into the bare-JVM test world:

[source,java]
----
Bundle host = felix.install("doctor-core");
felix.install("doctor-core-test");      // fragment — never started
felix.resolve(List.of(host));           // attaches the fragment (OSGi Core §3.14)
host.start();
Object result = host.loadClass(RUNNER_FQN).getMethod("run").invoke(null);
assertEquals("OK", result);
----

== Anti-patterns

❌ *Put jGiven-specific boot knowledge in `OutOfContainerFrameworkExtension`.* The generic testkit stays
jGiven-agnostic; the boot closure lives in `JGivenTestkit.felix()`. A second BDD lib would get its
own helper, not a second branch in the generic extension.

❌ *System-export `com.tngtech.jgiven.*`.* The whole point is that jGiven resolves as a *bundle*; a
system-export would give type resolution only and defeat in-container play. Nothing of jGiven is
system-exported — only slf4j/junit host concerns the wrap imports but no scenario runs against.

❌ *`DynamicImport-Package: *` on the host or fragment.* It never appeared in the spike and is not
needed: jGiven subclasses the concrete `Stage` it was handed (INJECTION into that stage's
classloader) and never looks stages up by name. The cost is bounded — one forced import, one boot
delegation.

❌ *Hand-write the forced import in each fragment.* Use the shared `-include`. If a fragment
re-declares `com.tngtech.jgiven.impl.intercept` by hand, the day jGiven renames it every host breaks
independently; the include is the single point of change.

❌ *Author the `Stage` in a different package from the host type it inspects.* Same-package
authoring inside the fragment is what grants white-box access; a black-box `Stage` in another package
loses the very capability the model exists for.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Cause / fix

| `sun.misc.Unsafe not found by net.bytebuddy`
| byte-buddy's `ClassInjector.UsingReflection` reaches `Unsafe` reflectively. `JGivenTestkit.felix()`
  already boot-delegates `sun.misc`; if you bypassed the helper, add `.bootDelegation("sun.misc")`.

| `NoClassDefFoundError: .../impl/intercept/StageInterceptorInternal`
| The forced fragment import is missing — the `-include` of `jgiven-fragment.bnd` did not take.
  Check the fragment's built `META-INF/MANIFEST.MF`: `Import-Package` must end with
  `com.tngtech.jgiven.impl.intercept`.

| `NullPointerException: reportModel is null` in `scenarioFinished`
| Not an OSGi symptom — standalone jGiven embedding needs `scenario.setModel(new ReportModel())`,
  which the JUnit integration would otherwise inject.

| fragment never attaches (host resolves without it)
| The host was resolved BEFORE the fragment was installed. Install the fragment first, then
  `resolve(host)` — the framework only folds a fragment present at host-resolution time.

| testkit cannot locate a bundle (`no <artifact> bundle … on classpath`)
| The bundle is not a test-scope dependency of the harness module. Add it; the testkit locates
  bundles by classpath substring, resolving reactor `-am` siblings to their `target/classes` dir.
|===

== Building & verifying

[source,bash]
----
flox activate -- ./mvnw -pl :jgiven-testkit -am test \
    -Dmaven.build.cache.skipCache=true -DskipTests=false
----

The guard is tagged `@Osgi` (not `@OsgiSpike`), so it runs in the default reactor — it is a lasting
regression guard, not a throwaway. The default build excludes `spike` and `live`; `osgi` runs.
