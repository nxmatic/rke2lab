= The netplan scion — blueprint export played through the broker
:toc:
:toclevels: 3

== Overview

The cluster network underlay — cluster/node IDs, MAC derivation scheme, IPv4 + the
ULA v6 mirror, DHCP leases — is derived once from rke2lab's
`ClusterNetworkBlueprint` (a pure function, `deriveRecipeModel`) and exported as a
flat data file the rke2lab flake feeds to nix-darwin-home (see
link:../patterns/netplan-blueprint-single-source.adoc[the blueprint single-source
pattern]). That export used to run FLAT in `netplan-cli` (`BlueprintExportCommand`),
referencing `ClusterNetworkBlueprint` directly on the host classpath.

That flat reference is a **realm-boundary violation**: `ClusterNetworkBlueprint`
lives in `netplan-contract`, a `type=contract` bundle — a bundle-realm type that
never crosses the host frontier as a TYPE (a flat reference `NoClassDefFoundError`s;
the realm-boundary gate is right). The export had been quietly broken since the
`netplan.api` → `netplan.contract` rename.

This spec records the fix: **`netplan-bdd`, the netplan scion** — the blueprint
export produced IN-CONTAINER (where the contract type is reachable) and reaped by the
host as JSON. The host names no contract type; only host-neutral JSON crosses the
broker door. It mirrors link:manifests-bdd-spec.adoc[the manifests scion]: a pure FS
materialiser (it writes a file, does not probe a live system), mode-blind, driven
through `broker.sow(RUNBOOK)`.

== The crossing — the blueprint travels as DATA, not as a TYPE

The architectural rule the fix honours: *the contract modules are dual-realm for the
codec, but their records do NOT cross the frontier as types — they serialize to
JSON.* So the derivation moves to the realm where `ClusterNetworkBlueprint` is
reachable, and only the serialized result crosses back.

The blueprint JSON crosses via a file the scion writes to the host-passed `SOIL`
path (embedded Felix, same filesystem) — the same SOIL-materialise harvest the
manifests scion uses. nix-darwin-home re-parses the flake's YAML via `yq -o=json`, so
only the DATA matters, not the YAML formatting — the host→YAML conversion is free to
drop the former decorative comments.

== The contract types (`netplan-contract`)

The scion is addressed through two new exported contract types, single-sourced in
`netplan-contract` like their manifests twins:

`NetplanCoordinate`:: an EMPTY `enum` (netplan owns no cellarable value-coordinate —
it materialises a file and stores no harvest), holding as static constants the shared
META coordinates netplan is addressed through: `AMEND` (the reflector serves it,
the assembler gathers on it), `SHAPE` (the schema projection), `RUNBOOK` (the export
trigger) — all keyed by one `DOMAIN = "netplan"`.

`NetplanRunbookInput`:: the `@SeedContract("runbook")` wire-record — the activation
payload a sower supplies. It carries a SINGLE `@Amendment(Amendment.SOIL)` component,
`materializationRoot` (`Optional<String>`), the plot the scion writes `blueprint.json`
into. The blueprint itself is fully derived in-container, so this input carries no
facet — *where to write* is the only host-held fact. `defaults()` is an unamended soil
(the scion writes into a temp dir for a bare `shape` probe).

== The scion trio (`netplan-bdd`)

A `type=model` embeddable bundle whose scenario class is non-exported (the launcher
plays it by class-selection; the host grafts its `ScenarioModel`). Three artefacts,
the pattern the shipped scions share:

`NetplanBlueprintScenario`:: `@SeedScenario`, `InputReceiver<NetplanRunbookInput>`. The
transposition of the former flat `BlueprintExportCommand`: the WHEN derives each
node's `ClusterNetworkBlueprint` and projects the complete addressing metadata
(MACs, IPv4 + ULA v6 mirror, DHCP leases) into a metadata tree mirroring the former
flat records EXACTLY (so the JSON keys the flake consumes —
`clusters`/`nodes`/`macPatterns`/`nodeTypes`/`addressing` — stay byte-identical),
then serialises it to `blueprint.json` in the SOIL. NO `@OsgiService`: the blueprint
is a pure static derivation, no live collaborator.

`NetplanRunbookHandler`:: `@Component(service = SeedHandler.class)` extending
`GenericRunbookHandler`. Supplies the coordinate it serves (`NetplanCoordinate.RUNBOOK`)
and its scenario class, and reads the trigger — `seedFrom` decodes `NetplanRunbookInput`
off the payload and routes it through `NetplanBlueprintScenario.INPUT`.

`NetplanAmendReflector`:: `@Component(service = SeedHandler.class)` serving
`NetplanCoordinate.AMEND`. Mirrors `ManifestsAmendReflector`: it serialises
`NetplanRunbookInput.defaults()` and hands them + the sower's `{SOIL}` role to the
foundation `AmendmentBinder`, which places each role's value in its `@Amendment`
field. So the vocabulary reconciliation (role → field) lives at the door, never in the
runbook handler.

== The host adapter (`plan-cli`, `plan network export`)

The former standalone `netplan-cli` has been folded into `plan-cli`, the unified `plan`
north-adapter that multiplexes two planes over one door: `plan network export` (this
netplan blueprint) and `plan dataset export` (the ZFS dataset layout). It is de-typed
off `netplan-contract`: it no longer references `ClusterNetworkBlueprint`. The `network
export` verb drives `PlanCliScenario` (host-flat, mirror of `ManifestsCliScenario`) on
the embedded JUnit launcher: the GIVEN opens the gardening over the world connection and
publishes an `EphemeralCellar` for the ROOT drain; the WHEN sows `netplan` with `{SOIL:
tempDir}` (dispatched by the `network` plane); then the host reads
`tempDir/blueprint.json` (generic JSON) and converts it to YAML with flat jackson,
printing to stdout — the flake's `plan network export > blueprint.yaml` bridge (the
former `netplan yamlExport`), unchanged in data.
