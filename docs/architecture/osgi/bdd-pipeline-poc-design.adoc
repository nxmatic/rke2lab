== La question que le POC doit trancher

____
Le pipeline de seeding (aujourd'hui : grammaire fluent type-state `during`/`then` + jgiven
enchevêtrés dans 2 topics sur 8) gagnerait-il à être *exprimé entièrement en scénarios BDD
jgiven*, orchestrés par le *JUnit Platform Launcher* embarqué au runtime, la dynamique
manquante étant *contribuée comme extensions Jupiter* ?
____

On ne le décide pas sur le papier. On construit une maquette compilable, on la joue, on
*regarde le code et le runbook produits*, et on décide alors.

== Ce qui a été écarté (et pourquoi) — ne pas rouvrir sans raison neuve

* *Spock* : techniquement de retour dans le jeu (moteur JUnit Platform comme Jupiter), mais
  aucun besoin identifié ne le justifie (son atout `where:` data-table ne répond à aucun besoin
  nommé du seeding), et il coûte Groovy comme citoyen de realm OSGi + il est encore plus
  _runner-shaped_ que jgiven. *Sorti*, à rouvrir seulement si un besoin data-table émerge.
* *Un moteur BDD maison* : réinventerait l'outillage jgiven (ReportModel, steps nested, modes
  d'invocation, rendu). Ne vaut pas le coup.
* *Finition RunMode/output-gate* (chantier `feature/pipeline-two-gates`, abandonné) : ce POC
  l'*absorbe*. Le commit spec orphelin « RunMode absorbe LiveGate » est préservé sous le tag
  `wip/runmode-absorbs-livegate` — son sort (abandon / reprise) se décide *après* la preuve.

== Les décisions de conception (prises ensemble, 2026-07-04)

. *Les scénarios BDD sont le MOTEUR D'EXÉCUTION du seeding*, pas une couche de description.
  Chaque phase = un scénario. Cohérent avec la contrainte fondatrice existante : « les probes
  SONT des steps jgiven, sinon pas de runbook ».
. *Moteur = jgiven* (déjà bundle OSGi `pipeline-jgiven` ; API programmatique déjà utilisée hors-JUnit
  dans `ClusterReadinessTopic`).
. *Substrat d'orchestration = le JUnit Platform Launcher*, embarqué au runtime. Ce n'est pas un
  pari : `InContainerJUnitRunner` (osgi/runtime/junit-testkit) pilote *déjà*
  `LauncherFactory.create(...)` avec engine explicite, listener et discovery-request, à
  l'intérieur d'OSGi. Le launcher est agnostique du moteur (Jupiter porte jgiven-junit5, déjà
  utilisé : `DoctorScenarioTest extends ScenarioTest`).
. *La grammaire fluent `during`/`then` disparaît* — jgiven compose tout. L'ordre et les
  dépendances s'expriment par les steps nested (`@NestedSteps` — déjà en prod :
  `ClusterReadinessScenario` rejoue `SystemdAdapterScenario`). _Décision à garder OUVERTE : le
  POC pourrait révéler qu'un mince ordonnanceur mérite de subsister ; ne pas la verrouiller avant
  d'avoir lu le runbook._
. *Le DAG de dépendances de VALEUR est porté par les annotations d'état jgiven*, pas perdu :
+
--
** `@ProvidedScenarioState(guaranteed=true)` = l'arête sortante (ce stage produit cette valeur)
** `@ExpectedScenarioState(required=true)` = l'arête entrante (ce stage requiert cette valeur)
** Un `required` sans `guaranteed` amont = un DAG mal câblé, détectable.
** *Le troc assumé* : on descend d'une sécurité _compile-time_ (le type-state `State<I,B>`
   shippé récemment) vers une vérification _déclarée + runtime_ (scenario-state). Pas un sac plat
   — un modèle typé et annoté. Le POC juge si ce cran est acceptable.
--
. *La dynamique manquante = extensions Jupiter contribuées.* JUnit ne LIVRE pas les primitives
  temporelles/DAG, mais il expose le SPI pour les FABRIQUER — et une extension EST une
  contribution (même paradigme que DS/`@Component` : un nœud enregistré, découvert, composé). Les
  3 hooks porteurs à stresser :
+
--
** `TestTemplateInvocationContextProvider` → la boucle poll-until-deadline (le mécanisme même de
   `@RepeatedTest`). Porte le *temporel* (triples boucles readiness, retry adaptatif systemd —
   vivent dans `ClusterBootstrapReadinessVerifier` / `SeedSystemdAdapterEndpointGate`).
** `ExecutionCondition` → le *gate* live/preview. *RunMode devient une condition d'exécution* —
   c'est là que RunMode se re-pose dans le nouveau modèle.
** `ExtensionContext.Store` (+ une `ExecutionCondition` de dépendance) → l'*ambient + l'enforcement
   du fan-in* (c'est le `PipelineContext`, natif).
--
. *Répartition host/OSGi via la world-gateway.* Les scénarios d'actualisation (couplés Pulumi/gRPC)
  restent host ; les scénarios de raisonnement (doctor, readiness authority) vivent OSGi (où jgiven
  vit déjà) ; ils dialoguent par `Document` à travers la gateway (le seam `consult(Document) →
  Document` existe déjà).
. *Arête cross-monde = runbook fusionné.* Un `@NestedSteps` compose dans UN monde (un moteur
  jgiven). Une dépendance qui traverse la gateway ne peut pas être un nested-step (deux moteurs,
  deux `ReportModel`). Elle devient un *step-passerelle* : envoie un Document, reçoit le verdict *+
  le `ScenarioModel` sérialisé* du scénario distant, que le monde appelant *fusionne* dans son
  `ReportModel`. Fondations vérifiées dans jgiven-core 2.0.3 :
  `ReportModel.addScenarioModel(...)` / `addScenarioModelOrMergeWithExistingOne(...)` (fusion
  native) + `com.tngtech.jgiven.report.json.{ScenarioJsonWriter,ScenarioJsonReader}`
  (sérialisation). Le `ScenarioModel` traverse en String JSON — patron Option B (le seam ne porte
  pas de type jackson vivant). *Question ouverte que le POC tranche* : le `ScenarioModel` EST-il le
  Document de retour (le verdict y vit déjà, comme steps/statuts/narration), ou faut-il deux
  Documents distincts (verdict + rapport) ?

== Ce que le POC construit

Un *nouveau module bench* `osgi/runtime/bench/bench-bdd-pipeline` (mouler sur
`bench-fragment-contribution`, le précédent POC qui a prouvé une hypothèse ; package
`io.nxmatic.rke2lab.osgibench.bddpipeline`). Deux faces si l'arête cross-monde l'exige (un bench
host + un bench OSGi), tout sous `bench/`, tout jetable.

*Livrable A — la FORME.* La transposition du pipeline *ClusterSeed entier* (6 phases : environment
/ preflight / bbox / incus / systemd-adapter / cluster-readiness / outputs) en scénarios jgiven
réels, compilables, avec *tout* le vocabulaire jgiven dans sa décomposition scenarios / stages /
states / steps :

* `@ProvidedScenarioState` / `@ExpectedScenarioState` (+ `required`/`guaranteed`) pour les deps ;
* intro-words (`given`/`when`/`then`/`and`/`with`/`but`) + `@IntroWord` / `@FillerWord`
  (`joinToPreviousWord`/`joinToNextWord`) pour la lisibilité ;
* `@As` / `@Format` / `@Formatf` / `@NamedFormat` / `@Quoted` / `@Hidden` / `@NestedSteps` /
  `@StepComment` / `@Table` selon les besoins de chaque phase ;
* `@ScenarioStage` pour la composition inter-stages.

Les probes sont *bouchonnés* (fake data, aucun système touché).

*Livrable B — la SORTIE.* On JOUE la maquette (via le launcher, à la manière de
`InContainerJUnitRunner`) → un `ReportModel` réel → un *runbook `.asciidoc` réellement généré*. Pas
dessiné à la main : la vraie sortie jgiven, pour juger la lisibilité de la forme opérateur.

== Les 4 chemins de l'échange (critères de succès — un runbook par chemin)

Le POC doit produire un runbook pour chacun (les 4 sont un point de départ ; s'il en manque, on le
verra en regardant les sorties) :

[cols="1,2,3,3",options="header"]
|===
| # | Chemin | Ce qui traverse la gateway | Rendu attendu
| P1 | Live + vert | checkpoint → verdict OK + ScenarioModel vert | step-passerelle ✓, sous-arbre OSGi greffé vert
| P2 | Live + symptôme | checkpoint → verdict échec + narration doctor | step ✗, diagnostic + « ⚕ » remontés fusionnés
| P3 | Preview (dry-run) | *rien* — gate fermée = dry-run jgiven | step *PENDING*, pas de traversée (la question RunMode absorbée)
| P4 | Panne de transport | gateway échoue (OSGi injoignable, Document illisible) | erreur d'*infrastructure*, distincte d'un symptôme métier
|===

P4 est le piège classique : distinguer _« l'autre monde dit que ça va mal »_ (P2) de _« je n'ai pas
pu joindre l'autre monde »_ (P4) — deux échecs de nature opposée qui doivent se lire différemment.

== Les risques à garder en tête pendant le POC (honnêtes)

* *Test-shaped assumptions.* On bâtit un framework de pipeline sur un SPI conçu pour le cycle de
  vie de _test_. Beaucoup de hooks tombent juste ; là où le modèle Jupiter ne colle pas _tout à
  fait_, on se contorsionne. Le POC doit repérer où les 3 hooks porteurs *épousent* vs *grincent*.
* *Le temporel reste dans les steps* quel que soit le résultat — le launcher orchestre _quand_ un
  scénario tourne, l'extension `TestTemplate` porte la boucle, mais la logique de retry/deadline
  elle-même vit dans le code de step. Ne pas attendre du launcher qu'il « résolve » le temporel,
  seulement qu'il l'*exprime* proprement.
* *Chaque itération de poll = une invocation dans le runbook* : signal utile pour l'opérateur
  (« tentative 1 échec, tentative 2 ready ») ou bruit ? À juger sur la sortie réelle.

== Retours d'expérience du POC (2026-07-04, module `bench/bench-bdd-pipeline`)

Le bench est construit et joué. Cinq enseignements, chacun mesuré (bytecode jgiven 2.0.3 décompilé
ou runbook réellement rendu), pas déduit. Ils orientent la matérialisation du pipeline.

=== E1 — Le dry-run de jgiven est incompatible avec l'enforcement des scenario-states

`@ProvidedScenarioState(guaranteed=true)` / `@ExpectedScenarioState(required=true)` (les attributs
qui porteraient le DAG, décision 5) *existent* en 2.0.3. Mais `ValueInjector.readValues` appelle
`checkGuaranteedStatesAreInitialized` **inconditionnellement à chaque transition de stage**, sans
garde de mode d'exécution. Le dry-run *saute les corps de steps* — donc le champ garanti reste
`null` → `JGivenMissingGuaranteedScenarioStateException`.

Ce n'est pas un défaut de la propriété `jgiven.report.dry-run` : c'est vrai de *tout* mécanisme qui
saute les corps (la propriété, le `DeferringScenarioExecutor` de la prod, une future
`ExecutionCondition` de preview). La cause est de fond : le preview demande _« ne produis rien »_,
l'enforcement demande _« prouve que tu as produit »_ — deux intentions opposées.

*Conséquence :* **enforcement du DAG XOR preview par dry-run — pas les deux.** L'enforcement des
states ne vit que dans un run exécutant (live ou fakes). Le P3 (preview) devra porter ailleurs son
_« ce qui va tourner »_, pas sur `guaranteed`/`required`. NB : tout le code prod actuel utilise la
forme *nue* (`@ProvidedScenarioState X x;`), jamais les attributs — le POC est le premier à les
essayer, et ils butent immédiatement.

=== E2 — On bouchonne le PROBE (le seam runtime), pas l'EDGE (le state)

Pour rendre un runbook hors-runtime sans dry-run : injecter un *faux probe* dans le corps du step
(le corps s'exécute, produit honnêtement l'edge à partir d'une sortie bouchonnée) plutôt que
pré-remplir l'edge à la main. Bouchonner l'edge directement re-crée le trou de E1 (states présents
mais non _produits_) ou fait mentir le runbook (steps rendus sans avoir rien calculé). C'est le
pattern déjà en prod : `SystemdAdapterProbe` / `ClusterReadinessProbe` sont des
`@FunctionalInterface` injectés — live branche le vrai, les tests le fake, le script du scénario est
identique.

=== E3 — Le mode d'exécution est piloté de l'EXTÉRIEUR du scénario

Le code du `ScenarioTest` est agnostique du mode. dry-run vs run réel se décide par une propriété
système (surefire `systemPropertyVariables`), pas dans le scénario. Corollaire vérifié : le bouton ▶
de VSCode et `mvn test` divergent tant que l'un applique la propriété et l'autre non ; retirée des
deux, comportement identique. Ça préfigure proprement _« RunMode devient une `ExecutionCondition` »_
(décision 7) : le mode est une décision de contexte, jamais une propriété du scénario.

=== E4 — Où vit l'arbre dans le modèle jgiven

`ReportModel.scenarios` est une **`List<ScenarioModel>` plate** — aucun lien parent/enfant entre
scénarios, et `sortByDescription()` les trie (d'où l'ordre alpha observé). L'arbre n'existe QUE dans
`StepModel.nestedSteps` (`List<StepModel>`, parcouru par `visitStepsRecursively`). Deux corollaires
mesurés au runbook :

* *JUnit `@Nested`* (spike login) → rend des **scénarios FRÈRES** groupés par la hiérarchie de
  classes, PAS un arbre de scénarios. La hiérarchie structure le _setup_ (le `@BeforeEach` empile le
  Given au bon niveau), pas le `ReportModel`.
* *`SharedRunbook`* (un `ReportModel` unique au Store racine, N phases pilotées programmatiquement) →
  agrège bien en **un seul modèle** (ta question « un seul runner » : OUI, hors du chemin
  `ScenarioTest`, en possédant le modèle — comme `ClusterReadinessTopic`), mais rendu **à plat**,
  trié alpha : le `ReportModel` n'a pas d'arbre à préserver.

=== E5 — Un step PEUT s'ouvrir sur un scénario imbriqué (la pièce maîtresse)

« Un step est un nested scenario » n'existe pas dans le modèle (`StepModel` ne pointe pas vers un
`ScenarioModel`). Mais un scénario n'est qu'un `Given/When/Then` de steps — et les intro-words
`given()/when()/then()` **se rendent à l'intérieur d'un bloc `@NestedSteps`**. Recette mesurée :
(1) méthode parente `@NestedSteps`, (2) pilotant un sous-stage injecté `@ScenarioStage`, (3) dont le
corps utilise les intro-words. Rendu réel obtenu :

[listing]
----
   Given the pipeline starts
    When the cluster-readiness checkpoint runs          ← step parent
           Given a reachable systemd adapter "..."      ← scénario enfant, imbriqué
           When the kubeconfig is published
           And the api is ready
           Then the cluster is ready
    Then the seed is ready
----

C'est la pièce qui réconcilie les deux modèles : le **nested-fixture** (E4/article — DAG comme
structure de classes, établissement une-fois via `computeIfAbsent`, teardown en ordre inverse,
sous-arbre rejouable) apporte le _lifecycle_ ; le **step-as-scenario** (E5) apporte l'_arbre du
runbook_. Une phase, en s'établissant, greffe son G/W/T sous le step de sa phase parente → un seul
runbook arborescent où chaque phase est un vrai scénario à sa place. C'est le modèle sur lequel le
pipeline complet est matérialisé.

=== E6 — Le statut vert/rouge a DEUX sens opposés selon le mode

Le launcher n'a qu'une notion de vert/rouge, le seeding en a deux :

[cols="1,3,3",options="header"]
|===
| | Vert veut dire | Rouge veut dire
| *Mode test* (CI) | le comportement attendu (même un échec) est reproduit | le pipeline a un bug
| *Mode moteur* (prod) | le seed a réussi | le seed a échoué — à diagnostiquer
|===

Un seed raté en prod DOIT être rouge (le masquer serait absurde) ; un test CI qui _vérifie_ le
chemin d'échec doit être vert. C'est le même code de scénario, statut de sens opposé. Le POC assume
le rouge comme fidèle en mode moteur (P2 : « le pipeline s'est arrêté sur l'erreur, le runbook
montre où »), et n'obtient un `@Test` vert pour P2 qu'au sens CI (« j'ai reproduit l'arrêt
attendu »), en pilotant le scénario programmatiquement.

=== E7 — jGiven DIFFÈRE la propagation d'un step qui échoue jusqu'à `finished()`

Un step qui jette n'est pas relevé à son call-site : jGiven enregistre le step `failed`, **saute les
steps chaînés aval (marqués SKIPPED, le fail-fast)** et ne propage qu'à `scenario.finished()`. Deux
conséquences mesurées : (a) un `assertThrows` autour du `when()` n'attrape RIEN — il faut envelopper
`finished()` ; (b) c'est ce qui rend le runbook de diagnostic ciblé — l'opérateur voit le step qui a
cassé et tous ceux non atteints. Rendu P2 réel :

[listing]
----
    the cluster becomes ready (failed)
        Given a reachable systemd adapter on "..." (passed)
        When the kubeconfig is published (passed)
        And the API is ready (failed)                       ← la rupture
        And the required controllers are effective (skipped) ← fail-fast
        Then the cluster reports a ready handoff (skipped)
----

Corollaire de rendu : le reporter texte de surefire n'imprime que les scénarios joués par le
`ScenarioTest` lui-même ; un scénario piloté programmatiquement doit imprimer son propre modèle
(`PlainTextReporter.toString(reportModel)`).

=== E8 — La couche d'orchestration doit être `@Hidden` + `@NestedSteps`

Le `When` qui séquence les phases porte des méthodes-relais. Si elles rendent comme des steps, elles
_re-narrent_ la phase → double titre. Les rendre `@Hidden` (retire le relais du rendu) +
`@NestedSteps` (promeut le contenu de la phase d'un cran) donne un nœud unique par phase — et en
prime le `@As` riche de la phase avec ses arguments (`the incus instance "bioskop-master" is
provisioned`) plutôt que le nom de méthode nu du relais. Règle : l'orchestrateur est transparent, la
phase est le nœud visible.

=== E9 — Le preview riche s'obtient en découplant le RENDU de l'EXÉCUTION (pas par dry-run)

Racine, mesurée au bytecode : **jGiven couple le rendu à l'exécution.** `doIntercept` retourne tôt —
SANS appeler `invoker.proceed()` — dès que le mode d'invocation est SKIPPED _ou_ PENDING. Donc tout
mécanisme qui saute les corps (la propriété `jgiven.report.dry-run`, un `disableMethodExecution()`,
un `setDefaultInvocationMode(PENDING)`) saute aussi la **construction de l'arbre** : un
`@NestedSteps` dont le corps ne tourne pas ne bâtit jamais son sous-arbre. Le plan sort **vide** (et
avec les relais `@Hidden` de E8, entièrement vide). Le dry-run naïf ne peut donc PAS rendre un
preview riche — c'est le cousin de E1.

*La sortie, trouvée et vérifiée dans le POC :* séparer _exécuter_ de _comment rendre_. Le seul seam
natif « exécute ET marque » est `@Pending(executeSteps=true)`, mais il est statique (par méthode,
pas un mode runtime). On obtient l'équivalent **au runtime** avec un `PreviewExecutor` qui
**décore le `ScenarioListener`** que l'exécuteur installe (`ScenarioBase.performInitialization`
appelle `executor.setListener(modelBuilder)`) : l'intercepteur garde son mode local NORMAL — donc il
`proceed()`, l'arbre entier se construit contre des probes inertes — mais le mode qui ATTEINT le
modèle est réécrit `NORMAL → PENDING`. Rendu P3 obtenu : le plan complet (7 phases, les 3
réservations bbox, le G/W/T readiness imbriqué), chaque step marqué `(pending)`, zéro traversée.

*Portée :* P3 n'est donc PAS le point faible qu'on craignait — le preview riche est atteignable, à
condition de rebrancher le rendu sans toucher l'exécution. C'est aussi une leçon méta : jGiven
sépare proprement _modèle / exécution / rendu_, ce qui a permis chacune de nos adaptations (E5, E8,
E9) par extension publique, sans réflexion sale ni fork — ce qui conforte la décision « pas de
moteur BDD maison ».

=== P2 vs P4 — symptôme métier vs panne d'infrastructure (la distinction P4)

Les deux s'arrêtent au même endroit visuel, mais de nature opposée, et le bench les sépare par le
**type** de l'arrêt :

* *P2 (symptôme)* — le probe RÉPOND « non » : `Observation.failed(symptom, …)`, le step lève une
  `AssertionError` métier. « L'autre monde dit que ça va mal. »
* *P4 (transport)* — le probe ne peut pas RÉPONDRE : il lève une `TransportException`
  (infrastructure). « Je n'ai pas pu joindre l'autre monde. »

Le test P4 assère que la cause-racine de l'arrêt est bien `TransportException`, PAS `AssertionError`
— la garantie que l'opérateur lira « injoignable », pas « refusé ». C'est le piège que la spec
nommait : ne pas confondre les deux échecs.

=== E10 — L'arête cross-monde : greffe du `ScenarioModel` distant en sous-arbre + propagation du statut

Un `@NestedSteps` ne traverse pas deux realms (deux moteurs, deux `ReportModel`). Le spike prouve le
*step-passerelle* : le monde distant (doctor/readiness OSGi) joue son scénario dans SON `ReportModel`,
et le monde appelant (host) le **greffe** dans le sien. Mécanique mesurée (le transport JSON par la
gateway — `Document` + codec — est déjà prouvé dans la codebase, donc _pas_ re-testé ici) :

* *Greffe en sous-arbre (E5 à travers la gateway) :* les `StepModel` du scénario distant deviennent
  les `nestedSteps` du step-passerelle host via `StepModel.addNestedStep`. Le reporter rend
  `getNestedSteps()` quelle qu'en soit l'origine → l'opérateur lit UN arbre continu, du seed jusqu'à
  la racine OSGi. (Pas `addScenarioModelOrMergeWithExistingOne`, qui donnerait un scénario _frère_ à
  plat — cf. E4.)
* *Propagation du statut (P2 à travers la gateway) :* le verdict voyage DANS le modèle —
  `remoteScenario.getExecutionStatus()`. Si le distant est `FAILED`, la greffe marque le
  step-passerelle `FAILED` et met les steps host aval en `SKIPPED` : le fail-fast local, reproduit à
  travers la frontière. Un « non » distant arrête le pipeline host exactement comme un « non » local.

*Réponse à la question ouverte de la spec (un ou deux Documents ?) :* **un seul suffit.** Le
`ScenarioModel` porte à la fois la narration (les steps → le sous-arbre) ET le verdict
(`executionStatus` → la propagation). Pas besoin d'un Document séparé pour le statut : il est déjà
dans le modèle qui traverse.

== Ce que le POC NE fait PAS

Pas de `pulumi up`, pas de migration OSGi des topics host-couplés, pas de suppression de la
grammaire fluent existante, aucune modification de `ClusterSeedPipeline` ni d'aucun code de prod.
Maquette à côté, dans `bench/`, pour décider — puis jetable.

== Le verdict — GO (2026-07-04)

On a regardé la forme (A) et le runbook (B) sur les 4 chemins, et on a tranché les trois questions
laissées ouvertes :

* *L'approche BDD-comme-moteur est-elle viable / désirable ?* → *OUI.* La transposition ClusterSeed
  entière compile et rend un runbook honnête sur les 4 chemins ; les 3 hooks Jupiter épousent le
  besoin (E9 prouve même que jGiven sépare proprement modèle / exécution / rendu, ce qui a permis
  chaque adaptation par extension publique — pas de moteur maison).
* *Garde-t-on RunMode ?* → *NON, dissous.* RunMode devient une `ExecutionCondition` + le
  `PreviewExecutor` (E9) ; `LiveGate` est effacé. Le tag `wip/runmode-absorbs-livegate` est
  *abandonné* (il présupposait un `LiveGate` à absorber, qui n'existe plus).
* *La grammaire fluent disparaît-elle entièrement ?* → *OUI.* jGiven compose tout (`@NestedSteps` +
  intro-words) ; aucun ordonnanceur mince ne mérite de subsister — le launcher JUnit porte
  l'orchestration, le DAG de valeur est porté par les scenario-states + un gate build-time.

*La suite (gravée dans le plan de migration) :* un cleanup de légibilité du réseau de specs
d'abord, puis la migration ClusterSeed-verticale, une pipeline à la fois, les 6 autres coexistant
sur Topic/State. Ce document est désormais un record de référence ; la spec courante est
link:pipeline-spec.adoc[pipeline-spec] (le modèle BDD-as-engine y est le contenu primaire).
