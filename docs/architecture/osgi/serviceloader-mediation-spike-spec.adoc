= ServiceLoader mediation — a targeted spike on the cdk8s carrier
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DRAFT / SPIKE (2026-07-22). A *falsifiable, time-boxed* probe, not an
architecture decision. It asks one question and answers it with running code:

[.text-center]
*Can OSGi ServiceLoader mediation (Apache Aries SPI-Fly) retire the `lib:=true`
nesting of `jackson-datatype-jsr310` AND the TCCL pin in `Cdk8sApps` — on the
single `manifests-cdk8s` carrier — without reintroducing the "one `Module` view"
regression?*

If the spike confirms, a follow-up decides whether to generalise (the two-tier
model). If it falsifies, the current "general shape" (nest + TCCL, see
link:realm-library-isolation-spec.adoc#follow-up[realm-library-isolation §
follow-up]) stands, now with a recorded reason.
====

== Why this spike exists

The seeding runtime does three distinct `java.util.ServiceLoader` lookups
(`FrameworkFactory` on the host, the dbus transport in the systemd edge, and the
jackson `Module` discovery under `manifests-cdk8s`). Only the third one is
painful, and it is the reason for this spike.

`jsii-runtime`, nested in the `io.seedmatic.rke2lab.manifests.cdk8s` carrier, builds
an `ObjectMapper` and calls `findAndRegisterModules()`, which runs
`ServiceLoader<com.fasterxml.jackson.databind.Module>`. `ServiceLoader` reads
`META-INF/services` off the *thread-context classloader*, not through OSGi package
wiring. Two consequences shaped the current design:

* *Discovery* — the provider (`jackson-datatype-jsr310`) is only found if it sits
  on a classloader the consumer's `ServiceLoader` scans.
* *Class identity* — the discovered `JavaTimeModule` must `extend` the *same*
  `Module` class the `ObjectMapper` uses, or jsii fails with "JavaTimeModule not a
  subtype".

The current answer forces *both* by nesting jsr310 whole (`lib:=true`) on the
carrier's classpath and pinning the TCCL to the carrier in `Cdk8sApps.create`.
It works, but it costs a duplicated jar (jsr310 is a genuine bundle elsewhere) and
an invasive `Cdk8sApps` wrapper that exists *only* for this.

**The insight the spike tests.** OSGi 133 (Service Loader Mediator) splits the
problem in two halves, and *both* halves are needed here:

[cols="1,3", options="header"]
|===
| Half | What it does for us

| *Registrar* (provider side)
| Reads a provider bundle's `META-INF/services` and registers each provider as an
  OSGi service. Applied to `jsr310` → its `JavaTimeModule` becomes a service.

| *Mediator* (consumer side, bytecode weaving)
| Weaves the consumer's `ServiceLoader.load(Module.class)` so it consults the OSGi
  *registry* instead of its own classloader. Applied to the jsii call site.
|===

*Discovery* is then handled by the mediator (registry lookup, no shared loader).
*Class identity* is handled by ordinary package wiring: if the jsr310 provider
bundle AND the carrier both `Import-Package` `com.fasterxml.jackson.databind` from
the *one* databind bundle, there is a single `Module` class — the nesting was only
ever a way to force that shared view. So *both* the nesting and the TCCL pin should
become removable. That is the falsifiable claim.

== Figure 3 — C4 Container (APRÈS: SPI-Fly mediated)

The spike target. `jsr310` is a *proper provider bundle* (re-wrapped to advertise
the `osgi.serviceloader` capability); the carrier opts into the *processor*
extender; SPI-Fly registers the provider and weaves the consumer. The carrier no
longer nests jsr310, and `Cdk8sApps` is a plain `new App(props)` — no TCCL.

== Scope — exactly what the spike touches

[cols="1,3", options="header"]
|===
| Change | Detail

| Install SPI-Fly
| Add `org.apache.aries.spifly.dynamic.bundle` (+ its asm) to the framework launch
  closure, started *before* the `io.seedmatic.rke2lab.embed` model carriers.

| Wrap `jsr310` as a provider bundle
| A bnd-wrapped `jackson-datatype-jsr310` carrying
  `Provide-Capability: osgi.serviceloader; osgi.serviceloader=com.fasterxml.jackson.databind.Module`
  and `Require-Capability: osgi.extender; filter:="(osgi.extender=osgi.serviceloader.registrar)"`,
  importing `com.fasterxml.jackson.databind` from the databind bundle.

| Opt the carrier into the mediator
| Add `Require-Capability: osgi.extender; filter:="(osgi.extender=osgi.serviceloader.processor)"`
  (+ the `osgi.serviceloader` requirement naming `Module`) to
  `manifests-cdk8s/bnd.bnd`. Prefer the header over the `@ServiceConsumer`
  annotation — the consuming call site is third-party (jsii), un-annotatable.

| Remove the nesting
| Drop `jackson-datatype-jsr310-*.jar;lib:=true` from the carrier
  `-includeresource`.

| Remove the TCCL pin
| Replace `Cdk8sApps.create(props)` with `new App(props)` at all call sites and
  delete the wrapper.
|===

*Explicitly OUT of scope:* the dbus-systemd edge (self-contained, no gain), the
`seed-broker-codec` path (registers modules explicitly, no ServiceLoader),
`FrameworkFactory` (host classpath, outside Felix), and the host-flat realm
(SPI-Fly is framework-only — synthesis runs in-framework, so unaffected).

== Hypotheses & success criteria

The spike PASSES iff all three hold, verified by running `manifests-cdk8s` synthesis
in-framework:

* *H1 — discovery.* With SPI-Fly installed and jsr310 wrapped, the woven
  `findAndRegisterModules()` picks up `JavaTimeModule` from the registry (an
  `Instant` field serialises; no "not a subtype").
* *H2 — nesting removable.* The build resolves and synthesis still passes with the
  `jsr310` `lib:=true` line deleted from the carrier.
* *H3 — TCCL removable.* Synthesis passes with `new App(props)` directly and the
  `Cdk8sApps.create` wrapper deleted.

Any failure is a *result*, not a defeat: record which hypothesis broke and why
(weaving missed the nested jsii class / boot order / class identity still split).

[[risks]]
== Risks / new failure modes

* *Boot order (principal risk).* The mediator's `WeavingHook` must be registered
  before `JsiiObjectMapper` is first loaded. If the `io.seedmatic.rke2lab.embed` scan
  installs and activates carriers before SPI-Fly, the `load()` call is never woven
  and falls back to the JRE scan — a *silent* failure, not an exception. The spike
  must assert weaving happened (e.g. SPI-Fly debug log, or a deliberate negative
  control with the provider absent).
* *Weaving a nested third-party class.* `JsiiObjectMapper` is loaded from the
  carrier's `Bundle-ClassPath` (nested jar). The spike must confirm SPI-Fly weaves
  classes loaded via the carrier loader when the *carrier* declares the processor
  requirement — not only top-level bundle classes.
* *asm version clash.* SPI-Fly bundles asm; verify no conflict with any asm already
  in the framework closure (the embed scanner uses asm at build time, not runtime —
  check the runtime closure).
* *Uniformity debt.* A pass makes `manifests-cdk8s` diverge from the documented
  "general shape". That divergence is acceptable *only* as a spike; generalising it
  is the follow-up's decision, not this spike's.

== Anti-patterns this spike must avoid

* ❌ *Half-adoption* — wrapping jsr310 as a provider but keeping the TCCL pin. That
  adds SPI-Fly for no gain and still reintroduces nothing. The provider wrap is
  worthless without the mediator weaving the consumer.
* ❌ *Assuming global weaving* — SPI-Fly weaves only bundles that *opt in* via the
  processor requirement. It does not rewrite every `ServiceLoader.load` in the
  framework.
* ❌ *Touching the dual-realm staging rules* — the "one Module view" here is bought
  by databind package wiring, not by changing how realms are staged.

== Rollback

Revert three edits (SPI-Fly install, jsr310 wrap, carrier `bnd.bnd`) and restore
`Cdk8sApps.create`. The nest + TCCL shape is the fallback and remains the
documented general shape until a follow-up says otherwise.
