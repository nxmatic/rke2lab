= The manifests scion — synthesis played through the broker
:toc:
:toclevels: 3

== Overview

The manifests domain synthesizes the node's material — the K8s manifests, the
systemd units, the rke2 config, the env-config overlay — from CDK8s units and node
contributors. Today that synthesis (`ManifestSynthesisService`) survives OSGi-side
but is driven by nobody in the seed flow: the host cannot resolve it by type across
the realm boundary, and doing so would be the realm-boundary anti-pattern (see
link:../bootstrap/provisioning-slice-architecture.adoc[the incus-bootstrap constat]
§ corroboration). This spec designs the missing piece: **`manifests-bdd`, the
manifests scion**, played in-container through the broker like bbox/incus/systemd/
cluster — the "graft cultivated fresh" the ClusterSeed map already names.

It is the fifth scion, on the exact trio pattern the four shipped ones share
(`*Scenario` + `*RunbookHandler` + `*BddScenarios`), with three differences its
nature forces — spelled out below so the implementation does not blindly copy bbox.

== What makes the manifests scion different from the four others

[cols="1,2,2",options="header"]
|===
| Concern | The four contact scions (bbox/incus/systemd/cluster) | The manifests scion

| The gesture
| *probe/reconcile* an external system (router, incus, dbus, kube-API) — read or
  converge live state
| *synthesize + materialize* files — pure generation into an output tree, touching
  no live system

| The input
| enumerated from a static blueprint (bbox rows) or fixed markers; the scion holds
  its own desired state
| the operator's per-domain *activation choice* (`mesh` on/off, `cluster-api` on/off)
  — which must arrive from the host, in the trigger

| The doctor
| consults on trouble (a refused row, an unreachable instance) — runtime symptoms
| *no consult* — a synthesis failure is a build defect (a missing unit, a bad
  template), surfaced as a failed step, not a medical symptom
|===

== The one config path — the sow trigger (general, manifests is the first consumer)

This is the crux, and it is bigger than manifests: it is THE single path by which
any policy reaches any scion. The rule (user decision): **one config path, and every
policy reachable through it.**

=== What exists today (the audit)

* The four shipped scions (bbox/incus/systemd/cluster) have **no policy config path
  at all**. They resolve only the ambient `RunGate` (the whole-run live/preview
  fact) and their contacts + the doctor, all from the registry. Every `handle(trigger)`
  **ignores its trigger** — the sow trigger is empty (`"{}"`) today.
* Manifests has TWO parallel paths that both produce `ManifestDomainPolicy` from two
  vocabularies — a duplication that drifts:
+
[cols="1,2,1",options="header"]
|===
| Path | Input → translation | Used by
| system properties | `-Drke2lab.manifests.policy.enabledDomains=…` →
  `ManifestSynthesisRequest.fromSystemProperties()` | `manifests-cli`
| host Pulumi config | `manifests.publish` sub-map → the `publish` facet → the scion
  derives `ManifestDomainPolicy` (+ `RKE2LAB_MANIFESTS_PUBLISH_*`) | seed
|===
* The host policies that WOULD target other scions (`ReadinessPolicy`,
  `PreviewPolicy` → cluster/systemd) are wired to NOTHING — neither the old nor the
  new path carries them.

So there is no unified path; there is one duplicated path (manifests) and several
dead-ends. The scion work installs the single path.

=== The single path — one file, the shape carves each soil's facet

The one source of truth is a PHYSICAL file: `Pulumi.dev.yaml`. It is already read by
ONE reader, `ConfigLoader`, abstracted from its source through a `SectionReader`
seam — the seed reads it live (`ConfigLoader.of(com.pulumi.Config)`, inside
`Pulumi.run`), and any off-Pulumi caller reads the SAME file parsed to a map
(`ConfigLoader.ofNestedRoot(yaml)`). So "one config path" is not an invented
in-memory policy threaded through `SeedRun`; it is the file both realms' callers
already point at, through the one reader.

The config is organised **by concern**, not by soil. The manifests concerns live under
`rke2lab:manifests` — `publish`, `debug`; the remaining policy concerns (`network`,
`readiness`, `preview`) stay under `rke2lab:policy`. The concern grouping is the operator's
natural vocabulary, and the seed reads each verbatim into typed DTO records (plain
`Optional<Boolean>` keyed by camelCase — NO manifests type named). The soil→facet mapping
does NOT live in the file; it is carried by the *shape* (below), so the file never needs a
by-soil reshuffle.

.Figure 2 — one file (by concern), the shape carves each soil's facet, one channel
[mermaid]
----

  yaml["Pulumi.dev.yaml<br/>rke2lab:manifests: publish · debug<br/>rke2lab:policy: network · readiness · preview"]
  loader["ConfigLoader — one reader, source-abstracted<br/>seed: of(Config) · CLI: ofNestedRoot(yaml)"]
  yaml --> loader
  loader --> sower["a sower toward soil S<br/>(seed WHEN or manifests-cli)"]

  trig --> scion["S's scion — reads its facet, translates in its OWN vocabulary"]

  classDef src fill:#dfd,stroke:#2a2,stroke-width:2px;
  classDef ch fill:#eef,stroke:#55a,stroke-width:2px;
  class yaml,loader src;
  class sower,shape,trig ch;
----

. **One source of truth — the file, one reader.** `Pulumi.dev.yaml`, read through
  `ConfigLoader`. The seed binds it live via Pulumi; the CLI parses the same file to
  a map and feeds `ofNestedRoot`. Neither caller invents a policy shape; both read
  the operator's file.
. **The shape carves the facet — no host names a domain vocabulary.** A soil's facet
  is NOT a sub-map the caller knows a priori; it is DISCOVERED:
  `sow(ShapeCoordinate(S), {})` reaps S's runbook-input schema, whose top-level
  properties ARE the concern keys S owns (`manifests` → `publish`, `debug`). The caller
  plucks exactly those concern sub-maps from the yaml `manifests` section and assembles
  the trigger. Generic — the sower names NO domain vocabulary; the schema dictates
  which concerns to pluck. This is why the concern grouping needs no by-soil sealing
  in the file: the sealing lives in each soil's wire-record (which concerns it
  declares), reviewed in one place, not in the yaml's shape.
. **One channel — the sow trigger.** The plucked concerns become the trigger
  `SeedEnvelope` payload (today `"{}"`). A soil whose schema names no concern gets
  `{}` — exactly today's behavior, so the four shipped scions are unaffected until
  they grow a wire-record. This is a `seed-bdd` change (`Gardening.sow` /
  `SowAndGraftStage` stop sending empty), not manifests-only.
. **One translator per domain — the scion.** Each scion reads its own facet in
  `handle(trigger)` and translates it in its OWN vocabulary. The manifests scion
  owns `ManifestDomainCatalog` + the `RKE2LAB_MANIFESTS_PUBLISH_*` naming, so it derives
  `ManifestDomainPolicy` + `FloxDebugPolicy` + the publish-time seed vars from the
  `publish`/`debug` concerns. A scion sees ONLY its facet, never another soil's config.

**Consequences.** `fromSystemProperties()` dissolves — the CLI reads the same file
as the seed, through the same reader. Both host policy classes are GONE (deleted at
`1f7c1ee54`): `ManifestLinkPolicy` (whose sole job was translating the raw booleans
into `ManifestDomainPolicy` + `toEnvMap()`) AND `ControlplanePolicy` (the aggregate
that held it) were orphaned live logic with no production caller, and the translation
now lives OSGi-side in the scion. The scion derives BOTH `ManifestDomainPolicy`
(synth-time filter) and the `RKE2LAB_MANIFESTS_PUBLISH_*` seed vars (publish-time overlay)
from its own `publish`/`debug` facet — it owns `ManifestDomainCatalog` + the
`RKE2LAB_MANIFESTS_PUBLISH_*` naming, so no host type names `manifests.contract` (the gate
is clear, and LOCKED at ERROR). The scion's facet is defaulted today
(`ManifestsRunbookInput.defaults()`); the host does not pilot it (a decision, not a
gap — the policy is a manifests concern, not a host one). `readiness` / `preview`
were always separate concerns (they lived on the now-deleted host policy); they stay
raw in the config (the residual `rke2lab:policy` section / `ReadinessConfig`) and belong
to a cluster/doctor scion the day it grows a wire-record, not to the host.

*Design constraint this puts on piece 2 (the wire-record).* For the pluck to stay
generic, the runbook-input wire-record's top-level component names MUST equal the
yaml concern keys (`publish`, `debug`) — the schema's top-level properties ARE those
component names, and the caller plucks `manifests.<name>` for each. So the wire-record
nests (`record …(PublishFacet publish, DebugFacet debug)`), mirroring the yaml's concern
nesting exactly, rather than flattening into one bag.

=== The policy has TWO ends — the scion must cover both

The activation choice does not stop at "which domains synthesize". It drives a path
with two distinct ends, and the scion owns BOTH:

[cols="1,2,2",options="header"]
|===
| End | What it decides | Where it lives today

| *synth-time* | which domains are *synthesized* — `ManifestDomainPolicy` filters
  the domain registry (`applyManifestDomainPolicy`), resolves inter-domain deps,
  rejects an all-disabled set
| in-container (manifests-core) — correct already

| *publish-time* | which layers the master *publishes live* — the `RKE2LAB_MANIFESTS_PUBLISH_*`
  env vars written into the `99-…env-config` overlay
  (`NodeEnvOverlayService.writeControlplaneOverlay(seedVariables)`), read by
  `rke2lab-manifests-install.sh` and the per-layer `*-ready.sh` gates on the master
| **in-container** — the scion derives the vars from its facet and writes the overlay
|===

Both ends derive from the SAME operator choice, and the scion covers both:

* from its facet (the `manifests` sub-map of the one policy, § the single path), the
  scion derives BOTH the `ManifestDomainPolicy` (synth-time filter) AND the
  `RKE2LAB_MANIFESTS_PUBLISH_*` seed variables (publish-time overlay) — it owns the
  `RKE2LAB_MANIFESTS_PUBLISH_<X>_ENABLED` naming, so this is legitimate in-container;
* the scenario's synthesis step drives `writeControlplaneOverlay` with those
  seed variables, so the `99-…` overlay lands with
  the right `RKE2LAB_MANIFESTS_PUBLISH_*` — the master's install/ready scripts see exactly
  what they need (the founding rule: invisible at the master frontier).

This is why the scion is the natural home: it is the single point that already knows
the catalog, and it can satisfy both ends from one payload without any host type
naming a domain vocabulary.

==== The scion owns both ends — the policy IS the synthesis input

The activation choice drives synthesis structurally, not by promise:
`ManifestSynthesisRequest` carries `manifestDomainPolicy` + `floxDebugPolicy` as
FIELDS — synthesis does not run without them. The scion derives both from its facet
(the `publish`/`debug` concerns) and calls `synthesize(request)`, so the policy IS the
synthesis input, not something computed beside it. It owns `ManifestDomainCatalog` +
the `RKE2LAB_MANIFESTS_PUBLISH_*` naming, so no host type names `manifests.contract`.

Both ends are covered in one place:

* *synth-time* — `ManifestDomainPolicy` filters which domains synthesize;
* *publish-time* — the scion writes the `RKE2LAB_MANIFESTS_PUBLISH_*` overlay
  (`writeControlplaneOverlay` → the `99-…env-config` ConfigMap). On the master those
  vars are sourced into the systemd env, and `rke2lab-manifests-install.sh <layer>`
  reads `RKE2LAB_MANIFESTS_PUBLISH_<LAYER>_ENABLED`: an enabled layer is STOWED (its
  non-local-config manifests `ln -sfn`'d into rke2's server manifest dir, where rke2
  auto-applies), a disabled one has its target removed. `rke2lab-layer-ready.sh` gates
  readiness on the same flag. The operator's choice made live — invisible at the
  master frontier (the founding rule).

The former host-side projection of this (the deleted `ManifestLinkPolicy`/`ControlplanePolicy`)
is gone; its logic is this scion's, driven by the sown facet.

=== Scope — which of the host policies this scion absorbs

The operator's policy has several concerns; not all route to manifests. This scion
owns the two that are manifests' business; the rest live elsewhere:

[cols="1,2,1",options="header"]
|===
| Policy concern | What it decides | Destination

| *publish* (the publish concern) | which domains synthesize + which layers publish live (the two-ended
  path above) | *this scion* (activation payload)
| `DebugPolicy` → `FloxDebugPolicy` | per-layer debug (flox NRI / mesh / networking
  image-command-env swap) — already a `manifests.contract` input of
  `ManifestSynthesisRequest` (`floxDebugPolicyFromSystemProperties`) | *this scion*
  (debug facet of the payload)
| `NetworkPolicy` (lanBinding) | host-side Incus provisioning (the Pulumi graph) | stays host
| `ReadinessPolicy` (raw severity overrides) | readiness verdict — cluster/doctor
  vocabulary; the host already carries it raw ("hands the raw value to the OSGi-side
  handler") | a *cluster/doctor* scion, not this one
| `PreviewPolicy` (raw fault simulation) | preview-only fault injection —
  cluster/doctor vocabulary, raw | a *cluster/doctor* scion, not this one
|===

So the manifests activation payload has TWO facets — *activation* (which domains,
from the *publish* facet) and *debug* (per-layer, from `DebugPolicy`→`FloxDebugPolicy`).
Both are already `manifests.contract` concepts; the scion assembles them from the
sown payload. `ReadinessPolicy`/`PreviewPolicy` are a separate transposition (a
cluster/doctor scion), out of scope here — noted so their host records are not
mistaken for dead when the manifests policies dissolve.

== The scion trio

Mirrors bbox's trio (link:bbox-edge-spec.adoc[bbox-edge-spec]), adapted:

=== `ManifestSynthesisScenario` (the `*Scenario`)

A production jGiven scenario in the MANIFESTS domain's vocabulary. Resolves its
collaborators from THIS bundle's registry (`FrameworkUtil`): the
`ManifestSynthesisService` (the SCR-published synthesis). MODE-BLIND — it injects no
`RunGate`: manifests is a pure FS materializer with no live touch (no
`Cultivating`/`Surveying` pair), so it runs identically in both modes. The
materialization target is carried by the SOIL amendment alone (the real staging tree
when the host amended a plot, a temp dir for a bare survey); rendering the run PENDING
under a surveying gate is the frontier's business (the engine's survey executor), not
the scenario's — the preview inertness the map requires, lifted out of the scenario.

[listing]
----
GIVEN the activation payload (which domains the operator enabled)
  AND the synthesis service, resolved from this bundle's registry
WHEN the policy is derived from the payload          [the scion builds BOTH ends: ManifestDomainPolicy + the RKE2LAB_MANIFESTS_PUBLISH_* seed vars]
  AND the manifests are synthesized                  [service.synthesize(request) → the K8s/systemd/rke2-config tree, filtered synth-time]
  AND the controlplane overlay is written             [writeControlplaneOverlay(seedVars) → the 99-… env-config with RKE2LAB_MANIFESTS_PUBLISH_*]
THEN every enabled domain produced its units         [domainCount matches the enabled set]
  AND the materialized tree is complete               [manifestFile + systemdUnitsDir exist, hit count > 0]
  AND the overlay carries the publish-time policy      [RKE2LAB_MANIFESTS_PUBLISH_* match the enabled set — what the master's scripts read]
----

No doctor consult. A synthesis `IOException` or an empty domain set fails the step —
jGiven marks it, the runbook shows the failure. The output tree location is the
run's `outdir`, chosen by the SOIL amendment alone (blank SOIL — a bare survey: a temp
dir; an amended SOIL: the staging slot incus PREPARE chose, later promoted to
`host.live.d` and mounted); the only surviving replace-trigger is the
nocloud→`replaceOnChanges` wire, NOT the removed `TargetChecksumPipeline` — see
host-cellar § the-grow-anatomy). The two synthesis
beats (units tree + controlplane overlay) are the two policy ends above: the scion
drives both, so a single sow produces the complete master material.

=== `ManifestsRunbookHandler` (the `*RunbookHandler`)

Identical shape to `BboxRunbookHandler`: `@Component(service = SeedHandler.class)`,
serves `RunbookCoordinate("manifests")`, and `handle(trigger)` plays the scenario
in-container via `ManifestsBddScenarios.run(trigger)`. THE one difference: it reads
the activation payload off `trigger.payload()` and threads it into the run (bbox's
handler ignores the trigger; this one needs it).

=== `ManifestsBddScenarios` (the `*BddScenarios`)

The in-container front-door, twin of `BboxBddScenarios`: `JUnitLauncherCore` with an
explicit `selectClass(ManifestSynthesisScenario)`, returning a `RunbookEnvelope`
(runbook JSON + empty consultations — the manifests scion consults no one) as one
serialized String across the realm boundary. It accepts the activation payload and
seeds it where the scenario reads it (a registry service or a scenario static, the
same scaffolding bbox uses for `lastRunbook`).

== Why this closes several deltas at once

* **The synthesis runs again** — driven as a scion, in-container, where SCR
  activation is normal (the `awaitService`-from-flat-host puzzle disappears).
* **`manifests-cli` becomes a sower** — it sows `RunbookCoordinate("manifests")`
  and names no contract type, so its `NoClassDefFoundError` (host→contract-flat)
  is gone by construction.
* **The five materialization targets get their trigger** (constat deltas #2–6) —
  the scion IS the trigger the demolition removed; the synthesis machinery it drives
  is intact.
* **The realm-boundary gate on the manifests policies falls** — the host stops
  naming `manifests.contract`; the choice travels as a sown payload.

=== Dependency — the CLI's schema discovery needs `shape`

.Figure 3 — the CLI sower: load the yaml, discover the shape, pluck, then sow
[mermaid]
----
sequenceDiagram
  participant CLI as manifests-cli (sower)
  participant Y as Pulumi.dev.yaml
  participant B as SeedBroker
  participant SH as ManifestsShapeReflector
  participant RH as ManifestsRunbookHandler
  CLI->>Y: ConfigLoader.ofNestedRoot(parse)
  Y-->>CLI: config sections (by concern)
  CLI->>B: sow(ShapeCoordinate("manifests"), {})
  B->>SH: route
  SH-->>CLI: JSON Schema of the runbook input (opaque String)
  Note over CLI: schema top-level = {publish, debug} → pluck those concerns from the yaml
  CLI->>B: sow(RunbookCoordinate("manifests"), {publish:{…}, debug:{…}})
  B->>RH: route
  RH-->>CLI: runbook JSON
----

Two couplings dissolve here, and they are the SAME move. A sower that KNOWS the
payload shape a priori is coupled to the wire-record; a sower that reads config from
its OWN vocabulary (system properties) is coupled to a second source of truth. The
shape closes both: the CLI reads the operator's `Pulumi.dev.yaml` (one file, § the
single path) and asks the broker "what config do you want for the manifests runbook?"
(`sow(ShapeCoordinate("manifests"), {})`). The reaped schema's top-level properties
name the concerns to pluck (`publish`, `debug`); the CLI plucks exactly those from the
yaml `manifests` section and sows the runbook — naming no manifests vocabulary, holding
no contract class.

For this the `shape` meta-coordinate must be realized (foundation piece 1 — SHIPPED,
`ShapeCoordinate` + `RecordSchemaProjector`, see
link:seed-broker-spec.adoc#shape-realization[seed-broker-spec § realization status]).
Piece 2 (a `@SeedContract("runbook")` input wire-record + a `ManifestsShapeReflector`
projecting it) gives the runbook input its typed home — its top-level components ARE
the yaml concern keys (design constraint above), so the pluck stays generic. Until
piece 2 ships the shape is known a priori (a temporary coupling, not the end state).
