==== Verdict — does it hold?

An honest reading of the three figures:

. *Monotone: yes.* No blue box or arrow is erased or rewired from A to B, or within C. Every change
  is an addition. The HealthSystem model is additive against the whole constellation.

. *Two honest edits (changes, not deletions):*
.. `Generalist` gains a held `ClinicalAccess` (it held registry + patient before). That is a *changed
   collaborator*, but the read core it ultimately calls is unchanged — the wrap is real, not a
   rewrite.
.. `LiveMedicalRecordRegistry.cohortFor` loses its `@Spike` marker on promotion. A marker strip, not
   a logic change.

. *The explorations gain seams, lose nothing:* the what-if planner now has a concrete patient-record
  provider (the HealthSystem), and the rules-engine / referral work has the named grant seam to plug
  into. The keystone does not merely sit beside the explorations — it makes them more buildable.

. *The one not-yet-proven edge* is the amber dashed "grant seam awaits referrals". It is proven only
  when step 2 plugs referral-derived grants into the GrantPolicy. Everything else is solid today.

Conclusion: the constellation holds, and HealthSystem is additive.

=== Additivity proof: Referral round-trip (shipped 2026-06-13)

The referral round-trip flips the diagnosis seam from `diagnose(Symptom, Observation) →
Optional<Prescription>` (the why drops on `Optional.empty()`) to `diagnose(Referral) →
ReferralReply` (the why — an `Assessment` — ALWAYS survives, prescription or not). Four new types
(`Referral`, `ReferralReply`, `Assessment`, `SchemaRef`) plus a persisted-shape change
(`RemediationPlan` carries `List<ReferralReply>` not `List<Prescription>`, with `prescriptions()` as
a derived view). The changed collaborator (`Prescription.humanHint` shrinks to action-only; the
reasoning migrates into `Assessment`). Two exemplar specialists (`NetworkSpecialist`,
`ClusterSpecialist`) co-consult.

==== Verdict — does it hold?

An honest reading:

. *Monotone at the persisted-shape level: yes.* `RemediationPlan` carries a new collection (`replies`)
  and a derived view (`prescriptions()`) — the old `prescriptions` field is gone, BUT the persisted
  output map gains a `replies` key (additive) and loses nothing (the doctor predates any persisted
  remediation plan in the dev stack, so no real data is rewritten). `ConsultationReport` gains the
  `assessment` key under each reply in `plan.replies`, additive. The negative check: no other
  shipped box or serialized shape was rewritten; `Observation`, `Symptom`, `ConsultationReport`
  envelope, and all read/write paths for them are untouched.

. *One honest changed collaborator:* `Prescription.humanHint` shrinks from "reasoning + action" to
  "action only" — the reasoning migrates into the reply's `Assessment`. This is a changed
  collaborator, not an erased one. The `Prescription` box itself remains; only its content shifts.

. *The seam method signature changed* (`diagnose(Symptom, Observation)` → `diagnose(Referral)`), but
  both the `Specialist` box and all its existing collaborators (`Patient`, `Observation`, `Symptom`,
  `MedicalRecord`, `HealthSystem`) remain — the flip adds a request/response envelope, rewires
  nothing downstream.

. *Two fake exemplar specialists added* (`NetworkSpecialist`, `ClusterSpecialist`) to show the
  integration seams (treatment vs decline-with-why). These are NEW boxes, not rewrites.

Conclusion: the referral round-trip is additive. The seam flip is monotone; the one changed
collaborator (`Prescription.humanHint` shrink) is honest and isolated.

=== The world gateway — the seam speaks Documents; the host-side migration is the live transition

The contract-layer transition is *consumed*: the doctor seams speak `Document`, the records stay
OSGi-private, and the boundary is enforced at build by `REALM_BOUNDARY` + `SCHEMA_CONCORD` (both
`ERROR`). So the "seam speaks records → seam speaks Documents" before/after has collapsed into the
current state, below. The reasoning and the full type/coordinate detail are in
link:../osgi/seed-broker-spec.adoc[the world-gateway spec].

The one transition still LIVE is the *host side*: the residual `Severity.parse()` / `== CRITICAL` /
`toOutputMap` sites the host must shed, and the six `<coordinate>.schema.json` files not yet authored.
That is the before/after the atlas now carries.

NOTE: the earlier `DomainDagMultiplexor` / `DomainDagMapper` / `DomainDagAdapter` mechanism was never
implemented (it appears in no commit's `.java`); it was a whiteboard design, and records-as-contract
was built INSTEAD — not a transposition of it. Its former before/after diagrams described code that
never existed, so they are gone; what actually crosses the seam is the `Document` + per-coordinate
reader/codec detailed in link:../osgi/seed-broker-spec.adoc[the world-gateway spec].

=== Design scenarios — the doctor capabilities as DSL sentences

The doctor view predates the capability-anchoring device, so its design lived only in the inventory
prose and the two additivity verdicts. The third movement (see <<the-scenario-map>>) lifts those
facts into scenarios. GIVEN the shipped substrate, WHEN a model lands, THEN the capability AND its
additivity.

. *The doctor reconstructs a patient's medical record on demand* — `[playable]` blue +
.. GIVEN per-node diagnosis serialized into Pulumi (layer3 write-side)
.. WHEN the medical-record query API reconstructs the record on demand from the host Cellar/journal
.. THEN the doctor reads a patient's full history without an accumulator — AND the read substrate is
   additive over the write-side, nothing rewired.

. *Each node serializes its diagnosis; the runbook renders it back* — `[playable]` blue +
.. GIVEN the clinical vocabulary and the live record wired in (vocabulary-and-live-record, step 1)
.. WHEN layer3 write-side serializes per node and the read-side enriches the runbook
.. THEN every node's diagnosis round-trips into the operator's runbook — AND the render is additive
   over the existing runbook.

. *A per-run HealthSystem admits a patient through a credentialed gate* — `[playable]` blue +
.. GIVEN the `MedicalRecordRegistry` read core shipped
.. WHEN the HealthSystem keystone wraps it with a `GrantPolicy` + `ClinicalAccess` and employs the
   `Generalist`
.. THEN the doctor admits a patient only through a credentialed access gate — AND the read core is
   wrapped, never edited (the one honest collaborator swap: `Generalist` holds `ClinicalAccess`).

. *The doctor reads a cohort across patients* — `[playable]` blue +
.. GIVEN `LiveMedicalRecordRegistry.cohortFor` proven by live `pulumi preview` (cohort-correlation)
.. WHEN the keystone promotes `cohortFor` off `@Spike`
.. THEN the doctor correlates findings across a cohort — AND the promotion is a marker strip, not a
   logic change.

. *A diagnosis always carries its reasoning, prescription or not* — `[playable]` blue +
.. GIVEN the old `diagnose(Symptom, Observation) → Optional<Prescription>` seam (the why dropped on
   `Optional.empty()`)
.. WHEN the referral round-trip flips it to `diagnose(Referral) → ReferralReply`
.. THEN a declined diagnosis still carries its `Assessment` — the why always survives — AND the flip
   is additive at the persisted shape (`replies` key added, none removed); the one named collaborator
   shrink is `Prescription.humanHint` → action-only.

. *The doctor replays a what-if on observed plus hypothesis* — `[narrated]` amber +
.. GIVEN the HealthSystem as a concrete patient-record provider
.. WHEN the preview/what-if planner lands
.. THEN the doctor replays a diagnosis against observed-⊕-hypothesis state — AND it attaches to the
   keystone's grant seam, adding nothing to the read core.

. *Diagnosis-layer redundancy dissolves into a rules engine* — `[narrated]` amber +
.. GIVEN the diagnosis layer's checkpoint topology
.. WHEN the rules-engine exploration lands
.. THEN the redundant per-node diagnosis collapses behind a rules engine — AND the grant seam awaits
   its referral-derived grants (the single not-yet-proven edge).

. *A Drools specialist sits behind the Specialist seam* — `[narrated]` amber +
.. GIVEN the `Specialist` SPI seam
.. WHEN a Drools-backed network specialist is plugged in
.. THEN a rules-driven specialist co-consults behind the same seam — AND the seam is unchanged, the
   specialist is a new box.

*Coverage of this view:* 8 capabilities, 8 scenarios — complete per <<scenario-completeness>>. Five
playable-and-blue today (all shipped), three narrated-amber (the explorations not built).

=== The ritual — how this atlas stays alive

Reopen this atlas at the START of every design activity (doctor or another subsystem), before
writing a new model's spec:

. *Add the new model* as a green box in a fresh before/after pair (or extend Diagrams A–C).
. *Prove monotone:* confirm no existing box or arrow is erased or rewired. If you must erase one,
  STOP — the new model is not additive; rework the seam until it is, or record explicitly why a
  breaking change is justified.
. *List honest edits:* any changed collaborator (not just additions) is named in the verdict, as
  the two edits above are.
. *Write the scenarios:* for every capability the model adds (every row of the view's capability
  map), write the design scenario it stands for — GIVEN the constellation before, WHEN the model or
  term lands, THEN the capability holds AND additivity holds (nothing erased). See <<the-scenario-map>>.
. *Flip green→blue* when a model ships, and update its inventory status.
. *Update the inventory table* with the new model and its links.

This keeps "a well-integrated spec is the proof we are on the right path" a standing practice, not a
one-time exercise.

[[the-scenario-map]]
=== The third movement — the scenario map (the design DSL)

Additivity proves nothing is *broken*; the capability map proves each box *earns its place* by
licensing a sentence; the *scenario map* writes that sentence in full as a design scenario, in our
own Given/When/Then DSL. A capability-map row is only the THEN clause; the scenario adds the GIVEN
(the constellation as shipped) and the WHEN (the model or term that lands), and pairs the THEN with
its AND (additivity). The three clauses map one-to-one onto the ritual above:

* *GIVEN* — the constellation BEFORE (the inventory rows already blue).
* *WHEN* — the model or term this activity lands (the green box).
* *THEN* — the capability we can now say (the capability-map row), *AND* additivity holds (the verdict).

*playable / narrated is NOT a nature of the scenario — it is the state of its GATES.* A scenario's
path runs GIVEN → WHEN → THEN, and each clause is licensed by a box. A box is GATED by its horizon
colour: blue (shipped) = gate OPEN, green (the current design increment) / amber (horizon) = gate
SHUT. The tag is then DERIVED, never hand-maintained:

* *playable* — every box on the scenario's path is blue (all gates open). The THEN is a fact
  re-derivable from the reactor today (a module exists, a capability is exported, the walker is gone,
  the unit count). Marked `[playable]`.
* *narrated* — at least one box on the path is still green or amber (a gate is shut). The scenario is
  ALREADY fully written — all three clauses are graved — it is only waiting for its gating boxes to
  ship. Marked `[narrated]`.

Every scenario is DESTINED to become playable; narrated is transitory, not a category. The ritual's
*flip green→blue* step (when a model ships) IS the act of opening a gate — it flips the scenario
narrated→playable automatically, by derivation. No scenario floats: a narrated scenario is moored to
the named green/amber boxes it waits on, so one can always point to exactly what must ship to make it
playable (see the worked example in <<unitrepo-view>>, scenario 3, where two named green boxes — a
concrete `UnitHandler` and load-from-store — are the shut gates).

This derivation is also the future guard's drift criterion, mechanical and judgement-free: a box is
blue but its scenario is still narrated → a gate was left shut (we forgot to flip); a scenario claims
playable but a box on its path is not blue → a gate opened falsely (a lie). Drift is no longer the
fuzzy "do we cover everything?" but the crisp "is each tag synchronized with the colour of its path's
boxes?".

Each per-subsystem view therefore carries a *Design scenarios* section: one scenario per
capability-map row, tagged playable/narrated (derived from its gates) and colored by horizon. The
link:../designer-runbook.adoc[designer's runbook] renders the playable ones live from the code; the
narrated ones it renders as prose until their gates open. The scenarios ARE part of the spec — not a
test artifact that lives only in Java.

[[scenario-completeness]]
==== The completeness clause (a standing rule)

The ritual is not done when the model is proven additive. *Every capability a view declares MUST
have a scenario, and every scenario MUST trace to a capability* — the two-way coverage test the
capability map already states ("a sentence with no enabling box is a design gap; a box licensing no
sentence is dead weight") is now extended to scenarios: a capability with no scenario is an
*uncovered* design fact; a scenario with no capability is a *stray*. The whole design is covered by
the DSL when every view's scenario map is complete. This is itself a re-entrance instance: the atlas
submits its OWN design state to the same "render it, do not let it drift" rule it imposes on the
operator's runtime state. The designer's runbook is the machine that will eventually *enforce* this
clause by replay; until then it is enforced by reading.

==== The answerability cascade — design → spec → plan → codebase

The completeness clause above is one link of a longer chain. Our delivery has four layers, and *each
layer must answer to the one above it* — be traceable up, and not invent down. This is the
superpowers shape (brainstorm/design → spec → plan → implementation), made explicit here so the
coverage test is the same at every seam:

[cols="1,2,2",options="header"]
|===
| Layer | Answers to the layer above by | Coverage test

| *design* (this atlas)
| —  (the root: the constellation + additivity + capability map)
| every box licenses a capability; every capability a box

| *spec* (the scenario maps, the per-subsystem docs)
| every capability has a scenario; every scenario traces to a capability
| <<scenario-completeness>> — the clause above

| *plan* (the increments, the WI breakdown)
| every planned increment realises one or more scenarios; no increment without a scenario
| a plan step with no scenario is scope creep; a scenario no plan touches is unscheduled design

| *codebase* (the reactor)
| every shipped slice flips a scenario playable-green; the designer's runbook replays it from code
| the designer-runbook's playable half — a green that no longer holds is drift, caught at render
|===

Read top-down it is generation (design licenses spec licenses plan licenses code); read bottom-up it
is answerability (code answers a scenario, a scenario answers a capability, a capability answers a
box). A break at any seam is the same failure the completeness clause names — an orphan one way, a
stray the other. The designer's runbook closes the bottom seam (code ⇄ spec) by replay; this atlas
closes the top seam (design ⇄ spec) by the scenario map; the plan seam (spec ⇄ plan) is closed by
each increment naming the scenario it lands. The whole chain is one re-entrance discipline applied at
four heights.
