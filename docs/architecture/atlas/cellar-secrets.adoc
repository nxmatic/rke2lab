= Cellar secrets & the clean/smudge filter (atlas L1)
:toc: macro
:toclevels: 3

⚠️ *Design Only.* The amendment channel, the `FACET` role, `ManifestsFacetContributor`, and
`PulumiCellar` (with its dummy passphrase) exist today. Everything this document adds — the unified
two-file operator input, the per-value *sensitivity attribute*, the cellar *clean/smudge filter*,
and the *recipient* model — is designed here and not yet implemented. The implementation sequence is
*foundation (this doc) → `bench-cellar` proof → live wiring on the master instance*. (There is no
production; there is one *live master* instance.)

toc::[]

== Overview — one channel in, one filter out

rke2lab feeds on two kinds of operator input — the Pulumi *stack config* and the *secrets* provided
in the worktree — which, once inside rke2lab, are **the same kind of information**: a decrypted
string. The git sops smudge already reveals the secrets when the worktree is materialised, so by the
time the seed reads them a secret is indistinguishable from config. This document settles how the
root scenario **unifies** them onto the one existing amendment channel, and how the *only* real
difference between config and a secret — that a secret must not be written in clear when it reaches
the **cellar** — is honoured by a **clean/smudge filter** modelled on git and refined by sops.

The model is not invented. It is git's `clean`/`smudge` idea (a declarative attribute + a filter at
one boundary, never a trace of derivations), applied to the cellar as a **second store at rest**,
and refined by what sops adds over plain git: field-level marking by declaration, and encryption
**for recipients** rather than under a single local passphrase.

== The vocabulary — three axes that never mix

The design blocked for a while on "what is the role of a secret versus config?". The resolution is
that the question conflates three orthogonal axes. Keep them apart and the block dissolves:

[cols="1,3",options="header"]
|===
| Axis | What it is

| *Coordinate* = the consuming domain
| `AmendCoordinate(domain)` names *who consumes* the input — `bbox`, `incus`, `manifests`. Not a
config-vs-secret axis. Constrained by the seed-broker BETA guard: a contributor's coordinate MUST
match a served `SeedHandler`, or the assembler throws.

| *Role* = the kind of provisioning input
| The neutral `Amendment` vocabulary — `FACET`, `SOIL`, `WORKTREE`, `IMAGE`. `FACET` is the
operator policy the host read once. A secret is **not a new kind**: it is part of the same `FACET`
subtree. There is deliberately **no `SECRET` role** — inventing one would confuse *sensitivity* (an
attribute) with *kind of input* (the role).

| *Sensitivity* = a per-value attribute
| A mark on an individual value, set **once by sops** (the sole authority — Pulumi's own `secure:`
provider is retired, see <<source>>). It rides *with* the value and is honoured only at the cellar.
Exactly the shape Pulumi's stack config already uses: a secret is a config key flagged `secure:`,
same namespace, one attribute — not a separate section or role.
|===

**Config and secrets are the same kind (`FACET`); they diverge only at the cellar filter.** That is
why the block felt intractable — it was a search for an *input* difference that does not exist; the
only difference is on *output*.

The root reads both operator YAML files, merges by coordinate into the `FACET` subtree, tags the

boundary, by coordinate.

== Store & fetch — clean / smudge

The `OpaqueCellar` never opens a payload, so the mark is consulted **by coordinate** — the whole
sealed envelope is the unit, exactly as a git filter acts on a whole blob. Sealing is one branch;
revealing is transparent once a recipient key is present.

== git ↔ sops ↔ cellar

[cols="1,1,1,1",options="header"]
|===
| Concern | git | sops | cellar (this design)

| store at rest | object store | file with `ENC[…]` values | Pulumi state → git
| into store | `clean` | encrypt | `PulumiCellar` seal
| out of store | `smudge` | decrypt | `PulumiCellar` reveal
| what's marked | `.gitattributes` (path→filter) | `encrypted_regex` / `sops:encrypted` | attribute registry (coordinate→sensitive)
| granularity | whole blob / file | field (regex) | envelope (≈ blob)
| recipients | — (local) | age keys — operator + cluster | *passphrase → age/sops* (the gap)
| self-describing | — | `sops:` metadata block | to introduce
|===

== What is feasible, and what is not

[cols="1,3"]
|===
| ✅ *Declarative marking*
| Name what is secret by *attribute* (coordinate / path), the way `.gitattributes` and
`encrypted_regex` do. The filter acts at one boundary. sops proves field-level marking is achievable
*by declaration*, not by tracing.

| ❌ *Tracing derivatives*
| Java has no native taint, and any mark is lost the moment a value flattens to a JSON string
crossing the OSGi seam. A leaky taint is *worse than none* — false confidence. A derivative that
must stay secret is *re-declared* where it is born, exactly as git needs a second `.gitattributes`
line for a rendered file.
|===

== The source model — two homes, one authority, one channel

Operator input has two tracked, sops-governed homes, under **one encryption authority** (sops) and
merged into **one amendment channel**:

* *Stack config* — `Pulumi.dev.yaml`, tracked and `filter=sops-yaml` in `.gitattributes` like
  `.secrets`. Pulumi's native secret provider (`encryptionsalt` / `secure:` / `pulumi config set
  --secret`) is **retired**: the git smudge means Pulumi only ever reads plaintext in the worktree,
  and sensitivity is marked by sops alone. This avoids two encryption authorities fighting over one
  file.
* *Shared secrets* — the sops YAML (`.secrets`) that also serves non-seed tooling (nix, flox, shell:
  cachix, tailscale, docker, github). Those consumers do not speak Pulumi, so this file cannot fold
  into the stack config; it stays a separate git-sops home.

Two rules keep the tracked config free of per-worktree noise:

* `worktree.dir` is **removed from config and derived at runtime** — the root already knows its own
  worktree; storing it would collide across worktrees.
* Per-worktree preferences (e.g. `logging.level`) live in an **untracked local overlay**, merged by
  the root at read time; the tracked file carries only the shareable.

NOTE: `ssh-to-age` stays a *domain transform*, not part of this unification. It feeds sops for Flux
(the in-cluster gitops decryption key derived from the cluster SSH key). A pure-Java age codec
(`jagged`) exists, but it is *age only* — it does not implement sops, nor the SSH→X25519 conversion
`ssh-to-age` performs — so the `ProcessBuilderSshToAgeConverter` edge remains the single door to the
CLI.

== The recipient gap and the `bench-cellar` thesis

The one thing sops has that the cellar lacks is **recipients**. `PulumiCellar` seals under a single
local passphrase (`PASSPHRASE = "rke2lab-cellar"`, currently a dummy, declared "holds no secrets") —
which works only while the writer and the reader are the same party (the single live master, today
— it runs on either bioskop or nikopol, currently nikopol). The moment the cellar travels (the
"git-backed cellar tomorrow" the `OpaqueCellar` contract anticipates), a passphrase breaks: it would
have to be shipped. sops solves exactly this by encrypting **for a set of recipients**, and rke2lab
already mints the cluster recipient (`ssh-to-age` on the cluster SSH key). The passphrase is just the
degenerate single-local-recipient case of the same seam.

NOTE: The concrete first traveller is the next rke2lab step, already scoped: only *one* cluster is
bootstrapped (on bioskop), and **that cluster seeds the next one** (on nikopol). The seeding
cluster's cellar/secrets must be readable by the *seeded* side — i.e. sealed *for its recipient* —
which is precisely the multi-recipient case this thesis proves. Today's single-master setup (seed +
cellar on the same host) is the degenerate one-recipient prelude to it.

Rather than build this speculatively, a disposable `bench-cellar` proof (mirroring `bench-startlevel`
/ `bench-scr` — real bnd bundles in embedded Felix, plain `@OsgiWorld` JUnit) will prove the *seam*
holds as recipients grow:

. *Roster* — a `clean` component's `@Reference(MULTIPLE)` over `Recipient` addresses the blob to
  every bound recipient, at boot and at runtime.
. *Independent smudge* — a `smudge` bound to one identity recovers the payload from a blob addressed
  to a *set* including it — no shared passphrase.
. *Additivity* — adding a recipient at runtime does not break the existing ones (the thesis).
. *Anti-cheat* — a smudge whose identity is not a recipient stays unsatisfied (`null awaitService`).

The crypto is a *faithful stand-in* (a data key wrapped once per recipient — the sops key-slot
shape), not real age: the bench proves the OSGi seam and the multi-recipient property, not the
cipher.

== Implementation sequence

. *Foundation* — this document (the vocabulary lock + the model). ✅ this commit.
. *`bench-cellar` proof* — the recipient seam, on the disposable bench. Design Only.
. *Live wiring* — on the master instance: the unified two-file input + per-coordinate contributors;
  the sensitivity attribute; the `PulumiCellar` clean/smudge branch honouring it. Design Only. Wire
  the first real consumer (bbox transport) independently — it needs no cellar mark (its password
  never reaches the cellar).
