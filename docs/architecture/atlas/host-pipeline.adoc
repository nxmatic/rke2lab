[[host-pipeline-view]]
== Host / control-plane pipeline — per-subsystem view

The sixth view, and the first for the HOST world (the five before are OSGi-centric). It holds the
control-plane pipeline that runs `pulumi preview`/`up` — the one process that decides what crosses the
system's two boundaries. Folds in the link:../osgi/pipeline-spec.adoc[pipeline design of record (OSGi-owned)], and
carries the null-safety governance note.

=== The thesis — the pipeline owns two gates; nothing else decides a crossing

The pipeline is the sole orchestrator of two boundaries, and until now both were crossed by scattered
code reaching for global state:

* the *living gate* (IN) — may an action touch the REAL system (systemd probe, kubeconfig wait)? In
  `preview` it must not. Today seven sites read `Deployment.getInstance().isDryRun()` inline, and one
  (cluster readiness) reads it too late: the live probe runs before the gate is consulted, so
  `pulumi preview` hangs one minute waiting for a kubeconfig that a dry-run will never publish.
* the *output gate* (OUT) — what is written to the stack? Today an omniscient `OutputBuilder` pulls
  each summary by name over raw `Map`s; one producer (`systemd`) flattens its typed snapshot at
  production time, so the flat map travels internally and `SeedNodeBootstrapWatcher` re-parses it
  (the null that triggered this whole view).

Neither gate is a new orchestrator. `LiveGate` is the preview/up STATE; `PulumiOutputRegistry` is a
guaranteed ASSEMBLER. The pipeline holds both and actions them — it consults the living gate per
action (`through(live, deferred)`) and drives the write once (`registry.add(...).assemble()`).

[NOTE]
.The living gate half is re-posed by the BDD-as-engine turn
====
The *living gate* framing below (`LiveGate` as a preview/up state) is *avant*: the BDD-as-engine turn
(§ <<the-bdd-as-engine-turn>>) erases `LiveGate` and re-poses preview as an `ExecutionCondition`
selecting a `PreviewExecutor` (rendering decoupled from execution, E9). What survives from Diagram P is
the *named erasure of the seven scattered `isDryRun()` reads* and the whole *output gate* half
(`PulumiOutputContributor`/`PulumiOutputRegistry`, `SystemdRuntimeStatusReport`) — the output axis is
orthogonal to the turn and stays exactly as drawn. Read Diagram P for those; read the turn section for
the preview mechanism.
====

=== Verdict — does it hold?

An honest reading:

. *Monotone-with-named-erasure.* Four things are deliberately erased: the seven scattered `isDryRun()`
  reads (collapsed to one passed `LiveGate`), the omniscient `OutputBuilder` (melts into the registry),
  the systemd production-time flatten + the watcher's re-parse helpers (`toBoolean`/`toInt`/
  `stringValue` + `@Nullable Object`), and the false `System.setProperty(JGIVEN_DRY_RUN)`. Each is
  named, none silent; behavior survives (same outputs, same preview/up semantics) — only WHERE the
  decision lives changes: from the domain reaching for globals to the pipeline holding a gate.

. *The mechanisms are not orchestrators.* `LiveGate` answers `isOpen()` and offers `through(...)`;
  `PulumiOutputRegistry` answers `assemble()` with a unique-key + deterministic-order guarantee. The
  pipeline is the only orchestrator — consistent with the fluent-pipeline grammar the boot pipeline
  already uses. No new live component, no new boot bind.

. *A real bug closes as a side effect.* The readiness preview hang (one minute per `pulumi preview`)
  is not a separate fix — it is what the living gate removes by construction: in preview the deferred
  probe is injected, the scenario still renders its runbook shell, but no `waitFor` fires.

. *The seam shrinks the null surface.* `SystemdRuntimeStatusReport` stays a domain-pure record, so the
  watcher reads `report.snapshot()` typed. The null-safety arc (below) turned WARN→ERROR on the live
  surface; this view keeps the host null-clean at the source rather than annotating consumers.

Conclusion: *additive-with-named-erasure; the pipeline gains one clear responsibility (own both gates)
and loses four scattered anti-patterns.* Status: DESIGN — the living gate is the first horizon
(it fixes the hang), then the systemd report, then the output registry.

=== The role map — every pipeline role, where it lives, who touches it (the AVANT)

|===
| Role | Lives | Touched by
| `FluentTopicRunner` | port | the transition (`runDuring`)
| `PipelineContext` (ambient, READ, static) | port type / instanced per pipeline | the transition (`require`) — NEVER a topic
| `Topic` (identification: `role` + nested natures) | port | the runner's bound; governance + retrofit read it
| `Topic.Sink` (write-face, per topic) | nested in each topic | the topic (pushes) + the transition (wires it → `B`)
| `Topic.{Execution,Checkpoint,Pipeline}` (nature = type) | port (nested in `Topic`) | identification (`instanceof`)
| `State<I,B>` (I + B + context + runner) | inner to each pipeline | the transition
| input record `I` (flux + ambient, fused) | inner (per topic) | the transition (composes) + the topic (reads)
| accumulator `B` (all outputs so far) | inner | the transition (folds sinks in, reads for next `I`)
| type-state `Awaiting/Done` | inner | the author (ordering)
| topics (fluent builders) | inner (`stages/`) | the transition
|===

Two axes make the roles fall out cleanly. *Direction × time:* `PipelineContext` is a READ source that is
STATIC (frozen before the first topic, an input of the pipeline itself); a `Topic.Sink` is a WRITE
channel that is FLOWING (one per topic, wired at the transition, it is how an output enters `B` and
becomes the next topic's flux). *API vs implementation:* the topic's API is its fluent verbs +
its `role()` and its nature type; its `(input, sink)` construction is implementation the transition wires — the sink
is never on the API, which is why `Topic.Sink` is nested, not a top-level type. A topic sees only its
frozen `I` and its `Sink` — never `B`, never the context — so it is deterministic and testable in
isolation. Writing an output by directly assigning an accumulator field (topic holding a state
reference) is a DERIVATION the `PIPELINE_PATTERN` governance gate is meant to catch.

== The BDD-as-engine turn — the seeding as jGiven scenarios (the APRÈS, GO 2026-07-04)

The role map above is the *avant*. This section is the *après* — the current model: express the whole
seeding as *jGiven scenarios orchestrated by the JUnit Platform launcher*, the fluent grammar

link:../osgi/pipeline-spec.adoc[pipeline-spec]; the discovery record is
link:../osgi/bdd-pipeline-poc-design.adoc[the bdd-pipeline POC] (ten measured learnings E1–E10). *GO
was reached 2026-07-04*: the turn is proven viable (a bench transposed the entire ClusterSeed pipeline
and rendered a real runbook) AND proven to hold on the atlas (below). The reference implementation is
pinned at tag `spike/bdd-pipeline-poc`. This view is where the *additivity proof* — the evolution
figure — lives.

[NOTE]
.Governance note — the build-time laws (staging extension) + the null-safety javac gate
====
The host doesn't only orchestrate at runtime; it is also where the build-time governance is enforced,
because `seed-master` is the module that shades+stages the exec-jar and its dependency closure. Two
sibling enforcement families, cross-cutting rather than subsystems of their own:

*Staging-extension laws (six `StagingGate`s, ASM over staged bytecode, committed `0299913a`+):* each is
an instance reached from `ResolvedBundle`, governable per-package via `@GovernedBy(StagingGate, level)`
(default ERROR) with single-element `@Exempt`. `RECORD_PURITY` (a `type=record` bundle exports only
records/enums/sealed ADTs — ERROR); `SPEC_COVERAGE` (every exported type is named in a `docs/` spec or
`@Transitional` — WARN, paid down domain by domain — this IS the law enforcing the very atlas-coverage
discipline this view is written under); `INSTANCE_DISCIPLINE` (no exported `public static` behaviour
helper — ERROR, debt cleared); `REALM_BOUNDARY` (a class stays in its host/OSGi realm — ERROR, locked
by 2C); `DUPLICATE_REALM_CLASS` (no class duplicated across realms — the jackson bug; exemptions
derived from the seam surface); `SCHEMA_CONCORD` (records-as-contract: every `Coordinate` has a
`@DocumentContract` wire-record whose schema is generated + checked — ERROR, locked by 2D). See
link:../osgi/staging-gates-governance-spec.adoc[staging-gates governance].

*Null-safety (2G, a javac gate — NOT a staging law):* JSpecify `@NullMarked` now covers doctor,
world-gateway, all OSGi modules, host `pulumi-edge` + boot-discovery, and (in progress) `exec`.
NullAway runs as an error-prone javac plugin (ep 2.50.0 / NullAway 0.13.7 / jspecify 1.0.0 on JDK 25),
gated by the build-parent `nullaway` profile — ON BY DEFAULT (`!nullaway.skip`), severity
`${nullaway.severity}` default `ERROR`, test sources excluded. Discipline: eliminate the null (return
`Optional`, fix at the SOURCE) rather than document it (`@Nullable`). This view exists partly BECAUSE
that discipline surfaced a design defect — the watcher's re-parse — which the two gates resolve at the
source.
====

=== Design scenarios — the host-pipeline capabilities as DSL sentences

. *The pipeline refuses to touch the live system in preview* — `[narrated]` green +
.. GIVEN seven scattered `Deployment.getInstance().isDryRun()` reads, one consulted too late so the
   readiness probe waits a full minute for a kubeconfig a dry-run never publishes
.. WHEN the injected `RunMode` fact becomes an `ExecutionCondition` selecting a `PreviewExecutor`
   (après — the `LiveGate` of the avant is erased): the executor decouples rendering from execution,
   the tree builds against inert probes and the reaching mode is rewritten NORMAL→PENDING (E9)
.. THEN no live probe or wait fires in preview (the one-minute hang is gone), and the runbook renders a
   RICH plan — every phase PENDING, the nested G/W/T present — not the empty shell a naive dry-run
   would give (named erasure of the seven reads + the false `JGIVEN_DRY_RUN` + `LiveGate` itself).

. *The pipeline decides the stack outputs through one guarded assembler* — `[narrated]` green +
.. GIVEN an omniscient `OutputBuilder` pulling each summary by name over raw maps, systemd flattening
   at production so the watcher re-parses an untyped map
.. WHEN outputs become `PulumiOutputContributor`s assembled by `PulumiOutputRegistry` (unique-key
   guarantee, single flatten point) and `SystemdRuntimeStatusReport` stays a typed record read by the
   watcher
.. THEN adding an output means implementing the SPI (never editing a hub), a key collision is a named
   failure not a silent overwrite, and the watcher reads typed fields — AND the change is additive: the
   same outputs cross, the hub + the re-parse helpers are the named erasure.

*Coverage of this view:* 2 capabilities, 2 scenarios — complete per <<scenario-completeness>>. Both
narrated-green. Scenario 1 is the *après* — its preview mechanism (`ExecutionCondition` +
`PreviewExecutor`) is proven on the bench (§ <<the-bdd-as-engine-turn>>) and flips playable when the
ClusterSeed-vertical increment ships. Scenario 2 (the output registry) is orthogonal to the turn and
flips playable when the registry ships.
