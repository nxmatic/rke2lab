== Seed orchestration — per-subsystem view

The seed's orchestration, host-side — historically "the control-plane / host-pipeline" (three names,
one thing: the process that orchestrates the seed and runs `pulumi preview`/`up`, deciding what crosses
the system's two boundaries). Named `seed` here by its stable NATURE, not its transitional host
(`seed-master`'s `controlplane` package is being redistributed into sub-modules). Folds in the
link:../bdd/bdd.adoc[BDD-as-engine design of record (OSGi-owned)], and carries the null-safety
governance note.

[NOTE]
====
The host logic drawn here (config, policy, readiness, incus, bbox) is being lifted into OSGi domain
services the host calls; see link:../osgi/controlplane-to-osgi-migration-spec.adoc[control-plane → OSGi
— migrating the domains] (the 87 Pulumi-free files migrated, only the 17 `com.pulumi` edge staying
host). The seeding itself is expressed as BDD-as-engine — jGiven scenarios on the JUnit launcher
(link:../bdd/bdd.adoc[design of record], GO 2026-07-04); the fluent `during/then` grammar it was first
built on is gone (its engine dissolved into manifests-core's internal synthesis, the boot into
`FrameworkLaunch`). What remains is wiring seed-master's own live pipeline onto the shipped socle — the
ClusterSeed vertical, tracked below as the residue, not an avant→après evolution.
====

=== The thesis — the pipeline owns two gates; nothing else decides a crossing

The pipeline is the sole orchestrator of two boundaries, and until now both were crossed by scattered
code reaching for global state:

* the *living gate* (IN) — may an action touch the REAL system (systemd probe, kubeconfig wait)? In
  `preview` it must not. Today seven sites read `Deployment.getInstance().isDryRun()` inline, and one
  (cluster readiness) reads it too late: the live probe runs before the gate is consulted, so
  `pulumi preview` hangs one minute waiting for a kubeconfig that a dry-run will never publish.
* the *output gate* (OUT) — what is written to the stack? Today an omniscient `OutputBuilder` pulls
  each summary by name over raw `Map`s; one producer (`systemd`) flattens its typed snapshot at
  production time, so the flat map travels internally and `SeedNodeBootstrapWatcher` re-parses it
  (the null that triggered this whole view).

Neither gate is a new orchestrator. `LiveGate` is the preview/up STATE; `PulumiOutputRegistry` is a
guaranteed ASSEMBLER. The pipeline holds both and actions them — it consults the living gate per
action (`through(live, deferred)`) and drives the write once (`registry.add(...).assemble()`).

[NOTE]
.The living gate half is re-posed by the BDD-as-engine turn
====
The *living gate* framing below (`LiveGate` as a preview/up state) is superseded: BDD-as-engine
(§ <<the-bdd-as-engine-turn>>) erases `LiveGate` and re-poses preview as an `ExecutionCondition`
selecting a `PreviewExecutor` (rendering decoupled from execution, E9). What survives from Diagram P is
the *named erasure of the seven scattered `isDryRun()` reads* and the whole *output gate* half
(`PulumiOutputContributor`/`PulumiOutputRegistry`, `SystemdRuntimeStatusReport`) — the output axis is
orthogonal to the turn and stays exactly as drawn. Read Diagram P for those; read the turn section for
the preview mechanism.
====

=== Verdict — does it hold?

An honest reading:

. *Monotone-with-named-erasure.* Four things are deliberately erased: the seven scattered `isDryRun()`
  reads (collapsed to one passed `LiveGate`), the omniscient `OutputBuilder` (melts into the registry),
  the systemd production-time flatten + the watcher's re-parse helpers (`toBoolean`/`toInt`/
  `stringValue` + `@Nullable Object`), and the false `System.setProperty(JGIVEN_DRY_RUN)`. Each is
  named, none silent; behavior survives (same outputs, same preview/up semantics) — only WHERE the
  decision lives changes: from the domain reaching for globals to the pipeline holding a gate.

. *The mechanisms are not orchestrators.* `LiveGate` answers `isOpen()` and offers `through(...)`;
  `PulumiOutputRegistry` answers `assemble()` with a unique-key + deterministic-order guarantee. The
  pipeline is the only orchestrator — consistent with the fluent-pipeline grammar the boot pipeline
  already uses. No new live component, no new boot bind.

. *A real bug closes as a side effect.* The readiness preview hang (one minute per `pulumi preview`)
  is not a separate fix — it is what the living gate removes by construction: in preview the deferred
  probe is injected, the scenario still renders its runbook shell, but no `waitFor` fires.

. *The seam shrinks the null surface.* `SystemdRuntimeStatusReport` stays a domain-pure record, so the
  watcher reads `report.snapshot()` typed. The null-safety arc (below) turned WARN→ERROR on the live
  surface; this view keeps the host null-clean at the source rather than annotating consumers.

Conclusion: *additive-with-named-erasure; the pipeline gains one clear responsibility (own both gates)
and loses four scattered anti-patterns.* Status: DESIGN — the living gate is the first horizon
(it fixes the hang), then the systemd report, then the output registry.

== The seeding as jGiven scenarios (BDD-as-engine, GO 2026-07-04)

The seeding is expressed as *jGiven scenarios orchestrated by the JUnit Platform launcher*, the missing
dynamics contributed as Jupiter extensions. Its spec is link:../bdd/bdd.adoc[BDD-as-engine]; the
discovery record is link:../osgi/bdd-pipeline-poc-design.adoc[the bdd-pipeline POC] (ten measured
learnings E1–E10). The engine-lifecycle socle SHIPPED (2026-07-05,
link:../osgi/engine-lifecycle-spec.adoc[engine-lifecycle-spec]): the launcher, connection, lever,
disciplines and a green connected `BulletproofPipeline` are live in `osgi/runtime/scenario-engine`. What
remains is the ClusterSeed vertical (increment 2) that wires seed-master's own live pipeline onto that
socle.

The fluent `during/then` grammar the seeding was first built on is gone from the codebase — its engine
dissolved into manifests-core's un-exported internal synthesis (`Phase`/`PhaseRunner`) and the boot
de-grammatised into `FrameworkLaunch`. The former text is in git (`pipeline-spec.adoc` @ `39fe4d8a`)
for anyone tracing the history; it is not described here.

=== How the seeding concepts map onto jGiven

The seeding phases are jGiven `Stage`s; the value-DAG is carried by scenario-state annotations. The
*Realized in* column names where each lives: the socle types are SHIPPED (increment 1,
`osgi/runtime/scenario-engine`); the vertical rows are what the ClusterSeed increment builds.

[cols="2,2,1",options="header"]
|===
| Seeding concept | jGiven mechanism | Realized in

| a checkpoint phase | a `Stage` opening a nested G/W/T | vertical: the two live islands become phases
| a phase's out-edge | `@ProvidedScenarioState` | vertical: each phase's provided state
| a phase's in-edge | `@ExpectedScenarioState` | vertical: each phase's expected state
| the value-DAG | scenario-state runtime **+ a build-time DAG gate** | vertical: the value-DAG; gate = the closing task
| phase composition | intro-words + `@NestedSteps` | vertical: the composing When stage
| the runbook node label | `@As("…")` | vertical: per-phase `@As`
| the launcher | the embedded JUnit Platform launcher | *socle SHIPPED:* `JUnitLauncherCore`
| the boot | `@SeedRuntime` self-boots via `OsgiConnection.embedded` (`FrameworkLaunch.embedded().launch()` under the hood) | *socle SHIPPED:* `SeedRuntime` + `OsgiConnection`
| ambient host-facts | `ExtensionContext.Store` | *socle SHIPPED:* `BaseWorldExtension` Store; vertical seeds host-facts

|===

The one load-bearing change is the value-DAG: it moves from compile-time type-state to runtime
scenario-state *plus* a build-time gate that reads the `@Provided/ExpectedScenarioState` annotations and
checks every `required` has a `guaranteed` upstream — the compile-time safety kept, as a
`SCENARIO_STATE_DAG` gate (a sibling of `SYNTHESIS_PATTERN`, the manifests-synthesis `Phase` law). That
gate is the CLOSING task of the vertical (nothing to check until the phases carry those annotations),
born WARN then flipped WARN→ERROR — the REALM_BOUNDARY ritual.

The membrane detail settled during the vertical's design: the socle's `LaunchedPipelineExchange` (a
custom `ThreadLocal` binding a connection + a pre-made model) was a TEST-ONLY crutch —
`SoclePipelineTest` boots Felix OUTSIDE the launcher, so it had to hand the scenario a non-owning
connection and a pre-made `ReportModel`. In the LIVE vertical it is ERASED: `@SeedRuntime` self-boots
(no connection to inject) and jGiven's own `ScenarioHolder` + `JGivenExtension` already hold the
`ReportModel` (verified in jGiven 2.0.3). Inbound host-facts ride `ExtensionContext.Store` (the
`ConnectionSeeder` pattern the socle already uses for the connection); outbound is the synchronous
harvest return `SeedRun(runbook, outputs)`. The four OSGi services (doctor, systemd probe, cluster
contact, readiness authority) leave the inbound bag — the scenario, running inside the booted
framework, resolves them from its connection.

Tested against the four structural invariants; each holds, and the socle (increment 1) now carries the
first three in-container for real (`SoclePipelineTest` boots Felix, drives `JUnitLauncherCore` over a
connected scenario, green) rather than on the disposable bench.

live pipeline onto it: the *ClusterSeed-vertical-first* increment; the six other pipelines stay on the

=== The go/no-go gate — closed; the socle shipped

The seven go/no-go mechanisms were proven on a bench (2026-07-04, adversarial pass) and the GO was
graved; increment 1 (the engine-lifecycle socle) then SHIPPED the load-bearing ones for real —
`JUnitLauncherCore` (the launcher premise + the dedicated-thread crossing), `OsgiConnection` +
`StartLevelLever` + `@SeedRuntime`/`@IsolatedWorld` (the lifecycle), `BulletproofPipeline`/
`SoclePipelineTest` (a connected scenario played end-to-end, green). This before/after has been
CONSUMED: the proof is no longer "a bench shows it viable" but "the socle realizes it." The detailed
seven-mechanism registry lived here to decide the GO; that decision is made, so it collapses to a
pointer — see link:../osgi/engine-lifecycle-spec.adoc[engine-lifecycle-spec] for the shipped socle and
its increment boundary, and the migration plan for the vertical sequence. Three mechanisms are NOT yet
productionised and belong to the vertical (increment 2) or its close: the `PreviewExecutor`
(preview-as-`ExecutionCondition`, Q3, not yet designed), the `SCENARIO_STATE_DAG` gate (the closing
task — a sixth `StagingGate` on the existing ASM+`@GovernedBy` mould), and the cross-world
`ScenarioModel` graft (only when an OSGi-world scenario is grafted). The bench code survives at tag
`spike/bdd-pipeline-poc`; the module is out of the default build.

[NOTE]
.Governance note — the build-time laws (staging extension) + the null-safety javac gate
====
The host doesn't only orchestrate at runtime; it is also where the build-time governance is enforced,
because `seed-master` is the module that shades+stages the exec-jar and its dependency closure. Two
sibling enforcement families, cross-cutting rather than subsystems of their own:

*Staging-extension laws (six `StagingGate`s, ASM over staged bytecode, committed `0299913a`+):* each is
an instance reached from `ResolvedBundle`, governable per-package via `@GovernedBy(StagingGate, level)`
(default ERROR) with single-element `@Exempt`. `RECORD_PURITY` (a `type=record` bundle exports only
records/enums/sealed ADTs — ERROR); `SPEC_COVERAGE` (every exported type is named in a `docs/` spec or
`@Transitional` — WARN, paid down domain by domain — this IS the law enforcing the very atlas-coverage
discipline this view is written under); `INSTANCE_DISCIPLINE` (no exported `public static` behaviour
helper — ERROR, debt cleared); `REALM_BOUNDARY` (a class stays in its host/OSGi realm — ERROR, locked
by 2C); `DUPLICATE_REALM_CLASS` (no class duplicated across realms — the jackson bug; exemptions
derived from the seam surface); `SCHEMA_CONCORD` (records-as-contract: every `Coordinate` has a
`@DocumentContract` wire-record whose schema is generated + checked — ERROR, locked by 2D). See
link:../osgi/staging-gates-governance-spec.adoc[staging-gates governance].

*Null-safety (2G, a javac gate — NOT a staging law):* JSpecify `@NullMarked` now covers doctor,
world-gateway, all OSGi modules, host `pulumi-edge` + boot-discovery, and (in progress) `exec`.
NullAway runs as an error-prone javac plugin (ep 2.50.0 / NullAway 0.13.7 / jspecify 1.0.0 on JDK 25),
gated by the build-parent `nullaway` profile — ON BY DEFAULT (`!nullaway.skip`), severity
`${nullaway.severity}` default `ERROR`, test sources excluded. Discipline: eliminate the null (return
`Optional`, fix at the SOURCE) rather than document it (`@Nullable`). This view exists partly BECAUSE
that discipline surfaced a design defect — the watcher's re-parse — which the two gates resolve at the
source.
====

`PulumiCellar.store` does (an `up()` registering a `CellarEntry` under the coordinate slug). So it is not
re-created: *every scion, in-container, harvests AND stores* — the host lays the `Cellar` into Felix at boot
(`registerService`), the scion resolves it (and the ambient current `Parcel`, published like the `RunGate`) and
stores its own harvest; the host does NOT round-trip a harvest back to re-store it (§
link:../osgi/host-cellar-realisation-spec.adoc#every-scion-contributes[host Cellar realisation — every scion
contributes]). The `RunbookEnvelope` keeps `(runbook, consultations)`: consultations cross because the host
GRAFTS them into the runbook; the harvest does not cross because its destination is the cellar, not the runbook.
Two natures follow: RESOURCES (graph nodes + the `dependsOn` edge, read CAUSALLY from the amendment graph, not
the runbook position) and top-level OUTPUTS (a PROJECTION of the resources — the read façade, host, no métier).
The scion — never the façade — marks what has output value, by the neutral `@Scion(Role.FRUIT)` it already uses;
the façade lifts what is marked, mechanically. Grain today = the whole fruit part; the finer field-level
flat-output marking is a planned evolution the top-down migration will hit.

*The cellar consults the RunGate — dry-run does not lose the harvest.* The cellar is a system tool, so like
every tool it reads the ambient `RunGate` and adapts: gate open → `stack.up()` (the CONSERVED state), gate
closed → `stack.preview()` (an EPHEMERAL PRE-RESERVE, the plan of this run, rendered PENDING in the runbook via
E9). The scion holds ONE verb (`store(Parcel, harvest)`) and never picks the mode. This is not a fake harvest
(`preview` mutates nothing, invents nothing — it is surveying). Note the runbook alone does NOT carry the
harvest: jGiven's `ReportModel` captures step arguments, not scenario-state — so the runbook is the plan, the
cellar is the data (two channels). See § link:../osgi/host-cellar-realisation-spec.adoc#every-scion-contributes[
host Cellar realisation — every scion contributes].

== The host tree the instance mounts — publish / validate / mount (design 2026-07-14)

=== Diagram V — the host half: `host.N.staging.d` → `host.live.d` → `host.N.drift` + the two deltas + the contract in the cellar

The scions conserve harvests at the cellar (Diagram R). The OTHER thing a run produces
is the FILESYSTEM TREE the incus instance binds. Three FIXED places, a pipeline:
`host.N.staging.d` (a run materialises here, rotation of 3, also carries its `change`) →
`host.live.d` (the physical, stable bind-mount target, synced from a staging by `jsync`) →
`host.N.drift` (NOT a `--backup-dir` of bytes — the DRIFT REPORT `host.live.d ↔ host.{live.syncedFrom}.staging.d`
measured before the sync, rotation of 3). The `main` FS mechanism (staging rotation, a
`--delete` sync into the physical `host.live.d`) is KEPT; what CHANGES is that the sync is
`jsync` (pure-Java, no `rsync` binary) and `main`'s `gc` becomes the drift report. R1 (never
lose what a live instance mounts) holds because the sync moves CONTENT while preserving the
mount DIRECTORIES (present in every replica, so `--delete` never removes them). ONE
host-manifest for the whole collection LIVES AT THE CELLAR (one entry per replica): staging
entries carry the CONTRACT (checksums + provenance + `change`, immutable), the `host.live.d`
entry references the `host.{SN}.staging.d` it mirrors (the ONLY mutable entry), each
`host.{DN}.drift` references the staging the live had drifted from (its `live.syncedFrom`, frozen until
recycled). The cellar is a FRIDGE (put / peek / take — § seed-broker-spec "the cellar is a
fridge", 2026-07-15): CURRENT state is mutable (the live case, the ring pointer — reached by
`<T> fetch`/`withdraw`), while its HISTORY axis (Pulumi's revision log) is append-only and gives
the timeline of live promotions FREE (each live mutation a new store → a new history version);
preview-vs-promoted is DEDUCED (a staging live never adopted). And because each staging entry
carries CHECKSUMS, the cellar DESCRIBES the FS in full without holding a byte — authority over
the FS state while pure storage of facets. (The staging-rotation position truth moves FS→cellar:
`HostSlotSelector` will `fetch` occupancy + `withdraw` the wrapped case; FS↔cellar reconciliation deferred.)

TWO deltas, both pivoting on `host.{live.syncedFrom}.staging.d` (the staging the live mirrors, read
from the `host.live.d` entry — NOT the arithmetic N-1, since interleaved previews produce
stagings the live never adopted; the common reference — OBSERVE before ACT): `change` =
`staging.N ↔ host.{live.syncedFrom}.staging.d` (the run's INTENDED change, computed ALWAYS — in
preview it IS the value report, travels in `host.N.staging.d`); `drift` = `host.live.d ↔
host.{live.syncedFrom}.staging.d` (the live's out-of-band DEVIATION, computed LIVE ONLY before the
sync — the one delta no staging captures, is `host.N.drift`). `java-diff-utils`
OBSERVES (walks both trees → per-file ADDED/REMOVED/MODIFIED + line-level unified diff for
text; each delta IS a `ReportModel`, adoc+json, dogfooding I5); `jsync` (`setDelete(true)`)
ACTS (the sync). Rollback re-syncs the immutable staging — never an inverse patch, never the
evicted bytes — which is why drift is a REPORT, not a byte backup. The `live.syncedFrom` slot
is PINNED out of the rotation while the live reflects it, so the pivot TREE is always present
for both deltas (the FS face of R1). `jsync` + `java-diff-utils` are HOST-classpath deps (the
GROW is Shape C, not in-container) — no `*-wrap`, no bundle.

Publish / validate / reconcile, no overlap: the producer PUBLISHES an availability
(it knows only its morceau); the incus prep VALIDATES the whole the instance will
mount (only it sees the ensemble) against the published checksums, catching a bad
tree BEFORE the rsync on its already-wired doctor channel; the host grow OBSERVES
(measures the drift into `host.N.drift` so nothing is overwritten blind) then ACTS
(`jsync` the validated staging into the physical `host.live.d`, mount dirs preserved) and
binds, never re-validating (that would leak metier host-side). The cellar carries a
FACET (checksums + a path), never the files — fetch-not-push, the twin of
`IncusHarvest.soil`. R2 (the compare cache) is the `host.N.staging.d` PLUS the `host.N.drift`
reports, indexed by the host-manifests; the no-op check is a checksum diff, not a
re-read. Preview realises the same RunGate axis as the cellar `up`/`preview` (Diagram R):
a preview materialises a `host.N.staging.d` and computes its `change`, but the gate does NOT
fire the sync — `host.live.d` untouched, no `drift` measured, and `live.syncedFrom` never names
it (traceable from the cellar, no mode-dir on the FS). Full model:
link:../osgi/host-cellar-realisation-spec.adoc#host-tree-provisioning[host-cellar-realisation-spec § The host tree the instance mounts].
