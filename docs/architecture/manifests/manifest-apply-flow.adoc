= Manifest Apply Flow
:toc:
:toc-placement: preamble

== Overview

RKE2Lab manifests flow through a multi-stage pipeline from CDK8s synthesis to live Kubernetes resources. **RKE2's built-in auto-deploy mechanism** applies manifests by watching a directory; no explicit `kubectl apply` is needed.

[NOTE]
====
*Partly historical.* The detailed on-node steps below (the `rke2lab-manifests-install.sh` installer
reading `RKE2LAB_MANIFESTS_PUBLISH_*` flags and symlinking `/srv/host/rke2-manifests.d/<layer>` into
the server-manifests dir) describe the former `/srv/host` install flow, which was *dissolved* with
the NixOS node substrate (see link:../nixos-substrate/target-vision.adoc[target vision]). Today the
synthesised, exploded tree is delivered straight to the node's `server/manifests` and RKE2
auto-applies it — no install script, no publish-flag gating, no symlink stow.
====

This document traces the complete flow using the `networking` layer as the reference example and explains how staged post-cluster resources fit into the same pattern.

**Package annotation** (in Java) — stamped on each `ApiObject` created in the unit constructor:
```java
public KdnsManifestsUnit(final Construct scope, final String id) {
  super(scope, id, MANIFEST_UNIT_ID, List.of());
  new ApiObject(this, "deployment-kdns", ApiObjectProps.builder()
      .metadata(ApiObjectMetadata.builder()
          .annotations(packageProfile.packageAnnotations("|Deployment|rke2lab-system|kdns"))
          // Results in annotation: io.seedmatic.rke2lab/package: "networking/kdns"
          .build())
      .build());
}
```

The exploder uses this annotation to route each resource to the correct directory.

== Stage 2: Push to Master (Pulumi Apply)

=== File Sync

**Local path**: `.local.d/bioskop/master/host/manifests.d/`
**Master path**: `/srv/host/rke2-manifests.d/`

Note the directory name change: `manifests.d` → `rke2-manifests.d` (to clarify purpose on the host).

**Mechanism**: `HostAssetRootLifecycle.syncStagingToFinal()` uses `incus file push -r` to push the entire `host/` directory to the master instance.

=== What Gets Pushed

All subdirectories under `host/`:
- `manifests.d/` → `/srv/host/rke2-manifests.d/`
- `systemd.d/systemd-units/` → `/srv/host/systemd-units.d/`
- `systemd.d/systemd-scripts/` → `/srv/host/systemd-scripts.d/`
- `k8s-daemonset.d/` → `/srv/host/k8s-daemonset.d/`
- etc.

== Stage 3: Systemd Unit Trigger

=== C4 Component: Layer Manifest Service

Each layer has a corresponding systemd oneshot unit:

**Unit file**: `/srv/host/systemd-units.d/rke2lab-networking-manifests.service`

```ini
[Unit]
Description=Install RKE2Lab networking manifests from host share (post-server)
After=rke2-server.service
Requires=rke2-server.service
After=rke2lab-storage-manifests.service
Requires=rke2lab-storage-manifests.service
ConditionPathExists=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh
ConditionPathExists=/srv/host/rke2-manifests.d/networking

[Service]
Type=oneshot
ExecStart=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh networking
ExecStartPost=/srv/host/systemd-scripts.d/rke2lab-cilium-ready.sh
RemainAfterExit=true

[Install]
WantedBy=rke2lab.target
```

**Key points**:
- `After=rke2-server.service` - waits for RKE2 to be running
- `ConditionPathExists` - ensures manifests and script are present
- `ExecStart` - calls the install script with the layer name
- `ExecStartPost` (optional) - layer-specific readiness checks

== Stage 4: Symlink Creation

=== The Install Script

**Script**: `/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh`

**Invocation**: `rke2lab-manifests-install.sh networking`

**What it does**:

1. Reads environment variables:
   - `RKE2LAB_MANIFESTS_DIR=/srv/host/rke2-manifests.d`
   - `RKE2_SERVER_MANIFESTS_DIR=/var/lib/rancher/rke2/server/manifests`

2. Checks policy (for linkable layers):
   - Reads `RKE2LAB_MANIFESTS_PUBLISH_NETWORKING_ENABLED` (etc.)
   - If `false`, removes existing symlinks and exits

3. Calls `link_manifest_tree()`:
   - Removes old symlinks in `/var/lib/rancher/rke2/server/manifests/{layer}/`
   - Walks `/srv/host/rke2-manifests.d/{layer}/` recursively
   - Skips manifests with `config.kubernetes.io/local-config: "true"` annotation
   - Creates symlinks preserving directory structure

**Result**:
```
/var/lib/rancher/rke2/server/manifests/networking/kdns/
├── 01-clusterrole-kdns-ingress-reader.yml → /srv/host/rke2-manifests.d/networking/kdns/01-clusterrole-kdns-ingress-reader.yml
├── 02-serviceaccount-kdns.yml → /srv/host/rke2-manifests.d/networking/kdns/02-serviceaccount-kdns.yml
└── 02-deployment-kdns.yml → /srv/host/rke2-manifests.d/networking/kdns/02-deployment-kdns.yml
```

=== Local-Config Annotation

Manifests with this annotation are **NOT symlinked**:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  annotations:
    config.kubernetes.io/local-config: "true"
```

**Use case**: Configuration data used by other manifests (e.g., Helm values, Kustomize bases) that shouldn't be applied as standalone resources.

=== Policy-Based Exclusion

Layers can be disabled via policy:

```bash
RKE2LAB_MANIFESTS_PUBLISH_MESH_ENABLED=false
```

If disabled, the script removes all symlinks for that layer, effectively uninstalling it from the cluster.

== Stage 5: RKE2 Auto-Deploy

=== The Auto-Deploy Mechanism

RKE2 has a built-in controller that watches `/var/lib/rancher/rke2/server/manifests/` using Kubernetes' `apply` semantics:

1. **File appears** → RKE2 applies it
2. **File changes** → RKE2 re-applies (server-side apply)
3. **File removed** → RKE2 **does NOT delete** the resource (manual cleanup needed)

**No explicit `kubectl apply` needed** - RKE2 handles this automatically.

=== Directory Structure

```
/var/lib/rancher/rke2/server/manifests/
├── rke2-cilium.yaml          # Built-in RKE2 manifests
├── rke2-coredns.yaml
├── rke2-traefik.yaml
├── networking/               # rke2lab-networking-manifests.service created this
│   ├── kdns/
│   ├── cilium-config/
│   └── envoy-gateway/
├── clusterapi/               # rke2lab-clusterapi-manifests.service would create this
│   ├── cluster-api-operator/
│   └── incus-identity/
└── storage/                  # rke2lab-storage-manifests.service created this
```

All files under this directory (including subdirectories) are auto-deployed by RKE2.

== Staged Post-Cluster Resources Pattern

=== The Problem

Some manifests need data that's only available AFTER Pulumi provider resources are created (e.g., image fingerprint from `incus.Image`). But manifest synthesis happens DURING host-state preparation, BEFORE provider resources exist.

**Example**: The Cluster API `image-state` ConfigMap needs:
- `imageFingerprint` - comes from `incus.Image` resource (created in provider-resources stage)
- `imageAlias`, `imageBuildChecksum`, `incusProject` - available during host-state

This is a **chicken-and-egg dependency**.

=== The Solution: Staged Synthesis

**Key insight**: Staged manifests follow THE SAME FIVE-STAGE FLOW, but synthesis happens later (during Pulumi Output resolution).

=== Directory Structure for Staged Manifests

**Local synthesis output**:
```
.local.d/bioskop/master/host/manifests/
└── clusterapi/
    └── staged/
        └── image-state-configmap.yaml
```

**Pushed to master** (next `pulumi up`):
```
/srv/host/rke2-manifests.d/
└── clusterapi/
    └── staged/
        └── image-state-configmap.yaml
```

**Symlinked by systemd unit**:
```
/var/lib/rancher/rke2/server/manifests/
└── clusterapi/
    └── staged/
        └── image-state-configmap.yaml → /srv/host/rke2-manifests.d/clusterapi/staged/image-state-configmap.yaml
```

**Applied by RKE2 auto-deploy** (no kubectl needed).

=== Staged Manifest Systemd Unit

**IMPORTANT**: Staged manifests use THE SAME `rke2lab-manifests-install.sh` script, just with a subpath argument.

**Correct pattern**:
```ini
[Unit]
Description=Install Cluster API staged image-state manifest
After=rke2-server.service
ConditionPathExists=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh
ConditionPathExists=/srv/host/rke2-manifests.d/clusterapi/staged

[Service]
Type=oneshot
ExecStart=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh clusterapi/staged
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

**Key difference**: The `ExecStart` argument includes the subpath: `clusterapi/staged` (not just `clusterapi`).

The script will:
1. Link from `/srv/host/rke2-manifests.d/clusterapi/staged/`
2. To `/var/lib/rancher/rke2/server/manifests/clusterapi/staged/`
3. RKE2 auto-deploy picks it up

=== Anti-Pattern: Direct kubectl apply

❌ **DO NOT** create units that run `kubectl apply -f`:

```bash
# WRONG - bypasses RKE2 auto-deploy
#!/bin/bash
kubectl apply -f /srv/host/manifests/clusterapi/staged/image-state-configmap.yaml
```

**Why this is wrong**:
1. Inconsistent with the rest of the manifest flow
2. Requires `kubectl` binary and kubeconfig access in the script
3. No policy-based enablement/disablement
4. No automatic re-application on file changes
5. Breaks the symlink pattern used everywhere else

✅ **DO** use the standard `rke2lab-manifests-install.sh` script with a subpath.

== Adding a New ManifestsUnit

**Step 1**: Create the unit in `manifests/src/main/java/.../units/{domain}/`, using the canonical
`(Construct scope, String id)` constructor and stamping package annotations on every resource.

```java
public final class MyManifestsUnit extends AbstractManifestsUnit {

  public static final String MANIFEST_UNIT_ID = ManifestDomainCatalog.MY_DOMAIN + "/my-thing";

  private final PackageMetadataProfile packageProfile =
      new PackageMetadataProfile("my-domain", "my-thing");

  public MyManifestsUnit(final Construct scope, final String id) {
    super(scope, id, MANIFEST_UNIT_ID, List.of());
    // Create ApiObjects on 'this', annotating with
    // packageProfile.packageAnnotations("|Kind|namespace|name")
  }
}
```

**Step 2**: Reference it from its domain registrar in `manifests/.../domain/`, via the lazy factory.

```java
public final class MyDomainRegistrar implements ManifestsDomainRegistrar {
  @Override
  public ManifestsDomain domain() {
    return new ManifestsDomain(
        ManifestDomainCatalog.MY_DOMAIN,
        List.of(),
        List.of(ManifestsUnit.lazy(
            MyManifestsUnit.MANIFEST_UNIT_ID, List.of(), MyManifestsUnit::new)));
  }
}
```

NOTE: the registrar provides a `ManifestsDomain`; the assembled registry's `resolve()` then orders
the units and checks coherence — see
link:manifests-architecture.adoc#ordering-and-coherence[Manifests Architecture → visit order and coherence].

**Step 3**: Create systemd unit in `manifests/src/main/resources/systemd/systemd-units/`

```ini
[Unit]
Description=Install RKE2Lab mylayer manifests from host share (post-server)
After=rke2-server.service
Requires=rke2-server.service
ConditionPathExists=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh
ConditionPathExists=/srv/host/rke2-manifests.d/mylayer

[Service]
Type=oneshot
ExecStart=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh mylayer
RemainAfterExit=true

[Install]
WantedBy=rke2lab.target
```

**Step 4**: Build and deploy

```bash
./mvnw clean package -pl :manifests,:seed-master
pulumi up
```

The new layer will automatically flow through all five stages.

== Adding a Staged Resource

**Step 1**: Create the staged manifest during Pulumi Output resolution

```java
// In ProviderStage or similar
final Output<String> manifestYaml = Output.all(
  state.someProviderOutput,
  Output.of("some-static-value")
).applyValue(outputs -> {
  return synthesizeStagedManifestYaml(outputs.get(0), outputs.get(1));
});

manifestYaml.applyValue(yaml -> {
  writeStagedManifest(yaml, "mylayer", "staged", "my-resource.yaml");
  return yaml;
});

private void writeStagedManifest(String yaml, String layer, String subpath, String filename) {
  Path targetDir = state.localPaths.assetsRoot()
    .resolve("manifests").resolve(layer).resolve(subpath);
  Files.createDirectories(targetDir);
  Files.writeString(targetDir.resolve(filename), yaml, StandardCharsets.UTF_8);
}
```

**Step 2**: Create systemd unit in `manifests/src/main/resources/systemd/systemd-units/`

```ini
[Unit]
Description=Install mylayer staged resource
After=rke2-server.service
ConditionPathExists=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh
ConditionPathExists=/srv/host/rke2-manifests.d/mylayer/staged

[Service]
Type=oneshot
ExecStart=/srv/host/systemd-scripts.d/rke2lab-manifests-install.sh mylayer/staged
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

**Note**: Use `mylayer/staged` as the argument to `rke2lab-manifests-install.sh`.

**Step 3**: First deploy writes the manifest locally

```bash
pulumi up  # Output.applyValue runs, writes to .local.d/.../manifests/mylayer/staged/
```

**Step 4**: Second deploy pushes to master and systemd applies it

```bash
pulumi up  # Pushes to /srv/host/rke2-manifests.d/mylayer/staged/, systemd unit runs
```

== Troubleshooting

=== Manifests not appearing in cluster

**Check 1**: Are manifests exploded locally?
```bash
ls .local.d/bioskop/master/host/manifests.d/{layer}/
```

**Check 2**: Are manifests on master?
```bash
incus exec master -- ls /srv/host/rke2-manifests.d/{layer}/
```

**Check 3**: Did the systemd unit run?
```bash
incus exec master -- systemctl status rke2lab-{layer}-manifests.service
```

**Check 4**: Are symlinks created?
```bash
incus exec master -- ls -la /var/lib/rancher/rke2/server/manifests/{layer}/
```

**Check 5**: Did RKE2 apply them?
```bash
kubectl get all -n {namespace}
```

=== Staged manifest not applied

**Check 1**: Does the manifest exist locally?
```bash
ls .local.d/bioskop/master/host/manifests/{layer}/staged/
```

**Check 2**: Was it pushed to master?
```bash
incus exec master -- ls /srv/host/rke2-manifests.d/{layer}/staged/
```

**Check 3**: Does the systemd unit exist and is it linked?
```bash
incus exec master -- ls /etc/systemd/system/rke2lab-{layer}-{name}-*.service
```

**Check 4**: Did the unit run?
```bash
incus exec master -- systemctl status rke2lab-{layer}-{name}-*.service
```

**Common issue**: Staged manifest was written during first `pulumi up` but not pushed until the SECOND `pulumi up`. The first deploy only creates the manifest locally; the second deploy pushes it to master.

=== Policy disabling layer

If policy disables a layer, the install script removes all symlinks:

```bash
# Check policy
incus exec master -- bash -c 'source /srv/host/rke2lab-environment.d/*.sh && env | grep MANIFESTS_PUBLISH'

# Example output
RKE2LAB_MANIFESTS_PUBLISH_MESH_ENABLED=false
```

If a layer is disabled, manifests remain in `/srv/host/rke2-manifests.d/` but symlinks are removed from `/var/lib/rancher/rke2/server/manifests/`, so RKE2 doesn't see them.

=== Unit condition not met

Check `ConditionPathExists` failures:

```bash
incus exec master -- systemctl status rke2lab-{layer}-manifests.service
# Look for "Condition: ... was not met"
```

Common causes:
- Wrong path in `ConditionPathExists` (e.g., `cluster-api` vs `clusterapi`)
- Manifests directory doesn't exist (synthesis failed or policy excluded it)
- Script path wrong

== Design Rationale

**Why RKE2 auto-deploy instead of kubectl apply?**

1. **Consistency**: All manifests (RKE2 built-ins + rke2lab layers) use the same mechanism
2. **Declarative**: File presence = desired state; no imperative apply commands
3. **Resilience**: RKE2 re-applies on file changes automatically
4. **Simplicity**: No need for kubeconfig management, retries, or error handling in scripts
5. **Boot-time application**: RKE2 applies manifests during startup, before other controllers run

**Why symlinks instead of copying files?**

1. **Storage efficiency**: Manifests stored once in `/srv/host/rke2-manifests.d/`
2. **Atomic updates**: Changing symlink target is atomic, no partial file writes
3. **Source tracking**: `ls -la` shows the original path, aiding debugging
4. **Policy application**: Script can remove/recreate symlinks without touching source files

**Why the manifests.d → rke2-manifests.d rename?**

Clarity of purpose: when operators see `/srv/host/rke2-manifests.d/`, it's immediately clear these are manifests for RKE2 to deploy, not arbitrary config files.

**Why separate layer units instead of one monolithic unit?**

1. **Dependency ordering**: Layers can depend on each other (storage before networking)
2. **Selective restarts**: Re-run just one layer without affecting others
3. **Failure isolation**: One layer failing doesn't block unrelated layers
4. **Policy control**: Each layer can be independently enabled/disabled
5. **Observability**: `systemctl status rke2lab-networking-manifests.service` shows layer-specific state
