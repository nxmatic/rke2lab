= Conditional Manifest Unit Inclusion
:toc: left
:toclevels: 3
:icons: font

== Overview

The manifest synthesis system supports **conditional inclusion of manifest units** and **bootstrap context access** within domains. This enables:

1. **Policy-driven conditional inclusion** - Optional manifest units based on policy flags (e.g., an optional unit within GitOps)
2. **Bootstrap identity access** - Infrastructure configuration (e.g., Incus remote name) passed through BootstrapIdentity
3. **Graceful ephemeral synthesis** - Units can skip when context is unavailable (smoke tests, unit tests)

**Key principle**: A single domain can contain both mandatory and optional manifest units. Optional units are controlled by policy flags, and all units have access to bootstrap context for configuration.

[CAUTION]
====
**Status (2026-06-03): this mechanism is dormant.**

The `ManifestsDomainRegistrar.domain(ManifestDomainPolicy)` hook exists as a default interface
method, but:

* No registrar in the `domain/` package currently overrides it — they all use the plain `domain()`
  form with a fixed unit list (see `GitopsDomainRegistrar`).
* So while the registry itself is live (it assembles the domains and `resolve()` orders them — see
  link:manifests-architecture.adoc#ordering-and-coherence[Manifests Architecture → visit order and coherence]),
  the *policy-driven conditional* hook that would vary a domain's unit list is not yet exercised.

The example used throughout this document is *illustrative only* — it uses a generic *optional
unit* placeholder. The component that once filled this role was evaluated and removed from the
project, so a neutral placeholder replaces it. Read this as the intended design for conditional
inclusion, to be restored alongside the domain registry; substitute a real optional unit when you
implement the mechanism.
====

== Implementation Details

=== ManifestsDomainRegistrar Interface

The link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/ManifestsDomainRegistrar.java[ManifestsDomainRegistrar] interface provides two methods:

[source,java]
----
public interface ManifestsDomainRegistrar {
  // Legacy method - no policy awareness
  ManifestsDomain domain();

  // Policy-aware method - override for conditional inclusion
  default ManifestsDomain domain(ManifestDomainPolicy policy) {
    return domain();
  }
}
----

**Backwards compatibility**: Existing registrars that don't need conditional logic continue using the no-arg `domain()` method. The default implementation calls it automatically.

**See also**: The interface JavaDoc includes a component diagram showing the policy flow. Navigate to link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/ManifestsDomainRegistrar.java[ManifestsDomainRegistrar.java] for implementation details.

=== Registrar Implementation Pattern

❌ **Don't do this** (separate domain per feature):

[source,java]
----
// Creates domain proliferation
public class OptionalDomainRegistrar implements ManifestsDomainRegistrar {
  public ManifestsDomain domain() {
    return new ManifestsDomain("optional-unit",
      List.of("gitops"),
      List.of(new OptionalManifestsUnit()));
  }
}
----

✅ **Do this** (conditional inclusion within domain):

[source,java]
----
public class GitopsDomainRegistrar implements ManifestsDomainRegistrar {
  @Override
  public ManifestsDomain domain(ManifestDomainPolicy policy) {
    List<ManifestsUnit> units = new ArrayList<>();

    // Mandatory units
    units.add(new FluxInstanceManifestsUnit());
    units.add(new SopsAgeSecretManifestsUnit());
    units.add(new FluxRootManifestsUnit());

    // Optional units based on policy
    if (policy.isEnabled("optional-unit")) {
      units.add(new OptionalManifestsUnit());
    }

    return new ManifestsDomain("gitops", List.of("replication"), units);
  }
}
----

**Real implementation**: See link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/domain/GitopsDomainRegistrar.java[GitopsDomainRegistrar.java] for the actual gitops registrar (note: it uses the plain `domain()` form today — the policy-aware variant above is the intended design, not current code), and link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/units/gitops/package-info.java[units/gitops/package-info.java] for the domain overview.

**Why this is better**:

* **Single source of truth**: One domain owns the feature, not scattered across multiple domains
* **Logical grouping**: the optional unit is part of GitOps, not a separate concern
* **No dependency complexity**: No need to declare cross-domain dependencies for tightly related features
* **Policy granularity**: Domain-level enable/disable + unit-level enable/disable

=== Policy Configuration

The policy is defined in two layers:

**1. ManifestDomainCatalog** (domain registry):

[source,java]
----
public String optionalUnit() {
  return "optional-unit";
}
----

**2. ManifestSynthesisScenario** (the scion derives the domain policy from its sown publish facet):

[source,java]
----
// ManifestSynthesisScenario.the_policy_is_derived_from_the_facet
final ManifestsRunbookInput.PublishFacet publish = facet.publish();
ManifestDomainPolicy domains =
    ManifestDomainPolicy.builder()
        .domainCatalog(CATALOG)
        .stageADefaults()
        .gitops(publish.gitops())            // <-- flat boolean read straight off the facet
        .networking(publish.networking())    // <-- the remaining domain flags follow the facet
        .build();
----

the optional unit is a UNIT *within* the gitops domain, not a domain flag of its own: its conditional
inclusion is decided by the gitops registrar's `domain(policy)` hook (see below), not by a
top-level publish toggle. There is no `publish.optional-unit` key.

**3. Pulumi Stack Configuration**:

[source,yaml]
----
config:
  rke2lab:manifests.publish.gitops: "true"   # Enable the gitops domain layer
  # (no publish.optional-unit key — the optional unit is a unit-level filter within gitops)
----

=== Accessing Bootstrap Identity for Infrastructure Configuration

Manifest units that need infrastructure configuration (Incus remote name, cluster name, etc.) access it via `bootstrapIdentity()`:

✅ **Do this** (use link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/profiles/BootstrapIdentity.java[BootstrapIdentity] for infrastructure context):

[source,java]
----
public class IncusIdentitySecretManifestsUnit extends AbstractManifestsUnit {
  @Override
  public void apply(final Chart chart) {
    final BootstrapIdentity identity = bootstrapIdentity();
    final String clusterName = identity.clusterName();           // "bioskop"
    final String incusRemoteName = identity.incusRemoteName();   // "bioskop-nixos"

    // Skip synthesis when running in ephemeral/test mode
    if (BootstrapIdentity.UNKNOWN.equals(clusterName)) {
      return;
    }

    // Read operator's Incus config using the remote name
    final Path incusConfigDir = Path.of(System.getProperty("user.home"), ".config", "incus");
    final String remoteAddress = readRemoteAddress(incusRemoteName, incusConfigDir);

    // Create secret with resolved infrastructure identity
    createIncusIdentitySecret(chart, clusterName, remoteAddress, ...);
  }
}
----

**Real implementation**: See link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/units/clusterapi/IncusIdentitySecretManifestsUnit.java[IncusIdentitySecretManifestsUnit.java] for the complete implementation, and link:../manifests/src/main/java/io/seedmatic/rke2lab/manifests/units/clusterapi/package-info.java[units/clusterapi/package-info.java] for the domain overview.

**Why this pattern**:

* **Separation of concerns**: Infrastructure identity comes from operator config, not hardcoded
* **Testable**: Units can run in ephemeral mode (smoke tests) by checking for `UNKNOWN`
* **Flexible**: Cluster name ≠ remote name; operator configures the mapping via Pulumi config
* **Fail-fast**: Missing config caught at synthesis time, not runtime

**BootstrapIdentity fields**:

* `clusterName` - Logical cluster name ("bioskop")
* `incusRemoteName` - Incus remote name from config ("bioskop-nixos")
* `clusterToken`, `clusterDomain`, `nodeName`, `nodeId`, `nodeKind` - See BootstrapIdentity.java

== Usage Patterns

=== Adding Conditional Units to Existing Domains

To add a new optional feature to an existing domain:

1. **Add policy flag** to `ManifestDomainCatalog` and `ManifestDomainPolicy`
2. **Override `domain(policy)`** in the domain registrar
3. **Check policy flag** before adding the unit to the list
4. **Map the facet key** in the scion's policy derivation (`ManifestSynthesisScenario`)

Example: Making mesh headplane optional:

[source,java]
----
public class MeshDomainRegistrar implements ManifestsDomainRegistrar {
  @Override
  public ManifestsDomain domain(ManifestDomainPolicy policy) {
    List<ManifestsUnit> units = new ArrayList<>();
    units.add(new MeshSystemNamespaceManifestsUnit());
    units.add(new HeadscaleManifestsUnit());
    units.add(new TailscaleManifestsUnit());

    if (policy.isEnabled("headplane")) {
      units.add(new HeadplaneManifestsUnit());
    }

    return new ManifestsDomain("mesh",
      List.of("networking", "replication"),
      units);
  }
}
----

=== When to Use Conditional Inclusion vs Separate Domains

**Use conditional inclusion when**:

* Feature is logically part of a larger concern (the optional unit ⊂ GitOps)
* Feature shares dependencies with sibling units
* Feature is optional/experimental/staged rollout
* You want fine-grained control without domain-level dependencies

**Use separate domains when**:

* Feature is independently valuable (storage, networking, mesh are distinct)
* Feature has complex cross-domain dependencies
* Feature represents a distinct architectural layer
* Domain-level enable/disable is the right granularity

== Policy Evaluation Flow

=== Two-Phase Filtering

The system applies policy in two phases:

**Phase 1: Unit-level conditional inclusion** (this document's focus)

* Happens during `domain(policy)` call
* Registrar queries policy flags
* Manifest units conditionally added to domain

**Phase 2: Domain-level filtering**

* Happens in `applyManifestDomainPolicy()`
* Entire domains enabled/disabled based on policy
* Domain dependency resolution (if A depends on B, enable B)

**Example**: `manifests.publish.gitops=true`, with the (illustrative) optional unit excluded within gitops

* **Phase 1**: GitopsDomainRegistrar creates domain with [Flux, SOPS, FluxRoot] (the optional unit excluded)
* **Phase 2**: gitops domain passes domain-level filter, units synthesized

**Example**: `manifests.publish.gitops=false`, with the optional unit included

* **Phase 1**: GitopsDomainRegistrar creates domain with [Flux, SOPS, FluxRoot, OptionalUnit]
* **Phase 2**: gitops domain filtered out entirely, nothing synthesized

== Troubleshooting

=== Optional Unit Always Included

**Symptom**: Manifest unit appears in synthesized YAML even when policy flag is disabled.

**Causes**:

1. Registrar not overriding `domain(ManifestDomainPolicy)`
2. Registrar checking wrong policy flag name
3. Policy not passed through from Pulumi config

**Fix**:

[source,bash]
----
# The optional unit has no top-level publish flag — it is filtered within the gitops
# registrar's domain(policy) hook. Verify the gitops layer is enabled:
pulumi config get rke2lab:manifests.publish.gitops

# Check synthesis logs
grep "Applying manifest-domain policy" /tmp/rke2lab.log

# Verify registrar override
grep -A 10 "domain(ManifestDomainPolicy" \
  manifests/src/main/java/.../GitopsDomainRegistrar.java
----

=== Optional Unit Never Included

**Symptom**: Manifest unit missing from synthesized YAML when policy flag is enabled.

**Causes**:

1. Parent domain disabled at domain level
2. Policy flag name mismatch between catalog and registrar
3. Unit constructor throws exception

**Fix**:

[source,bash]
----
# Check domain-level policy
pulumi config get rke2lab:manifests.publish.gitops  # Must be true

# Check policy flag matches catalog
grep 'public String optionalUnit()' \
  manifests/src/main/java/.../ManifestDomainCatalog.java

# Check for synthesis exceptions
grep "OptionalManifestsUnit" /tmp/maven.log
----

=== Policy Changes Not Reflected

**Symptom**: Changing Pulumi config doesn't affect synthesized manifests.

**Causes**:

1. Stale Pulumi state
2. Policy cached from previous run
3. Wrong stack active

**Fix**:

[source,bash]
----
# Verify active stack
pulumi stack ls

# Force policy refresh
pulumi config refresh

# Re-run with clean state
pulumi up --refresh
----

=== Remote 'X' Not Found in Incus Config

**Symptom**: Error during synthesis: `Remote 'bioskop' not found in /Users/nxmatic/.config/incus/config.yml`

**Causes**:

1. Manifest unit using `clusterName` instead of `incusRemoteName` to lookup Incus remote
2. Incus remote name doesn't match cluster name (e.g., cluster "bioskop" → remote "bioskop-nixos")
3. `BootstrapIdentity.incusRemoteName` not properly passed through from config

**Fix**:

[source,bash]
----
# Check Pulumi config for remote name
pulumi config get rke2lab:incus.defaultRemote

# Check what's in Incus config
grep -A 3 "^remotes:" ~/.config/incus/config.yml

# Verify BootstrapConfig loads the remote name
grep "incusDefaultRemote" seed-master/src/main/java/.../BootstrapConfig.java
----

**In manifest units**, always use `incusRemoteName()` not `clusterName()`:

[source,java]
----
// ❌ Wrong - assumes cluster name = remote name
final String remoteName = bootstrapIdentity().clusterName();

// ✅ Correct - uses configured remote name
final String remoteName = bootstrapIdentity().incusRemoteName();
----
