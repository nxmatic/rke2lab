= The Flux Kustomization planner — per-service today, domain-scoped (v2) planned
:toc: left
:toclevels: 3

== Overview

Every rendered branch (`manifests/<cluster>`) is reconciled by Flux. `FluxRootManifestsUnit`
seeds one root `Kustomization` `flux` (`path ./flux`) that OWNS a set of child Kustomizations
generated POST-EXPLODE by `FluxServiceKustomizationPlanner` (package-private in `manifests-core`,
wired in `DefaultManifestSynthesisService` after `explodeService.explode(...)`). The planner has the
exact set of non-empty `(layer, domain, package)` cells (from `ManifestExplodeResult.writtenFiles`)
and the in-memory unit graph (`CoherentManifestsDomainRegistry`), so it can wire each child's
`dependsOn` from real structure rather than a hand-maintained list.

This document records the *current* per-service model, the two gaps a live cold-start exposed, and
the *planned* v2: a **domain-scoped** layout that reflects the codebase (`ManifestDomainCatalog`
domains) with cross-domain ordering *derived* from the rendered CRDs rather than the coarse global
layer barrier.

WARNING: v2 is a DESIGN (not yet implemented). The current model below is what ships today.

== Current model (shipped) — flat per-service, global layer barrier

[mermaid]
....
flowchart TB
  Root["Kustomization 'flux'<br/>(root, OWNER, path ./flux)"]
  Root --> A["gitops-githubapp"]
  Root --> B["networking-kdns"]
  Root --> C["cicd-repository"]
  Root --> D["cicd-render-pipeline"]
  Root --> E["… 40 flat per-service Kustomizations"]
....

* One child Kustomization per cell `<layer>/<domain>/<package>`, named `<domain>-<package>` (a
  `-<layer>` suffix only when a service spans layers). `path ./<layer>/<domain>/<package>`, `prune`,
  `wait`, per-child SOPS decryption.
* `dependsOn` is *(a)* the **global layer barrier** — every cell of the immediately-previous
  non-empty layer (`crds → foundation → operators → workloads`), transitive, so a CR's CRD is applied
  first without enumerating each `CR → CRD` edge — plus *(b)* the **intra-layer** `service → service`
  edges from the unit graph (same layer only; cross-layer unit edges are dropped as either covered by
  the barrier or cycle-risking).

*Why it looks the way it does:* the exploded tree is **layer-first** (`<layer>/<domain>/<package>`)
and the barrier is **global** (all `crds` before all `operators`, across every domain). The model is
organised around reconcile ORDER, not the codebase — the domain is only a name segment, never a level
or a boundary. Good: per-service progress in `flux get ks`, local failure, independent retries.

== Two gaps a live cold-start exposed (2026-09-01)

. *Operator-installed CRDs aren't in the tree.* Tekton's `tekton.dev` (Task/Pipeline) and
  `pipelinesascode.tekton.dev` (Repository) CRDs are installed by the Tekton operator when it
  reconciles `TektonConfig` (profile `all`), ASYNC — they are not cells. The layer barrier cannot
  order a CR against a CRD that isn't in the tree, so `cicd-repository` / `cicd-render-pipeline`
  reconciled before the CRDs existed → `no matches for kind "Repository"/"Task"` → fail-then-retry
  until the operator caught up. Self-healed via Flux retry, but noisy + slow.
. *A `WaitForFirstConsumer` PVC + `wait: true` deadlocks the Kustomization.* The default storageClass
  (`openebs-zfs`) binds only when a pod consumes the PVC; the `manifests-maven-cache` PVC therefore
  stays `Pending` until the first PipelineRun mounts it, but Flux `wait: true` health-gates it → the
  `cicd-render-pipeline` Kustomization can never reach `Ready` (a false negative; the Tasks/Pipeline
  it also applies ARE usable).

Both point at the same root: the *global layer barrier* is a coarse proxy for real dependencies, and
`wait: true` health-checks every applied object indiscriminately.

== v2 (planned) — domain-scoped, derived cross-domain edges

Goal: a Kustomization layout that **reflects the codebase** (the `ManifestDomainCatalog` domains),
decouples domains, and derives cross-domain ordering from the rendered CRDs.

=== Structure — three levels (ownership)

[mermaid]
....
flowchart TB
  Root["Kustomization 'flux' (root, OWNER)"]
  Root --> Dgit["domain 'gitops'"]
  Root --> Dnet["domain 'networking'"]
  Root --> Dcicd["domain 'cicd'"]
  Dcicd --> Ktek["cicd-tekton-pipelines<br/>(healthCheck: TektonConfig)"]
  Dcicd --> Krepo["cicd-repository"]
  Dcicd --> Krender["cicd-render-pipeline<br/>(wait:false — WFC PVC)"]
  Dcicd --> Khook["cicd-pac-webhook"]
  Krepo -->|dependsOn| Ktek
  Krender -->|dependsOn| Ktek
....

* Root `flux` owns per-**domain** Kustomizations; each domain Kustomization owns its per-**service**
  Kustomizations. `flux tree` then shows the domain groups natively; `flux get ks` reads grouped.
* *Intra-domain* ordering: the layer barrier applies WITHIN a domain (`crds → operators →
  workloads`) + intra-layer service edges — unchanged, but domain-scoped.
* *Cross-domain* ordering: **only** the derived `CRD → CR` edges (below) + the declared domain deps
  from the registrars (`ManifestsDomain`'s second arg). The coarse GLOBAL barrier is RETIRED — no
  more false coupling (e.g. `networking` workloads waiting on `cicd`'s slow operator).

The declared domain DAG today (registrars) is small: `gitops → platform`, `networking → cluster`,
`runtime → cluster, platform`. An audit proved it is INCOMPLETE for `CRD → CR` (see below) — which is
exactly why v2 DERIVES the edges instead of trusting the hand-declared list.

=== The derivation — `kind → CRD-defining cell`

The planner already runs post-explode with every written file. v2 adds two passes:

. *Build the CRD-provider index* — scan every written doc; for each `CustomResourceDefinition`, key
  `(spec.group, spec.names.kind)` to the cell that wrote it:
+
[source]
----
Map<GroupKind, Cell> crdProvider   // (group, kind) -> defining cell
----
. *Resolve every rendered CR's CRD dependency* — for each written doc, read `apiVersion` (→ group) +
  `kind` and resolve:
+
[cols="1,2",options="header"]
|===
| Case | Resolution
| `(group,kind)` in `crdProvider`, provider cell ≠ this cell
| add a DERIVED `dependsOn` (this cell → the CRD-defining cell) — may be cross-domain, e.g.
  `cluster-api`'s `cert-manager.io` `Certificate` → `platform`'s cert-manager cell.
| built-in kind (Deployment, Service, Secret, Namespace, Ingress, ConfigMap, …)
| skip — no CRD.
| `(group,kind)` not in the tree, but group is a KNOWN operator group (`tekton.dev`,
  `pipelinesascode.tekton.dev`, `triggers.tekton.dev`)
| the CRD is operator-installed → attach a healthCheck (see below), not a `dependsOn` edge.
| otherwise (no provider, unknown group)
| *fail-fast at render* — an unresolved CRD is a bug; failing loud beats a silent cold-start
  fail-retry.
|===

=== Operator-installed CRDs — a healthCheck that also fixes gap (1)

CRDs an operator installs at runtime aren't cells, so no edge can be derived. A small explicit map
routes them to the operator's readiness resource:

[source]
----
tekton.dev | pipelinesascode.tekton.dev | triggers.tekton.dev
  operator cell : cicd/tekton-pipelines
  healthCheck   : { operator.tekton.dev/v1alpha1, TektonConfig, config }
----

The operator cell (`cicd-tekton-pipelines`) gets `spec.healthChecks: [TektonConfig config]` → it is
`Ready` only once the operator has FINISHED installing the CRDs; the CR cells `dependsOn` the operator
cell → they reconcile only after. This closes gap (1): no more `no matches for kind` at cold-start.

=== `WaitForFirstConsumer` PVCs — no health-gate (gap 2)

A cell that renders a PVC bound `WaitForFirstConsumer` gets `wait: false` (or excludes the PVC from
an explicit `spec.healthChecks`), so a legitimately-`Pending`-until-first-consumer PVC never wedges
the Kustomization at `Ready=false`.

== Anti-patterns

* ❌ *Hand-declare cross-domain deps and trust them.* The `cluster-api → platform` cert-manager edge
  was MISSING from the registrars for months — the global barrier hid it. ✅ Derive `CRD → CR` edges
  from the rendered tree; the declared domain deps are a coarse supplement, not the source of truth.
* ❌ *A global layer barrier as the CRD-before-CR mechanism.* It couples unrelated domains and still
  misses operator-installed CRDs. ✅ Precise derived edges + operator healthChecks.
* ❌ *`wait: true` over a `WaitForFirstConsumer` PVC.* Deadlocks on a Pending-by-design PVC. ✅
  `wait: false` for that cell.
* ❌ *Domain as a mere name segment.* ✅ Domain as an ownership level (root → domain → service), so
  the reconcile graph mirrors `ManifestDomainCatalog`.

== Troubleshooting

[cols="1,2",options="header"]
|===
| Symptom | Cause / fix
| `no matches for kind "<X>"` on a cicd Kustomization at cold-start
| The operator hasn't installed the CRD yet. v2: the CR cell `dependsOn` the operator cell whose
  healthCheck waits for `TektonConfig` Ready. Pre-v2: Flux retries; force with `flux reconcile`.
| A render Kustomization stuck `Ready=false` / Progressing with all objects applied
| A `WaitForFirstConsumer` PVC is `Pending` (binds on first consumer) but `wait: true` health-gates
  it. v2: `wait: false` for that cell. `kubectl get pvc -n <ns>` shows `WaitForFirstConsumer`.
| A cross-domain CR applies before its CRD after retiring the global barrier
| A derived `CRD → CR` edge is missing — the CRD isn't in the tree AND its group isn't in the
  operator map. The planner should fail-fast at render; add the operator group or fix the CRD cell.
|===
