= Doctor: clinical-vocabulary refactor, then live medical-record wiring
:toc: left
:toclevels: 3

== Overview

This branch delivers the FIRST step of the doctor roadmap — _wire the medical record into
the live doctor_ — but a design review surfaced a prerequisite: the doctor's domain
vocabulary contains one French word, `Dossier`, sitting on the *wrong concept*. Fixing the
names is mandatory and must land *before* the wiring, so the new code is written in the
correct vocabulary from the first line.

The work is therefore two sequenced chantiers on one branch:

. *Clinical-vocabulary refactor* (prerequisite) — rename the model to authentic American
  clinical English. Atomic, no-compat.
. *Live medical-record wiring* (the original goal) — the doctor retrieves the patient's
  record from a registry he holds, as the first act of a consultation.

Why this is worth a big refactor: the vocabulary is *load-bearing* for the two chantiers
that follow this branch (remediation round-trip; what-if planner). A word that means the
opposite of what it says would compound across all three. Caught at design time, the fix is
cheapest now.

== Chantier 1 — the clinical-vocabulary refactor

=== The defect

The patient consults *exposing symptoms*; he does not carry his file. The doctor retrieves
the file himself. But the code's `consult(Symptom, Dossier)` names the patient-brought
probe snapshot `Dossier` — a French word that, in clinical English (_dossier médical_),
actually means the *file the doctor retrieves*. The word is both non-English (against the
shared-artifacts-in-English convention) and on the inverted concept.

The English word for "the file the doctor retrieves" already exists in the code: it is
`MedicalRecord` (US _medical record_ / _chart_). So we do NOT move "dossier" onto the file —
we remove it, and free its slot (the self-observed snapshot) to be named `Observation`
(the US clinical term for a recorded finding about a patient's state).

=== Vocabulary: before → after

The mapping to read first — _Patient_ = the stack; _Visit_ = one deployment / update;
_MedicalRecord_ = the file across all visits; the snapshot the probe presents = _Observation_.

`Generalist`, `Specialist`, `Prescription`, `Symptom`, `ConsultationReport`,
`RemediationPlan`, `RemediationProgramRef`. "Remediation" is our own established English
design vocabulary, not French — kept.

=== Roles vs types — the "prescriber" note

"Prescriptor" is not English. The correct word is *prescriber* (one who writes a
prescription). It is a ROLE the `Specialist` already plays (it writes the `Prescription`),
not a new type. The one who later *fills/administers* the order is the step-2 Remediator
(clinically a pharmacist/nurse). No new type is introduced by this chantier.

=== Documentation strategy (the hard half)

Code has a compiler; docs do not. A stale `Dossier` in Java fails to build; a stale
`Dossier` in an `.adoc` silently misleads the next reader. So the docs are where this
refactor can rot invisibly — handled deliberately:

* *Live / authoritative docs — rename now*: `runbook-doctor.adoc`,
  `medical-record-query-api-design.adoc`, `layer3-medical-record-design.adoc`,
  `layer3-readside-runtime-enrichment-design.adoc`, `pulumi-doctor-integration.adoc`, and
  the `docs/README.adoc` hub.
* *Frozen exploration docs — glossary pointer only*: `preview-whatif-replay-exploration.adoc`,
  `rules-engine-checkpoint-topology-exploration.adoc`,
  `drools-network-specialist-prototype.adoc`. These record point-in-time thinking; rewriting
  them would falsify history. Each gets a one-line note: "predates the vocabulary rename
  (2026-06-10); see glossary".
* *New `docs/architecture/doctor/glossary.adoc`* — the single source of truth: each term, its
  meaning, and the old→new mapping with rationale.

=== Verification

Per the build-verification discipline: the rename is green only when proven by the real
build with the cache skipped and tests forced on, counting surefire reports — never trusting
a bare BUILD SUCCESS. The existing doctor test suite (MedicalRecord/Reader/Dump,
DiagnosisReader, Doctor scenarios) is the safety net: it must stay green with zero behavior
change, only renamed symbols.

== Interlude — practitioner communication and the Assessment gap

A design question surfaced while fixing the vocabulary: _where is the transfer of
information between the Generalist and the Specialist figured?_ Today the only channel is
`Specialist.diagnose(Symptom, Observation) → Optional<Prescription>`. So:

* When the specialist has a treatment, its communicated "why" rides in the `Prescription`
  (`humanHint` = prose, `payload` = structured findings), and the `RemediationPlan` holds the
  list of prescriptions plus the `generalistSummary`. For this case the transfer IS figured,
  and the `RemediationPlan` is its home.
* When the specialist has FINDINGS but NO treatment, it returns `empty()` and everything it
  concluded is dropped. A specialist can only speak by prescribing — there is no home for a
  standalone assessment.

The clinical frame names the gap. US clinical notes are SOAP — Subjective, Objective,
*Assessment*, Plan:

[cols="1,2,1",options="header"]
|===
| SOAP | Our model | Status
| Objective | `Observation` (the renamed `Dossier`) | have it
| *Assessment* (the clinician's "why") | — | *the gap*
| Plan | `RemediationPlan` / `Prescription` | have it
|===

Critically, the transfer is NOT a point-to-point letter: the specialist shares findings with
the generalist AND the other prescribers, persisted in the chart. *The `MedicalRecord` IS the
shared communication channel* — every prescriber writes findings into it and reads it. That is
exactly why chantier 2 (wiring the record into the live doctor) is the prerequisite: there is
no practitioner-to-practitioner communication until the live doctor can READ the record.

=== Decision — `diagnose()` returns a `Diagnosis` (step 2, not built in this branch)

The specialist should ALWAYS speak. `Specialist.diagnose(...)` will return a `Diagnosis`
carrying an `Assessment` (the findings/"why", always present) and an `Optional<Prescription>`
(the plan, when one exists). The `RemediationPlan` aggregates the diagnoses; the `Assessment`
is persisted on the `ConsultationReport`, hence in the `MedicalRecord`, readable by all
prescribers.

This also fixes a pre-existing misnomer: the existing `DiagnosisReader` does not read
diagnoses — it reconstructs `ConsultationReport`s from output maps. Chantier 1 renames it
`ConsultationReportReader`, which frees the word `Diagnosis` for this new return type.

== Chantier 2 — live medical-record wiring

With the vocabulary corrected, the original goal — in the new words.

=== The clinical model

The patient consults exposing only symptoms. The doctor's FIRST act of the visit is to
retrieve the patient's `MedicalRecord` from a `MedicalRecordRegistry` he holds; THEN he
processes the visit (the existing route → diagnose → synthesize). `consult(Symptom,
Observation)` is unchanged in shape — the record is NOT a parameter; the doctor pulls it.

There is exactly one patient today (the stack being provisioned). The registry is general by
interface (`recordFor(Patient)`), populated with one — no multi-patient machinery is built
for patients that do not exist yet.

=== Lazy retrieval

`consult` only fires on a checkpoint FAILURE, so healthy runs never retrieve and never
reconstruct. On the first failure the held registry reconstructs once and memoizes for the
rest of the run. Retrieval runs in BOTH `up` and `preview` (the read is pure, lock-free, and
step 3's what-if planner will need it in preview) — no `isDryRun` gate on the read.

=== Degrade-to-empty

Reconstruction must NEVER break provisioning. A non-file backend, unresolved coordinates, or
a reconstruction failure yields an empty `MedicalRecord` and a logged reason — never a throw
into the pipeline. The doctor processing a visit with an empty record is a valid, safe state.

[mermaid]
....

    Q1 -->|no| EMPTY["empty MedicalRecord<br/>log degrade reason"]
    Q1 -->|yes| Q2{coordinates resolved}
    Q2 -->|no| EMPTY
    Q2 -->|yes| READ["MedicalRecordReader read"]
    READ --> Q3{read clean}
    Q3 -->|reconstruction failure| EMPTY
    Q3 -->|yes| FULL["full MedicalRecord"]

=== Scope guarantee — wire-only

Step 1 is the FOUNDATION: the record reaches the doctor and the retrieval really runs, but it
does NOT yet change routing or severity, and NOTHING derived is stored back into any
`ConsultationReport` (no hand-rolled history duplicating what Pulumi already keeps). Proven by
a test (seeded backend → doctor retrieves a non-empty, correctly-reconstructed record; absent
backend → empty record) plus a log line. Existing output/runbook golden tests stay green.
Acting on the record is step 2 (remediation).

== Sequencing and conventions

. Chantier 1 lands first and is verified green (real build, tests forced, surefire counted)
  before any chantier-2 code is written — the new code must be born in the corrected
  vocabulary.
. No-compat throughout: old names and the old output key are deleted in the same change that
  introduces the new ones; no aliases, no deprecation.

== Typed recovery errors — the `Symptomatic` capability

A scenario's readiness check has two channels for the SAME failure. The structured one is the
`ObservationWire` it records into the `readiness-checkpoint` envelope — a `status`, a `summary`, a
typed `SymptomKind`, and an open `details` bag — which the doctor reads after the play. The second
is the throwable the fail-fast WHEN/THEN raises so jGiven marks the step FAILED and the chain skips
the rest.

The defect was that this throwable was a *bare* `AssertionError` whose only signal was a flattened
message string: a catcher (a doctor specialist, the runbook's error enricher) got a sentence to
re-parse, not data. `Symptomatic` (in `doctor-contract`, beside `SymptomKind`) closes that gap —
the capability a readiness failure carries so its recovery data is typed:

* `symptom()` — the same `SymptomKind` routing key the observation records, so a catcher routes to a
  specialist without string-matching;
* `recoveryContext()` — the typed twin of the observation's `details` bag.

It is an INTERFACE, not a base class, deliberately: `doctor-contract` is a pure-contract bundle
(only records / enums / interfaces / sealed ADTs may cross its exported surface — the
`contract-purity` staging gate), and a throwable base would be a concrete class. So each domain
raises its own `AssertionError` subclass that `implements Symptomatic` and ALSO exposes its own
typed member — the datum a domain-aware catcher downcasts for: `SystemdNotReadyError.snapshot()`
(the systemd status snapshot, or null when the endpoint was unreachable),
`ClusterNotReadyError.phase()`, `IncusImageBuildError.request()`,
`BboxReservationError.refusedRows()`, `NetplanExportError` (path + reason), `ManifestSynthesisError`
(result + which `Gap` failed). A consumer reads them uniformly by pattern:

[source,java]
----
if (throwable instanceof Symptomatic s) {
  route(s.symptom());            // typed routing key, no string-parsing
  inspect(s.recoveryContext());  // structured facts
}
----

[cols="1,1",options="header"]
|===
| ❌ Anti-pattern | ✅ Typed
| `throw new AssertionError(phase.label() + ": not ready")` | `throw new ClusterNotReadyError(phase, symptom)`
|===

It does NOT couple the scenario engine to `doctor-contract`: the engine's `enrichFailedCase` still
renders the throwable's message + stack; the typed data is for the in-realm catcher and mirrors the
checkpoint channel, it does not replace it.
