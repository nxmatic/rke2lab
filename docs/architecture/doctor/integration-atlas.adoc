[NOTE]
====
*Status:* LIVING INTEGRATION VIEW — maintained, not frozen. This atlas is the one place that holds
the whole doctor *specification* corpus together and proves each new model is *additive* against the
others. It is reopened at the START of every doctor design activity (see "The ritual"). It carries
no implementation detail of its own; it is a map of models and their seams.
====

== Why this atlas exists

The doctor subsystem accumulated a dozen design models across many sessions — some implemented, some
explorations. Each new model risks silently contradicting or duplicating the others. This atlas is
the antidote: a single view that lists every model, draws how they connect, and — when a model is
added — *proves it is additive* by a simple visual test.

*The test of "additive" is MONOTONE before/after.* Draw the model constellation without the new
model (before), then with it (after). Additive means: *no box erased, no arrow rewired, only
additions.* If "after" cannot be drawn without rubbing out a line of "before", the model is not
additive — and the figure says so out loud. This operationalizes the project principle that *a
well-integrated spec is itself the proof we are on the right path.*

Legend used throughout: thin/blue = IMPLEMENTED (built); thick/green = the model under design;
dashed/amber = EXPLORATION (not built, future); grey = cross-cutting foundation.

== Verdict — does it hold?

An honest reading of the three figures:

. *Monotone: yes.* No blue box or arrow is erased or rewired from A to B, or within C. Every change
  is an addition. The HealthSystem model is additive against the whole constellation.

. *Two honest edits (changes, not deletions):*
.. `Generalist` gains a held `ClinicalAccess` (it held registry + patient before). That is a *changed
   collaborator*, but the read core it ultimately calls is unchanged — the wrap is real, not a
   rewrite.
.. `LiveMedicalRecordRegistry.cohortFor` loses its `@Spike` marker on promotion. A marker strip, not
   a logic change.

. *The explorations gain seams, lose nothing:* the what-if planner now has a concrete patient-record
  provider (the HealthSystem), and the rules-engine / referral work has the named grant seam to plug
  into. The keystone does not merely sit beside the explorations — it makes them more buildable.

. *The one not-yet-proven edge* is the amber dashed "grant seam awaits referrals". It is proven only
  when step 2 plugs referral-derived grants into the GrantPolicy. Everything else is solid today.

Conclusion: the constellation holds, and HealthSystem is additive.

[NOTE]
====
*Confirmed in code (2026-06-11).* HealthSystem shipped on `feature/healthsystem-keystone`, and the
additivity the figures predicted held: no built box was rewritten — `Generalist` swapped its held
collaborator (registry+patient → `ClinicalAccess`) but the read core it calls is unchanged, and the
only other touch was stripping the `@Spike` marker. The 121-test build stayed green throughout. The
before/after figures above are kept *frozen* as the design-time proof; the inventory row carries the
live ✅ status. The amber "grant seam awaits referrals" edge remains the single not-yet-proven edge,
deferred to step 2.
====

== The ritual — how this atlas stays alive

Reopen this atlas at the START of every doctor design activity, before writing a new model's spec:

. *Add the new model* as a green box in a fresh before/after pair (or extend Diagrams A–C).
. *Prove monotone:* confirm no existing box or arrow is erased or rewired. If you must erase one,
  STOP — the new model is not additive; rework the seam until it is, or record explicitly why a
  breaking change is justified.
. *List honest edits:* any changed collaborator (not just additions) is named in the verdict, as
  the two edits above are.
. *Flip green→blue* when a model ships, and update its inventory status.
. *Update the inventory table* with the new model and its links.

This keeps "a well-integrated spec is the proof we are on the right path" a standing practice, not a
one-time exercise.
