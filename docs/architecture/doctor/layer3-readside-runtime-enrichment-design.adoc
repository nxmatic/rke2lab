.OSGi re-baseline
====
The mechanism is preserved: the doctor's diagnosis (`⚕` summary + `℞` prescriptions) is injected into
the JGiven `ReportModel`'s `extendedDescription` so JGiven's AsciiDoc generator renders it into the
runbook node — no custom renderer, no text post-processing. What migrated is the *ownership*: in the
OSGi as-built the `scenario-engine` owns the play + the shared `ReportModel`, `ScenarioGraft` grafts
each played scenario (and its FAILED status) into it, and `RunbookRenderer` renders the enriched model
to AsciiDoc (into `host.live.d`). The pre-OSGi carriers this doc names — `ConsultationLog`,
`BootstrapStage`'s `finally`, `render(ReportModel, ConsultationLog)` — are the pre-OSGi shape; the
join still anchors on the `Checkpoint` enum (`doctor-contract`), `scenarioTitle()`.
====

== The problem

The write-side made the stack state self-describing, but the *operator* still cannot read the
diagnosis where it is comfortable. Today, on a (simulated or real) checkpoint failure, the doctor's
diagnosis (`⚕` summary + `℞` prescriptions, e.g. the `incus exec … systemctl restart …` remediation
command) appears ONLY in the verbose Pulumi log — interleaved with JGiven's `PlainTextReporter` prose
(`Given/When/Then`, `Test Class: null`). The *rendered runbook* (`target/runbook/adoc/…`, previewed
in VSCode — the readable surface) shows the FAILURE but NOT the diagnosis: the diagnosis lives in the
`ConsultationLog`, which is separate from the JGiven `ReportModel` that the renderer consumes, so the
JGiven AsciiDoc generator never sees it.

== Scope — runtime enrichment only; reconstruction re-discussed after

The "read-side" conflates two ambitions of very different sizes. This chantier is the SMALL one:

* *NOW — runtime enrichment.* Inject the diagnosis into the rendered runbook AT RUNTIME, so the
  operator reads `⚕`/`℞` in the VSCode `.adoc` preview. The `ConsultationLog` is already available at
  the render point, so this is cheap and reads no state.
* *DEFERRED — post-hoc reconstruction.* The offline tool (parse `pulumi stack export` → rebuild the
  DAG → graft the serialized `consultationReport` → render) is NOT built here. The write-side already
  made it POSSIBLE (the diagnostic is in state). *User's call: re-discuss it AFTER this runtime change
  ships, with the rendered runbook in front of us* — deciding on concrete output may reframe it as
  "just reproduce this same render from the state", which sharpens the no-drift criterion (runtime
  render == reconstructed render). Not abandoned; just not pre-built (YAGNI).

== Approach — inject into the JGiven model (fork resolved: A)

The renderer fork (spec left a/b/c open) is resolved to *A: inject into the JGiven model; JGiven keeps
rendering.* Verified fact (inspected jgiven-core 2.0.3): the AsciiDoc report visitor reads BOTH a
scenario's `description` and `extendedDescription` — so those fields ARE rendered into the AsciiDoc.
That makes `extendedDescription` the injection vehicle: no fighting JGiven's layout, no custom
renderer, no fragile text post-processing.

Rejected: *B (our own renderer)* — would re-implement the index/statistics/features generation JGiven
gives for free; the long-term "our model = source" direction, but not justified for this small need.
*C (post-process the generated AsciiDoc)* — fragile, depends on JGiven's output format.

== The injection mechanism

Before rendering, walk the `ConsultationLog`; for each `ConsultationReport`, find the matching
`ScenarioModel` in the `ReportModel` and set its `extendedDescription` to the formatted diagnosis
(`⚕` generalist summary + each `℞` prescription with its remediation command). JGiven renders it.

*The join key — a third identity, anchored on the enum.* The `ConsultationReport` is keyed by
`checkpointId()` = `Checkpoint.slug()`. A `ScenarioModel`, however, is identified by its TITLE (the
string passed to `startScenario(...)`: "systemd adapter becomes reachable", "cluster becomes ready")
— a THIRD vocabulary beside slug and resourceName. Rather than hand-align a third literal (the
clusterApi/cluster-api risk again), the `Checkpoint` enum gains a `scenarioTitle()` identity
attribute; the two production `startScenario(...)` call-sites consume it. The runtime join is then
`slug → Checkpoint → scenarioTitle → ScenarioModel`, all from the single source. *The enum carries
identity (slug, resourceName, scenarioTitle), never topology* — consistent with the write-side
decision.

*Where it lives.* `RunbookRenderer.render(...)` takes the `ConsultationLog` as a second argument —
`render(ReportModel, ConsultationLog)` — and does the graft just before generating, so enrichment and
rendering are one unit, tested together. `BootstrapStage`'s `finally` passes the `consultations` it
already owns.

== TDD entry point + ordering

The TDD entry point is `RunbookRenderingTest`. Today it plays a FAILED systemd-adapter scenario with
NO `ConsultationLog` and asserts the runbook does NOT contain "Diagnosis"/"Mitigation" ("before the
doctor exists"). The flip: build a `ConsultationLog` carrying one `ConsultationReport`, call
`render(model, consultations)`, and assert the runbook now CONTAINS the diagnosis (the
`restart-systemd-unit` prescription). Red until `render` injects; green after — the test drives the
implementation.

*Step 4 — the log cleanup, last by design (operator-UX decision).* Strip the Pulumi log to
*reference-pure*: remove the two `logReport(reportModel)` calls (the verbose JGiven prose) AND the
`log(⚕)`/`log(℞)` lines in each stage's `consultDoctor(...)`. The log keeps only the per-checkpoint
status (`✓`/`⚠`/`✗`) and the existing `runbook rendered → …/index.asciidoc` reference. This is LAST
because the diagnosis must already live in the rendered runbook before it is removed from the log —
otherwise the remediation command would vanish from both places.

== Guard — unchanged from the write-side

No Pulumi outputs change: the `extendedDescription` is set on the in-memory `ReportModel` (the local
runbook render), never on the stack state. `OutputBuilder` is untouched; the per-node
`consultationReport` outputs from the write-side are untouched; `ClusterReadinessProjectionTest` stays
green. The scenario TITLES are kept byte-identical (only their SOURCE moves to the enum), so
`NestedRunbookTest` / `RunbookRenderingTest` title assertions stay valid.

== Verification

* Steps 1-2: unit tests (real TDD, no preview) — `Checkpoint` test green; `RunbookRenderingTest`
  flipped to assert the diagnosis is present.
* Steps 3-4: fully verifiable only by a user-run simulated-incident preview
  (`pulumi preview … -c rke2lab:policy.preview.simulate.systemd-adapter=connection-refused`): the
  diagnosis appears in `target/runbook/adoc/…` AND the Pulumi log is concise (reference-pure). The
  blocking gate on the agent side is the green build + flipped test.
