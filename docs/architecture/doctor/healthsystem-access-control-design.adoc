== Overview

The doctor diagnoses provisioning failures by consulting a patient's longitudinal record. As the
model gained multiple clinicians (Generalist + Specialists) and the prospect of multiple patients
(stacks), three questions surfaced that the bare "registry returns a record" seam could not answer:

. *Who may read whose record?* A clinician should see a patient's record only when it has a
  legitimate reason — not ambient access to everyone.
. *What may a clinician share?* It may use a record in its analysis but emit only *deductions*
  (conclusions), never copy one patient's specifics into another's record.
. *How does cross-patient correlation work* without a shared data store, given each patient's record
  lives in its own stack?

The answer is a keystone entity — the *HealthSystem* — built once per run, that holds the shared
records registry and a grant policy, employs the clinicians, and admits the current patient. Access
is gated by a grant table; correlation is consent-bounded to a clinician's granted cohort; and
*nothing cross-cutting is persisted centrally* — the HealthSystem is shared by *identity* (same
code, same clinician ids in every run), not by a shared stack.

[NOTE]
====
*The metaphor is a tool, not a target.* We are developers, not clinicians. We keep a clinical term
only when it makes a concept instantly clear to a developer, and we drop healthcare *jargon* a
developer would have to look up: *NPI* (→ `ClinicianId`), *MRN* (→ `Patient`, which already is the
identity), *EHR* (→ `MedicalRecordRegistry`, the shipped type). What stays — Generalist, Specialist,
MedicalRecord, Visit, Prescription — earns its place by being immediately legible.
====

=== Vocabulary (developer-clear terms)

[cols="1,3",options="header"]
|===
| Term | Meaning

| *HealthSystem*
| The per-run keystone: holds the `MedicalRecordRegistry` and the `GrantPolicy`, employs the
  clinicians, admits the current patient. *Flat* for now — it employs clinicians directly, with no
  facility/Clinic sub-tier (a documented future, for multi-facility). One is built per run.

| *MedicalRecordRegistry*
| The shared records registry the HealthSystem holds; every read goes through it. It does not *hold*
  records — it *reconstructs* them on demand (see "Derived, not stored"). The shipped type; its role
  in this layer is "the registry".

| *Clinician*
| The supertype over `Generalist` and `Specialist`: an employed actor with a stable `ClinicianId`.
  Nothing else in the codebase is a Clinician, so the name is unambiguous.

| *ClinicianId*
| A clinician's stable, *self-declared* id (kebab-case, like `treats()`/`programRef`). The join key
  for grants and cohort correlation. The roster is *open* so a recruited clinician joins with a
  fresh id (a closed enum could not recruit — aligns with link:runbook-doctor.adoc[recruit-a-specialist]).

| *Patient*
| The patient's identity within the system = the stack identity (today's `Patient`
  org/project/stack). One record per patient. There is no separate "MRN" type — `Patient` already is
  the identity.

| *ClinicalAccess*
| The grant-checked, id-bound view a clinician reads records through. The HealthSystem mints one per
  clinician at employment, with the clinician's `ClinicianId` *closed over* (not a call parameter).
  A clinician cannot read as another id, and cannot mint its own access.

| *Grant*
| The right of a `ClinicianId` to read a `Patient`'s record. Keyed `(ClinicianId, Patient)`.

| *GrantPolicy*
| Mints and checks grants. Today from explicit *interim* rules (self-grant on admission; same-backend
  cohort granted). The exact seam where *referral-derivation* replaces the interim cohort rule later.

| *granted cohort*
| The set of patients a given `ClinicianId` holds grants on. A clinician may correlate across its
  cohort but emit only de-identified findings into the current patient's record.
|===

== The approach — gated EHR facade + credentialed views

The HealthSystem, built once at the readiness transition, does three things at construction:

* *holds* the raw `MedicalRecordRegistry` and a `GrantPolicy`;
* *admits* the current patient — the `GrantPolicy` mints this run's grants (self-grant; cohort);
* *employs* each clinician by minting it a `ClinicalAccess` bound to its `ClinicianId`.

A clinician reads through its access: `access.record(patient)` asks the `GrantPolicy`
`isGranted(boundId, patient)` and reads the registry only if granted — otherwise it returns an empty
record and logs the reason (the degrade-to-empty contract; the access never throws into
provisioning). The id is closed over in the access, so the clinician never passes an id and cannot
forge one; only the HealthSystem mints accesses, so a clinician cannot self-grant.

=== What the gate actually bites

The self-read (the admitted patient's own record) is *always* granted — admission mints the
self-grant — so the gate is trivial there. The gate is genuinely *exercised* on the *cohort*: the
cohort query returns only the sibling patients the clinician holds grants on. So "grant gating" and
"cohort correlation" are the *same layer*, exercised by the same `isGranted` check. A test
constructing a restricted `GrantPolicy` where a sibling is *not* granted, and asserting the cohort
*excludes* it, is the proof the gate is real and not decorative.

== Cross-patient correlation — confidentiality-safe

The registry offers a clinician a *granted-cohort query*: the records for the patients that clinician
holds grants on. Derived, not stored — enumerate the stacks in the shared backend, reconstruct each
record from its own history, filter by `(ClinicianId, Patient)` grant. The clinician folds over its
cohort and emits an *aggregate, de-identified deduction* (e.g. "this symptom is environmental, seen
across the cohort") into *only the current patient's record* — no other patient is ever named.

This is epidemiology by consent: a clinician correlates only over patients it legitimately holds
grants on, and the population insight is published as an aggregate (the way real epidemiology shares
findings as statistics, never as another patient's chart). The cohort is read-input; the only write
is the de-identified finding to the patient in the room.

The read half of this is *already proven* — the cohort-correlation spike folded across two seeded
patients live under `pulumi preview`, lock-free, with the benefit coming only from the sibling. This
layer adds the grant *filter* over that cohort and the de-identified emission.

== Derived, not stored — the no-shared-stack bridge

The crux that keeps this lightweight: *the HealthSystem is shared by identity, not by a store.* It
is the same code, with the same clinician ids, instantiated in every run. Therefore nothing
cross-cutting is persisted centrally — it is all derived per run:

* a *patient record* is folded from that patient's *own stack history* (already in the shared
  backend);
* the *granted cohort* is enumerated by scanning the *sibling stacks in the shared backend*
  (lock-free — reconstruction reads do not take the stack lock);
* the *clinician ids* are self-declared by the clinician code;
* *grants* are minted per run by the `GrantPolicy` — today from explicit rules, later derived from
  referrals recorded in the records.

So the registry is a *view over the union of per-patient stacks* plus per-run code. This is the same
single-source-of-truth principle that retired the earlier self-referential accumulator: do not store
what you can re-derive from a stable key. A dedicated records/clinic stack (persisting a grant index
centrally, written via the Automation API) is the *heavy, lock-bound fallback* — reached only if a
finding ever genuinely cannot be re-derived. It is not the design.

=== Interim grants vs referral-derivation

The north-star is *grants derived from referrals*: a clinician may correlate over a patient only if
that patient's record carries a referral naming the clinician. But no referral is persisted yet, so a
faithful referral-derived cohort gate would grant nothing today and turn off the proven correlation.
The chosen path: the `GrantPolicy` mints grants from *explicit interim rules now* (same-backend
cohort granted), keeping the gate real and enforced while the *source* is explicit. Referral
derivation plugs into the `GrantPolicy` later, without touching the registry, the clinicians, or
`ClinicalAccess`. The integration atlas marks this as the one not-yet-proven seam.

=== Boundary

This holds while *all patients share one backend* — enumerate-and-fold reaches sibling stacks only
within a backend. Multi-backend (patients on different Pulumi services) breaks enumerate-and-fold and
would force a real shared store. Noted as the boundary, not designed.

== Relationship to what is built

* As-built (OSGi): `MedicalRecordReader` (`doctor-core`) + the host `SnapshotSource`
  (`pulumi-edge`) + `JournalMedicalRecordRegistry` (`doctor-core`, renamed from the design-time
  `LiveMedicalRecordRegistry`) reconstruct a patient record from the host journal, backend-bound (not
  stack-bound) — so the *read* substrate for enumerate-and-fold exists.
* `JournalMedicalRecordRegistry.recordFor(Patient)` is the read seam. `ClinicalAccess` (`doctor-core`)
  wraps it with the grant check (`GrantPolicy.isGranted(boundId, patient)`); the registry's read core
  is unchanged.
* `JournalMedicalRecordRegistry.cohortFor(Patient)` is shipped and *promoted* (the `@Spike` marker is
  gone; the registry-level fold is ungated by design). The `(ClinicianId, Patient)` grant filter is
  *realized* one layer up, in `ClinicalAccess.cohort()`.
* The keystone is the single construction site: `DefaultHealthSystem` (`doctor-core`, the
  `HealthSystem` contract) holds the registry + `GrantPolicy`, employs the clinicians by minting each
  a `ClinicalAccess`, and admits the current patient — replacing the loose duplicated `Generalist`
  wiring.

== Build scope

* *Keystone + interim gate — SHIPPED (OSGi):* `HealthSystem` (`DefaultHealthSystem`),
  `Clinician`/`ClinicianId`, `ClinicalAccess`, `GrantPolicy` + `Grant` with explicit interim rules;
  `cohortFor` promoted off `@Spike`; the grant filter realized in `ClinicalAccess.cohort()`; the loose
  wiring collapsed into the keystone. Exercised by `ClinicalAccessTest`
  (`cohort_returns_only_granted_siblings`, `an_ungranted_read_degrades_to_empty_and_logs`),
  `HealthSystemTest`, and `GrantPolicyTest` in `doctor-core-test`.
* *Referral-derivation (later, step 2):* the `GrantPolicy` derives cohort grants from referrals
  recorded in the records — the one seam this design leaves explicit.
* *What-if correlation (later, step 3):* the granted-cohort query feeds the what-if planner.
