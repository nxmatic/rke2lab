== The distinction this doc rests on (read first)

The rules-engine exploration rejected *option ③ — Drools as substrate* because it would subsume the
`Generalist` and `Checkpoint`, and its working memory is hidden mutable global state (vs the
project's instance-passing discipline). This doc explores the *inverse containment*: the
architecture is unchanged and *contains* Drools inside a single `Specialist` implementation.

Why containment is legitimate where substrate was not:

* `Specialist.java` *names itself* "the AI-ready seam": _"`diagnose(Symptom, Dossier)` makes no
  assumption about implementation … a future Phase 2 could back the same interface with an
  out-of-process tool."_ A Drools-backed specialist is one such implementation; the Generalist
  neither knows nor cares.
* The working-memory objection *dissolves*: the `KieSession` is created, fed (`insert`),
  `fireAllRules()`, and disposed *within one `diagnose()` call*. It is a local, short-lived
  computation — not hidden global state. Instance-passing is respected because the session never
  escapes the method.

== Why the NetworkSpecialist is the right candidate (not DbusTcp)

`DbusTcpSpecialist.diagnose()` is *one `if`* (`symptom == CONNECTION_REFUSED → restart unit`). RETE
behind that is a sledgehammer on a pin. The threshold for "Drools earns its keep" is **a specialist
that diagnoses by several conditions that interact**, where the *combination* decides — and the
codebase already points at exactly one:

* The `Generalist.routeBySymptom` table *already* anticipates a network domain:
  `TIMEOUT → NETWORK`, `CONNECTION_REFUSED → SYSTEMD, NETWORK`, `API_NOT_READY → CLUSTER, NETWORK`.
  The `NETWORK` `SpecialistDomain` exists; no specialist fills it yet.
* A network failure is *intrinsically multi-condition*: the same symptom (`TIMEOUT`) can come from a
  missing route, a closed firewall port, an MTU/path-MTU mismatch, or DNS — and the *right*
  prescription depends on *which combination* of facts the dossier shows. That is the canonical
  shape RETE was built for.

== Where the facts come from — the PATIENT record IS the fact base (patient-centric, not practitioner-centric)

*Scope decision (2026-06-07, corrected): the fact base is the PATIENT record — the grouping of ALL
the consultations a given patient has been through, independently of which practitioner performed
them.* The patient (the Pulumi stack) is the grouping key, never the practitioner. An earlier cut of
this doc framed the fact base as "the specialist's own case history (all patients that consulted
me)" — *that was a practitioner-centric mistake.* The record does not slice by who diagnosed; it
slices by *who was treated*. Per the doctor model (`spec.adoc` line 24: "Medical record = the
patient-stack's longitudinal history … the git-versioned runbook `.adoc`"), there is *one record per
patient*, and a specialist diagnosing patient P reasons over *P's whole history* — every visit P has
been through, regardless of practitioner. RETE reasons over that accumulated patient memory, not over
a single snapshot.

This *strengthens* the Drools case rather than weakening it: RETE over a single dossier is marginal
(an `if` often suffices); RETE over a *patient history* — correlating "this patient showed
dbus-degraded three visits running", "the same prescription was issued to P and the symptom
returned" — is exactly what a forward-chaining engine is for. The patient memory IS the working
memory, and it is already built the project's way: the persisted, caller-owned medical record, not a
hidden singleton.

[#no-authored-by]
=== No `authoredBy` edge is needed — the record is patient-centric

An earlier cut claimed a *missing* patient↔specialist edge (`Prescription.authoredBy`) was a
prerequisite, so a specialist could retrieve "its" patients. *That requirement dissolves under the
patient-centric definition.* Because the record groups by patient — not by practitioner — building
patient P's history needs no knowledge of *who* diagnosed each past visit. The specialist diagnosing
P simply reads P's record whole. `ConsultationReport = { checkpointId (the patient), dossiers, plan }`
is already keyed by patient; that is sufficient. Recording the authoring specialist *might* still be
useful for other reasons (audit, the recruitment gradient), but it is *not* a prerequisite for the
fact base — a real simplification the correction buys.

=== Where the patient history is READ from — RESOLVED by the `medicalRecord` accumulator

[IMPORTANT]
====
*The read-path is no longer an open tension — it is resolved.* An earlier cut of this doc had the
specialist read P's history from *P's git runbook `.adoc`* (prose `⚕`/`℞`, not queryable) and noted
"the layer-3 placement is not resolved by the what-if". The what-if subject's *landing* superseded
that: the *self-referential `medicalRecord` accumulator* (link:preview-whatif-replay-exploration.adoc#the-solution[preview-whatif §THE SOLUTION]).
====

The patient record is delivered as a *first-class top-level stack output*: each run reads the
previous record (a self-`StackReference` Read, resolves in preview AND up), *appends* this run's
consultations, and *re-exports* it — so P's longitudinal history rides forward *in the output*, not
in fragile history reconstruction. For the rules-backed specialist this is strictly better than the
git-runbook framing on three axes:

. *Structured, not prose.* `medicalRecord` carries the consultations as structured data (the
  `ConsultationReport`s), not the rendered `⚕`/`℞` AsciiDoc the `RunbookRenderer` emits. Directly
  decomposable into facts — no re-parsing of prose.
. *Already in memory — the specialist stays pure.* The accumulator does the StackReference Read
  *once, above the seam* (in the generalist/orchestration layer); the longitudinal record is then the
  in-memory `ConsultationLog` (caller-owned) passed *into* `diagnose()` (via the `Referral`'s
  reference, per [[doctor-remediation-model]] pt.5). The specialist never touches Pulumi — instance-passing
  is respected exactly as for the current dossier.
. *Longitudinal by construction.* The time axis lives in the carried-forward output; the
  recurrence patterns a rules engine wants ("symptom X recurred 5× between t1–t2") are precisely the
  retention summary the accumulator keeps.

[#single-patient]
NOTE: *There is exactly one patient today* — the `rke2lab-management-cluster/dev` stack (verified:
one `Pulumi.yaml`, one state file). The *cross-stack* axis (one patient consulting *another* patient's
record) is a *different, future* concern — empty until a second stack appears (the `seed-vcluster`
chantier). The accumulator resolves the *cross-time, same-patient* read this prototype needs, which is
the one that is real now.

NOTE: *The cross-stack future case is also covered by the same solution.* Because `medicalRecord` is
*top-level* (`ctx.export`), a cross-stack `StackReference` *can* read another patient's record back
(top-level is the only channel `StackReference` sees — proven in the what-if). The earlier worry
(diagnosis serialized per-node → invisible to `StackReference`) is mooted: the accumulator's record is
top-level *on purpose*. The per-node `consultationReport` (shipped recadrage) stays intact as the
runbook read-side source; `medicalRecord` is *additive*, a different role.

Once a patient's history is in hand, the specialist's first job in `diagnose()` is to **decompose it
into typed facts** and insert them into the session — the current dossier plus the patient's relevant
past ones.

This decomposition step is itself a design point: the dossier's flat map becomes a *small set of
typed `NetworkFact` records*. Typing them is the precondition for RETE pattern-matching — Drools
matches on fact *shape*, not map keys.

== The rule set as a decision table (the design artifact, not DRL)

Expressed as a decision table — the same form a Drools spreadsheet compiles, and the form that
reviews fastest. Each row is a rule: a *when* (a conjunction of fact patterns) and a *then* (the
`Prescription` it writes). Salience orders conflict resolution.

[cols="1,3,2,1",options="header"]
|===
|Salience |When (fact pattern conjunction) |Then → Prescription |programRef

|40 (lowest layer first)
|`Reachability(reachable=false)` ∧ `RouteEntry(present=false)`
|"no route to host — add the route on the seed node"
|`CHECK_CONNECTIVITY`

|35
|`DnsResolution(resolved=false)`
|"name does not resolve — fix DNS / use the IP"
|`CHECK_CONNECTIVITY`

|30
|`Reachability(reachable=true)` ∧ `PortProbe(open=false)`
|"host up but port closed — open the firewall port (or the listener is down)"
|`CHECK_CONNECTIVITY`

|25
|`Reachability(reachable=true)` ∧ `PortProbe(open=false)` ∧ symptom=`CONNECTION_REFUSED`
|"port refused by a live host — the unit is down → restart it" (defers to systemd domain)
|`RESTART_UNIT`

|20
|`MtuObservation(pathMtu < expectedMtu)` ∧ symptom=`TIMEOUT`
|"path-MTU smaller than expected — large dbus/API payloads hang — clamp MTU"
|`CHECK_CONNECTIVITY`

|10 (catch-all)
|`Reachability(reachable=true)` ∧ `PortProbe(open=true)` ∧ symptom=`TIMEOUT`
|"reachable and open but timing out — suspect path/MTU or app-layer; escalate"
|`CHECK_CONNECTIVITY`
|===

The point this table makes: *the rows interact.* "Port closed" means different things when the
host is unreachable (route) vs reachable (firewall) vs reachable-and-refused (dead unit). In a Java
`if/else` cascade this becomes nested conditions whose order is load-bearing and easy to get wrong.
In RETE the *facts* drive matching and *salience* drives precedence — declaratively.

== Lifecycle — the bounded session (the instance-passing reconciliation)

.Sequence — KieSession lives and dies inside one diagnose() call, fed by the PATIENT record
[mermaid]
....
sequenceDiagram
  participant G as Generalist (reads medicalRecord ABOVE the seam)
  participant N as NetworkSpecialist
  participant K as KieSession (local)

  G->>G: medicalRecord = self-StackReference.read ⊕ this-run (accumulator)
  G->>N: diagnose(Referral) — refs P's record (in-memory) + run siblings
  N->>N: decompose (current dossier ⊕ P's record).details → List~NetworkFact~
  N->>K: newKieSession()
  loop each fact (current + P's history)
    N->>K: insert(fact)
  end
  N->>K: insert(symptom)
  N->>K: fireAllRules()
  K-->>N: prescriptions accumulated (by salience; recurrence rules can fire)
  N->>K: dispose()
  N-->>G: ReferralReply — carries the prescription(s), or keeps the why with none
  Note over K: session never escapes the method →\nno hidden global mutable state
  Note over G: medicalRecord read happens ABOVE the seam;\nthe specialist gets it by reference (instance-passing) — never touches Pulumi
....

The `KieContainer` (the compiled rule base) *can* be a stateless, immutable, long-lived singleton
(rules don't change at runtime); only the *stateful session* is per-call. That split is the clean
mapping onto the project's values: immutable rule base (shared, safe) + ephemeral session (local,
disposed).

== When does RETE actually win? — the honest threshold

.Java if-cascade vs Drools, for THIS specialist
[cols="1,2,2",options="header"]
|===
|Dimension |Java `if/else` cascade |Drools (RETE) behind the seam

|Few independent conditions (today: DbusTcp = 1)
|✅ trivial, obvious
|❌ overkill — do NOT use

|Several *interacting* conditions (NetworkSpecialist)
|⚠ nested, order-dependent, brittle to extend
|✅ declarative patterns; facts drive matching

|Conflict resolution (which prescription wins)
|hand-coded priority ints, easy to break
|✅ built-in (salience / agenda)

|Adding a rule
|edit the cascade, re-reason the ordering
|✅ add a row; engine re-derives

|Cost (deps, build, mental model)
|zero
|❌ KIE on the classpath, DRL/decision-table tooling, a second mental model
|===

*Reading:* the win is real *only* at the "several interacting conditions" row. The NetworkSpecialist
plausibly reaches it; DbusTcp never will. So the design conclusion is conditional, not absolute:
*Drools belongs in this system at most as one or two genuinely-correlating specialists — never as the
default specialist shape, and never above the seam.*

== Open tensions (named, not resolved)

. *Return arity — now framed by the `ReferralReply`, not `Optional<Prescription>`.* RETE naturally
  fires *several* rules. The new exchange ([[doctor-remediation-model]] pt.5) already moves the seam
  to `diagnose(Referral) → ReferralReply`, and a reply can carry *several* prescriptions (and keeps
  the *why* with none). So within-specialist multiplicity is *native* to the new seam — RETE's
  multiple firings map onto one `ReferralReply` carrying N prescriptions. The remaining sub-question is
  only conflict resolution *inside* the specialist (salience picks an order/winner) before it fills
  the reply. The old `Optional<Prescription>` tension is dissolved by the exchange redesign.
. *Who produces the network facts?* Today no probe emits reachability/port/MTU/DNS into
  `dossier.details`. The Drools specialist is only as good as the facts the probe captures — so a
  richer `NetworkReadinessProbe` is a *prerequisite*, and may be the larger piece of work than the
  rules themselves.
. *Ingesting P's longitudinal record at diagnose-time — cost & shape, not placement.* The read-path
  itself is *resolved* (the `medicalRecord` accumulator — see the IMPORTANT box above; structured,
  top-level, in-memory, passed in via the `Referral`). What remains open is *cost* (how much history
  to carry forward vs. summarize — the accumulator's retention policy) and *how the structured record
  is decomposed into `NetworkFact`s*. The doctor stays pure (read-only); placement is no longer a
  tension.
. *Decision table vs DRL vs Java rules.* The table above is the reviewable design form. Whether to
  author rules as a spreadsheet (decision table), `.drl`, or the Drools Java rule API is an
  authoring-surface choice deferred to implementation — all three compile to the same RETE network.
. *Is the dependency worth one class?* Pulling the KIE stack onto the classpath for a single
  specialist is a real cost. The honest answer may be "prototype on paper (this doc), and only adopt
  KIE if a *second* multi-condition specialist appears" — the rule-of-three the project applies
  elsewhere (cf. the domain-registry abstraction deferral).
