== Overview — the goal and the obstacle

After specialist distribution, three actors are DS `@Component`s (the institution
`DefaultHealthSystem` + the three domain `Specialist`s). Two are NOT: the `Generalist` and the
`DriftSpecialist`. They are built per-run by `DoctorGraph.assemble` at each `admit(patient)`.

The user wants *uniformity*: every actor a component of the system, each carrying its own
*operational mode* (its verbs) the way it already carries a `ClinicianId` (its identity). The
obstacle is a single piece of per-run state.

`DefaultHealthSystem` is a component precisely because its three fields are all `@Reference` — zero
per-run state. The `Generalist` cannot be a singleton because it *holds* a `ClinicalAccess` that has
*closed over* the admitted `patient`, its `GrantPolicy` and its bound `ClinicianId` — deliberately,
so a clinician cannot read as another id nor mint its own access. That closed-over patient is the
whole obstacle. (The `DriftSpecialist`'s `ledgerWriter` is NOT per-patient — it is run-infra, like
the HealthSystem's own; it resists far less.)

== The reframe — a doctor is EMPLOYED once; each CONSULTATION is an act

The real defect is not "the Generalist isn't a component" — it is that *we recreate the doctor at
every patient* instead of employing him once and creating a consultation. In a real health system
the practitioner is hired once (identity, a slot in the directory); each consultation is a distinct
act bound to one patient.

Split the one fused object in two:

[cols="1,2",options="header"]
|===
| today (fused) | corrected (split)
| `Generalist` = behaviour (consult/route/synthesize) + per-run `ClinicalAccess`
| *practitioner* = behaviour + identity + operational mode (a stable `@Component`); *consultation* =
  the per-run value carrying the `ClinicalAccess`
|===

Once the per-run state lives in the consultation, the practitioner has *no* per-run state → it is
singleton-able like every other actor. The same move frees the efficacy analyst (ex-DriftSpecialist)
and any future actor: *behaviour is a component; the run is a value it operates over.*

== The genus, generalised — identity AND operational mode

Today `Clinician` declares only `clinicianId()`. This design adds the second universal: every
clinician declares its *operational mode* — the verbs it answers with, already surfaced this cycle:

[cols="1,1,1",options="header"]
|===
| clinician | identity | operational mode
| Specialist | domain-derived id | `assess` + `prescribe`
| Remediator | its id | `administer`
| GeneralPractitioner | `generalist` | `consult` (route + synthesize)
| efficacy analyst | its id | `review` → `EfficacyReport`
|===

Identity says *who*; operational mode says *what it does*. Both belong on the genus.

== Instantiation mechanism — CHOSEN: C (employment registry)

Splitting off the consultation makes the practitioner stateless; the mechanism that instantiates it
was the fork. Three candidates were weighed (none used in the repo yet — no `ComponentFactory`/PROTOTYPE
today); the deciding question was *where the per-run `ClinicalAccess` lives*:

[cols="1,2,1",options="header"]
|===
| option | where the access lives | "closed over" guarantee
| A — access as a call parameter | a call parameter that circulates | ❌ lost (access becomes data)
| B — DS ComponentFactory | a factory-component field | ✅ kept, but rich access through scalar DS props is contra-natural
| *C — employment registry (CHOSEN)* | a field of a `Consultation` VALUE | ✅ kept, simple, navigable
|===

*Decision (user, 2026-06-26): C.* It keeps DS for what it is good at (stable services), models the
per-run act as a plain value (no contrived component lifecycle, no host signature changes), keeps the
access encapsulated, and makes the directory fall out for free.

A was rejected (sacrifices the "cannot read as another id" guarantee — the access stops being closed
over); B was rejected (passing a rich `ClinicalAccess` through DS component-properties, which are
scalar maps, is contra-natural, and it spins a component lifecycle up/down per admit for no gain).

== Falls out for free — the practitioner directory (Generalist-visibility backlog)

Once every actor is an employed component with an identity + operational mode, "who is employed in
this health system?" is answerable uniformly: the HealthSystem holds the directory; Specialists
arrive by `@Reference`, the practitioner(s) by employment. This absorbs the deferred
Generalist-visibility slice — the directory is uniform even if the *arrival* mechanism differs.

== Anti-patterns

* ❌ *Recreate the practitioner per patient.* Fusing behaviour with the run's access forces a new
  object each admit and blocks componentisation. ✅ Employ the practitioner once; mint a consultation
  per run.
* ❌ *Force a per-run actor into a singleton `@Component` as-is.* DS instantiates once; closed-over
  patient state makes that unsound. ✅ Remove the per-run state first (the split), then componentise.
* ❌ *Leak the access as an open call parameter just to win the singleton* (option A) without
  weighing the lost "cannot read as another id" guarantee.
