= Flox Store-Resolved Runtime + Remote Nix Builder
:toc: left
:toclevels: 3
# :kroki-server-url: https://kroki.io

[IMPORTANT]
====
*Substrate alignment (2026-08-25).* This design predates the NixOS node-base
substrate; it assumed a distrobuilder image plus the `/srv/host` DaemonSet-installer
as the *only* delivery path. Three things changed and this doc is rewritten around
them:

. *A two-tier delivery model.* What is *known at image-build time* is baked into
  the node-base image's `/nix/store` (the *foundation* tier — LIVE today:
  `nixos/containerd.nix` already resolves `flox-runtime.packages.<system>.flox-nri-plugin`
  and symlinks it to `/opt/nri/plugins/10-flox`, NRI enabled via `90-nri.toml`).
  What must be contributed *at runtime, post-boot* — new/unknown binaries AND node
  configuration — stays a *retained runtime-extension* tier (the DaemonSet installer/
  reconciler + the Part 2 remote builder). The extension is KEPT in the codebase for
  future use even though the baked foundation is the primary path now; only the stale
  `/srv/host` hostPath coupling is pruned (→ a substrate-compatible source).
. *The shim source moves to its own repo.* The flox NRI shim (a *fork* of flox's
  containerd plugin) + the `flox-runtime-scripts` are extracted to
  `github:seedmatic/flox-nri-plugin` and consumed by rke2lab as a flake INPUT, not
  shipped as Java resources inside the manifests-core jar. This IS Part 1 below,
  reframed: "sources as flake inputs" now means "sources in the fork repo."
. *The flox ENVS move out of the baked image to a runtime store (2026-08-27).*
  The envs are no longer baked into the node-base `/nix/store` — that model forced
  a control-node cold-start on every package bump. They are delivered at RUNTIME in
  the k8s plane: a ZFS-backed PVC (`zfs-localpv`) holds a *self-contained* nix store
  (flox + closures + a valid Nix DB), populated by a *reconciler DaemonSet* that
  `nix copy`s the locked closures from the builder; the NRI plugin overlays that PVC
  store into containers as its single lowerdir. This is now THE design (see
  <<runtime-env-delivery>>); the earlier "bake envs in the image" model is retained
  only as a short migration note — it is the LIVE interim, being migrated away.
====

== Overview

This design covers two intertwined changes to the Flox container runtime, both
now positioned inside the two-tier model above:

. *Store-resolved runtime* — the shell scripts under `runtime/flox/` and the flox
  envs are resolved from a nix store, never copied. Scripts become nix-built
  packages (`flox-runtime-scripts`, an output of the fork repo's flake). The envs
  live in a *runtime ZFS-PVC nix store* — NOT the baked image (see the banner and
  <<runtime-env-delivery>>): the reconciler realises them there and the container
  consumes them via a fine-grained `.flox` symlink farm (`env/` → store,
  `run/cache/log` → local). This removes the `cp` trampoline, the lock-propagation
  step, and the relative-flake-ref breakage in one stroke — and de-buries the Go +
  script sources into the fork flake.
. *Remote nix builder* — let any Flox-injected container build arbitrary,
  unknown-at-provision-time packages by delegating builds to the NixOS host
  (`{bioskop,nikopol}-nixos`) over `ssh-ng`, while never building locally. This is
  the *runtime-extension* tier's binary-contribution mechanism.

They share one boundary, which is why they are designed together: the line
between *immutable code* (belongs in `/nix/store`, read-only) and the *mutable
runtime workspace* (`/var/run/...`, where locks are written and builds stage).
Both changes are about pushing immutable artifacts into the store and keeping
only genuinely mutable state in `/var/run`.

=== Why now

The loose-script model surfaced two defects already fixed (see
xref:_related_documentation[Related Documentation]): a stale install-time
manifest patch and a missing lock propagation. Both were symptoms of shipping
runtime code as raw resource files copied through a ConfigMap trampoline rather
than as versioned, store-addressed build outputs. Moving to store resolution
removes the class of bug where "the file on the node" and "the file in the repo"
drift, and it is the prerequisite for the builder feature (a builder must hand
back store paths the container can actually resolve).

== Background: the runtime-extension delivery model

NOTE: This section describes the *runtime-extension* tier (the DaemonSet installer),
which the substrate RETAINS but demotes from primary. The plugin *binary* itself is
no longer delivered this way — it is baked into the node-base image
(`nixos/containerd.nix` → `/opt/nri/plugins/10-flox`, LIVE). What the extension tier
still owns is contributing new/unknown binaries and node configuration *post-boot*.
The one substrate change is the source of the materialized assets: the `/srv/host`
hostPath is dissolved, so a migrated installer reads from a store-resolved package /
ConfigMap / the rendered branch instead.

For the flox ENVS specifically, that migrated form is now designed — a *reconciler
DaemonSet* writing a ZFS-PVC store (see <<runtime-env-delivery>>). The three-contract
copy model below is the superseded historical shape; the reconciler is its clean
reborn form (writes its own PVC volume, no `/srv/host`, no `nsenter`).

The Flox runtime installer DaemonSet materializes assets through three distinct
delivery contracts. Any migration of the *extension tier* must preserve all three.

[cols="1,3,2",options="header"]
|===
| Contract | Scripts | How resolved today

| *A. Pod-mode `/.sh/bin/`*
| `flox-nri-plugin-run.sh`
| ConfigMap mounted read-only at `/.sh`; run as `/bin/sh /.sh/bin/...`
  (`FloxRuntimeLayer` init container).

| *B. Node-local `/var/run/.../bin/`*
| `flox-nri-plugin-installer.sh`, `flox-runtime-lib.sh`,
  `flox-nri-plugin-reload.sh`
| `cp -af /.sh -> /var/run` at pod start, then exec'd from the node-local copy.

| *C. Fixed `/usr/local/sbin/`*
| `flox-nri-overlay-hook.sh`, `flox-nri-chown-hook.sh`
| OCI hook contract: runc looks them up at a fixed host path. The installer
  copies them there via `on_materialize`.
|===

A separate shared library, the daemonset policy lib
(`runtime/daemonset/.sh.d/`: `daemonset-runtime.sh`, `daemonset-trampoline.sh`,
`daemonset-host-shell-policy.sh`), is shipped as its own
`runtime-daemonset-script-policy` ConfigMap mounted at `/.sh-daemonset`. The
runtime scripts source it. It is generic daemonset infrastructure reused beyond
Flox, so it is treated as a distinct artifact in this design.

=== The mutable-vs-immutable boundary

The `cp -af /.sh -> /var/run` step is not incidental. It makes
`/var/run/k8s-daemonset.d/runtime/flox` a *writable git tree* because:

* `flox activate` writes `manifest.lock` there (the lock-propagation path),
* `nix build` runs against the flake source there,
* the path must be a real git tree so nix's path-flake fetcher hashes the
  source via git's index rather than walking volatile files.

`/nix/store` is read-only. Therefore scripts can move to the store, but the
*workspace* (the flake source nix builds against, `environment.d/`, the written
locks) cannot. The design must keep these separate.

== Part 1 — Store-resolved runtime scripts (the fork-repo extraction)

=== Goal

The scripts under `runtime/flox/` stop being source-tracked loose files copied
through a ConfigMap. They become outputs of a nix package built by the *fork
repo's* flake, resolved from `/nix/store`. "Sources as flake build inputs, not
runtime-shipped resources" now means: the Go plugin sources + the orchestration/
hook scripts live in `github:seedmatic/flox-nri-plugin` and are consumed as a
flake input — never copied into the manifests-core jar.

=== Flake topology after the split

The single in-tree flake (which today builds *both* the plugin and the env
packages) splits into two, wired through the `nix-flake-commons` aggregator:

[cols="1,2,2",options="header"]
|===
| Flake | Outputs | Consumed by

| `github:seedmatic/flox-nri-plugin` (fork)
| `flox-nri-plugin`, `flox-nri-plugin-debug`, `flox-runtime-scripts`
| rke2lab flake input `flox-runtime` (URL repointed from `path:./…/runtime/flox`)

| rke2lab `runtime/flox/flake.nix` (retained)
| the env catalog — `kdns`, `headplane`, `headscale`, `tailscale` (+`-debug`)
| `FloxRuntimeAssets` / the NRI plugin injects these into opted-in pods
|===

The shim (fork) is the ONLY thing that leaves; the env packages it *injects* stay
in rke2lab because they are rke2lab's workload catalog, not the shim.

[NOTE]
.Flake-input hygiene (the aggregator discipline)
====
Both the fork flake and the retained env flake pin their externals to the
seedmatic aggregator so the whole closure resolves to *one* nixpkgs (no skew, no
repeat of the lock bloat). This is already the in-tree pattern — the fork repo
inherits it verbatim.

* In the fork's `flake.nix`:
+
[source,nix]
----
flake-commons.url = "github:seedmatic/nix-flake-commons/develop";
nixpkgs.follows    = "flake-commons/nixpkgs";
flake-utils.follows = "flake-commons/flake-utils";
flox.follows        = "flake-commons/flox";
----
* In rke2lab's root `flake.nix` (repointing the existing `flox-runtime` input):
+
[source,nix]
----
flox-runtime.url = "github:seedmatic/flox-nri-plugin";      # was path:./osgi/.../runtime/flox
flox-runtime.inputs.nixpkgs.follows      = "nixpkgs";
flox-runtime.inputs.flake-utils.follows  = "flake-utils";
flox-runtime.inputs.flake-commons.follows = "flake-commons";
----
The `follows` lines already exist for the `path:` input; the extraction only
repoints the `url`.
====

=== Package shape

Add to the *fork repo's* `flake.nix` a `flox-runtime-scripts` package built with
`pkgs.writeShellApplication` per script (or a single `stdenvNoCC.mkDerivation`
installing the set), with `runtimeInputs` declaring `bash`, `coreutils`,
`inotify-tools`, etc. so the closure is self-contained. This mirrors how
`flox-nri-plugin` is already a flake package there.

[source,nix]
----
flox-runtime-scripts = pkgs.stdenvNoCC.mkDerivation {
  pname = "flox-runtime-scripts";
  version = nriPluginVersion;
  src = ./scripts;            # sources move here from bin/
  installPhase = ''
    mkdir -p $out/bin $out/libexec
    install -m0755 flox-nri-plugin-installer.sh $out/bin/
    install -m0755 flox-nri-plugin-run.sh       $out/bin/
    install -m0755 flox-nri-plugin-reload.sh    $out/bin/
    install -m0644 flox-runtime-lib.sh          $out/libexec/   # sourced, not exec'd
    install -m0755 flox-nri-overlay-hook.sh     $out/libexec/   # contract C: installed to /usr/local/sbin
    install -m0755 flox-nri-chown-hook.sh       $out/libexec/
  '';
};
----

=== Handling the three contracts after migration

* *Contract A & B (orchestration scripts)*: `FloxRuntimeAssets` stops emitting
  the five `addInstallerAsset` script entries. Instead the synthesis layer
  resolves the store path of `flox-runtime-scripts` and the init container runs
  the installer/lib/run/reload directly from `/nix/store/...-flox-runtime-scripts/bin/...`.
  The `SCRIPT_MOUNT_DIR` env in `FloxRuntimeLayer` points at the store path
  instead of `/var/run/.../bin`.
* *Contract C (OCI hooks)*: runc's hook path is fixed and not store-aware, so
  the hooks still land at `/usr/local/sbin/flox-nri-*-hook.sh`. The change is
  the *source*: the installer installs them *from the store package's libexec*
  rather than from the `cp`-populated `/var/run/.../bin`.

=== Store-located envs via a fine-grained `.flox` symlink farm

The same store-resolution principle extends past scripts to the *flox envs
themselves*. The container's `/nix/store` overlay LOWER is the host store (NRI
plugin: `nix-store /nix/store -> /nix/store`), so any store path the host holds,
the container sees. The static part of an env (`manifest.toml` + `manifest.lock`)
is immutable and belongs in the store; only flox's `run/`/`cache/`/`log/` are
mutable.

The split must be done at *`.flox`-internal* granularity. The following layout
is verified working on the master:

----
.flox/                  ← real local writable directory
  env  -> /nix/store/<hash>-<env>/env   ← symlink into store (manifest.toml + lock)
  env.json              ← small local file
  run/   cache/  log/   ← real local writable dirs (flox writes here)
----

`flox activate` from this layout writes its `run/aarch64-linux.<env>.dev` into
the *local* `.flox/run`, leaves the store path pristine, and resolves the
workload from the locked store paths — `ACTIVATE_OK`.

[WARNING]
====
Do *not* symlink the whole `.flox` into the store (a naive `xstow` of the env
dir). flox resolves `run/` relative to the symlink's *real target*, tries to
create a GC root inside `/nix/store`, and nix itself refuses:
`creating a garbage collector root ... in the Nix store is forbidden`. The
mutable/immutable boundary is *inside* `.flox`, so a whole-dir symlink cannot
straddle it. Likewise, activating directly from a read-only store path while
running as root silently pollutes the store (root has `CAP_DAC_OVERRIDE`).
====

This is the `xstow` pattern already used by `rke2lab-systemd-link.sh`, applied
at `.flox`-internal granularity (or a tiny purpose-built linker). It replaces
the `cp -af /.sh -> /var/run` env-consumption path.

=== What this removes

Store-located envs collapse machinery the copy model required:

[cols="1,2",options="header"]
|===
| Current (copy model) | With store-located env

| `cp -af /.sh -> /var/run` for env consumption | gone — `.flox/env` symlinks into store
| overlay-mount `.flox` at `$HOME/.flox` | gone — local `.flox` with store-symlinked `env/`
| lock propagation to `/var/run` | gone — the lock is immutable in the store path
| relative `path:../../..` re-resolution breakage | gone — a locked store env never re-resolves
|===

=== What still needs `/var/run` (master-only, production side)

The mutable workspace remains, but only on the *master* and only for *producing*
locked envs and realizing packages:

* the flake source `nix build` runs against,
* the `flox activate` pass that *writes* `manifest.lock` (lock production),
* the staging area for builds.

The container *consumption* side no longer needs a writable workspace at all.
The conflation in the current model — using one `cp`-everything tree for both
production and consumption — is what this design separates.

=== The plugin's runtime deps the substrate does NOT yet bake

The plugin *binary* is baked (foundation, LIVE), but injection is a no-op until
two host-side inputs exist — and neither is currently provisioned by `nixos/`
(both were casualties of the `/srv/host` dissolution, commit `6e8cd3c28`):

[cols="1,3",options="header"]
|===
| Runtime dep | Status / what must provision it

| *flox-env GC-roots* — `/nix/var/nix/gcroots/flox-runtime/env/<category>/<name>`
| The plugin's `resolveFloxEnvironment` reads these to map `category/name` → the
  immutable env store path. In the target model they live on the *runtime PVC store*
  and are written by the reconciler (sole writer), NOT baked. The GC-root contract
  path is unchanged — only its populator moves from `nixos/flox-runtime.nix` (interim
  bake) to the reconciler DaemonSet (see <<runtime-env-delivery>>).

| *`/etc/flox.toml`* (host file, optional)
| Projected read-only into every injected container if present (the `floxSystemConfigPath`
  path in `plugin.go`). Absent from `nixos/` → projection is silently skipped. It
  can simply be baked as an `environment.etc` entry in a `nixos/` module (it is
  static host config, foundation-tier — no runtime contribution needed).
|===

The plugin reads *no* environment variables beyond `NRI_PLUGIN_SOCKET` (set by
containerd at launch). It is not affected by the dissolved NodeEnv env-var
mechanism (see <<node-config-contribution>>) — that fed the *RKE2 server / node*,
not the plugin.

=== Open question: how the node gets the store paths (+ GC-roots)

NOTE: RESOLVED for the flox ENVS by the *runtime reconciler* — see
<<runtime-env-delivery>>. The reconciler DaemonSet `nix copy`s each env's closure
into the ZFS-PVC store and writes its GC-root there (sole writer); the container
overlays that store. The interim LIVE model bakes them instead
(`nixos/flox-runtime.nix`) and is being migrated. The remaining open part is only
the Part-2 builder for *unknown-at-build* packages.

The store path (scripts package + env subtrees) AND the GC-roots above must exist
on the node before a container can resolve an env. Two options, to be decided at
implementation:

* *(a)* the runtime flake's `flox activate` prebuild pass (already runs on the
  master) realizes the packages, `nix store add-path`s the env subtrees, and
  writes the `gcroots/flox-runtime/env/<cat>/<name>` links as a side effect; the
  synthesis layer passes the resolved store paths in;
* *(b)* the packages are added to the set the master pre-builds explicitly, and
  the store paths + GC-roots are published through the image-state/handoff surface.

This intersects Part 2: realizing a store path (script package or env subtree) on
a node that lacks it is itself a remote build.

[[runtime-env-delivery]]
[[l1-realised]]
== Runtime env delivery — reconciler DaemonSet + ZFS-PVC store (target)

The flox envs are delivered at RUNTIME, in the k8s plane, decoupled from the
node-base image. A package bump therefore NEVER cold-starts the control node — the
image (and its `imageBuildChecksum`) does not change when an env version moves.

=== The invariant seam

Both the baked interim and this target write the SAME contract the plugin reads: a
GC-root at `/nix/var/nix/gcroots/flox-runtime/env/<category>/<name>` → `readlink` →
the immutable env store path. The plugin's per-container injection (overlay +
`.flox` farm + `flox` on PATH) is unchanged. Only the *populator* of that GC-root
moves — from `nixos/flox-runtime.nix` (interim bake) to the reconciler.

=== The reconciler DaemonSet (sole writer)

A DaemonSet mounts the PVC and reconciles the node's flox store to the desired set
in ONE pass — it is the sole writer of both the store and the `gcroots/flox-runtime/`
subtree (the same single-writer discipline the baked `systemd.tmpfiles` held):

[source]
----
desired = ConfigMap → { (cat/name) → store-paths }
actual  = scan gcroots/flox-runtime/env (+ activation)
for env in desired:        nix copy --to 'local?root=<pvc>' <closure> ; symlink the GC-root
for link in actual - desired:   rm the symlink                        # prune — SAME component
----

It does NOT `nsenter` the host or write `/srv/host`; it writes its OWN PVC volume —
which is why the DaemonSet form is clean here (the taint that retired the old
installer was the host mutation, not the DaemonSet). Disk reclaim of pruned closures
is left to a separate `nix.gc.automatic` cadence.

=== The PVC is a self-contained nix store

The PVC (default ZFS storage class, `zfs-localpv`) holds a COMPLETE store — `flox`
itself + every env closure + a valid `/nix/var/nix/db` (populated by the
`nix copy`). The plugin overlays THIS store as its single lowerdir, so:

* no multi-store union — the container sees one store that has flox AND the env;
* the DB is valid by construction → the force-register/OOM pathology (a container
  seeing store files with no DB registration) CANNOT recur;
* `flox` on PATH resolves from the PVC store, not the node's `/run/current-system`.

Persistence: the ZFS datasets are provided by the NixOS hypervisor (bioskop-nixos),
not the node's ephemeral instance rootfs, so the store SURVIVES a node replace — a
cold-start (rare now, foundation-only) does not re-substitute the envs.

=== Determinism — the store is reconciled, never hand-edited

The `manifest.lock` per env stays COMMITTED in the repo (like a `flake.lock`); the
operator triggers bumps via an *env-bumper* CLI — a scenario in the shape of the
existing manifests `VersionBumper` (bump `runtime/flox/flake.nix` pins + re-lock
`environment.d/*/manifest.lock` → commit). The reconciler NEVER re-locks; it only
realises the committed, resolved store-paths carried by the ConfigMap. "Visible in
k8s" means inspect / VolumeSnapshot / observe — the reconciler stays the sole
writer; no out-of-band mutation (determinism preserved).

The ConfigMap carries store-path POINTERS only (tens of bytes each) — the heavy
lock/closure bytes travel by nix substitution, so the etcd 1 MiB ConfigMap limit
never binds (no chunking, no hostPath archive).

=== Ordering — no gate, fail-closed + retry

Flux is the first service in every cluster, so the env-set ConfigMap lands early
(foundation/operators layer) — before the workload pods that consume the envs. No
explicit gate is needed: the plugin is *fail-closed* — if a GC-root is absent
`resolveFloxEnvironment` returns an error, `CreateContainer` propagates it →
`CreateContainerError` → k8s retries with back-off. Realisation is substitute-only
(seconds), so the window self-heals. (Reserve: confirm containerd's NRI fail-closed
knob at implementation.)

[NOTE]
.Interim: the LIVE baked model, being migrated
====
Today the envs are still BAKED at image-build by `nixos/flox-runtime.nix`
(`mkEnvSubtree` + `mkEnvActivation` + tmpfiles GC-roots; env catalog under
`environment.d/…` read as flake SOURCE). That model is LIVE (kdns + the mesh family
run on it) but forces a control-node cold-start on every package bump — the coupling
this target removes. The migration also drops the `environment.d` fold in
`GrowPlanAssembler.imageSourceDigest` and the shell-side TWIN GATE in
`build-node-base-image.sh` (both added *solely* to force that cold-start). The baked
implementation stays retrievable in git for reference during the migration.
====

[[node-config-contribution]]
== The node-configuration contribution (the other half of the retained mechanism)

The governing principle keeps the runtime-contribution mechanism for *both*
binaries AND node configuration. Part 1 + Part 2 cover the binary half. This
section records the *node-configuration* half — the mechanism that let the seed
world contribute environment/config to the node's runtime — so it is not lost.

=== What it was (dissolved, recoverable)

Originally the seed world defined a rich, *domain-extensible* set of node
environment variables that the RKE2 node's runtime consumed. The shape:

* a `NodeEnvContributor` SPI + a registry, with *one contributor per domain* —
  each domain contributed its own `RKE2LAB_*` variables;
* the aggregate rendered by `RKE2LabEnvConfigManifestsUnit` (+ `HostPaths`) and
  delivered to the node, where it was loaded into the RKE2 runtime.

Commit `6e8cd3c28` *dissolved* this along with the `/srv/host` systemd-infra
synthesis, because the NixOS substrate bakes node config declaratively.
`NodeEnvContext`/`DefaultNodeEnvContext` survive, but *slimmed* to the identity +
topology views (synthesis-side only). The SPI, the registry, the per-domain
contributors, `RKE2LabEnvConfigManifestsUnit` and `HostPaths` are gone from the
tree — *recoverable at `6e8cd3c28^`* if a re-implementation is ever needed.

=== What the substrate does today

The node's runtime config is a *fixed* six-variable set, not domain-extensible:
`rke2lab-identity` (`nixos/identity.nix`) resolves them from devlxd
(`user.rke2lab.node-*`) into `/run/rke2lab/node.env` —
`RKE2LAB_NODE_{NAME,HOSTNAME,KIND,ID}` + `RKE2LAB_CLUSTER_{POD,SERVICE}_CIDR` —
consumed as an `EnvironmentFile` by the boot oneshots (`rke2lab-dualstack`,
`rke2lab-tls-san`, `rke2lab-zfs-containerd`). There is no flox-env carrier and no
per-domain contribution surface anymore.

=== Decision: document-only (retained as design)

Same treatment as the orchestration scripts: the *mechanism* is retained as this
documented design, not resurrected in code. If a domain later needs to contribute
a runtime variable, the re-implementation target is a substrate-native
`NodeEnvContributor` (domains → vars → `devlxd`/`node.env`, extensible) — restored
from `6e8cd3c28^` and adapted to write `node.env` rather than the `/srv/host`
ConfigMap. Until then, add a one-off variable directly in `nixos/identity.nix`.

== Part 2 — Remote nix builder

=== Goal

A Flox-injected container that needs to build a package it does not already have
must *not* build locally. It delegates to the NixOS host builder over `ssh-ng`.
Default workload envs are unaffected: they are pre-locked (lock propagation) and
resolve from store paths already present, so they never trigger a build.

=== The three-builder distinction

There are three nix-build entities; this design targets exactly one.

[cols="1,3,1",options="header"]
|===
| Entity | What it is | Use here?

| vz-host embedded `linux-builder` VM
| The QEMU/Lima `aarch64-linux` VM `linux-builder.nix` spins up *on the darwin
  host* so darwin can cross-build Linux. A different role.
| *No*

| `{bioskop,nikopol}-nixos` native daemon
| The NixOS hosts' own `nix-daemon`, native `aarch64-linux`, already holding the
  store + cache-trust signing + nixbld users.
| *Yes*

| `master` incus container daemon
| The Debian instance. Never a builder.
| *No*
|===

`{bioskop,nikopol}-nixos` are native `aarch64-linux`, so there is no VM
indirection — the host builds the container's packages on bare metal directly.

=== Reuse map — almost everything already exists

[cols="1,1",options="header"]
|===
| Piece | Status

| Builder (`{bioskop,nikopol}-nixos` native daemon) | exists
| Hardened inbound endpoint: `nix-store` SSH user whose forced login shell is
  `nix-daemon --stdio` (nix-darwin-home `nix-store-identity.nix`) | exists
| Dedicated key + cert: `nix-store` entry in `keys.yaml` | exists
| Fleet store-trust signing key `io-nxmatic-nix-darwin-home` (`cache-trust.nix`) | exists
| SOPS key delivery into rke2lab via `.ndh-ssh.d` subtree (git smudge decrypts
  in-tree) | exists
| Container `builder.conf` + ssh `nix-store.<host>` alias, authored by the NRI
  manifest unit | *new*
| NRI plugin RO-mounts builder.conf + key into every container | *new*
|===

=== The `nix-store` peer identity

nix-darwin-home already defines a complete peer-to-peer remote-store mechanism.
The inbound side runs a dedicated `nix-store` user with forced shell
`nix-daemon --stdio` (a locked-down remote-build endpoint). The canonical
outbound access path is `ssh-ng://nix-store.<host>`, cert-signed. A Flox
container that needs to build is exactly "a new consumer" of this path. No new
key, no new host user.

=== Container-side config (the only new material)

Authored by the NRI plugin's manifest unit (single, patchable source of truth),
bind-mounted read-only into *every* Flox container, mirroring the existing
`/etc/flox.toml` pattern (`floxSystemConfigPath` in `plugin.go`).

`/etc/nix/nix.conf.d/builder.conf`:

[source,ini]
----
max-jobs = 0
builders = ssh-ng://nix-store.bioskop-nixos aarch64-linux /etc/nix/nix-store-key - <speed> <features>
builders-use-substitutes = true
trusted-public-keys = io-nxmatic-nix-darwin-home:U/at4v0hCbZhn3u7uvQhQo+lzq5ZobOJyn3Be3txbqg= ...
----

`max-jobs = 0` is the key primitive: the container performs *zero* local builds.
Anything not in-store and not substitutable goes to the remote builder.

=== Decisions locked

* *No local builds*: `max-jobs = 0`. The container is a pure client; it needs no
  in-container nixbld users.
* *Build identity*: the existing `nix-store` key (purpose-built, cert-signed,
  forced-command endpoint). Not the `linux-builder` key (that is host->VM).
* *Universal, not opt-in*: every Flox container gets `builder.conf` mounted.
* *Config ownership*: authored by the NRI manifest unit so it is retrievable and
  patchable from code, not baked into the node-base image.

=== Secret-handling discipline

`.ndh-ssh.d/keys.yaml` is always plaintext in the working tree (git SOPS smudge
on checkout; clean re-encrypts on commit). The manifest unit reads the
`nix-store` key material at synth time, exactly like
`SopsAgeSecretManifestUnit` reads `rke2-cluster`. The *private* key must flow
only into the runtime asset tree mounted into containers — never into a
committed path or a world-readable location. Synthesis happens on the operator
machine; the container only ever receives the materialized key as a read-only
mount, never the git filter or SOPS.

=== Overlay store + copy-back semantics

The container's `/nix/store` is an overlay (read-only lower + ephemeral tmpfs
upper). A remote build copies its closure *back into the container's store* —
landing in the ephemeral upper. This is correct for "packages we don't know":
they are transient by nature and live as long as the container. Persisted
artifacts (workload packages, the scripts package) are built by the master and
already present in the real store the overlay lowers from.

== Open questions to resolve at implementation

. *Network reachability*: can a container reach `nix-store.bioskop-nixos`
  through the cluster netns (cilium), or must the builder be addressed by a
  host-routable path? This is the one unverified runtime unknown.
. *SSH PATH on the inbound side*: remote builds run `nix-store --serve` via the
  forced shell; confirm the `nix-store` user's non-interactive session resolves
  the nix binaries (the forced shell already execs an absolute
  `nix-daemon --stdio`, which likely sidesteps this — verify).
. *Script-package realization on the node* (Part 1 open question): option (a)
  prebuild side effect vs (b) explicit publish. Intersects the builder: a node
  missing the script closure would itself remote-build it.
. *`known_hosts` for the container*: the `nix-store.<host>` alias uses
  `StrictHostKeyChecking accept-new`; decide whether to pre-seed the host key
  via the same mount.

== Sequencing

. *Part 0 — the fork-repo extraction (the concrete first step of Part 1).* The
  `seedmatic/flox-nri-plugin` repo exists (empty root commit). Move the
  `runtime/flox` flake's shim half (Go plugin + orchestration/hook scripts +
  `flake.nix` producing `flox-nri-plugin` + `flox-runtime-scripts`) into it with
  aggregator-following inputs; repoint rke2lab's `flox-runtime.url` from `path:`
  to `github:seedmatic/flox-nri-plugin`; stop shipping the Go source as Java
  resources in manifests-core. The env catalog stays in rke2lab's retained
  `runtime/flox/flake.nix`.
. *Part 1 (scripts to store)* is the foundation: it establishes the immutable-vs-
  mutable split cleanly and removes the loose-file delivery model.
. *Part 2 (builder)* builds on a store-resolved world and reuses the split — but
  the `builder.conf` mount is independent enough to land alongside Part 1 if
  reachability is confirmed early.
