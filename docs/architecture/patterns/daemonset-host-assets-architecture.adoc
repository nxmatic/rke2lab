= Daemonless Host Assets Architecture
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

This note captures the current daemonset runtime pattern for host-mutating workflows that begin in a Kubernetes pod and complete on the node host.

It is specifically concerned with:

* the daemonset execution contract
* the host asset materialization path
* the ownership boundary between shared daemonset policy and workflow-specific installer assets
* the current encoded archive provider used by the Flox shim runtime path

== Canonical terminology

The following terms are canonical in the current model:

* *daemonset execution mode* — explicit execution context selected through `DAEMONSET_EXEC_MODE`
* *host asset root* — the canonical host-side materialization directory for a workflow
* *daemonset policy scripts* — shared helper scripts mounted from the runtime daemonset policy ConfigMap
* *workflow installer assets* — workflow-specific scripts, manifests, and payload files mounted from the runtime installer assets ConfigMap

For the Flox shim runtime path, the canonical host asset root is:

* `/srv/host/k8s-daemonset.d/runtime/containerd-shim-flox`

This host asset root is intentionally *not* the developer worktree.
The worktree remains an upstream source input that originates on the macOS workstation running the NixOS VM through Tart/VZ.
The daemonset workflow materializes verified host assets from delivered payloads; it does not redefine the repository checkout as a host-owned runtime asset.

== Execution contract

Daemonless workflows do not infer whether they are running in a pod or on the host.
The caller declares the execution context explicitly.

Current canonical values:

* `DAEMONSET_EXEC_MODE=pod`
* `DAEMONSET_EXEC_MODE=host`
* `DAEMONSET_EXEC_MODE=guest` (supported by the trampoline contract, though not used by the Flox runtime installer DaemonSet path)

The important rule is:

* execution context is *declared*, not auto-detected

This keeps behavior deterministic, observable in logs, and stable across environment changes.

== Worktree provenance

The authoritative repository worktree for local iteration comes from the macOS machine where development happens.
That macOS machine is also the machine that runs the NixOS VM through Tart/VZ.

So the architecture boundary is:

* macOS workstation: authoritative repo checkout and editing surface
* NixOS VM: execution environment that consumes a projected/shared view of that checkout
* daemonset host assets: generated runtime outputs materialized under `/srv/host/*`

This distinction matters because the worktree is a source input, while daemonset host assets are provisioned outputs.
They should not be modeled as the same class of path.

== Shared daemonset policy surface

The shared daemonset policy is currently provided by `RuntimeDaemonsetScriptPolicyLayer` through the `runtime-daemonset-script-policy` ConfigMap.

At the time of writing, that policy surface includes:

* `daemonset-logging.sh`
* `daemonset-trampoline.sh`
* `daemonset-host-asset-materializer.sh`

Responsibilities:

=== `daemonset-logging.sh`

* configures colocated stderr log mirroring for daemonset scripts

=== `daemonset-trampoline.sh`

* owns pod→host and guest→host re-exec behavior
* consumes the explicit daemonset execution contract

=== `daemonset-host-asset-materializer.sh`

* owns deterministic host-asset materialization for encoded archive payloads
* verifies archive and entry checksums from a manifest before moving payloads into the host asset root

== Workflow-specific installer assets

The Flox runtime path is provided by `FloxContainerdShimLayer` through the `flox-runtime-installer-assets` ConfigMap.

This workflow-specific asset set includes:

* `shim-installer.sh`
* `shim-build.sh`
* `shim-build.yaml`
* `flake.nix`
* `flox-rootfs-sync.sh`
* debug helper scripts
* encoded wrapper-go payload files:
** `wrapper-go.tar.b64`
** `wrapper-go.manifest.json`

This means the ownership split is:

* shared daemonset behavior → `runtime-daemonset-script-policy`
* workflow-specific payloads and scripts → `flox-runtime-installer-assets`

== Who provides the encoded archive

The current encoded wrapper-go archive is provided by `WrapperGoArchiveAssets`.

More precisely:

. `WrapperGoArchiveAssets` loads embedded `wrapper-go` source resources from the `manifests` module.
. It builds a deterministic tar archive.
. It base64-encodes that archive.
. It emits the accompanying JSON manifest containing:
* archive size
* archive checksum
* per-entry size and checksum metadata
. `FloxContainerdShimLayer` places those outputs into the installer assets ConfigMap.
. `shim-installer.sh` consumes those files through the shared daemonset host-asset materializer.

So:

* the *policy* layer does not provide the encoded archive payload
* the *wrapper-go asset generator* provides the payload
* the *workflow asset layer* delivers it into Kubernetes
* the *daemonset host-asset materializer* verifies and materializes it on host

== Shared policy model: `HostAssetDeliveryPolicy`

The current codebase already has a concrete host-asset runtime contract:

* canonical host asset roots
* shared daemonset helper delivery
* workflow-specific installer asset delivery
* host asset root lifecycle handling in the bootstrap path

What it previously did not have was a single shared policy model that describes *how* a workflow delivers host assets.

`HostAssetDeliveryPolicy` is now implemented as a shared Java type in `manifests/src/main/java/io/nxmatic/rke2lab/manifests/api/` alongside:

* `HostAssetDeliveryBackend`
* `HostAssetMaterializationMode`

The shared model currently provides:

* validated policy identifiers and owner domain ids
* canonical host asset root declaration
* explicit delivery backend and materialization mode enums
* convenience helpers such as `usesDaemonsetDelivery()` and `materializesEncodedArchives()`
* a concrete `floxContainerdShim()` factory for the current runtime workflow

The shared model is implemented but not yet threaded through the manifests scion's policy facet as a first-class aggregated field.

The purpose of the model would be to connect:

* manifests-scion policy intent (the sown debug/link facet)
* workflow-specific host asset delivery
* shared daemonset helper usage
* host asset root lifecycle rules

Reading this diagram from left to right:

* the manifests scion's policy facet already carries `DebugPolicy` and the `LinkFacet`
* `HostAssetDeliveryPolicy` is the implemented shared model for host-asset delivery rules
* `FloxContainerdShimLayer` remains the current workflow-specific delivery layer for Flox shim assets
* `RuntimeDaemonsetScriptPolicyLayer` remains the current shared helper delivery layer
* `shim-installer.sh` remains the runtime execution point where those two delivery surfaces meet

In other words, the shared policy does not replace the current daemonset host-asset runtime flow.
It gives that flow an explicit, human-readable policy model while the wider controlplane wiring can still be layered in incrementally.

The component view shows the sharp boundary that matters for maintenance:

* the editable worktree is an upstream macOS-backed source input
* policy helpers define the reusable behavior surface
* workflow assets provide the installer and payload files
* the wrapper-go provider emits the encoded content
* host mutation happens only after policy-driven verification and materialization
* the source worktree is visible to the workflow but is not itself reclassified as a host asset root

== Current Flox shim daemonset flow

== Sequence summary

. The DaemonSet launches `shim-installer.sh` in pod mode.
. Pod mode sources shared daemonset policy helpers from `/runtime-daemonset`.
. Pod mode materializes workflow assets into the host asset root.
. Pod mode uses `daemonset::host_asset:materialize_encoded_tar` to verify and unpack the encoded wrapper-go payload into the host asset root.
. Pod mode trampolines onto the host and re-execs the same `shim-installer.sh` with `DAEMONSET_EXEC_MODE=host`.
. Host mode sources the same policy helpers from the host asset root and performs build/install/runtime reconfiguration work.

== Design guardrails

The current daemonset host-assets model keeps the following invariants:

* one canonical installer script per workflow (`shim-installer.sh` in this case)
* one canonical host asset root per workflow
* explicit execution mode rather than heuristic environment detection
* shared daemonset behavior isolated from workflow payload ownership
* deterministic archive verification before host mutation

== Expected extension path

The current naming intentionally leaves room for future host-delivered payload types beyond archives.

Expected future uses of the host-asset materializer surface may include:

* additional encoded trees
* plain configuration files
* checksum-validated generated assets
* manifest-driven host asset layouts for other daemonset workflows

If that expansion happens, keep the ownership split intact:

* policy helpers define *how* host assets are materialized and re-executed
* workflow asset layers define *which* payloads are delivered
