= FloxEnv readiness gating — the three loci
:toc: left
:toclevels: 3

[NOTE]
====
*Status: ✅ Implemented (locus A, 2026-09-06) in `github:seedmatic/flox-controller`
(`develop`).* This records how a flox-injected pod waits for its `FloxEnv` to be
realised, and where each part of the "waiting problem" is solved. It supersedes the
earlier pod-polls-the-API sketch AND the shell `flox-wait` init container (both removed).
Companion to
link:flox-store-resolved-runtime-and-builder.adoc[flox-store — resolved runtime & builder]
(the delivery) and link:../nixos-substrate/flox-containerd-runtime.adoc[the flox containerd runtime]
(the baked foundation).

*What shipped vs. the earlier plan.* The original migration was "B first (Go `flox-wait`
init container hitting the kube API), A next (scheduling gate)". B was *dropped*: an
init container runs with the *workload pod's* ServiceAccount (one SA per pod, shared),
so it cannot get its own `FloxEnv`-read RBAC — the pod-pull model hits a wall. We
implemented *A directly*. A also absorbed B's intended multi-node role via
*node-affinity narrowing* (below), so no free-floating fallback is needed.
====

== Overview — the problem

Workload flox environments are no longer baked into the node image: each is a `FloxEnv`
custom resource realised at runtime by the flox-controller (node-agent) onto the node's
`/nix` store, exposed as a GC-root the NRI plugin bind-mounts into the pod. A consuming
pod must therefore WAIT until its env is realised on its node before its container can
start. That wait *was* a shell-script `flox-wait` init container polling the GC-root file;
it is now a scheduling gate the controller removes (locus A below), so the pod never starts
on a node that cannot mount its env in the first place.

Two distinct problems hide behind "the wait", and — the key insight — **each can only be
solved at the locus that owns it**:

. *Pod readiness* — is the env realised ON THIS node, at the CURRENT spec generation?
  (correctness: the GC-root path is deterministic per ref, overwritten on re-realise, so a
  stale `ready` from a prior generation must not unblock the pod).
. *Realisation latency* — the controller realises envs SERIALLY (~1/min, each a nix build);
  at cold-start the critical-path env can queue behind unrelated ones.
. *The deployment cascade* — Flux gates a dependent Kustomization (`operator dependsOn
  tailnet-purge`) on a health-check of the gated Job; if realisation is slow the Job stays
  InProgress past Flux's health-check `timeout`, the Kustomization goes NotReady, and the
  dependency cascade stalls (self-healing on retry, but noisy).

== The partition — three loci, each owning what only it can

[cols="1,1,3",options="header"]
|===
| Problem | Locus | Mechanism

| Pod readiness (node + generation)
| flox-controller
| Scheduling-gate *A*: the webhook adds `spec.schedulingGates:[flox.seedmatic.io/env-ready]`
  so the pod stays unscheduled; the `PodGateReconciler` then *narrows* the pod's required
  `nodeAffinity` to the nodes where **every** referenced env is realised at the current
  generation (the intersection) and removes the gate — so the scheduler can only place the
  pod on a node that can actually mount its envs. Zero pod-side API/node access.

| Realisation latency
| flox-controller
| The realiser is *demand-prioritised*: an env that gates a pod (critical path) jumps the
  serial queue. Only the controller can do this — it both injects the gate (sees the demand)
  and owns the realisation order.

| Deployment cascade
| *Flux*
| `spec.timeout` / `spec.retryInterval` calibrated on the FloxEnv-gated Kustomizations. The
  Job health-check is KEPT (it is what guarantees "purge completes before the operator
  registers") — only its timeout is tuned. This is the ONLY locus that owns the cascade.
|===

The pod (A/B) and Flux can only *endure* the wait; the controller can *act* on it (reorder
realisation). The cascade mechanism (dependsOn + health-check + timeout) is entirely Flux's,
so only a Flux-side lever resolves it.

== The readiness predicate (the generation invariant)

A node `n` counts as ready for one env only when:

[source]
----
n.ready && n.observedGeneration == floxenv.metadata.generation
----

The reconciler computes, per referenced env, the set of such nodes, then *intersects* those
sets across all the pod's envs — the eligible node set. It pins `kubernetes.io/hostname In
{eligible}` and ungates only when that set is non-empty (else the pod stays gated). The
generation check is non-negotiable: `gcrootPath` is deterministic per ref (NOT per
generation), so on a spec bump the controller OVERWRITES the same path — without the check, a
pod could start against the prior subtree or mid-re-realisation.

== What it brings

* *Pod correctness* — `realized[node] && obsGen==gen`: never a mount on a stale / mid-realise env.
* *Latency collapsed* — demand-prioritised realisation removes the queueing cost (the dominant
  cold-start cost); the critical-path env goes from "behind N others" to "one build".
* *Cascade bounded* — Flux keeps the Job health-check (ordering preserved) with a calibrated
  timeout + self-healing retry.
* *One producer, one fact* — the controller writes `realized[]`; pod and Flux only observe.

== Resolved during implementation

* *(u1 — RESOLVED) Node resolution* — a gated pod has no `nodeName` yet, but the reconciler does
  not need one: while the pod is gated the API server permits *adding* required node-affinity
  (KEP-3521), so the reconciler pins the pod to the exact ready-node intersection *before*
  ungating. The scheduler then chooses among those nodes. Single-node mgmt degenerates to "the
  one node" for free; multi-node is correct by construction (no free-floating fallback needed).

== What stays uncertain

* *(u2) The aggregate `conditions[Ready]`* — still last-writer-wins across nodes. The gate no
  longer depends on it (it reads per-node `status.realized[]` directly), so this is *no longer on
  the readiness critical path* — but cluster-wide "rolled out" consumers (e.g. a Flux health-check
  on the CR) still read the incoherent aggregate. Making it node-aware / target-set-aware remains
  open, now decoupled from gating.
* *(u3) The Flux timeout value* — demand-priority shrinks the realisation queue, not the build; a
  single large from-scratch build can still exceed a modest timeout (a bound, not a guarantee).
* *(u4) Priority resolves the queue, never the build* — an irreducible floor remains if the
  critical-path env is heavy and cache-cold.

== Why the gate is INERT in-cluster today — the grow→cluster secret flow (2026-09-06)

Live diagnostic on `bioskop-mgmt`: the gate gates *nothing*. `daemonset/flox-controller` runs with
`--gcroot-base`/`--env-root` only — *no* `--enable-webhook` — and there is *no* flox
`MutatingWebhookConfiguration`. The webhook AND the `PodGateReconciler` are registered only under
`--enable-webhook` (the cluster-manager mode the DaemonSet enters when the flag is present), so with
the flag absent no pod is ever gated: flox-consuming pods (e.g. `tailnet-purge`) schedule before
their env is realised → `CreateContainerError: … not GC-rooted …`, self-healing only by NRI retry
once the node-agent realises the gcroot.

*Root cause — a secret-flow defect, not a gate bug.* `--enable-webhook` and the
`MutatingWebhookConfiguration` are emitted ONLY when `ManifestSynthesisContext.webhookServing()
.isPresent()` at render (`FloxControllerManifestsUnit`, `FloxWebhookManifestsUnit`). That serving
cert is a cluster-pki leaf sealed ONLY at the GROW (`ClusterPkiCoordinate.WEBHOOK_SERVING`, durable
cellar). The in-cluster steady-state render (`PublishCliScenario`) runs *secret-blind* — an
`EphemeralCellar` seeded only by `ghapp`, with `.secrets` sops-encrypted at rest — so
`revealWebhookServing()` is empty, the webhook renders OFF, and the branch loses it (the grow turns
it on; the first in-cluster render strips it — proven at `manifests/bioskop-mgmt@e0f789d5`: no
`--enable-webhook`, an empty `flox-webhook` group).

This is *systemic*: any Secret that is reveal-gated AND rendered onto the branch is stripped by a
secret-blind in-cluster render. Tracing the units, only TWO were actually exposed — the flox webhook
TLS (`revealWebhookServing`) and the CAPI `<cluster>-kubeconfig` (`revealOperatorPki`). The
`githubapp` Secret and the replicator source secret already avoid it — they ride the durable
NODE_BOOTSTRAP lane (`nodeBootstrap=true`), diverted off the branch entirely.

*The two lanes for a grow→cluster secret:*

* *Durable — NODE_BOOTSTRAP/devlxd*: the grow collects sealed material OUT of the branch into
  `.bootstrap/rke2lab-bootstrap.yaml` (`SERVER_MANIFESTS`), poses it on the instance's
  `user.rke2lab.server-manifests` devlxd key, and the master applies it at bootstrap. Off-git, never
  touched by an in-cluster render.
* *Fragile — branch-rendered*: a `Secret` rendered into the git branch, gated on the grow's cellar →
  stripped in-cluster.

*Fix — two steps (decided 2026-09-06; refined after tracing the units — see
link:../cluster-api/pac-in-cluster-render-spec.adoc#secret-delivery[the two doors for a delivered
secret]):*

. *Route the durable secret through devlxd — Door 1 (shipped).* The only reveal-gated Secret still
  branch-rendered is the CAPI `<cluster>-kubeconfig` (`ClusterKubeconfigManifestsUnit`); its Secret +
  its namespace now carry `NODE_BOOTSTRAP` (per-resource, the operator-kubeconfig stays a
  host-consumed `local-config` dotfile). `githubapp` and the replicator source ALREADY ride the lane.
  This re-arms the CAPI kubeconfig delivery — but it does NOT re-arm the flox gate: the webhook is
  not a pure-secret case (below).
. *Align the webhook with the K8s standard — cert-manager, Door 2 — THIS re-arms the gate.* The
  webhook's `--enable-webhook` (on the DaemonSet), its `MutatingWebhookConfiguration`, and that
  config's `caBundle` are ALL branch-rendered AND gated on `webhookServing().isPresent()`, so the
  durable lane alone cannot re-arm the webhook (the `caBundle` in particular cannot be rendered
  in-cluster without the cert — moving only the TLS Secret to Door 1 would be throwaway work). Mint
  the flox webhook serving cert in-cluster from a self-signed CA `Issuer`; cert-manager OWNS the
  Secret (never in the branch, never pruned) and `ca-injector` fills the `MutatingWebhookConfiguration`
  `caBundle`. `--enable-webhook` and the webhook manifests are then emitted UNCONDITIONALLY (no
  `webhookServing().isPresent()` gate), and the whole cluster-pki `WEBHOOK_SERVING` path — whose only
  consumer is this webhook — is deleted. The webhook cert MUST stay self-signed (it gates the
  tailscale pods themselves → a Tailscale-signed cert is circular and pre-tailnet; its SAN is the
  internal `*.svc`), and needs no persistence (the API server reads the ca-injected `caBundle`, so a
  per-lifetime self-signed CA is self-consistent). A Tailscale-signed + `tank/rke2lab/persist`-backed
  cert is for EXTERNAL endpoints (funnel/headscale `*.ts.net`) — a separate concern.

== Migration path

. *A (shipped)* — the webhook adds the `flox.seedmatic.io/env-ready` scheduling gate (replacing the
  shell `flox-wait` init container + its hostPath volume, both deleted); the `PodGateReconciler`
  (cluster-manager, `--enable-webhook`) narrows the pod's `nodeAffinity` to the ready-node
  intersection and removes the gate on the per-node generation predicate. No init container, no
  pod-side API/node access. *B (the Go init-container wait) was dropped* — an init container shares
  the workload pod's SA and so cannot carry its own `FloxEnv`-read RBAC.
. *RBAC + webhook scope (rke2lab follow-up)* — grant the controller SA `pods get;list;watch;update`
  and scope the pod `MutatingWebhookConfiguration` to *CREATE* (adding a scheduling gate is illegal
  on update), in `FloxControllerManifestsUnit`.
. *Flux calibration (separate)* — tune `timeout`/`retryInterval` on the FloxEnv-gated
  Kustomizations; keep the Job health-check.
