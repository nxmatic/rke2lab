= Fluent Pipeline Grammar
:toc: left
:toclevels: 3

This document defines the conventions for authoring multi-stage workflows in the seed-master codebase as fluent pipelines that read like English narrative.

== Motivation

A workflow expressed as a sequence of method calls on a builder is easy to write but hard to read. Boolean arguments lose context (`reconcileBbox(true, false, true)`), and stage boundaries are invisible — readers cannot tell where one logical phase ends and another begins.

The grammar below makes the structure explicit: stages are scoped, conjunctions are explicit, and labels carry weight (logging, error context). The result reads as a sentence describing the workflow.

== The four primitives

=== 1. Topic blocks via scoped lambdas

Each domain is entered through a `during(label, lambda)` call. The lambda receives a topic-specific builder; the compiler enforces that only that topic's verbs are callable inside the lambda.

[source,java]
----
.during("preflight", preflight -> preflight
    .enforceEntryGates()
    .requireLocalCommands("ssh", "kubectl")
    .requireRemoteCommand(host, "incus"))
----

Topic builders are package-private interfaces. The lambda parameter type narrows the surface, so `preflight.loadReservations()` will not compile.

=== 2. Conjunctions

Stages are joined with explicit `then()`. The conjunction is mandatory — its purpose is readability, not data flow.

[source,java]
----
.during("preflight", preflight -> ...)
.then()
.during("bbox reconciliation", bbox -> ...)
.then()
.during("incus provisioning", incus -> ...)
----

=== 3. Real labels

The string passed to `during(...)` is not decoration. It is used in three places:

* On entry: `→ entering preflight` is logged.
* On exit: `← leaving preflight` is logged with elapsed time.
* On failure: the exception is wrapped as `TopicFailure("preflight", cause)` so the topic name appears in stack traces and reaches the failure handler.

Labels are short, lowercase, descriptive of the *domain* not the action. Good: `"bbox reconciliation"`. Bad: `"step 2"`, `"reconcile-bbox-and-update"`.

=== 4. Failure handler

A per-topic failure handler is registered *before* the first `during(...)` call, typically via an `.onFailure(handler)` method on the pre-execution builder state. This is mandatory by structural design: the handler is consumed by `FluentTopicRunner` on every topic execution, so it must be in place when the first topic runs. Putting it at the end (after all `during` calls) was the previous shape and silently never fired — the type-state pattern now puts the handler before any `during` so it's always live.

The handler is optional; when not supplied, failures still propagate as `TopicFailure` carrying the topic label, but no user-supplied side-effect runs.

=== 5. Outcome verbs

The pipeline ends with one terminal verb that turns the chain into a result:

* `.collectOutputs()` — return a result map
* `.complete()` — terminal with no return value (used by entry-point pipelines)
* `.toResult()` — return a domain object

== Type-state ordering

Stage order is enforced by the type system. Each `during(...)` returns a distinct class representing "topic X done", which exposes only `then()`. Each `then()` returns the next-expected `Awaiting…` class, which exposes only the corresponding `during(...)`.

Authors literally cannot:

* skip `.then()`
* reorder topics
* call `.collectOutputs()` early
* register a failure handler after a topic has already run (the slot exists only on the pre-execution builder state)

The cost is one class per state transition (typically one method each). The benefit is that valid pipelines are the only ones that compile.

== State shape: immutable inputs + a mutable output builder

The shared state threaded through the transitions is not one flat mutable bag. It has two parts with two different natures, and conflating them is what makes a pipeline state hard to keep null-safe:

* **inputs** — everything the pipeline was configured with (config, policy, options, resolved services, the booted framework…). These are *known before the first topic runs* and never change afterwards. Model them as an **immutable record**, assembled once at the pre-execution → execution boundary (the `running…()` transition, where the last inputs — logger, mode, the services resolved from the booted registry — are settled). Because the record is built complete, every input read is `@NonNull` by construction: nothing to annotate.
* **outputs** — what each topic *produces* (the bbox result, the incus bootstrap result, the launch summary…). These come into being *during* the run, one per topic. Hold them in a **mutable output builder**: the topic writes its result through a sink, the next topic reads it. This builder is a set-once accumulator, so its fields follow the builder convention — `@MonotonicNonNull` + a `requireNonNull` guard where the next topic reads them (see the null-safety memory).

The insight that ties it to the grammar: **the output of the current state is the builder of the next.** Each transition constructs its topic from `state.inputs` (complete) plus the outputs already accumulated, runs it, folds the new output into the builder, and hands the enriched state to the next `Awaiting…` class. The type-state guarantees a topic can only read outputs that an earlier topic has already produced.

[source,java]
----
final class PipelineState {
  final PipelineInputs inputs;   // immutable record, frozen at running…()
  final Outputs outputs;         // mutable set-once builder (@MonotonicNonNull fields)
  final FluentTopicRunner runner;
}
----

Genuinely-optional inputs (a caller-supplied runbook, an optional failure handler) are `Optional<>` fields on the record — real absence, not "not yet set". Do not use `@Nullable` for either part: inputs are complete, outputs are set-once. See the null-safety conventions (`@MonotonicNonNull` for set-once, `Optional` for genuine absence).

== Pitfalls observed in this codebase

These are mistakes we made and fixed. Listing them so the next author doesn't repeat them.

=== Don't share `runDuring` on a state object via an unchecked cast

A tempting DRY: put a generic `<S, R> R runDuring(topic, stage, body)` on the shared state class so every transition reads `return state.runDuring(...)`. The body looks like:

[source,java]
----
state.runner.runDuring(topic, stage, body, onFailure);
@SuppressWarnings("unchecked")
final R cast = (R) this;
return cast;
----

This compiles. It does not work. `(R) this` lies — `this` is the shared `State`, not the next-state class — and the JVM throws `ClassCastException` the first time a transition runs. The `@SuppressWarnings` was suppressing a real bug.

**Correct shape**: each transition calls `FluentTopicRunner.runDuring(...)` directly and returns `new <Next>(state)` explicitly. Three lines instead of one, but type-safe at runtime:

[source,java]
----
public PreflightDone during(String topic, Function<PreflightTopic, PreflightTopic> body) {
  final PreflightTopic stage = new PreflightTopic(...);
  state.runner.runDuring(topic, stage, body, state.onFailure);
  return new PreflightDone(state);
}
----

Mnemonic: **the type-state pattern is the deduplication.** Don't try to deduplicate the transitions themselves.

=== Don't put the failure handler at the end of the chain

An `.onFailure(handler)` placed after the last `during(...)` *cannot work*: every preceding topic already ran with a `null` handler. Failures still propagate as `TopicFailure`, but no user-supplied side-effect fires.

**Correct shape**: the handler slot lives on the pre-execution builder state, before any `during(...)`. Optional, defaults to no-op when not called. See <<_failure_handler>>.

== Error semantics

Failures are caught per-topic. A throw inside any `during(...)` lambda is wrapped:

[source,java]
----
catch (Throwable cause) {
  throw new TopicFailure(topicLabel, cause);
}
----

`TopicFailure` carries the topic label so logs and handlers receive structured context (`"bbox reconciliation: <message>"`).

The default mode is *fail-fast*: the wrapped exception propagates to the terminal handler, the pipeline aborts, no later stages run. A degraded-continuation mode is intentionally not provided — add it only when a real workflow needs it.

== Authoring a new pipeline

When you find yourself writing a builder with three or more boolean parameters or a sequence of methods that need explanatory comments, consider expressing it as a fluent pipeline:

. Identify the topics. Each topic should map to a real domain in the codebase (a package, a problem area), not an arbitrary chunk of work.
. Define a topic builder for each (a `<Topic>Topic` class with the verbs that topic supports). Topic builders live in `pipeline/stages/` and have a public constructor so the pipeline machinery in the parent package can instantiate them.
. Build the type-state machine: one `Awaiting<Topic>` class per entry point, one `<Topic>Done` class per transition. Each transition calls `state.runner.runDuring(topic, stage, body, state.onFailure)` (the `FluentTopicRunner` is instance-based, its scope fixed at construction) and returns `new <Next>(state)` explicitly. Do *not* try to factor the runDuring call onto the shared state with an unchecked cast — see Pitfalls.
. Add an optional `.onFailure(handler)` method on the pre-execution builder state, before the first `during(...)` slot.
. Add the terminal verb(s) on the final `*Done` class.
. Write a sample call site as the first thing — let the call site shape the API.

Reuse from `controlplane.pipeline`:

* `FluentTopicRunner` (in `osgi/foundation/pipeline/pipeline-port`) — instance-based; `new FluentTopicRunner(scope)` then `.runDuring(topic, stage, body, onFailure)` — the topic-execution loop with logging and exception wrapping
* `OnFailure` — failure callback SAM
* `TopicFailure` — wrapped exception type

Exemplars in this codebase:

* `controlplane.pipeline.ClusterSeedPipeline` — outer workflow (5 topics)
* `controlplane.pipeline.ApplicationPipeline` — entry-point pipeline (3 topics)
* `controlplane.incus.IncusResourceBootstrap` — internal incus apply, state-machine inner classes (4 topics)

== When *not* to use this

A fluent pipeline is overkill for:

* Single-step operations.
* Workflows with two stages whose order is obvious from data flow alone.
* Code that needs to vary stage order at runtime (the type-state pattern is rigid by design).

For those, prefer a plain method or a small builder without the topic/conjunction machinery.

== Naming

* **Topic builders**: `<Topic>Topic` (e.g. `PreflightTopic`, `BboxTopic`) — the grammar unit is a *topic*; `Stage` is jgiven's reserved word (a class `extends Stage<>`), never our fluent unit.
* **State classes**: `Awaiting<Topic>`, `<Topic>Done`. Package-private.
* **Failure type**: the shared `TopicFailure` (in `pipeline-port`).
* **Outer pipeline**: short, domain-named (e.g. `ClusterSeedPipeline`), not `…ExecutionPipeline` or `…Orchestrator`.
