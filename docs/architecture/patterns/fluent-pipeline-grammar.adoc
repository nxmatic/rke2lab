= Fluent Pipeline Grammar
:toc: left
:toclevels: 3

This document defines the conventions for authoring multi-topic workflows in the seed-master codebase as fluent pipelines that read like English narrative.

== Vocabulary

One word per concept, used everywhere (code, docs, commits). This table is the authority.

[cols="1,4",options="header"]
|===
| Term | Meaning

| *topic* | The grammar unit — one domain phase, entered with `during(label, lambda)`. The topic builder class is `<Topic>Topic` (e.g. `PreflightTopic`). This is the ONLY word for a phase. Its contract is a *fluent multi-verb builder*: constructed with `(inputs, sink)`, each verb returns `this` and pushes its part of the output through the sink as it runs; the chain is executed by `FluentTopicRunner.runDuring(label, topic, Function<S,S>, onFailure)`. A topic reads only its frozen input `I` (never the context) and writes only through its `Sink` (never the accumulator `B`) — so its output is a function of `I` alone. (There is deliberately no single `O run(I)` interface: a topic is a multi-verb chain, not one mono-shot call — the verbs are the readable narration of `during(env -> env.loadX().loadY())`.) A topic's body has one of three natures (see <<_the_three_topic_body_natures>>): execution, checkpoint (narrated), or pipeline (a nested one).
| *pipeline (nested)* | A topic whose body is itself a `during/then` chain, with its own `State<I,B>` (own `B`, own topics), returning ONE composite output to the parent. ("sub" is implicit — a topic whose body is a pipeline IS a pipeline; the nesting is carried by where it sits, not by a prefix.) The parent sees one slot; the nested pipeline encapsulates its complexity, keeping the parent's `B` small and each `I` narrow. It SHARES the parent's `PipelineContext` (ambient is common) but its `B` is strictly local.
| *input* | The typed record `I` a topic consumes — only what THAT topic needs. Built explicitly by the transition, `@NonNull` by construction. Carries both flux and ambient, already fused; the topic need not know which field came from where.
| *output* | The typed record `O` a topic produces. Named by what it is (`bbox`, `bootstrap`), never suffixed `Result`/`Summary` — everything a topic yields is an output.
| *flux* | Data produced by an upstream topic and consumed by a downstream one. Carried by fields of the input record `I`, so a missing flux value is a compile error. NEVER carried by the context.
| *ambient* | Transverse data known before the first topic (modes, orchestrators, resolved services, shared charts). Carried by the `PipelineContext` registry; a miss is a fail-fast `require` (mis-wiring), not a "not-yet-produced".
| *builder* | The `StateBuilder`: the builder of the *next* state — the set-once accumulator of the outputs. Each topic folds its output in via a sink; a transition reads the accumulated outputs to build the next topic's input. Set-once fields (`@MonotonicNonNull`), read through guarded accessors.
| *context* | The `PipelineContext`: a type-safe `Class→record` registry for AMBIENT records, shared by every pipeline (generalized from the per-pipeline registries that were each reinvented). Read AND written ONLY while a transition builds an input — never inside a topic.
| *state* | The `State<I,B>` aggregate: `inputs` (the record `I`) + `builder` (the accumulator `B`) + `context` (`PipelineContext`) + `runner`. A per-pipeline SHAPE, not a factored base — the transition classes stay explicit. Inner to each pipeline, so it is `State`, not `PipelineState`: the outer pipeline already supplies the qualifier. `I` moves per topic; `B` is fixed for the pipeline. (No `O` parameter: a topic pushes its output through its `Topic.Sink` into `B`, it does not return it — so an output type would be phantom on `State`, the same code smell we refused for `Topic`.)
| *sink* | The `Consumer<O>` a topic writes its output through, into the builder — the WRITE face, symmetric to the input record `I` (the READ face). A topic has exactly two handles: it reads its frozen `I`, it writes through its `Sink<O>`. It sees neither the accumulator `B` nor the `PipelineContext` — the transition owns both and wires the sink to fold into `B`. This is what makes a topic deterministic AND testable in isolation (give it an `I` and a throwaway sink, assert what it writes). Writing a topic's output by directly assigning an accumulator field (topic holding a reference to the state) is a DERIVATION from the pattern: it couples the topic to `B` and defeats isolation — use a sink. *Sink vs context — orthogonal axes:* the `PipelineContext` is a READ source that is STATIC (frozen before the first topic, an input of the pipeline itself, never mutated mid-flow — the determinism rule); a `Sink<O>` is a WRITE channel that is FLOWING (one per topic, wired at the transition, it is how an output enters `B` and becomes the next topic's flux). Context answers "where does the ambient I read come from"; sink answers "where does the output I produce go". The transition is the one place that touches both — reads context + `B` to build `I`, wires the sink to fold back into `B`.

*The read-face — a `Supplier` is the canonical dual of the sink `Consumer`, an ownership-delegation principle (design 2026-07-03).* A `Consumer<O>` sink is the WRITE face: the topic *produces*, and the OWNER of the accumulator (the `State`) hands it `x -> state.field = x` — the producer writes without knowing the owner. A `Supplier<X>` is the READ face, the exact mirror: the owner hands a consumer `() -> state.field()` — the consumer reads without knowing the owner. In BOTH directions the owner holds the reference at ONE point and distributes a *capability* (write / read) to blind entities. That is the whole value: the reference to a produced value is borne once (the owner's slot), never copied and carried around; a downstream topic gets a read capability, not a hard reference to the upstream topic (the `SystemdInfrastructureSynthesizer` derivation — a topic taking the whole upstream *topic* and calling its getters — is exactly what this dissolves).

This is a CHOSEN decoupling principle, not a technical constraint — and that asymmetry is worth stating honestly. The write side is *forced* into a `Consumer`: a multi-verb topic cannot *return* its outputs, it must push them as the verbs run, so a sink is mandatory. The read side is *not* forced: a topic's inputs are available at construction (final fields), so a bare value works too. We adopt the `Supplier` read-face anyway, because it keeps the ownership model coherent (one owner, capabilities out) and because reads are themselves distributed across a topic's verbs (`StorageTopic` reads `floxInstall` in both `containerdZfsMountConfig()` and `vipKubeconfig()`) — the same "spread across execution" shape that forces the write sink. A bare value is admissible only for a trivially eager, single-use read where delegating buys nothing; when in doubt, the `Supplier` is the default.

Naming: `source == Supplier`. There is no nested `Topic.Source` type. Writes AGGREGATE per producer (a multi-verb topic pushes several outputs → a custom nested `<Topic>.Sink` collects them), but reads do NOT aggregate per consumer — a consumer reads single slots from *several distinct owners*, so each read-face is just a `Supplier<thatSlot>` (a JDK brick), not a consumer-owned interface. The aggregate of a topic's reads already exists: it is the input `I`. So the dual of the `Sink` (write aggregate) is `I` (read aggregate); the dual of a `Consumer<O>` (write slot) is a `Supplier<X>` (read slot). A `Topic.Source` type would just duplicate `I`.

*Determinism holds:* the owner supplies the `Supplier` over a set-once monotonic slot (the read cannot drift), so no order-coupling — the topic still never names `state.builder`, it only holds capabilities the transition wired.

*The invariant (GZ-2, applied uniformly across all pipelines 2026-07-03).* Every value a topic consumes it reaches through a `Supplier` that resolves at the source of truth (the owner — the `State`/sub-pipeline) on each read; a topic NEVER holds a copied reference to that value. This is *one source of truth* made structural: a copied reference is a constant only at the instant it is read — the moment the system evolves (a mid-flow write, a reordering, a slot that gains a second writer) the copy silently diverges from its source, and that drift is exactly the kind that is hard to find because nothing signals the two have parted. Delegating the read via `Supplier` makes the drift impossible by construction. This holds for BOTH kinds of input, with no exception:

* *flux* (produced by a sibling topic) — `state::nixInstall`, `state.builder::bootstrap`;
* *inherited ambient* (precedes the pipeline: a chart, a context, a config, paths) — ALSO a read-face. The owner holds the ambient once and hands `state::systemdChart` / `this::policy`; the topic takes `Supplier<Ambient>`. This resolves the G4 open question (`should inherited ambient become a Supplier or stay direct?`) in favour of uniformity: the ambient's owner is the `State`, so it delegates its read like any other slot. The earlier "inherited ambient passed direct" rule is RETIRED.

The one admissible bare value: a trivially eager, single-use read that a topic merely *forwards* without consuming (e.g. `ResourcesTopic` unwraps its `Supplier` fan-in inside `createAll()` and forwards config/policy straight to `resourceManager.createResources()`) — delegating there buys nothing. When in doubt, the `Supplier` is the default.

*Idiom.* A topic holds `Supplier` fields; it unwraps at the head of the verb that reads them (`final var chart = this.systemdChart.get();`) so the verb body is untouched. A topic read across MANY methods (Incus's `HostStage`) keeps a private accessor (`context()` → `context.get()`) that every read goes through, so bodies change only `context.` → `context()`. The owner exposes the matching accessor and the transition wires the method-ref (`state::systemdChart`); `state::accessor` IS the `Supplier` — the compiler synthesises it, capturing the owner. No explicit `Supplier` field on the owner: `state::accessor` already carries the read logic from the accessor, so an owner-held `Supplier` would be ceremony for the same call path (see [[pipeline-state-per-topic-io-refactor-backlog]]).
| *during* / *then* | The two grammar verbs: enter a topic / conjoin to the next. `then()` is mandatory, for readability.
| *transition* | The move from one topic to the next, carried by the type-state classes `Awaiting<Topic>` and `<Topic>Done`.
| *runner* | `FluentTopicRunner` — runs one topic (entry/exit logging + exception wrapping). Instance-based, scope fixed at construction.
| *onFailure* / *TopicFailure* | The per-topic failure handler (SAM) / the exception that wraps a topic throw, carrying the label.
| *outcome verb* | The terminal verb ending the chain: `collectOutputs()` / `complete()` / `toResult()`.
| *label* / *scope* | The topic's name (passed to `during`) / the runner's log scope.
|===

*Forbidden words (they belong to jGiven, never to our grammar):*

* *stage* — jGiven's `Stage<>` (a scenario class `extends Stage<>`). Our phase is a *topic*. A field/var named `stage` or a class `<X>Stage` in a pipeline is a bug.
* *step* — jGiven's step methods (`@As`). Use *topic* for the unit, *transition* for the move between them.

== Motivation

A workflow expressed as a sequence of method calls on a builder is easy to write but hard to read. Boolean arguments lose context (`reconcileBbox(true, false, true)`), and topic boundaries are invisible — readers cannot tell where one logical phase ends and another begins.

The grammar below makes the structure explicit: topics are scoped, conjunctions are explicit, and labels carry weight (logging, error context). The result reads as a sentence describing the workflow.

== The four primitives

=== 1. Topic blocks via scoped lambdas

Each domain is entered through a `during(label, lambda)` call. The lambda receives a topic-specific builder; the compiler enforces that only that topic's verbs are callable inside the lambda.

[source,java]
----
.during("preflight", preflight -> preflight
    .enforceEntryGates()
    .requireLocalCommands("ssh", "kubectl")
    .requireRemoteCommand(host, "incus"))
----

Topic builders are package-private interfaces. The lambda parameter type narrows the surface, so `preflight.loadReservations()` will not compile.

=== 2. Conjunctions

Topics are joined with explicit `then()`. The conjunction is mandatory — its purpose is readability, not data flow.

[source,java]
----
.during("preflight", preflight -> ...)
.then()
.during("bbox reconciliation", bbox -> ...)
.then()
.during("incus provisioning", incus -> ...)
----

=== 3. Real labels

The string passed to `during(...)` is not decoration. It is used in three places:

* On entry: `→ entering preflight` is logged.
* On exit: `← leaving preflight` is logged with elapsed time.
* On failure: the exception is wrapped as `TopicFailure("preflight", cause)` so the topic name appears in stack traces and reaches the failure handler.

Labels are short, lowercase, descriptive of the *domain* not the action. Good: `"bbox reconciliation"`. Bad: `"topic 2"`, `"reconcile-bbox-and-update"`.

=== 4. Failure handler

A per-topic failure handler is registered *before* the first `during(...)` call, typically via an `.onFailure(handler)` method on the pre-execution builder state. This is mandatory by structural design: the handler is consumed by `FluentTopicRunner` on every topic execution, so it must be in place when the first topic runs. Putting it at the end (after all `during` calls) was the previous shape and silently never fired — the type-state pattern now puts the handler before any `during` so it's always live.

The handler is optional; when not supplied, failures still propagate as `TopicFailure` carrying the topic label, but no user-supplied side-effect runs.

=== 5. Outcome verbs

The pipeline ends with one terminal verb that turns the chain into a result:

* `.collectOutputs()` — return a result map
* `.complete()` — terminal with no return value (used by entry-point pipelines)
* `.toResult()` — return a domain object

== Type-state ordering

Topic order is enforced by the type system. Each `during(...)` returns a distinct class representing "topic X done", which exposes only `then()`. Each `then()` returns the next-expected `Awaiting…` class, which exposes only the corresponding `during(...)`.

Authors literally cannot:

* skip `.then()`
* reorder topics
* call `.collectOutputs()` early
* register a failure handler after a topic has already run (the slot exists only on the pre-execution builder state)

The cost is one class per state transition (typically one method each). The benefit is that valid pipelines are the only ones that compile.

== State shape: per-topic `State<I,B>` + an ambient `PipelineContext`

The state threaded through the transitions is not one flat mutable bag. Each topic works against a **narrow input** it fully owns, and everything transverse lives in a **shared context** touched only at the seams. Three parts, three natures — conflating them is what makes a pipeline state hard to keep null-safe AND deterministic:

* **input `I`** — the typed record a topic consumes, *only what THAT topic needs*. Built explicitly by the transition just before the topic runs, so every field is `@NonNull` by construction. It carries two kinds of data, already fused so the topic can't tell them apart:
** **flux** — an upstream topic's output. Read from the accumulated outputs by the transition. Because it lands in the record `I`, a missing flux value is a *compile* error, not a runtime one.
** **ambient** — transverse data known before the first topic. Read from the `PipelineContext` by the transition.
* **output `O`** — the typed record a topic *produces*, one per topic. Folded through a sink into the `StateBuilder`, a set-once accumulator (`@MonotonicNonNull` + `requireNonNull` guard where the next transition reads it).
* **context** — the `PipelineContext`, a `Class→record` registry for the ambient records, shared by every pipeline.

[NOTE]
.What `PipelineContext` is FOR — the ambient verdict (three pipelines observed, 2026-07-03)
====
`PipelineContext` is NOT a blanket replacement for a clean immutable inputs record. It earns its place ONLY for *pipeline-level ambient* — transverse data the TRANSITIONS read to build inputs, shared across a pipeline and its sub-pipelines. Confirmed by migrating three pipelines:

* `IncusResourceBootstrap` — genuinely needed it: an ad-hoc `ContextRegistry` written mid-flow (`registry.update(BuildMetadata)`), ambient shared parent↔sub-pipelines. This is the disease `PipelineContext` cures.
* `ClusterSeedPipeline` / `ApplicationPipeline` — did NOT: each already has a clean set-once inputs shape (an immutable `PipelineInputs` record / direct `@MonotonicNonNull` fields), no mid-flow write, no sub-pipeline sharing. Converting to a `Class→record` registry would trade typed compile-time access for runtime `require(...)` — a downgrade. Left as-is.

Two ambient shapes it must NOT absorb, both surfaced by `DefaultManifestSynthesisService` (G3):

* *Deep-render ambient* — `ManifestSynthesisContext` is a THREAD-LOCAL read by 20+ manifest UNITS deep inside the `ManifestsUnitVisitor`, which are not topics. Crucially it carries the SAME KIND of data as `PipelineContext` — pure ambient, frozen before the first topic: the host→OSGi `ManifestSynthesisRequest` (identity, network topology, versions, image state…) plus the pre-synthesis-resolved age key. It is NOT accumulated flux (that would be a misplacement to pull back into `B`); it is genuine pre-run ambient. The two differ on ONE axis — the DEPTH OF THE READER, not the nature of the data. `PipelineContext` is read by the TRANSITIONS (few, at the pipeline surface) and passed as an explicit instance; the thread-local is read by the UNITS (many, deep inside the visitor, not topics at all) and is ambient by necessity — passing an instance explicitly would contaminate 20+ unit signatures that have nothing to do with the pipeline. Surface ambient → explicit `PipelineContext`; deep ambient → thread-local. `PipelineContext` is not "better", it is for a different reader depth.
* *Flux mistaken for ambient* — `SystemdSynthesisContext` looks ambient but is FLUX: the `systemd targets` stage builds it INTO its `Targets` output record, and the `systemd units` stage reads it off the accumulator. It belongs in `B`, not the context.

*Why these two co-occur (the deeper G3 lesson):* both the sink-less effect topics and the deep-render thread-local are symptoms of ONE fact — in `DefaultManifestSynthesisService` the real accumulator is not our `B`, it is the EXTERNAL cdk8s tree (`App`/`Chart`, built by the setup stage, mutated by every later stage, then walked by `synth()`) — a build-by-side-effect subsystem. `Topic.Sink` and `PipelineContext` are the WRITE and READ faces of OUR `B`; when the work lands in an external accumulator instead, both faces fall away together: the topic has no value to push (sink-less effect) AND the ambient must reach code deep outside the pipeline (a thread-local, not a stage-threaded `PipelineContext`). The pipeline ORCHESTRATES this subsystem (narration, order, per-phase failure) but does not CONTAIN it. Not a strict 1:1 though — a stage can both push a sink AND trigger the thread-local deep-render (`domain registry` does both), and an effect topic can mutate disk with no thread-local at all (`synthesis`). The correlation is "external accumulator ⇒ both I/O faces of `B` recede", not "sink-less ⇔ thread-local".
====

The insight that ties it to the grammar: **the output of the current state is the builder of the next.** Each transition reads the accumulated outputs (flux) and the context (ambient), *fuses them into the next topic's input `I`*, runs the topic, folds its output into the builder, and hands the enriched state to the next `Awaiting…` class. The type-state guarantees a topic can only receive an `I` built from outputs an earlier topic has already produced.

[source,java]
----
final class State<I, B> {          // a per-pipeline SHAPE, not a factored base
  final I inputs;                  // per-topic (moves)     — flux + ambient fused at the transition, @NonNull, safe alone
  final B builder;                 // per-pipeline (fixed)  — the set-once accumulator; topics push into it via their Topic.Sink
  final PipelineContext context;   // ambient registry      — read/written ONLY by a transition
  final FluentTopicRunner runner;
}

// The port's topic contract is IDENTIFICATION, not a mono-shot `O run(I)`. A topic is a fluent
// multi-verb builder constructed with (inputs, sink); the sink is its nested Topic.Sink.
// The NATURE is a nested type, not a returned enum: a topic implements one of the three.
interface Topic {
  String role();
  interface Sink {}                // a sink is the write-face OF a topic → nested, not top-level
  interface Execution  extends Topic {}   // most topics
  interface Checkpoint extends Topic {}   // plays a jGiven scenario
  interface Pipeline   extends Topic {}   // a nested during/then chain
}
----

The two type parameters of `State` are not of the same kind: `I` *moves* — it is the input each transition rebuilds for the next topic. `B` is *fixed* for the whole pipeline: it is the one accumulator that grows as outputs fold in, but its type never changes across topics. There is deliberately no `O` parameter: a topic does not RETURN its output, it PUSHES it through its `Topic.Sink` into `B` — so an `O` on `State` would bind to no field, a phantom parameter (the same reason `Topic` is not generic on `I`/`O`). Parameterizing `B` (rather than a raw `StateBuilder` base) keeps the shared shape typed — the transition folds each topic's sink-writes into `B`, so "the output of the current state is the builder of the next" holds by construction. `B` also carries the fan-in: a late topic's input is built by reading several outputs off the accumulator (see <<_the_fan_in>>). And `Topic` itself is NOT generic on its input/output/sink: those are the topic's own construction detail (a fluent builder taking `(inputs, sink)`), not its identifying surface — see <<_the_two_faces_api_vs_implementation>>.

=== The determinism rule — the context is touched only when a transition builds an input

`PipelineContext` is a *mutable* aggregator: nothing technically stops a topic from writing a record mid-flow. If a topic could, its input would depend on the runtime context state at execution time — order-coupled, *non-deterministic*, the exact flat-bag disease wearing a clean type. So the rule:

**The context is read AND written only while a transition builds a topic's input. Never inside a topic.**

* A topic is constructed with `(inputs, sink)` — it does NOT receive the context, so it can neither read a record at an arbitrary instant nor write one back. Its output is a pure function of its input `I` → deterministic, testable in isolation (give it an `I` and a throwaway `Topic.Sink`, assert what it pushes).
* The transition is the single point of contact: read flux (accumulated outputs) + read ambient (`context.require(...)`) → fuse into a frozen `I` → optionally write newly-available ambient for later transitions. Read and write co-located, at one instant.
* Flux and ambient meet inside `I`; where each field came from is a transition detail the topic need not know.

This turns a *typed* contract into a *typed + deterministic + localized* one: at the moment `I` is assembled it is frozen, and the topic has no handle to reopen the context.

Genuinely-optional inputs (a caller-supplied runbook, an optional failure handler) are `Optional<>` fields on the input record — real absence, not "not yet set". Do not use `@Nullable`: inputs are complete, outputs are set-once, ambient is fail-fast. See the null-safety conventions (`@MonotonicNonNull` for set-once, `Optional` for genuine absence).

====
Before this design converged, the state was *flat*: a single `PipelineInputs` record + a single `StateBuilder`
merging EVERY topic's inputs and outputs, threaded via `state::` suppliers. That was null-safe (the null-cleanup
chantier), but each topic saw the whole sack — `PreflightTopic` could reach `doctor` or the `bootstrap` output it
has no business with — and the mutable `ContextRegistry` inside `IncusResourceBootstrap` could in principle be
written mid-flow, making an input order-dependent. The `State<I,B>` + `PipelineContext` shape above is the target;
the migration is a wave across all pipelines (its own plan), and until a given pipeline is migrated it may still
show the flat shape. The census of which pipelines conform, diverge, or are pending lives in the
`pipeline-state-per-topic-io-refactor-backlog` memory.
====

== The three topic-body natures

A topic comes in three natures, and **the nature IS a type, not a returned value**: each is a nested sub-interface of `Topic` — `Topic.Execution`, `Topic.Checkpoint`, `Topic.Pipeline` — and a topic implements exactly one. There is no `nature()` method and no `TopicNature` enum: the type already carries it. Governance and retrofit test the nature at compile time (`topic instanceof Topic.Checkpoint`) rather than switching on a stringly value, and the three interfaces are the **entry points** where a nature-specific shared contract could later be defined (empty today — honest). This is symmetric with `Topic.Sink`: `Topic` nests both its write-face and its natures.

* **`Topic.Execution`** — does a gesture, and EITHER pushes its output through its `Topic.Sink` (most topics: resolve paths, ensure a provider resource, create an instance) OR performs a pure EFFECT with no output to fold into `B` — mutating an external builder (a cdk8s `App`/`Chart` produced by an earlier stage) or writing to disk. The sink is OPTIONAL: an effect topic (`DefaultManifestSynthesisService`'s `systemd units` / `target finalization` / `synthesis` stages mutate the shared cdk8s chart, then `synth()` walks it) has no record for `B`, so it declares no `Sink`. It stays a topic for the NARRATION, not for a flux: the `during/then` label, the phase logging, the per-phase `TopicFailure`. (This is why a topic is identified by `role()` + nature, not by an output type — an output would be phantom on an effect topic, the same reason `State` has no `O`.)
* **`Topic.Checkpoint`** — runs a jGiven scenario to produce a `ReportModel` narrative + a verdict, for the parts an operator must *read*. Only two exist today (`ClusterReadinessTopic`, `SystemdAdapterTopic`, via `*Scenario extends Stage<>`). This is the answer to "do we have jGiven's scenarios in the pipeline model?" — **yes, as a topic nature, not a rival grammar.** *One engine (jGiven), two layers*: `during/then` orchestrates; jGiven narrates *inside* a checkpoint.
* **`Topic.Pipeline`** — the body is itself a `during/then` chain with its own `State<I,B>`. It returns one composite output to the parent, so the parent's `B` stays small and each `I` narrow. It shares the parent's `PipelineContext` (ambient is common) but its `B` is strictly local. Already present organically: `ApplicationPipeline`→`ClusterSeedPipeline`; `ClusterSeedPipeline`→`ResourceCreationPipeline`; `DefaultManifestSynthesisService`→`SystemdInfrastructureSynthesizer`.

**No shared-ceremony base — decided against on the code (2026-07-03).** An earlier design gave checkpoint and nested-pipeline an abstract base *above* the interface, to host the ceremony proven identical across instances. Two findings killed it:

* *Checkpoint:* the two checkpoints share the jGiven lifecycle SHAPE but diverge on ~6 axes — the scenario script, the skip-bodies condition (`preview && simulated.isEmpty()` vs `preview`), all three outcomes (success / preview / failure — the failure path is `ReadinessAuthority` STOP/degraded vs `VerificationResult` projection), the consult-checkpoint shape (one observation vs a phase collection), and even the collaborator field types (`doctor` `Optional` vs nullable, `recordedAt` `Optional<Instant>` vs `Instant`, sink `Map` vs `VerificationResult`). A template-method base would need ≥6 hooks — a leaky abstraction hiding more than it shares. The ceremony stays honestly duplicated. Also: the two do NOT live in one pipeline — `SystemdAdapterTopic` is in `ClusterSeedPipeline`, `ClusterReadinessTopic` is driven by `ResourceCreationPipeline` (out of the type-state pattern).
* *Pipeline:* A5 verdict (Incus pilot) — the 3 hand-written nested pipelines have distinct typed-field accumulators; a `PipelineTopic` base earned nothing (~3 lines, would force generics + a map). Honest duplication.

So `Topic.Checkpoint`/`Topic.Pipeline` are identification-only (fix the nature by their type, prescribe no body). Extract a base only if a genuinely shared shape appears (a 3rd checkpoint, a shared nested-pipeline accumulator).

A 10-field `B` (a topic producing four outputs at once) is the smell that a pipeline is hiding several: extract the offender as a nested pipeline so its outputs live in *its* `B`, not the parent's. Composition is how the small-`I` / small-`B` rule is honoured, rather than one flat giant accumulator.

== Pitfalls observed in this codebase

These are mistakes we made and fixed. Listing them so the next author doesn't repeat them.

=== Don't share `runDuring` on a state object via an unchecked cast

A tempting DRY: put a generic `<S, R> R runDuring(topic, stage, body)` on the shared state class so every transition reads `return state.runDuring(...)`. The body looks like:

[source,java]
----
state.runner.runDuring(topic, topicBuilder, body, onFailure);
@SuppressWarnings("unchecked")
final R cast = (R) this;
return cast;
----

This compiles. It does not work. `(R) this` lies — `this` is the shared `State`, not the next-state class — and the JVM throws `ClassCastException` the first time a transition runs. The `@SuppressWarnings` was suppressing a real bug.

**Correct shape**: each transition calls `FluentTopicRunner.runDuring(...)` directly and returns `new <Next>(state)` explicitly. Three lines instead of one, but type-safe at runtime:

[source,java]
----
public PreflightDone during(String topic, Function<PreflightTopic, PreflightTopic> body) {
  final PreflightTopic preflight = new PreflightTopic(...);
  state.runner.runDuring(topic, preflight, body, state.onFailure);
  return new PreflightDone(state);
}
----

Mnemonic: **the type-state pattern is the deduplication.** Don't try to deduplicate the transitions themselves.

=== Don't put the failure handler at the end of the chain

An `.onFailure(handler)` placed after the last `during(...)` *cannot work*: every preceding topic already ran with a `null` handler. Failures still propagate as `TopicFailure`, but no user-supplied side-effect fires.

**Correct shape**: the handler slot lives on the pre-execution builder state, before any `during(...)`. Optional, defaults to no-op when not called. See <<_failure_handler>>.

== Error semantics

Failures are caught per-topic. A throw inside any `during(...)` lambda is wrapped:

[source,java]
----
catch (Throwable cause) {
  throw new TopicFailure(topicLabel, cause);
}
----

`TopicFailure` carries the topic label so logs and handlers receive structured context (`"bbox reconciliation: <message>"`).

The default mode is *fail-fast*: the wrapped exception propagates to the terminal handler, the pipeline aborts, no later topics run. A degraded-continuation mode is intentionally not provided — add it only when a real workflow needs it.

== Authoring a new pipeline

When you find yourself writing a builder with three or more boolean parameters or a sequence of methods that need explanatory comments, consider expressing it as a fluent pipeline:

. Identify the topics. Each topic should map to a real domain in the codebase (a package, a problem area), not an arbitrary chunk of work.
. Define a topic builder for each (a `<Topic>Topic` class with the verbs that topic supports). Topic builders live in `pipeline/stages/` and have a public constructor so the pipeline machinery in the parent package can instantiate them.
. Build the type-state machine: one `Awaiting<Topic>` class per entry point, one `<Topic>Done` class per transition. Each transition calls `state.runner.runDuring(topic, stage, body, state.onFailure)` (the `FluentTopicRunner` is instance-based, its scope fixed at construction) and returns `new <Next>(state)` explicitly. Do *not* try to factor the runDuring call onto the shared state with an unchecked cast — see Pitfalls.
. Add an optional `.onFailure(handler)` method on the pre-execution builder state, before the first `during(...)` slot.
. Add the terminal verb(s) on the final `*Done` class.
. Write a sample call site as the first thing — let the call site shape the API.

Reuse from the pipeline-port (`osgi/foundation/pipeline/pipeline-port`):

* `FluentTopicRunner` — instance-based; `new FluentTopicRunner(scope)` then `.runDuring(topic, stage, body, onFailure)` — the topic-execution loop with logging and exception wrapping. Bound `runDuring(<S extends Topic>…)`.
* `OnFailure` — failure callback SAM
* `TopicFailure` — wrapped exception type
* `Topic` — the topic IDENTIFICATION contract: `role()`, the nested `Topic.Sink` marker, and the three nested nature sub-interfaces `Topic.Execution`/`Topic.Checkpoint`/`Topic.Pipeline` (a topic implements one). NOT `O run(I)` (a topic is a fluent multi-verb builder, not a mono-shot call). The runner's bound; the governance/retrofit hook (`instanceof Topic.Checkpoint`, not a `nature()` switch). No `TopicNature` enum — the nature is the type.
* `PipelineContext` — the shared ambient `Class→record` registry, `require`/`lookup`/`register`/`contains` (no `update` — ambient is set once before the first topic). Generalized from `controlplane.incus.ContextRegistry`, which is then deleted.

Exemplars in this codebase:

* `controlplane.pipeline.ClusterSeedPipeline` — outer workflow (5 topics)
* `controlplane.pipeline.ApplicationPipeline` — entry-point pipeline (3 topics)
* `controlplane.incus.IncusResourceBootstrap` — internal incus apply, state-machine inner classes (4 topics)

== When *not* to use this

A fluent pipeline is overkill for:

* Single-operation tasks.
* Workflows with two topics whose order is obvious from data flow alone.
* Code that needs to vary topic order at runtime (the type-state pattern is rigid by design).

For those, prefer a plain method or a small builder without the topic/conjunction machinery.

== Naming

* **Topic builders**: `<Topic>Topic` (e.g. `PreflightTopic`, `BboxTopic`) — the grammar unit is a *topic*; `Stage` is jgiven's reserved word (a class `extends Stage<>`), never our fluent unit.
* **State classes**: `Awaiting<Topic>`, `<Topic>Done`. Package-private.
* **State aggregate**: `State<I,B>`, and its accumulator `StateBuilder` — inner to each pipeline. NOT `PipelineState`/`PipelineInputs`: see the `Pipeline`-prefix rule below.
* **Failure type**: the shared `TopicFailure` (in `pipeline-port`).
* **Outer pipeline**: short, domain-named (e.g. `ClusterSeedPipeline`), not `…ExecutionPipeline` or `…Orchestrator`.

=== The `Pipeline` prefix — top-level only

A type carries the `Pipeline` prefix only when it is *top-level* and the prefix is what qualifies it (`PipelineContext`, `ClusterSeedPipeline`). A class, interface, or record defined *inner* to a pipeline inherits the qualifier from its outer class, so the prefix there is redundant noise:

* ✅ inner: `State`, `StateBuilder`, `Launch`, `Awaiting<Topic>`, `<Topic>Done` — the enclosing `…Pipeline` already names the context.
* ✅ top-level / shared port: `PipelineContext`, `Topic`, `FluentTopicRunner`, `TopicFailure` — no enclosing class, so the name stands alone (domain-named, `Pipeline`-prefixed only where it disambiguates).
* ✅ nested where it belongs to its owner: `Topic.Sink` (the write-face OF a topic), a topic's own `<Topic>.Sink` and its output records — a sink has no existence outside its topic, so it lives in the topic's namespace, not top-level.
* ❌ `PipelineState`, `PipelineInputs` as *inner* names — redundant; drop to `State` / the input record's own name.
