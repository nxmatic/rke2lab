== How the framing evolved (read this first)

The subject was first captured as *"unify the two DSLs into one language"* and pushed toward
*Option D / Shape C* — make the pipeline *become* a JGiven scenario (everything in
Given/When/Then). The 2026-06-07 brainstorm walked that back through two corrections from the user:

. *"unify is too strong."* The pipeline is the *operational base* of the system. The BDD logic
  should *rest on* that base, not merge with it into a third thing.
. *"…but re-coding the BDD layer on our side is the wrong move."* JGiven already *is* a
  narration+report engine. Rather than reimplement that on top of `TopicRunner`, keep JGiven as the
  engine and *share it across two layers* — orchestration and verification — each using it at its
  own altitude.

So the landing direction is *neither* "one merged language" *nor* "BDD rests on a
hand-rolled pipeline engine". It is:

> *One engine (JGiven), two layers. The fluent `during/then` grammar stays the authoring surface;
> JGiven is the runtime substrate underneath it.*

== The lifecycle mapping (the crux we explored)

JGiven has *two* levels that must not be conflated:

* *a scenario* = one single-pass `given… when… then…` (no G/W/T looping);
* *a `ReportModel`* = an *accumulator of many scenarios* — this is what becomes the living doc.

Two ways to map a pipeline run onto that:

* *Mapping A — one run = ONE scenario with N steps.* Collapses 8 topics into a single
  given/when/then (the old "Shape A"). Loses the topic-by-topic structure, forces action topics into
  a `When`. *Rejected.*
* *Mapping B — one run = ONE `ReportModel`, ONE scenario per topic.* Each `during(label, …)` becomes
  `scenario.startScenario(label)` into the shared report. This is JGiven's natural granularity and
  *already* how the 2 checkpoints work — generalise it to all 8. *This is the direction.*

Under Mapping B the user's "two layers" become *two flavours of scenario in one report*:

* *action topic* (preflight, incus, …) → `when`-only scenario (narrates, does not assert);
* *verification topic* (systemd adapter, cluster readiness) → full `given/when/then` + doctor.

=== The type-state question DISSOLVES

The earlier capture's big open worry — *"pipeline-as-scenario loses the compile-time type-state
ordering"* — no longer applies. With Mapping B, `during/then` stays the *authoring surface*
(type-state, compile-time), and JGiven is only the *runtime substrate* (narration + report). They
sit at different levels and never compete. *Syntax vs engine.* No ordering is lost.

== The real remaining tension: the STATE model

This is the open decision now (it replaces the type-state question). JGiven threads state *inside a
scenario* via thread-locals — `@ProvidedScenarioState` / `@ExpectedScenarioState`
(`SystemdAdapterScenario` ~line 22-25). The pipeline threads state by passing `PipelineState` as an
*instance*. The project's CLAUDE.md "instance-passing discipline" explicitly proscribes hidden
thread-local state.

So "JGiven as shared engine" collides with a documented project rule — *unless* we bound JGiven's
role. Two sub-options:

* *Role 1 — narration + report only (recommended starting hypothesis).* JGiven supplies
  `startScenario/given/when/then/finished` + the shared `ReportModel` + step-name prose. Inter-topic
  state stays `PipelineState` passed as an instance. Thread-local is confined to *within* a single
  verification scenario (local, short-lived, low harm). Respects instance-passing discipline.
* *Role 2 — full state engine.* Adopt `@ProvidedScenarioState` as the threading mechanism too. One
  uniform JGiven mechanism, but frontally contradicts instance-passing — would require amending
  CLAUDE.md. Higher cost, weaker fit.

*Not decided.* The user wants a prototype to decide, not a vote.

== Options considered (history, condensed)

* *A — JGiven replaces TopicRunner as the orchestrator.* Rejected: wrong level; forces every action
  topic to become a verification scenario.
* *B — keep the separation, just document the discipline.* Viable, lowest cost, but the user wants
  shared substrate, not two documented engines.
* *C — common `PipelineStage` abstraction.* Stages share too little for the abstraction to earn its
  keep.
* *D — pipeline BECOMES a scenario (Shape C, nested scenarios).* The earlier landing spot. Now
  *superseded* by the engine-sharing framing: we don't make the pipeline *be* a scenario; we make
  JGiven the *engine under* the pipeline, with topics as scenarios in a shared report (Mapping B).
