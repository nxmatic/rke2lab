= Configuration Restructuring Specification
:toc: left
:toclevels: 3

This specification restructures rke2lab's configuration from a fragmented multi-reader model
into a single-source-of-truth architecture: all configuration flows through Pulumi config into
one immutable DTO (`Rke2labConfig`), assembled from fragments that infra domains contribute, with
missing-input remediation expressed through the doctor pattern.

[NOTE]
====
The core is BUILT: `ConfigLoader`, the immutable `Rke2labConfig` DTO, and `InfraDomain` (the six
domains, each self-loading its `InfraConfigFragment` via a polymorphic `contribute(loader)`) exist in
`exec/seed-master/.../config/`. What shipped is the CLOSED form (an enum), not the open registrar
interface this spec's diagrams still draw — see § <<open-registrar-p2p>> for why, and when that opens.
====

The design output is *C4 / UML diagrams*, not code. The implementation follows the project's
documented patterns (fluent pipeline grammar, builder/record discipline, single-source-of-truth
catalogs); this document fixes the architecture, not the syntax.

== Overview

=== Problem statement

[cols="1,3",options="header"]
|===
| Issue | Detail

| Multiple Config readers
| Three classes (`BootstrapConfig.Builder`, `ControlplanePolicy`, `ConfigResolver`) each read
  Pulumi `Config` independently, with divergent `EnvironmentValues` wrappers.

| Mixed fallbacks
| Values fall back to env vars (`RKE2LAB_ACCESS_HOST`, `SYSTEMD_ADAPTER_DBUS_*`,
  `INCUS_CONFIG_DIR`, `user.home`), to git detection (`GIT_WORKTREE`, JGit), or to hardcoded
  paths - inconsistently.

| Flat key structure
| Pulumi config uses flat dotted keys (`incus.configDir`) that don't reflect logical grouping.

| Dead / buggy keys
| Some keys are unused; one lacks the `rke2lab:` prefix.

| Nix-hostile
| Git-worktree detection and `user.home` fallbacks don't work under `nix run/exec`, where git
  context and home directories may be absent.
|===

=== Goals

. *Single source of truth* - one component reads Pulumi config; everything else consumes an
  immutable DTO.
. *Explicit configuration* - no env/system fallbacks. What's in the YAML is what's used.
. *Nested structure* - config keys mirror the nested DTO for readability.
. *Domain-contributed* - each infra domain owns its config fragment (and, in the future, its
  doctor specialist), mirroring the manifest-domain registry.
. *Nix-compatible* - works without git context or home directories.
. *Incremental* - delivered in small, independently green increments.

| The assembled, immutable DTO. Infra fragments via the registry; cross-cutting identity
  loaded directly. No defaults, no logic beyond load-time mandatory validation.

| `BootstrapConfig` / `ControlplanePolicy`
| Optional-free views *derived* from the DTO. Defaults applied here.
|===

== Detailed design

=== The DTO structure

`Rke2labConfig` composes an `InfraConfigRegistry` (the contributed Stage-A fragments) with the
cross-cutting identity records. Infra fragments implement a sealed `InfraConfigFragment` marker
so the registry's single cast is provably exhaustive.

==== Field contract: mandatory vs optional

The decisive rule, applied uniformly:

[cols="1,1,2",options="header"]
|===
| Kind | DTO type | On absence

| *Mandatory*
| plain (`Path` / `URI` / `String`)
| Throws `MissingRequiredConfiguration` at load time (accumulated, see remediation).

| *Optional / defaulted*
| `Optional~T~`
| Stays empty in the DTO. The default is applied *later*, in the derivation layer - never here.
|===

Mandatory today: `incus.configDir`, `image.sharedFolder`, `worktree.dir`. Everything else is
optional with a derivation-time default. The DTO is a faithful, immutable view of what the
operator wrote - no defaults, no logic.

=== Domains contribute their fragments

Mirroring `ManifestsDomainRegistrar → ManifestsDomainRegistryBuilder → ManifestsDomainRegistry`,
each infra domain is a *registrar* that contributes a self-loaded fragment. The DTO is assembled
by iterating registrars, not by hand-listing fragments - so a new provisioning concern is one
new registrar, with no edit to a central monolith.

[mermaid]
----

==== The heterogeneity cost (flagged, resolved)

The manifest registry has it easy: every registrar yields the same `ManifestsDomain` type, so
the registry flattens uniformly. Infra fragments are *heterogeneous* (`IncusConfig` ≠
`ImageConfig`), so a uniform registrar interface returns the `InfraConfigFragment` marker, which
erases the concrete type. We pay this in exactly one place and recover full type-safety for
consumers:

* the registry stores fragments keyed by `InfraDomainCatalog` id;
* `Rke2labConfig`'s typed accessors (`incus()`, `image()`, …) do the single cast, validated once
  at `build()` against the registrar's declared id↔type mapping;
* the `sealed` marker keeps the cast honest (the permits list is the closed set of fragment
  types). Consumers never see the cast.

=== Two taxonomies, two layers

We deliberately do *not* force config into the manifest taxonomy: provisioning (Stage A - how the
VM comes up) and deployment (Stage B - what runs in Kubernetes) are different layers. Two catalogs
follow the same single-source-of-truth pattern at their respective layers.

* `policy.link.*` flags *are* manifest-domain IDs, so `ControlplanePolicy.isLinkEnabled` MUST
  resolve them through `ManifestDomainCatalog` accessors (the `clusterApi`-vs-`cluster-api`
  discipline) - never a hardcoded switch.
* Stage-A infra keys are tagged by `InfraDomainCatalog` for symptom routing.
* Cross-cutting identity (`cluster.name`, `node.name`, `api.endpoint`, `kubeconfig.ref`,
  `readiness.*`) belongs to *neither* catalog - it has no domain and no specialist.

=== Deriving the runtime configs

The DTO carries `Optional` and no defaults. Turning it into the Optional-free `BootstrapConfig`
and `ControlplanePolicy` is a multi-stage workflow, expressed in the former fluent pipeline
grammar (see link:../bdd/bdd.adoc#the-avant[Pipeline spec (the avant — former fluent
grammar)]; that model is now superseded by BDD-as-engine — jGiven scenarios on the JUnit launcher).
This `resolve(...)` step is the single seam where `Optional` becomes concrete and
where every default lives.

[mermaid]
----

    subgraph resolve["resolve(...) - fluent pipeline"]
        S1["during bootstrap<br/>→ BootstrapConfig.from(dto)"]
        S2["during policy<br/>→ ControlplanePolicy.from(dto)"]
        S1 -->|"then"| S2
    end
    BOOT["BootstrapConfig<br/>(Optional-free)"]
    POL["ControlplanePolicy<br/>(link keyed by catalog)"]

    DTO --> resolve
    S1 --> BOOT
    S2 --> POL

    style DTO fill:#90EE90,stroke:#2e7d32
    style BOOT fill:#FFE4B5,stroke:#e65100
    style POL fill:#FFE4B5,stroke:#e65100
----

* Each `during(label, …)` stage *delegates* to the matching factory; the pipeline supplies the
  labels (entry/exit logs, `PipelineStageFailure(label, cause)`) and type-state ordering.
* Defaults are literal `orElse(...)` at this single site - every default that used to hide in
  `BootstrapConfig.Defaults` (env vars, `user.home`, JGit) becomes a visible literal here.
* `ControlplanePolicy` builds a `link-by-catalog-id` map by pairing each `ManifestDomainCatalog`
  accessor with its policy getter, so a caller querying `CATALOG.clusterApi()` can never miss.

== Remediation via the doctor pattern

A missing or malformed mandatory key is, in the doctor's vocabulary, a *symptom*. Config
validation is an *entry gate* - a precondition checked *before* provisioning, the same species as
`EntryGatePolicyEnforcer`. So when it fails, the operator should get a *prescription*, not a bare
stack trace.

=== Config is the doctor pattern's first use case

The doctor subsystem (Generalist → Specialists → Prescription → RemediationPlan) is introduced by
the link:../doctor/runbook-doctor.adoc[runbook & doctor design]. But chronologically, config load is the *earliest*
gate in a `pulumi up` - earlier than any readiness checkpoint - so missing-input remediation is
the doctor pattern's *first* application.

config relative to them; their internals stay runbook-doctor's.

=== Knowledge lives with the domain specialist

There is a *single, shared* `Generalist` - no config-specific doctor. There is also *no*
`ConfigSpecialist`: the config layer knows only a *structural* fact ("key `incus.configDir`,
type `Path`, mandatory, absent"), so a config specialist would be hollow. The *meaning* lives
with the *domain specialist* the infra domain contributes - the Incus specialist knows
`incus.configDir` is the client-cert dir and why it matters, exactly as it knows
`instance-not-found` at runtime. A missing input is just another *symptom in that domain*.

This is why the registrar's `specialist()` is the *future* shape: the infra domains will
contribute their specialists once the doctor types exist, and the runtime specialists
(`DbusTcpSpecialist`, `IncusExecSpecialist`) *converge into* these domain-contributed ones - the
convergence the deferred "a domain owns {fragment, units, specialist}" abstraction predicts.

=== Accumulate, then consult once

Fail-fast on the first missing key forces a frustrating one-error-per-run loop. So `from()`
*accumulates* every missing/malformed mandatory key (domain-tagged), then consults once. Each
domain specialist writes one `Prescription` per offending key; the Generalist synthesizes them
into one `RemediationPlan`.

[mermaid]
----
graph TB
    LOAD["Rke2labConfig.from()"] --> ACC{"accumulated<br/>missing keys?"}
    ACC -->|"none"| OK["return DTO"]
    ACC -->|"≥1 (domain-tagged)"| GEN["Generalist.consult"]
    GEN -->|"route by domain"| SI["Incus specialist"]
    GEN -->|"route by domain"| SOTHER["...other domain specialists"]
    GEN -->|"no specialist for domain"| BARE["bare structural message"]
    SI --> PLAN["RemediationPlan"]
    SOTHER --> PLAN
    BARE --> PLAN

    style GEN fill:#fff4e6,stroke:#ff9900

NOTE: Until the doctor exists, `MissingRequiredConfiguration` works *standalone* - it accumulates
and throws a single aggregated message listing all keys (with their domain tags). Routing to
domain specialists for the *why* is the only part that waits for the doctor.

| `BootstrapConfig.from(dto)` factory. Delete `Builder`, `Defaults`, `applyConfig`, all env/git
  detection. Document the github-clone fallback contract on `WorktreeConfig`.
| `pulumi up` provisions with `worktree.dir` from config; zero `com.pulumi.Config` /
  `System.getenv` / JGit references remain in bootstrap config.

| *C* +
derive ControlplanePolicy
| `ControlplanePolicy.from(dto)`; `isLinkEnabled` keyed off `ManifestDomainCatalog`. Delete
  `ConfigResolver` and the `EnvironmentValues` wrapper.
| All policy comes from the DTO; `ConfigResolver` deleted; build green.

| *D* +
doctor remediation +
(*first doctor use case*)
| Build the minimal doctor core consumed first here (Generalist, specialist interface,

  the loader's accumulated, domain-tagged symptoms route to them.

DAG + checkpoint machinery on top, becoming the *second* use case. *(Open for confirmation - see
Review questions.)*

== Testing strategy

[cols="1,3",options="header"]
|===
| Test | Asserts

| Loader
| `optional*` → empty for absent keys; `require*` accumulates a domain-tagged symptom (no throw
  mid-load).

| DTO population
| Nested YAML → infra fragments via registry + cross-cutting records populated.

| Registrar contribution
| Each `contribute()` yields its fragment; `fragment(id, type)` + typed accessors resolve.

| Mandatory validation
| Absent `worktree.dir` / `image.sharedFolder` / `incus.configDir` reported by name; *multiple*
  absences reported together.

| BootstrapConfig derivation
| Each `orElse` default applied; result Optional-free.

| Policy catalog-keying
| `isLinkEnabled(CATALOG.clusterApi())` returns the value set under `policy.link.clusterApi` -
  guards the kebab/camel mismatch.

| Doctor remediation (D)
| Accumulated keys route by domain to the right specialist; one `RemediationPlan`; missing
  specialist degrades to bare message.

| Integration
| `pulumi preview` / `pulumi up` succeed with nested config.
|===

== Risks and mitigations

[cols="1,3",options="header"]
|===
| Risk | Mitigation

| Pulumi/Jackson can't bind nested objects into `Optional` records
| *Decided, not a risk.* We never ask it to. `ConfigLoader` reads scalars key-by-key and wraps
  them. The only `getObject` use is the two nested `Map~String,String~` maps
  (`policy.readiness.override` / `simulate`) - a shape Pulumi handles.

| Breaking existing deployments
| Each increment is independently testable; validate the new nested YAML before removing old code.

| Nix deployment still won't work
| Explicit config is a *prerequisite*, not the whole solution. Nix deploys must still ensure
  `worktree.dir`, `incus.configDir`, `image.sharedFolder` are accessible. This spec documents the
  requirement; Nix packaging is separate.
|===

== Future work

[[open-registrar-p2p]]
=== Open the domain set: the registrar, required by the distributed peer-to-peer mode

This spec's diagrams draw an open `InfraDomainRegistrar` `<<interface>>` — "a new provisioning concern
= one new registrar, no edit to a central monolith". What SHIPPED is the closed form: `InfraDomain`, a
polymorphic enum whose six values each self-load their fragment via `contribute(loader)`. The enum
KEEPS most of the design's value — per-domain self-load, decoupled assembly (`values()` iterates, no
hand-list), logic encapsulated per value — and loses ONLY the OPEN axis: adding a domain edits the
central enum rather than dropping in a new file/bundle.

For the current CENTRALIZED bootstrap (seed-master orchestrates six fixed structural infra domains)
the enum is the sound, idiomatic choice — the open registrar would be speculative. The registrar
becomes REQUIRED in the DISTRIBUTED peer-to-peer mode: when the system is a mesh of unitrepo peers that
extend their capabilities dynamically — contributing a domain as a bundle to answer a new need — a
closed compiled enum cannot be extended by a peer, but a DS-collected roster of registrars
(`@Reference(cardinality=MULTIPLE) List<InfraDomainRegistrar>`) can. This is the SAME open-vs-closed
tension, with the same p2p driver, as the world-gateway egress roster (the "multiplexor") — see the
link:../osgi/world-gateway-spec.adoc#open-extensibility-chantier[world-gateway planned evolution]. Both
open the contributor set; both are scheduled with the unitrepo peer-to-peer work, not before. The open
registrar design in this spec is PRESERVED as that future direction.

=== GitHub clone fallback

If `worktree.dir` is inaccessible (e.g. Nix) and `worktree.source = github`, clone the repo to a
temp dir. Contract documented on `WorktreeConfig` in Increment B; implementation deferred.

=== Secrets integration

If Incus certs must be embedded rather than referenced, materialize `incus.configDir` at runtime
from the existing `.secrets` mechanism.

=== Deferred: abstract the two domain registries (separate branch)

Once `ManifestDomainCatalog` (Stage B) and `InfraDomainCatalog` (Stage A) both exist, the
*catalog → registrar → builder → registry, validate-on-build()* shape is duplicated and
abstractable into a generic `DomainRegistry`. *Not in scope here* - future branch
`refactor/domain-registry-abstraction`. Deferred deliberately (rule of three): the two registries
differ exactly where abstraction is hard (homogeneous units + DAG validation vs heterogeneous
sealed fragments + id↔type validation), and the doctor adds a third facet
("domain owns {fragment, units, specialist}") still being defined on the runbook-doctor branch.
Trigger: a third instance, or the doctor's domain model landing - whichever first reveals the real
variation axes.
