= Bootstrap Identity Provider
:toc: left
:toclevels: 3

This document explains the bootstrap identity provider pattern, how to use it in manifest units, and how to set up infrastructure identities (Incus credentials).

== Overview

The bootstrap identity provider is a **thread-local context** that supplies cluster and infrastructure identity to manifest units during synthesis. It prevents parameter proliferation and ensures consistent identity access across all manifest units.

5. **Context Provider** (mechanism) - ThreadLocal injection - synthesis-scoped

=== What BootstrapIdentity Provides

`BootstrapIdentity` is a record in the `manifests.contract.profiles` package (exposed to units via `ManifestSynthesisContext`) that carries these nine components:

[cols="1,3",options="header"]
|===
|Field |Description
|`clusterName` |Cluster identifier (e.g., "bioskop", "nikopol")
|`clusterId` |Numeric cluster identifier
|`clusterToken` |RKE2 cluster join token
|`clusterDomain` |Kubernetes cluster domain (default: "cluster.local")
|`clusterEnv` |Environment label (e.g., "dev", "prod")
|`nodeName` |Node identifier for seed node
|`nodeId` |Numeric node identifier
|`nodeKind` |Node role (e.g., "master", "worker")
|`incusRemoteName` |Configured Incus remote for this cluster — may differ from `clusterName` (e.g., cluster "bioskop" uses remote "bioskop-nixos")
|===

=== Incus Infrastructure Identity

Each cluster uses its own Incus remote, but all clusters share a single CAPN identity:

* **Remote naming**: The remote is configured per cluster in the `incusRemoteName` field and MAY differ from the cluster name (e.g., cluster "bioskop" uses remote "bioskop-nixos") — which is exactly why the dedicated field exists rather than deriving the remote from `clusterName`
* **Single CAPN identity**: All clusters use identity name `"capn"` for Cluster API Provider Incus
* **Operator environment**: Credentials stored in operator's environment (`.secrets`, `~/.config/incus`)

== Usage Pattern: How to Access Identity in Manifest Units

=== Anti-Pattern: Constructor Parameters

**❌ Don't do this:**

[source,java]
----
public final class IncusIdentitySecretManifestsUnit extends AbstractManifestsUnit {

  private final String clusterName;  // ❌ Constructor parameter
  private final String remoteAddress;  // ❌ Constructor parameter

  public IncusIdentitySecretManifestsUnit(String clusterName, String remoteAddress) {
    super(MANIFEST_UNIT_ID, List.of());
    this.clusterName = clusterName;
    this.remoteAddress = remoteAddress;
  }
}
----

**Problems:**

1. Manifest units are statically instantiated by `DomainRegistrar` - no way to pass runtime parameters
2. Leads to duplication of identity concerns across manifest units
3. Breaks the separation: orchestration (registrar) vs. runtime config (context)

=== Correct Pattern: Context Access

**✅ Do this instead:**

[source,java]
----
public final class IncusIdentitySecretManifestsUnit extends AbstractManifestsUnit {

  public IncusIdentitySecretManifestsUnit() {
    super(MANIFEST_UNIT_ID, List.of());
  }

  @Override
  protected void doSynthesize(Construct scope, ManifestsUnitContext context) {
    // Identity + material come from the synthesis context — never the filesystem.
    String clusterName = ManifestSynthesisContext.current().bootstrapIdentity().clusterName();
    Optional<IncusIdentityMaterial> material =
        ManifestSynthesisContext.current().incusIdentity();

    // Ephemeral/test runs carry no identity: nothing to render.
    if (BootstrapIdentity.UNKNOWN.equals(clusterName) || material.isEmpty()) {
      return;
    }

    // Render the <cluster>-incus-identity Secret from the material seed-master handed over.
    // (base64-encode the raw PEM/address blobs at render time — a Secret encoding concern)
    new ApiObject(scope, "secret-incus-identity", /* Secret props from material.orElseThrow() */ ...);
  }
}
----

**Benefits:**

1. Manifest units have no runtime dependencies - statically instantiable
2. Identity access is consistent across all units
3. Clear separation: structure (constructor) vs. data (context)
4. Runtime configuration injected via thread-local context

=== Reaching Context From a Unit

`AbstractManifestsUnit` provides NO identity accessors — the base is a template method
(`apply(ManifestsUnitContext)`) that only creates the unit's CDK8s scope and emits its group
marker. Units reach synthesis-scoped data directly through the thread-local
`ManifestSynthesisContext.current()`, which delegates each slice to the bound
`ManifestSynthesisRequest`:

[source,java]
----
// Cluster + node identity (manifests.contract.profiles.BootstrapIdentity)
ManifestSynthesisContext.current().bootstrapIdentity();

// Network topology (CIDRs, interfaces, gateway addresses)
ManifestSynthesisContext.current().networkTopology();

// Component versions (kube-vip, tailscale, operators, ...)
ManifestSynthesisContext.current().componentVersions();

// Incus identity material for the CAPN Secret (Optional — empty on ephemeral runs)
ManifestSynthesisContext.current().incusIdentity();

// Flox NRI debug toggles for development
ManifestSynthesisContext.current().floxDebugPolicy();
----

== Incus Identity Setup (One-Time Bootstrap)

=== Prerequisites

* OpenSSL installed
* Incus CLI configured with remote access
* Access to `.secrets` file for storing private keys

=== Step 1: Generate CAPN Client Certificate

[source,bash]
----
# Generate EC private key (secp384r1 curve)
openssl ecparam -name secp384r1 -genkey -noout -out capn-client.key

# Generate certificate signing request
openssl req -new -key capn-client.key -out capn-client.csr \
    -subj "/CN=capn-provider"

# Self-sign certificate (valid for 10 years)
openssl x509 -req -in capn-client.csr -signkey capn-client.key \
    -out capn-client.crt -days 3650

# Clean up CSR
rm capn-client.csr
----

**Note**: The CN `capn-provider` is descriptive but not tied to a specific cluster. All clusters share this identity.

=== Step 2: Add Certificate to Incus Trust

For each Incus remote, add the certificate to the trust store:

[source,bash]
----
# Add to bioskop remote
incus config trust add-certificate capn-client.crt \
    --name "cluster-capn" \
    --type client

# If you have multiple remotes, repeat for each
incus config trust add-certificate capn-client.crt \
    --name "cluster-capn" \
    --type client \
    --remote nikopol
----

=== Step 3: Store Certificate in the host application resources

Copy the public certificate to seed-master's resources (the host world):

[source,bash]
----
cp capn-client.crt \
    exec/seed-master/src/main/resources/incus/capn-client.crt
----

The `capn-provider` identity is host-owned: seed-master holds it and hands it off to Stage B (it is
NOT the identity seed-master authenticates with — that is the operator cert in `~/.config/incus/`).
The host-side `IncusIdentityMaterialAssembler` reads this cert (plus the client key from `.secrets`
and the server cert + remote address from `~/.config/incus/`), bundles them into an
`IncusIdentityMaterial`, and passes it across the host→OSGi frontier on the `ManifestSynthesisRequest`.
The OSGi `IncusIdentitySecretManifestsUnit` only RENDERS the Secret from that material — it never reads
a host file or classpath resource itself (it cannot: it runs inside an isolated bundle whose
classloader sees neither the flat classpath nor `~`).

=== Step 4: Store Private Key in `.secrets`

Add the private key to the `.secrets` file in the repository root:

[source,yaml]
----
incus:
  capn:
    # sops:encrypted
    clientKey: |
      -----BEGIN PRIVATE KEY-----
      MIG2AgEAMBAGByqGSM49AgEGBSuBBAAiBIGeMIGbAgEBBDCRtb9cilzN7q8wYrjR
      328PF/Tk4rBLt9ZD5cY34vHr7T+hCixRdmMACPzjuithMDOhZANiAAQWIauKN9+J
      ...
      -----END PRIVATE KEY-----
----

**Important**: Encrypt with SOPS before committing:

[source,bash]
----
sops --encrypt --in-place .secrets
----

=== Step 5: Verify Setup

Check that the certificate is trusted:

[source,bash]
----
# List trusted certificates
incus config trust list

# Should show:
# +------------------+--------+----------------------+
# |       NAME       |  TYPE  |    FINGERPRINT       |
# +------------------+--------+----------------------+
# | cluster-capn     | client | abc123...            |
# +------------------+--------+----------------------+
----

== How Manifest Synthesis Uses Identity

=== Synthesis Flow

[mermaid]
----
sequenceDiagram
    participant Bootstrap as seed-master synthesis entry
    participant Service as DefaultManifestSynthesisService
    participant Context as ManifestSynthesisContext
    participant Unit as IncusIdentitySecretManifestsUnit

    Bootstrap->>Service: synthesize(request)
    Note over Bootstrap,Service: Request carries BootstrapIdentity<br/>+ IncusIdentityMaterial (assembled host-side)

    Service->>Context: of(request, ...).bind()
    activate Context

    Note over Service: Create cdk8s App + Chart

    Service->>Unit: apply(context) → doSynthesize(scope, context)

    Note over Unit: No constructor parameters!

    Unit->>Context: bootstrapIdentity().clusterName()
    Context-->>Unit: "bioskop"

    Unit->>Context: incusIdentity()
    Context-->>Unit: IncusIdentityMaterial (PEM + addr)

    Note over Unit: Render from material — no filesystem read

    Unit->>Unit: Create <cluster>-incus-identity Secret

    deactivate Context
----

=== Entry Point: the seed-master synthesis entry

The seed-master synthesis entry point builds the `ManifestSynthesisRequest`, populating its
`BootstrapIdentity` (and the Incus identity material) before handing it across the host→OSGi
frontier:

[source,java]
----
final BootstrapIdentity identity = BootstrapIdentity.builder()
    .clusterName(config.clusterName())
    .clusterId(config.clusterId())
    .clusterToken(config.clusterToken())
    // ... other fields ...
    .build();

final ManifestSynthesisRequest request = baseRequest
    .withBootstrapIdentity(identity)
    .withComponentVersions(versions)
    .withNetworkTopology(topology);

synthesisService.synthesize(request);
----

=== Context Binding: DefaultManifestSynthesisService

The context wraps the whole `ManifestSynthesisRequest` (plus the pre-synthesis-resolved age
material), and `bind()` is an instance method publishing it on the thread-local for the duration of
synthesis, returning a `Scope` that restores the previous binding on close:

[source,java]
----
final var contextScope =
    ManifestSynthesisContext.of(request, sopsAgeMaterial).bind();  // ← identity injected via the request
try (contextScope) {
    // All manifest units can now reach ManifestSynthesisContext.current()
    return synthesizeInContext(request);
}
----

=== Unit Access: During doSynthesize()

Manifest units read identity in their `doSynthesize(scope, context)` hook (the `apply(...)` template
method is `final` on the base and only frames the scope + group marker):

[source,java]
----
@Override
protected void doSynthesize(Construct scope, ManifestsUnitContext context) {
    // Context access - no constructor parameters needed
    String clusterName = ManifestSynthesisContext.current().bootstrapIdentity().clusterName();
    String version = ManifestSynthesisContext.current().componentVersions().of(Component.CLUSTER_API_OPERATOR);

    // Create K8s resources under the unit's scope
    new ApiObject(scope, "provider", ...);
}
----

== Adding New Identity Fields

When Stage B / multi-cluster work requires new identity fields:

1. **Add field to `BootstrapIdentity` record**:
+
[source,java]
----
public record BootstrapIdentity(
    String clusterName,
    // ... existing fields ...
    String newField  // NEW
) {
    // Update constructor validation if needed
}
----

2. **Update the seed-master synthesis entry point**:
+
[source,java]
----
final BootstrapIdentity identity = BootstrapIdentity.builder()
    .clusterName(config.clusterName())
    // ... existing fields ...
    .newField(config.newField())  // NEW
    .build();
----

3. **Access in manifest units** via `bootstrapIdentity().newField()`

No need to update `ManifestSynthesisContext` - it passes the entire `BootstrapIdentity` record through.

== Troubleshooting

=== "Client certificate resource not found"

**Symptom**: `IllegalStateException: Client certificate resource not found: /incus/capn-client.crt`

**Cause**: Certificate missing from seed-master's host-world resources, where the
`IncusIdentityMaterialAssembler` reads it.

**Fix**: Copy certificate to `exec/seed-master/src/main/resources/incus/capn-client.crt` and rebuild.

=== "incus.capn.clientKey not found in .secrets"

**Symptom**: `IllegalStateException: incus.capn.clientKey not found in .secrets`

**Cause**: Private key not in `.secrets` file or incorrect YAML structure.

**Fix**:
1. Decrypt `.secrets` with `sops --decrypt .secrets`
2. Add key under `incus.capn.clientKey` as YAML block scalar (`|`)
3. Re-encrypt with `sops --encrypt --in-place .secrets`

=== "Server certificate not found"

**Symptom**: `IllegalStateException: Server certificate not found for remote <host> at ~/.config/incus/servercerts/<host>.crt`

**Cause**: Missing server certificate or wrong hostname.

**Fix**:
1. Check remote address in `~/.config/incus/config.yml`
2. Extract hostname from address (e.g., `https://192.168.1.1:8443` → `192.168.1.1`)
3. Ensure `~/.config/incus/servercerts/192.168.1.1.crt` exists
4. If missing, connect to remote once: `incus remote add bioskop https://192.168.1.1:8443`

=== "Remote '<cluster>' not found in config.yml"

**Symptom**: `IllegalStateException: Remote 'nikopol' not found in ~/.config/incus/config.yml`

**Cause**: Remote not configured or name mismatch.

**Fix**:
1. Add remote: `incus remote add nikopol https://192.168.1.2:8443`
2. Verify the configured `incusRemoteName` matches a remote in `config.yml` (it need not equal the cluster name)
3. Check `incus remote list` to see configured remotes
