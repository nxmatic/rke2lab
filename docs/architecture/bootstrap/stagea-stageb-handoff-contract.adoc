= Stage A -> Stage B Handoff Contract (CAPN/CAPI)
:toc: left
:toclevels: 3

This document defines the normalized output contract between:

* *Stage A* — Pulumi bootstrap (host-side, via `seed-mgmt`) that seeds the *management cluster*.
* *Stage B* — CAPI + CAPN + CAPRKE2 running *inside the management cluster*, greenfield-creating the
  *separate* workload clusters.

The objective is to avoid drift between bootstrap assumptions (Stage A) and the CAPI templates that
create the workload clusters (Stage B).

[IMPORTANT]
====
Rewritten for the *management/workload separation*. Read
link:../cluster-api/management-workload-topology.adoc[Management / Workload Topology] (the anchor)
first. Under the old self-managed model, "Stage B inside cluster" meant CAPI scaling the *seed* cluster
in place. It no longer does: Stage B's CAPI lives in the dedicated management cluster and creates
*separate* workload clusters — the handoff kubeconfig is the *management* cluster's, and the CAPN
resources target *workload* clusters on possibly-different bare-metals.
====

[[handoff-sequence]]
== The handoff at a glance

[mermaid,stagea-stageb-handoff-sequence,svg]
----
sequenceDiagram
  autonumber
  participant SM as seed-mgmt (host)
  participant MG as management cluster
  participant CAPI as CAPI/CAPN/CAPRKE2<br/>(in management cluster)
  participant WL as workload cluster<br/>(bioskop-wrkld / nikopol-wrkld)

  SM->>MG: Stage A — nix-seed + validate single node
  MG-->>SM: handoff assets (mgmt kubeconfig, identity, checksums, 2 CAPN identity secrets)
  SM->>CAPI: Stage B — install controllers into management cluster
  SM->>CAPI: apply workload CRs (Cluster / LXCCluster / RKE2ControlPlane / LXCMachineTemplate)
  CAPI->>WL: greenfield-create over the node mesh (mammoth-skate)
  WL-->>CAPI: control-plane ready → kubeconfig for the workload cluster
----

The handoff assets flow *from* the management cluster (Stage A output) *into* the Stage B install that
runs against that same management cluster. The workload clusters are the *product* of Stage B, not a
party to the handoff.

== Ownership boundary

Stage ownership is strict:

* Stage A creates and validates only the *management* control node required to establish the
  management API's reachability.
* Stage B owns all *workload-cluster* lifecycle (creation, scale, replacement, rollout, remediation)
  through the Kubernetes controllers running *in the management cluster*. It never scales the
  management cluster itself.

NOTE: The workload-CR *apply mechanism* (this section's imperative "Stage B `kubectl apply`" vs
GitOps-in-mgmt vs another driver) is UNDER RE-DESIGN as of 2026-08-25 — see
link:../cluster-api/cluster-workload-completion-plan.adoc[the completion plan] §2.B and the live
whiteboard. What is settled and live: the management cluster runs its own Flux against
`manifests/bioskop-mgmt` (all layers reconciling), and Stage A already shrank to nix-seed + the
node-bootstrap set (`FluxRoot` + CNI + sops). Where the workload CRs are declared and by whom applies
them is the open question the re-brainstorm answers.

== Required handoff assets

The following assets are the minimum shared contract. Unless noted, they describe the *management*
cluster (the target of the Stage B install); the machine-class and identity-secret surfaces describe
the *workload* resources Stage B will render.

[cols="1,2,3",options="header"]
|===
|Asset |Example field |Why it must be shared

|Management identity
|`managementClusterName`
|Binds the Stage B controller install and its GitOps state to the management cluster identity.

|Management API endpoint
|`apiEndpoint`
|Required for the management-plane controller install and health checks.

|Management kubeconfig reference
|`kubeconfigRef`
|Lets the Stage B installer authenticate against the newly bootstrapped *management* cluster.

|Management node provider identity
|`seedNodeId`
|Traceability of the management control node and break-glass operations.

|Incus project scope
|`incusProject`
|Ensures management-node provisioning and CAPN resources target the intended tenancy/project scope.

|Image alias
|`imageAlias`
|Human-facing baseline image contract used by templates and operations.

|Image fingerprint
|`seedImageFingerprint`
|Immutable provenance for reproducibility and drift detection.

|Provisioning checksum
|`seedProvisioningChecksum`
|Deterministic fingerprint of Stage A materialized provisioning inputs; drives node replacement when changed.

|Image build checksum
|`seedImageBuildChecksum`
|Deterministic fingerprint of image build inputs; drives node replacement when changed.

|Default machine class
|`machineClassRef` (or equivalent)
|Maps bootstrap assumptions to the *workload* CAPN `LXCMachineTemplate` fields.

|Load balancer mode
|`loadBalancerMode`
|Must match the workload control-plane endpoint strategy (`lxc`, `oci`, `ovn`, `kube-vip`, `external`).

|Handoff readiness marker
|`handoffReady`
|Explicit gate that Stage B prerequisites are complete.

|Systemd runtime status summary
|`systemdRuntimeStatusSummary`
|Operator-facing runtime signal for Stage A convergence diagnostics (pending jobs, failed units, node service state).
|===

== CAPN-aligned machine class surface

The machine class published by Stage A should be translatable to CAPN fields in the *workload*
`LXCMachineTemplate.spec.template.spec`:

* `instanceType` (for current parity: `container`)
* `flavor`
* `profiles`
* `devices`
* `target`
* `image` (`name` and optionally `fingerprint`/`server`/`protocol`)

== Identity secret compatibility (one per incus remote)

Because the management cluster drives *two* bare-metals, CAPN needs *two* identity secrets — one per
incus remote — each referenced by that workload's `LXCCluster.spec.secretRef`. The endpoint keys
(`server`, `server-crt`) differ per remote; the CAPN client identity (`client-crt`, `client-key`) is
the same across both.

Required keys (validated during handoff preparation):

* `server` — *per remote*
* `server-crt` — *per remote*
* `client-crt` — *shared* (single CAPN client identity)
* `client-key` — *shared*

Optional keys:

* `project`
* `insecure-skip-verify`

== Recommended Stage A output object

[source,yaml]
----
# @codebase
handoff:
  managementClusterName: bioskop-mgmt        # <host>-mgmt, host-indifferent
  apiEndpoint: https://10.66.106.10:6443     # the MANAGEMENT cluster's API
  kubeconfigRef: .local.d/kubeconfig.yaml     # BootstrapPaths.STATE_DIR — /srv/host is dissolved
  seedNodeId: incus://rke2lab/bioskop-mgmt-master
  incusProject: rke2lab
  imageAlias: control-node
  seedImageFingerprint: sha256:TODO
  seedProvisioningChecksum: sha256:TODO
  seedImageBuildChecksum: sha256:TODO
  machineClassRef: lxc-control-default-v1
  loadBalancerMode: kube-vip
  handoffReady: false
  # Stage B targets — the separate workload clusters CAPI will greenfield-create,
  # one CAPN identity secret per incus remote (server/server-crt differ; client shared).
  workloadTargets:
    - clusterName: bioskop-wrkld
      incusRemote: bioskop
      identitySecretRef: capn-identity-bioskop
    - clusterName: nikopol-wrkld
      incusRemote: nikopol
      identitySecretRef: capn-identity-nikopol
----

== Acceptance criteria

* Stage A emits all required handoff fields describing the *management* cluster.
* Stage B can render CAPI/CAPN resources for *both* workload clusters without external discovery of
  missing data.
* Handoff fields are stable across idempotent Stage A re-runs (function-of-git: a re-seed lands in the
  same functional state).
* Management node image fingerprint and provider identity are auditable.
* Seed checksum fields are auditable and change when Stage A provisioning/image inputs change.
