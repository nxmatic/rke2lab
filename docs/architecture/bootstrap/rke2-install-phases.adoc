= RKE2 Install Phases — Modelling RKE2's Place in the System
:toc: macro
:icons: font

toc::[]

== Overview

*Status*: IMPLEMENTED (2026-06-03)

This document introduces the *InstallPhase* concept: an explicit model of *where each
manifest attaches to RKE2's lifecycle*. It exists because RKE2 has been mis-modelled in
our system as "a systemd service we depend on" (`After=rke2-server.service`), when it is
really a *multi-phase lifecycle*. Manifests attach at different phases, each with distinct
ordering and readiness requirements. Treating them all as uniform "post-server" caused
recurring systemd ordering bugs.

=== The problem this solves

Empirically, our `networking` domain alone needs three different timings:

[cols="1,2,2,1",options="header"]
|===
|Manifest |Nature |Required timing |Today

|`cilium-config`
|`HelmChartConfig` patching the Cilium chart RKE2 itself deploys
|*Before* `rke2-server` starts (RKE2 reads it at boot)
|Ad-hoc `synthesizeSystemdUnits` override (pre-server service)

|`cilium-advanced`
|Cilium CRs (BGP, L2, LoadBalancerIPPool)
|*After* Cilium CNI is Ready (CRDs must exist)
|Nothing → race condition

|`envoy-gateway`, `kdns`
|Standard resources
|*After* `rke2-server` (API up)
|Generic post-server installer
|===

Each unit reinvents its ordering in an ad-hoc `synthesizeSystemdUnits` override. This is
fragile, non-uniform, and — critically — *invisible to `ManifestsUnit.lazy()`*, which only
propagates `apply(Chart)` and metadata, NOT `synthesizeSystemdUnits`. So a unit's special
ordering silently disappears when wrapped in `lazy()`. The bug and the missing concept are
the same thing: *ordering should be declared metadata, not overridden code.*

== The concept: InstallPhase

Each `ManifestsUnit` declares *which phase of RKE2's lifecycle it attaches to*, as metadata
(like `manifestUnitId` and `dependsOnManifestsUnitIds`). The systemd synthesis *derives*
the ordering directives and readiness gate from that phase — centrally and uniformly.

Because the phase is metadata, `ManifestsUnit.lazy()` propagates it for free. No unit needs
to override `synthesizeSystemdUnits` anymore; the special cases (cilium-config pre-server,
cilium-advanced post-CNI) become declarations, not bespoke services.

=== Proposed phases (to refine)

[cols="1,2,2",options="header"]
|===
|Phase |When |Derived systemd ordering

|`PRE_SERVER`
|Before rke2-server starts; RKE2 consumes the manifest at boot (e.g. HelmChartConfig)
|`Before=rke2-server.service`, attached to `rke2lab.target`

|`POST_SERVER`
|API server up, RKE2 watches `server/manifests/` (default, most domains)
|`After=rke2-server.service`, `WantedBy=rke2lab-manifests.target`

|`POST_CNI_READY`
|After Cilium CNI Ready (Cilium CRDs exist) — e.g. cilium-advanced CRs
|`After=rke2lab-cilium-ready.service`

|(future) `POST_OPERATOR_READY`
|After a specific operator's CRDs are established (e.g. vCluster, Flux for seed-vcluster)
|`After=<operator>-ready.service`
|===

NOTE: `POST_OPERATOR_READY` connects directly to the seed-vcluster work (see
`.claude/seed-vcluster-plan.md`) — waiting for vCluster/Flux operators is the same
"wait for CRDs" pattern as cilium-advanced.

=== Phase ↔ target: do not build a parallel hierarchy

A phase and a systemd *target* are two views of the same lifecycle moment. The target
hierarchy in `systemd-architecture.adoc` already materializes the first two phases:

[cols="1,2",options="header"]
|===
|Phase |Existing target that materializes it

|`PRE_SERVER`
|`rke2lab-bootstrap.target` ("pre-server initialization complete")

|`POST_SERVER`
|`rke2lab-manifests.target` ("post-server manifest installers")

|`POST_CNI_READY`
|none yet → new `rke2lab-cni-manifests.target` (ordered `After=rke2lab-manifests.target`)

|`POST_OPERATOR_READY`
|none yet → new `rke2lab-operator-manifests.target` (ordered after CNI)
|===

CAUTION: *The phase must not create targets.* Targets are created exactly once, in the
synthesis pipeline (`DefaultManifestSynthesisService`'s `SystemdTargetsStage`), and exposed
through `SystemdSynthesisContext` (`bootstrapTarget()`, `manifestsTarget()`, ...). The phase
only *selects* which context target an installer is `WantedBy`/`PartOf`. Otherwise we'd have
two creators for `bootstrap.target` / `manifests.target` — a parallel hierarchy that drifts
from the pipeline's. So:

* The pipeline stays the single source of truth for target creation. The two new targets
  (`cni-manifests`, `operator-manifests`) are added there, alongside the existing six, and
  exposed via new `SystemdSynthesisContext` accessors.
* `InstallPhase` carries a *reference selector* (which context accessor), not a target it
  builds. Derivation reads `context.<phase target>()` — same pattern as the ready-gate, but
  the gate is a service we provision on demand whereas the target is pre-created.

Today's gap (to fix when wiring targets): `PRE_SERVER` installers are currently `WantedBy`
the root `rke2lab.target` instead of `rke2lab-bootstrap.target`, and `POST_CNI_READY` shares
`rke2lab-manifests.target` instead of its own. The ordering is correct (the `After=` gate
distinguishes them); only the target grouping is imprecise.

== Place in the architecture

`InstallPhase` is not a new isolated component: it is *metadata* added to the existing
`ManifestsUnit` contract, consumed by systemd synthesis. This diagram shows where it plugs
into the current model (catalog → registrar → domain → unit → synthesis).

[mermaid]
....

    CAT["ManifestDomainCatalog<br/>(domain IDs)"]
    REG["XxxDomainRegistrar<br/>(domain())"]
    DOM["ManifestsDomain<br/>(units, synthesizeSystemdUnits)"]

    subgraph contract["ManifestsUnit (contract)"]
        ID["manifestUnitId()"]
        DEP["dependsOnManifestsUnitIds()"]

    LAZY["ManifestsUnit.lazy(...)<br/>propagates metadata<br/>(incl. installPhase)"]

    CAT --> REG --> DOM
    DOM -->|holds| LAZY
    LAZY -.implements.-> contract
    DOM -->|synthesizeSystemdUnits| SYNTH
    PH -->|read by| SYNTH
    CTX -->|targets + gates| SYNTH

*Reading the diagram*: The phase enters through the `ManifestsUnit` contract (alongside
`manifestUnitId` / `dependsOn`), survives propagation through `lazy()` (which carries all
metadata), and `SystemdUnitSynthesizer` — and it alone — translates it into systemd
directives. No unit writes ordering anymore: the knowledge "phase → `Before=`/`After=`/gate"
is centralized in the synthesizer.

== Construction: how synthesis derives ordering

The key point of the model: *units declare, the synthesizer builds*. Here is the flow for a
domain that spans multiple phases (the `networking` case).

[mermaid]
....
sequenceDiagram
    participant D as ManifestsDomain
    participant U as ManifestsUnit lazy
    participant S as SystemdUnitSynthesizer
    participant C as SystemdChart

    D->>D: group units by phase
    Note over D: networking splits into 3 phases
    loop for each phase in the domain
        D->>U: read installPhase
        U-->>D: PRE_SERVER or POST_SERVER or POST_CNI_READY
        D->>S: installer for domain and phase
        S->>S: derive ordering from phase
        Note over S: PRE before rke2-server
        S->>C: emit rke2lab manifests service
    end
....

Each emitted service runs the same `rke2lab-manifests-install.sh` script (which already knows
how to link an entire domain *or* a specific sub-path), but with ordering derived from the
phase. The phase therefore *never* appears in the shell script — it lives entirely in the Java
synthesis, which is the source of truth (see "single-tier" decision).

== Usage pattern (proposed)

[source,java]
----
public interface ManifestsUnit {
  // ... existing manifestUnitId(), dependsOnManifestsUnitIds(), apply(Chart) ...

  // NEW: declares lifecycle attachment. Default covers the common case.
  default InstallPhase installPhase() {
    return InstallPhase.POST_SERVER;
  }
}

// A unit that must run before rke2-server:
public final class CiliumConfigManifestsUnit extends AbstractManifestsUnit {
  @Override public InstallPhase installPhase() { return InstallPhase.PRE_SERVER; }
}

// A unit that must wait for the CNI:
public final class CiliumAdvancedManifestsUnit extends AbstractManifestsUnit {
  @Override public InstallPhase installPhase() { return InstallPhase.POST_CNI_READY; }
}
----

=== ✅ Do / ❌ Don't

* ✅ *Declare* the phase as metadata; let synthesis derive `After=`/`Before=`/ready-gate.
* ✅ Keep `lazy()` propagating `installPhase()` (it already carries metadata).
* ❌ Don't hand-write `synthesizeSystemdUnits` per unit to bolt on ordering — that's the
  anti-pattern that produced the bug and that `lazy()` silently drops.
* ❌ Don't model RKE2 as a single `After=rke2-server.service` dependency — that flattens
  the phases and hides the real ordering constraints.

== Resolved design decisions (2026-06-03)

. *Granularity = per-(domain, phase)*. Installer services are emitted per couple
  (domain, phase) actually present. `networking` emits 3 services (PRE_SERVER /
  POST_SERVER / POST_CNI_READY); the 9 other domains emit 1 each (POST_SERVER). Each
  service links the sub-paths belonging to its phase. No ordering is hand-coded in units —
  everything is derived from `installPhase()` metadata.
+
Naming: a single-phase domain keeps a clean name (`rke2lab-storage-manifests`); a
multi-phase domain decorates with the phase (`rke2lab-networking-pre-manifests`,
`rke2lab-networking-manifests`, `rke2lab-networking-cni-manifests`).

. *Readiness gate = carried by the enum (convention)*. Each phase declares its ready
  service (or none). Derivation is generic — `phase.readyGate().ifPresent(g -> after(g))` —
  with no per-phase branch. Adding a gated phase is one enum entry, not a new code branch.
  The gate service itself is synthesized (it runs the existing `rke2lab-cilium-ready.sh` /
  future operator-ready script).

. *Phase set = 4 phases*. `PRE_SERVER`, `POST_SERVER`, `POST_CNI_READY`,
  `POST_OPERATOR_READY`. The fourth is added now (not strictly needed for Layer 1) because
  seed-vcluster will need it and adding it later would churn the enum + derivation.

. *Migration = remove the override directly*. `CiliumConfigManifestsUnit.synthesizeSystemdUnits`
  is deleted as part of the implementation; PRE_SERVER derivation reproduces its ordering.
  Validation is at the next boot (the override's specifics — `Before=rke2-server`, dep on
  `rke2lab-install` — are folded into the PRE_SERVER derivation).
