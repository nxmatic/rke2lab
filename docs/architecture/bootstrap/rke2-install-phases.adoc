= RKE2 Install Phases — Modelling RKE2's Place in the System
:toc: macro
:icons: font

toc::[]

== Status: DISSOLVED

[NOTE]
====
This document described the *InstallPhase* model — an enum
(`PRE_SERVER` / `POST_SERVER` / `POST_CNI_READY` / `POST_OPERATOR_READY`) that a
`ManifestsUnit` carried so the manifests synthesis could derive systemd *installer*
ordering (one `rke2lab-<domain>-manifests.service` per phase, wired with
`After=` / ready-gate directives).

That whole model is *gone*. It existed to order the `/srv/host` systemd installer
services the manifests synthesis emitted — and that systemd-infrastructure
synthesis was dissolved when the node moved to a declarative NixOS substrate.
RKE2 unit ordering is now expressed directly in the node base, not derived from
manifest metadata:

* `nixos/rke2.nix` declares `services.rke2` and the `rke2lab.target` aggregate,
  with explicit `wants` / `after` over `rke2lab-identity.service`,
  `rke2lab-zfs-containerd.service` and `rke2-server.service`;
* per-concern ordering (tls-san, sops-fetch, zfs mount) is declared on each
  `systemd.services.*` unit in the `nixos/` modules.

The Kubernetes manifests themselves are still synthesised and delivered to the
node's `server/manifests` tree (RKE2 auto-deploys them once the API is up) — but a
unit no longer declares a lifecycle *phase*; readiness ordering that used to ride
`InstallPhase` is either intrinsic to RKE2's own apply order or expressed as a
Kubernetes dependency.
====
