= Provisioning Slice Architecture
:toc:
:toclevels: 3

== Overview

Provisioning slices are independently reconcilable resource partitions that enable hot-reload of node components without full instance renewal. Each slice is a self-contained materializer component that declares what to materialize, its storage policy, and its materialized paths for checksum computation.

== Execution Domains

Slices are organized by *where* the resources execute:

* **Node**: Runs on the node OS (systemd units, NRI plugin binary)
* **K8s**: Runs in Kubernetes API (Pods, Services, ConfigMaps)
* **Infrastructure**: Defines the instance itself (cloud-init, RKE2 initial bootstrap)

== Storage Policies

Each slice has a storage policy that determines lifecycle behavior:

* **STATIC**: Changes trigger full instance renewal. Stored in Incus instance config (`user.rke2lab.provisioning.slice.*`). Used for infrastructure that defines the instance bootstrap.

* **HOT_RELOAD**: Changes trigger reconciliation without instance renewal. Stored in Pulumi outputs and ConfigMaps. Used for runtime components that can be updated dynamically.

== Three-Slice Architecture

=== InfrastructureSlice (STATIC)

Node infrastructure that defines the instance itself:

* Cloud-init files (`/srv/host/cloudconfig-nocloud.d`)
* RKE2 initial bootstrap config (`/srv/host/rke2-config.d`)
* Environment ConfigMaps for systemd (`/srv/host/rke2lab-environment.d`)

Changes require instance recreation because they define the bootstrap process.

=== K8sSlice (HOT_RELOAD)

Kubernetes API resources - reloadable via RKE2 auto-apply:

* All manifest units from all domains (`/srv/host/rke2-manifests.d/<layer>/<package>/`)
* Organized by: cluster, storage, replication, gitops, runtime, networking, mesh, ha, cicd
* Includes DaemonSet manifests (e.g., flox-runtime DaemonSet)

Hot-reloadable because RKE2 watches `/srv/host/rke2-manifests.d/` and Kubernetes reconciles changes.

=== NodeSlice (HOT_RELOAD)

Node runtime components:

* Systemd units and scripts (`/srv/host/systemd-units.d`, `/srv/host/systemd-scripts.d`)
* NRI plugin binary + hooks (`/srv/host/k8s-daemonset.d/runtime/flox`)
* Future: other node-side agents, configs, binaries

Hot-reloadable because:

* Systemd can `daemon-reload` to pick up unit/script changes
* DaemonSet init container + reconciler sidecar handle binary updates via trampoline to node

**Legend:**

* Red (STATIC): Changes trigger full instance renewal via Incus instance config
* Green (HOT_RELOAD): Changes trigger reconciliation without renewal

**Key Flows:**

1. **Materialization**: Bootstrap orchestrates each slice to materialize its resources to `/srv/host/*`
2. **Registration**: Slices self-register with registry, declaring name, policy, and paths
3. **Checksum Partitioning**: Inventory computes checksums and partitions by policy
4. **Storage Split**: STATIC → Incus config (triggers renewal), HOT_RELOAD → outputs (no renewal)
5. **Runtime Consumption**: Each runtime component consumes its slice from mounted filesystem

Each slice component:

1. Implements `ProvisioningSlice` interface
2. Materializes its own resources to filesystem
3. Self-registers with the registry
4. Declares its storage policy
5. Provides paths for checksum computation

The registry partitions checksums by policy:

* `staticSlices` → stored in Incus instance config
* `hotReloadSlices` → stored in Pulumi outputs / ConfigMaps

== Instance Replacement Mechanism

The slice architecture integrates with Pulumi's resource lifecycle via a deliberate layering:

1. **Our code**: Computes slice checksums and decides which go into instance config (STATIC only)
2. **Pulumi layer**: Instance resource configured with `.replaceOnChanges(List.of("config", "config.*"))`
3. **Incus SDK**: Auto-generated from upstream Pulumi provider (`pulumi-language-java`), vendor code
4. **Incus API**: Receives delete + create operations from Pulumi

When a STATIC slice checksum changes:

* Our code writes new checksum to `user.rke2lab.provisioning.slice.*` in instance config
* Pulumi detects config change → triggers replacement due to `replaceOnChanges`
* Incus SDK executes delete-before-replace → instance renewed

When a HOT_RELOAD slice checksum changes:

* Our code stores checksum in Pulumi outputs (not instance config)
* Pulumi sees no config change → no replacement triggered
* Reconciler reads new checksum from outputs → hot-reloads component

**Key insight**: We're not duplicating checksums. We're controlling **which** checksums appear in instance config to leverage Pulumi's existing `replaceOnChanges` mechanism. The Incus SDK doesn't have its own checksum logic - it's just a pass-through to the Incus API.

== Key Design Decisions

=== Why Systemd Units are in NodeSlice

Systemd units and scripts are provisioned to `/srv/host/systemd-*` as disk mounts. They are:

* Consumed by systemd daemon at runtime (not embedded in cloud-init)
* Referenced via `RequiresMountsFor` and `ConditionPathExists` in unit files
* Hot-reloadable via `systemctl daemon-reload`

Therefore they belong in NodeSlice (HOT_RELOAD), not InfrastructureSlice (STATIC).

=== Why Separate K8s and Node Slices

K8sSlice contains Kubernetes API resources (YAML manifests). NodeSlice contains node-side binaries and configs consumed by those resources. Different execution domain, different reconciliation mechanism:

* K8s: RKE2 auto-applies manifest changes → Kubernetes reconciles
* Node: DaemonSet trampolines updates to host → systemd/containerd reloads

=== Component Self-Registration vs ServiceLoader

Slices are explicitly instantiated in `IncusResourceBootstrap.prepareHostState()` rather than discovered via `ServiceLoader`. This keeps the flow explicit and avoids the complexity of auto-discovery for a small, fixed set of slices.

Revisit if slice count grows significantly.
