= The incus bootstrap of master — the Pulumi graph and the materialized targets
:toc:
:toclevels: 3

== Overview

Seeding a master is two distinct gestures, fused for a long time in a single
host class (`IncusResourceBootstrap`) and now being split along the realm
boundary the gardening model draws:

* **The Pulumi graph** — the `com.pulumi.incus` resources that provision the VM
  itself: `Project · Network · Profile · Image · Instance`. This is a
  `com.pulumi.*` object graph; it **stays host** (Pulumi cannot enter Felix). It
  is the commissioner's own gesture, kept in `seed-master`.

* **The materialization** — writing onto the master the files its downstream
  consumers read (cloud-init seed, systemd units, k8s manifests, rke2 config, the
  env-config overlay). This is *metier*: it reasons over domains, catalogs, layer
  contributions. In the gardening model it is a **scion played in-container**
  (`broker.sow`), fed a host-neutral activation payload — never a host class that
  names `manifests.contract`.

This document is the map of both gestures: what each materialized target writes,
who reads it downstream, and its reload protocol — the load-bearing knowledge that
must survive the transposition. It closes with the *current gap*: what the
top-down demolition removed ahead of its replacement, so the work-list is explicit.

== The materialized targets — what lands on master, and who reads it

Each target is a downstream consumer that reads files we materialize and has its
own reload protocol. This table is the authoritative contract of the seam; the
paths and reload policies are what the master's scripts and daemons actually
depend on.

[cols="1,2,2,1",options="header"]
|===
| Target | Materializes onto master | Downstream consumer | Reload

| `cloud-init`
| `/var/lib/cloud/seed/nocloud/` (user-data, meta-data, network-config)
| cloud-init, first boot
| STATIC (defines the instance → change triggers instance renewal)

| `systemd`
| `/srv/host/systemd-{units,scripts,libexec}.d/`
| systemd daemon
| DYNAMIC (`systemctl daemon-reload`)

| `k8s`
| `…/server/manifests/` (`/srv/host/rke2-manifests.d/<layer>/<package>/`)
| rke2-server manifest watch
| DYNAMIC (RKE2 auto-apply → Kubernetes reconciles)

| `rke2-config`
| `manifestsRoot/runtime/rke2-config/` (etcd flags, advertise-address, TLS-SAN)
| rke2-server, startup
| DYNAMIC

| `rke2lab-env`
| `manifestsRoot/runtime/env-config/` — the per-section ConfigMaps + the
  aggregated `99-configmap-env-section-controlplane-layer-contributions.yml`
| flox `profile-common.sh` sources the YAMLs and turns their `data:` keys into
  shell environment variables (incl. `RKE2LAB_POLICY_LINK_*`, read by
  `rke2lab-manifests-install.sh` to decide which layers are symlinked live, and by
  the per-layer `*-ready.sh` gates)
| DYNAMIC
|===

`k8s` and `rke2-config` are *passive* — the cdk8s synthesis + explode fills their
directories upstream; the target only declares ownership for checksum/inventory.
`cloud-init`, `systemd`, and `rke2lab-env` are *active* producers.

== The checksum→reload mechanism — the glue between the two gestures

The reload column above is not documentation; it is *driven*. It is the nerve that
joins the materialized targets (metier) to the Pulumi Instance (host), and it
decides — per change — whether the master is *renewed* or *hot-reloaded*. Losing
it means: even with the graph and the scions restored, a re-synthesis has no way to
reconcile.

The mechanism, as it stood:

* Each target declares a `TargetReloadPolicy`: **STATIC** (consumed once, at
  boot — e.g. cloud-init, which defines the instance) or **DYNAMIC** (re-watched
  and re-applied on change — systemd, k8s, rke2-config, rke2lab-env).
* A checksum is computed per target over its materialized roots (with foreign-
  descendant scoping so a file owned by another target does not perturb the digest).
* **STATIC** checksums are written into the Incus instance config under
  `user.rke2lab.provisioning.slice.*`. The Pulumi `Instance` is configured with
  `replaceOnChanges(["config", "config.*"])`, so a STATIC checksum change makes
  Pulumi see a `config.*` diff and **replace the instance** (delete-before-create).
* **DYNAMIC** checksums are stored in Pulumi outputs (not instance config). Pulumi
  sees no config diff → no replacement; a reconciler reads the new checksum from
  outputs and **hot-reloads** the component.

The key insight the old design captured: we do not duplicate checksums, we control
*which* checksums appear in instance config, to leverage Pulumi's existing
`replaceOnChanges` — the Incus SDK is a pass-through to the Incus API, it has no
checksum logic of its own.

This straddles the realm boundary: the checksum *computation* reads materialized
paths (metier, in-container with the scion), but the *partition* into instance
config vs outputs and the `replaceOnChanges` wiring live on the Pulumi `Instance`
(host). The target vision must place each half on its side and define how the
per-target checksums cross from the scion to the host graph.

== The activation payload — how "which layers" reaches the master

The `RKE2LAB_POLICY_LINK_*` variables in the env-config overlay are the master's
copy of the operator's per-domain activation choice (mesh on/off, cluster-api
on/off, …). Their journey is the crux of the realm split:

. The operator's choice lives in the Pulumi config (`policy.link.*`).
. It must reach the `rke2lab-env` materialization as *seed variables* the
  synthesis folds into the overlay ConfigMap.
. The synthesis (the manifests domain) knows the vocabulary — the
  `ManifestDomainCatalog`, the `RKE2LAB_POLICY_LINK_<X>_ENABLED` naming, the
  `ManifestDomainPolicy` that filters which domains are synthesized at all.

**Target shape:** the host `sow`s a host-neutral activation payload (raw booleans,
`mesh: false`) — naming no domain type — and the in-container manifests scion
translates it into both the `ManifestDomainPolicy` (synth-time: which domains are
built) and the `seedVariables` (link-time: the `RKE2LAB_POLICY_LINK_*` written into
the overlay). The translation that used to live host-side (`ManifestLinkPolicy`,
`ControlplanePolicy`) descends into the scion, which alone may name its own catalog.
`writeControlplaneOverlay(root, layerContext, seedVariables)` — already published
OSGi-side as `NodeEnvOverlayService` — is the sink; it awaits a caller in the scion.

== Current gap — what the demolition removed ahead of its replacement

`IncusResourceBootstrap` (host, ~3800 lines) fused the Pulumi graph *and* a
`ProvisioningTargetRegistry` of the five targets above. A top-down cut, driven by
the target ClusterSeed scenario map (which shows only the gardening: preflight →
`Cellar.fetch` → sow-and-graft → `Cellar.store`), removed the whole class before
the replacement scions existed. The result is seven open deltas:

[cols="1,3,2",options="header"]
|===
| # | Delta | Target home

| 1
| **Pulumi graph** — `Project/Network/Profile/Image/Instance`. Called nowhere
  outside the generated SDK today. The scion `IncusProvisionScenario` builds the
  *image* and probes *reachability*, but states itself that "the actual instance
  provisioning stays host-side" — it does not provision. This is a **regression**:
  the graph should have stayed host, per the atlas target.
| host (`seed-master`) — restore

| 2
| `cloud-init` materialization
| in-container scion, sow-triggered

| 3
| `systemd` materialization
| in-container scion, sow-triggered

| 4
| `k8s` materialization (passive; synthesis already fills it)
| in-container scion, sow-triggered

| 5
| `rke2-config` materialization (passive)
| in-container scion, sow-triggered

| 6
| `rke2lab-env` overlay — `writeControlplaneOverlay` survives OSGi-side but is
  orphaned (no caller); `ManifestLinkPolicy`/`ControlplanePolicy` survive
  host-side but are consumed only by tests, their env-maps read by no production
  path.
| in-container scion (sink already present)

| 7
| **checksum→reload glue** — `TargetChecksumPipeline`, `TargetReloadPolicy`, the
  STATIC/DYNAMIC partition, and the `replaceOnChanges` + `user.rke2lab.provisioning.slice.*`
  instance-config wiring. Deleted whole. Without it, a re-synthesis cannot decide
  renew-vs-hot-reload — the master neither recreates nor reconciles.
| split: checksum computation in-container (scion); partition + `replaceOnChanges`
  host (Pulumi Instance)
|===

There is no `manifests-bdd` yet: nothing in the seed flow triggers synthesis or
materialization. The only live entry point is `manifests-cli` (outside the seed
flow, via `ManifestSynthesisRequest.fromSystemProperties()`). All five
materialization targets are orphaned *of trigger*, not of mechanism — the
synthesis machinery survives intact OSGi-side, waiting to be played as a scion.

**Why this matters:** a master provisioned by the previous binary carries the
materialized files (the `99-…` overlay, the `RKE2LAB_POLICY_LINK_*` vars) because
that binary still ran the registry. The current `seed-master` reproduces neither
the Pulumi graph nor the materialization — so a fresh seed would not stand up a
master. Closing these deltas is the substance of the incus/materialization
transposition, distinct from (and larger than) the realm-boundary gate that first
surfaced it.
