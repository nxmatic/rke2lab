= Stage A Bootstrap Contract — seeding the management cluster
:toc: left
:toclevels: 3

This document defines the first executable contract for Pulumi-based bootstrap of the *management
cluster* under the management/workload separation.

[IMPORTANT]
====
This contract was rewritten for the *management/workload separation*. Read
link:../cluster-api/management-workload-topology.adoc[Management / Workload Topology] (the anchor)
first — it establishes the vocabulary used here: the dedicated single-node management cluster,
greenfield workload creation, `seed-mgmt`, the two-plane mesh, and the function-of-git invariant.

Under the *old* self-managed model this contract seeded `bioskop` *as* the management cluster and
Stage B scaled that same cluster in place. That model is gone: CAPI/CAPN/CAPRKE2 now live *only* in a
dedicated management cluster, which greenfield-creates *separate* workload clusters.
====

== Scope

Stage A provisions and validates the *dedicated management cluster* — a single-node, nix-seeded,
on-demand cluster that holds the global vision (`seed-mgmt` is its seeder) — and emits deterministic
handoff outputs.

Stage A is intentionally limited to bootstrap responsibilities. It seeds *one* node (the management
control node) and never grows it into a workload cluster; the management cluster stays single-node by
design (see the anchor, § _Seeding the management cluster_).

After Stage A reaches readiness, *Stage B is the management cluster's own controllers*: CAPI + CAPN +
CAPRKE2, running inside the management cluster, greenfield-create the *separate* workload clusters
(`bioskop-wrkld`, `nikopol-wrkld`) on their respective bare-metals over the node mesh plane. Stage B is
*not* the scaling of the seed — it is a different cluster's lifecycle being driven from the management
cluster.

== Sequencing

Stage A completion is the delivery priority: a management cluster that is reproducibly seedable and
verifiable end-to-end is the prerequisite for everything downstream.

The Stage B entry point is established through Stage A's exported handoff/orchestration outputs
(`nextStep`, readiness status, registry summary, image build summary). Stage B consumes them to install
the CAPI management-plane components *into the management cluster* and to apply the workload-cluster
CRs (`Cluster` / `LXCCluster` / `RKE2ControlPlane` / `LXCMachineTemplate`) that greenfield-create the
workload clusters.

== Function-of-git invariant

Because the management cluster is single-node and on-demand, it MUST be reconstructible from git alone
(see the anchor, § _Function of git_). Stage A therefore treats the management node as *derived*, not
as durable state:

* desired workload CRs are persisted in git (GitOps);
* deterministic secrets (CAs, tokens, CAPN identities, age key) are SOPS-in-git — the cellar PKI moves
  out of Pulumi state and into git;
* deterministic identities come from `ClusterNetworkBlueprint`.

A re-seed of the management cluster on *any* available bare-metal must land in the same functional
state. Stage A owns no unique runtime state that git cannot regenerate.

== Non-goals

The following are explicitly out of scope for Stage A:

* Creating the workload clusters — that is Stage B, driven by the management cluster's controllers.
* Growing the management cluster beyond its single node.
* Any workload-cluster reconciliation, scaling, or rolling update (owned by CAPI in the management
  cluster once it exists).

== Required inputs

[cols="1,3",options="header"]
|===
|Input |Description
|`clusterName` |Management cluster identifier, `<host>-mgmt` (host-indifferent; e.g. `bioskop-mgmt`)
|`incusProfile` |Incus profile set for the management control node
|`networkProfile` |Network profile/selector used for the management node
|`sshHost` |NixOS host endpoint used for orchestration and probes
|`readinessTimeout` |Max wait duration for API readiness
|===

== Required outputs

[cols="1,3",options="header"]
|===
|Output |Description
|`managementClusterName` |Resolved management-cluster name (`<host>-mgmt`)
|`apiEndpoint` |Management control-plane endpoint for API access
|`kubeconfigRef` |Path or secret reference for the management kubeconfig
|`seedNodeId` |Provider-specific identifier for the management control node
|`seedImageFingerprint` |Immutable image fingerprint used for management-node provisioning
|`seedProvisioningChecksum` |SHA-256 fingerprint of Stage A provisioning inputs
|`seedImageBuildChecksum` |SHA-256 fingerprint of Incus image build inputs
|`incusProject` |Resolved Incus project used during management-node provisioning
|`handoffReady` |Boolean flag indicating Stage B prerequisites are satisfied
|`bootstrapPhase` |Terminal phase (`Ready` or `Failed`)
|===

== Stage B handoff contract

A successful Stage A run must provide enough information to install the CAPI management-plane
components *into the management cluster* and to drive greenfield workload creation from it:

. Management API endpoint and kubeconfig reference are valid.
. Management-node infrastructure identity is emitted (`seedNodeId`, project, image fingerprint).
. Drift identity is emitted (`seedProvisioningChecksum`, `seedImageBuildChecksum`).
. Handoff marker is explicit (`handoffReady=true`).
. Re-run safety is preserved (idempotent bootstrap with deterministic node replacement when checksum
  inputs change) — consistent with the function-of-git invariant.

== Readiness gates

. Management node provisioned and reachable.
. Management host systemd preconditions converged (environment mount present, no pending jobs, no
  failed units).
. RKE2 server active and healthy on the management node.
. Kubernetes API of the *management* cluster reachable and responsive.
. Minimum bootstrap manifests applied successfully.
. **BDD Scenario Resources**: infrastructure provisioned through BDD scenarios with built-in
  verification and drift detection.

Operator observability:

* Stage A exports `systemdRuntimeStatusSummary` as an explicit runtime-status contract so operators can
  see why readiness is blocked without ad-hoc host shelling.
* **Diagnostic runbook**: on a failed checkpoint the doctor is CONSULTED (a sub-step, not a root
  scenario) and its diagnosis grafts into the rendered runbook. See
  link:../bdd/bdd.adoc#doctor-consulted-sub-step[bdd — the doctor as a consulted sub-step] and
  link:../doctor/runbook-doctor.adoc[runbook-doctor].

== BDD scenarios verify the seed (BDD-as-engine)

[NOTE]
.Superseded model removed (2026-07-17)
====
An earlier draft here modelled scenarios as Pulumi `ComponentResource`s (wrapping infrastructure as
children, caching results in Pulumi state, drift via `pulumi refresh`/`read()`, publishing 3-format
actor reports). That model is ABANDONED (it lives in git history). The shipped architecture is
BDD-as-engine: scenarios are jGiven `Stage`s played on the embedded JUnit launcher, sown through the
broker (`SeedBroker.sow` → a domain `*RunbookHandler` played on the shared `ScenarioPlayer`), the verdict travelling IN the ReportModel
(`ScenarioGraft` reads `ExecutionStatus.FAILED`), the run rendered as ONE runbook (`RunbookRenderer` →
AsciiDoc into `host.live.d`). Severity (stop-vs-degraded) lives in the doctor (`DefaultReadinessAuthority`,
§ link:../doctor/runbook-doctor.adoc[runbook-doctor]); the doctor is a CONSULTED sub-step (§
link:../bdd/bdd.adoc#doctor-consulted-sub-step[bdd]). The scenario map is
link:../bdd/bdd.adoc#clusterseed-scenario-map[bdd § the ClusterSeed scenario map].
====

== Failure semantics

* Fail fast with explicit reason code and message.
* Emit last successful phase for resumability.
* Preserve diagnostics references for break-glass operations.
* **Diagnostic scenarios**: on verification failure, AsciiDoc reports contain targeted diagnostics
  (systemd status, logs, port checks) and remediation steps specific to the failure mode.

== Acceptance criteria (Slice 1)

* `pulumi up` (via `seed-mgmt`) reaches `bootstrapPhase=Ready` for the management cluster on a clean
  environment, on *either* bare-metal host.
* Re-run is idempotent (no destructive drift for unchanged config).
* Outputs are sufficient for the Stage B CAPI management-plane install *into the management cluster*.
* Stage A provisions only the management node — it creates no workload cluster and grows no second
  management node.
