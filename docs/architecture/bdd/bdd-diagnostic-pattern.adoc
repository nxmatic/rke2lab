= BDD Diagnostic Pattern: Scenarios as Pulumi Resources
:toc: left
:toclevels: 3

This document defines the pattern for BDD scenarios as Pulumi `ComponentResource` - infrastructure resources with built-in verification, diagnostics, and drift detection.

== Overview

BDD diagnostic scenarios **ARE the infrastructure**, not tests OF infrastructure. Each scenario extends Pulumi's `ComponentResource`, wraps actual infrastructure resources as children, executes verification during provisioning, and integrates with Pulumi's native drift detection.

**What this solves:**

- Living documentation that never drifts (scenarios co-located with production code)
- Verification intrinsic to provisioning (not bolted on after)
- Actor-specific diagnostic output (system metrics vs orchestrator decisions vs operator troubleshooting)
- Native drift detection (via `pulumi refresh`, not custom mechanisms)
- Uniform abstraction (all resources provisioned through scenarios)

== Pattern Evolution

**IMPORTANT:** This pattern evolved significantly during design. The current architecture (scenarios as ComponentResource) supersedes earlier approaches.

=== Before: Scenarios as Separate Gates

Initial design had scenarios as separate verification components that ran between provisioning steps:

```
Provision resource → Run scenario as gate → Continue or fail
```

**Problems:**

- Duplication between Pulumi resource and scenario
- Custom drift detection needed (reinventing Pulumi's wheel)
- Scenarios executed on every resource reference (wasteful)
- Separation between provisioning and verification

=== After: Scenarios as ComponentResource

Current design makes scenarios first-class Pulumi resources that wrap infrastructure:

```
Scenario IS the resource (extends ComponentResource) → Wraps actual infrastructure as child
```

**Benefits:**

- Single abstraction (scenario = resource)
- Pulumi's native drift detection (via `read()` lifecycle hook)
- Execution once per provision (cached in Pulumi state)
- Verification intrinsic to provisioning

== The Pattern

=== 1. Nested Class Co-Location

All BDD components nest inside the scenario resource they belong to:

[source,java]
----
public class SystemdAdapterScenario extends ComponentResource {
  // Production methods (verification + diagnostic helpers)
  private ScenarioResult executeScenario(SystemdAdapterArgs args) { /* given/when/then */ }
  private String getSystemdUnitStatus(String unitName) { /* ... */ }
  private List<String> getJournalLogs(String unitName) { /* ... */ }

  // ===== BDD Components (all nested) =====

  public interface DiagnosticCollector { /* ... */ }
  public class SystemDiagnostics implements DiagnosticCollector { /* ... */ }
  public class OrchestratorDiagnostics implements DiagnosticCollector { /* ... */ }
  public class OperatorDiagnostics implements DiagnosticCollector { /* ... */ }
  public class GeneralistDiagnostic { /* triage → specialists → plan */ }
  public class DbusTcpSpecialist { /* ... */ }
  public class Stages extends Stage<Stages> { /* ... */ }
  public class JGivenScenario extends ScenarioTest<...> { /* ... */ }
  public enum Severity { CRITICAL, WARNING }
}
----

**Benefits:**
- Open production class → scenario is right there
- Refactor/rename → scenario moves automatically
- Code review → can't merge production code without its diagnostic

=== 2. Stage-Specific Typed Collector Interface

Each production class defines its own diagnostic collector interface:

[source,java]
----
public interface DiagnosticCollector {
  void onDbusProbeStart(String host, int port);
  void onDbusProbeSuccess(Duration elapsed, Map<String, Object> adapterStatus);
  void onDbusProbeFailure(Exception cause);
  void captureSystemdUnitStatus(String unitName, String status);
  void captureJournalLogs(String unitName, List<String> logs);
  void capturePortStatus(int port, boolean listening);
  void suggestDbusRemediation(String... steps);
}
----

**Key principle:** The interface is typed to the domain (dbus probes, systemd units), not generic.

=== 3. Actor-Specific Implementations

Each actor (System, Orchestrator, Operator) implements the collector interface:

[source,java]
----
public class SystemDiagnostics implements DiagnosticCollector {
  private final SharedMetricsCollector metrics = new SharedMetricsCollector();

  @Override
  public void onDbusProbeSuccess(Duration elapsed, Map<String, Object> status) {
    metrics.recordLatency("dbus-probe", elapsed);
    metrics.captureFlag("dbusEndpointReachable", true);
  }

  @Override
  public void suggestDbusRemediation(String... steps) {
    // System ignores remediation (not actionable for automated systems)
  }
}

public class OperatorDiagnostics implements DiagnosticCollector {
  private final SharedReportBuilder report = new SharedReportBuilder();

  @Override
  public void onDbusProbeFailure(Exception cause) {
    report.addSection("Dbus Probe Failure")
        .addException(cause)
        // Direct access to outer class methods via non-static inner class
        .addDetail("Unit Status", getSystemdUnitStatus("rke2lab-dbus-tcp-system-bus"))
        .addDetail("Journal", String.join("\n", getJournalLogs("rke2lab-dbus-tcp-system-bus")));
  }

  @Override
  public void suggestDbusRemediation(String... steps) {
    report.addRemediation(steps);  // Operator gets full troubleshooting steps
  }
}
----

**Pattern:** Actor implementations are **non-static inner classes** so they can access outer class production methods directly (no duplication).

=== 4. JGiven Stages (DSL Building Blocks)

Stages define reusable DSL vocabulary:

[source,java]
----
public class Stages extends Stage<Stages> {
  private final DiagnosticCollector diagnostics;
  private final BootstrapConfig config;

  public Stages(DiagnosticCollector diagnostics, BootstrapConfig config) {
    this.diagnostics = diagnostics;
    this.config = config;
  }

  public Stages systemd_adapter_probe_runs() {
    diagnostics.onDbusProbeStart(config.systemdAdapterDbusHost(), config.systemdAdapterDbusPort());

    try {
      final long start = System.nanoTime();
      final Map<String, Object> result = ensureReachable(config, null);  // Call production method
      final Duration elapsed = Duration.ofNanos(System.nanoTime() - start);

      diagnostics.onDbusProbeSuccess(elapsed, result);
    } catch (Exception e) {
      diagnostics.onDbusProbeFailure(e);

      // Capture diagnostics on failure only (targeted capture)
      final String unitStatus = getSystemdUnitStatus("rke2lab-dbus-tcp-system-bus");
      diagnostics.captureSystemdUnitStatus("rke2lab-dbus-tcp-system-bus", unitStatus);

      if (unitStatus.contains("inactive")) {
        final List<String> logs = getJournalLogs("rke2lab-dbus-tcp-system-bus");
        diagnostics.captureJournalLogs("rke2lab-dbus-tcp-system-bus", logs);
      }

      diagnostics.suggestDbusRemediation(
          "Check if socat is installed: incus exec master -- which socat",
          "Verify script is executable: incus exec master -- ls -la /srv/host/systemd-scripts.d/",
          "Check systemd unit status: incus exec master -- systemctl status rke2lab-dbus-tcp-system-bus.service");
    }

    return self();
  }

  public Stages dbus_endpoint_responds() {
    // Additional stage method
    return self();
  }
}
----

**Pattern:** Stages call production methods directly, delegate diagnostic capture to the injected collector.

=== 5. JGiven Scenario (Verification Logic)

The nested `JGivenScenario` composes stages into a readable specification. The scenario
constructor runs it once per provision (and `read()` re-runs it for drift):

[source,java]
----
public class JGivenScenario extends ScenarioTest<GivenStage, WhenStage, ThenStage> {
  public ScenarioResult systemd_adapter_becomes_reachable() {
    given().incus_instance_exists("bioskop-master")           // From IncusInstanceScenario.Stages
        .and().bootstrap_config_is_loaded();                  // From BootstrapConfig.Stages

    when().systemd_adapter_probe_runs();                      // From SystemdAdapterScenario.Stages

    then().dbus_endpoint_responds()                           // From SystemdAdapterScenario.Stages
        .and().systemd_target_is_active("rke2lab.target");   // From SystemdTargetMonitor.Stages

    return capturedResult();
  }
}
----

**Pattern:** the scenario captures diagnostics through the injected `DiagnosticCollector`,
so the same given/when/then feeds the system, orchestrator, and operator views without
duplicating the flow.

=== 6. DSL Composition Across Scenarios

Stages from different scenario resources compose into a single specification — the DSL
vocabulary emerges from each domain's `Stages`:

[source,java]
----
// IncusInstanceScenario.java
public class Stages extends Stage<Stages> {
  public Stages incus_instance_exists(String name) { /* ... */ }
}

// SystemdAdapterScenario.java
public class Stages extends Stage<Stages> {
  public Stages systemd_adapter_probe_runs() { /* ... */ }
  public Stages dbus_endpoint_responds() { /* ... */ }

// SystemdTargetMonitor.java

}

// JGivenScenario composes all three vocabularies
public class JGivenScenario
    extends ScenarioTest<IncusInstanceScenario.Stages,
                         SystemdAdapterScenario.Stages,

  // Uses vocabulary from all three stage classes

**Key principle:** The DSL emerges naturally from composing domain-specific stage vocabularies.

== Naming Conventions

Enforce absolute uniformity across the codebase:

[cols="1,2",options="header"]
|===
|Component |Naming Rule
|Scenario resource |Domain-specific name ending in `Scenario`, extends `ComponentResource` (e.g., `SystemdAdapterScenario`)
|Collector interface |Always `DiagnosticCollector` (nested in the scenario)
|Actor implementations |`SystemDiagnostics`, `OrchestratorDiagnostics`, `OperatorDiagnostics` (nested)
|Triage |Always `GeneralistDiagnostic` (nested); specialists named `<Domain>Specialist`
|Stage class |Always `Stages` (nested in the scenario)
|JGiven scenario |Always `JGivenScenario` (nested in the scenario)
|Severity |Always `Severity` enum (`CRITICAL`, `WARNING`)
|===

**Enforcement:** Every scenario resource has exactly these nested components. No variations.

== Lifecycle: Provision Once, Reference Free

A scenario is a Pulumi resource. The stack provisions it like any other; dependent
resources reference its wrapped output without re-triggering verification.

[source,java]
----
// In the stack
var adapter = new SystemdAdapterScenario("dbus-adapter",
    SystemdAdapterArgs.builder()
        .instance(masterScenario.instance())  // reference, no re-execution
        .port(12434)
        .build(),
    ComponentResourceOptions.builder().dependsOn(masterScenario).build());

// Downstream resources just reference the wrapped unit — verification does not re-run
new ManifestUnitScenario("manifest-a", ManifestUnitArgs.builder()
    .systemdUnit(adapter.unit())
    .build());
----

The scenario constructor runs verification exactly **once** per provision and caches
the result in Pulumi state via `Output<ScenarioResult>`:

[source,java]
----
public SystemdAdapterScenario(String name, SystemdAdapterArgs args, ComponentResourceOptions opts) {
  super("rke2lab:bdd:SystemdAdapter", name, opts);

  this.unit = new SystemdUnit(name + "-unit", /* ... */,
      ComponentResourceOptions.builder().parent(this).build());

  final ScenarioResult result = executeScenario(args);   // given/when/then, ONCE
  this.result = Output.of(result);

  handleScenarioResult(result);                           // severity + operator policy
  if (result.failed()) publishDiagnostics(result);        // multi-channel reports

  registerOutputs(Map.of("unit", unit, "scenarioResult", this.result));
}
----

== Drift Detection: Use Pulumi's Native Mechanism

**Do not build a custom drift mechanism.** Pulumi already detects drift via
`pulumi refresh`; scenarios hook into it through the `read()` lifecycle method.
We nearly reinvented this — the note below exists so we don't again.

Pulumi reasons about three states:

[cols="1,3",options="header"]
|===
|State |Meaning
|Desired |What the program declares (the code)
|Pulumi state |What Pulumi thinks exists (stored in the backend)
|Actual |What actually exists in the infrastructure
|===

`pulumi up` reconciles *desired* against *Pulumi state*. `pulumi refresh` reconciles
*Pulumi state* against *actual* — and that is where drift surfaces. Pulumi calls these
hooks on each `ComponentResource`:

[cols="1,1,2",options="header"]
|===
|Hook |When |Purpose
|`constructor()` |`pulumi up` |Provision infrastructure, execute scenario once
|`read()` |`pulumi refresh` |Query actual state, re-execute scenario for drift
|`delete()` |`pulumi destroy` |Clean up resources
|===

The scenario implements `read()` to re-run verification against live infrastructure and
hand the actual state back; Pulumi compares and reports the diff:

[source,java]
----
@Override
protected CompletableFuture<ReadResult> read(String id, ReadArgs args) {
  final ScenarioResult actual = executeScenario(argsFromState(args));
  // Return actual state; Pulumi compares against cached state and shows drift
  return CompletableFuture.completedFuture(ReadResult.builder()
      .id(id)
      .props(Map.of("scenarioResult", actual, "status", actual.status()))
      .build());
}
----

[source,console]
----
$ pulumi refresh
  ~ rke2lab:bdd:SystemdAdapter  dbus-adapter  refreshed
    ~ scenarioResult: "failed" → "passed"   (socat fix detected)
----

This integrates with the operator's existing workflow (`pulumi refresh` /
`pulumi preview --refresh`) instead of introducing new commands.

== Doctor Hierarchy: Generalist → Specialists → Plan

On failure the scenario always invokes a **Generalist** first. The generalist triages
symptoms, decides which **Specialists** to consult, then synthesizes their findings into
a single `RemediationPlan`. This keeps clean output on success and escalates depth only
when something breaks.

[mermaid]
----
graph TB
    FAIL[Scenario fails] --> GEN[GeneralistDiagnostic<br/>examines symptoms]
    GEN -->|connection_refused| DBUS[DbusTcpSpecialist<br/>unit status, journal, port]
    GEN -->|name unresolvable| NET[NetworkSpecialist<br/>DNS, routing, firewall]
    GEN -->|instance unreachable| INCUS[IncusExecSpecialist<br/>instance state, exec path]
    DBUS --> PLAN[RemediationPlan]
    NET --> PLAN
    INCUS --> PLAN

    style GEN fill:#fff4e6,stroke:#ff9900
    style PLAN fill:#ccffcc,stroke:#00cc66
----

Specialists are invoked only when the generalist's triage points at their domain — the
`NetworkSpecialist` and `IncusExecSpecialist` stay dormant for a plain socat failure.

[source,java]
----
} catch (Exception e) {
  diagnostics.onDbusProbeFailure(e);

  final GeneralistDiagnostic generalist = diagnostics.requestGeneralistDiagnostic();
  generalist.recordSymptom("connection_refused", e);
  generalist.invokeSpecialists();                 // decides DbusTcp / Network / IncusExec
  final RemediationPlan plan = generalist.establishRemediationPlan();
  diagnostics.publishDiagnostic(generalist, plan);
}
----

== Severity and Operator Policy

Each scenario declares its own severity from domain knowledge — failure of a
non-essential adapter is `WARNING` (provision degraded); failure of something nothing can
proceed without is `CRITICAL` (stop). The operator can override to strict mode during
debugging, forcing every failure to `CRITICAL`.

[source,java]
----
public Severity severity() {
  return Severity.WARNING;  // master can provision without the adapter (degraded)
}

private void handleScenarioResult(ScenarioResult result) {
  final Severity effective = policy.isStrictMode() ? Severity.CRITICAL : severity();
  if (result.failed() && effective == Severity.CRITICAL) {
    publishDiagnostics(result);
    throw new PipelineStageFailure("blocked by scenario: " + result.name());
  }
  if (result.failed() && effective == Severity.WARNING) {
    publishDiagnostics(result);
    log.warn("Continuing in degraded mode: {}", result.name());
  }
}
----

[cols="1,1,1,2",options="header"]
|===
|Scenario severity |Operator policy |Failed |Action
|CRITICAL |any |yes |Stop, publish reports
|WARNING |strict |yes |Stop, publish reports
|WARNING |lenient |yes |Continue degraded, publish reports
|any |any |no |Continue
|===

== Report Publication (Multi-Actor)

Each actor gets its diagnostic data in the format it needs:

Publication happens inside the scenario when verification fails (`publishDiagnostics`),
emitting the same diagnostic data in three formats for three actors:

[source,java]
----
private void publishDiagnostics(ScenarioResult result) {
  // A) ConfigMap - YAML for system (machine-readable metrics)
  final String yamlReport = systemDiag.toYaml();
  new ConfigMap("diagnostic-reports", ConfigMapArgs.builder()
      .metadata(ObjectMetaArgs.builder()
          .name("rke2lab-diagnostic-reports")
          .namespace("rke2lab-system")
          .build())
      .data(Map.of("diagnostic-report.yaml", yamlReport))
      .build());

  // B) Stack outputs - JSON for orchestrator (structured decision data)
  final Map<String, Object> jsonReport = orchDiag.toJson();
  ctx.export("diagnosticReports", Output.of(jsonReport));

  // C) File resources - AsciiDoc for operator (human-readable troubleshooting)
  final String adocReport = opDiag.toAsciiDoc();
  new local.Command("publish-diagnostic-reports-to-fs",
      local.CommandArgs.builder()
          .create(String.format(
              "mkdir -p /var/lib/rke2lab/reports && echo '%s' > /var/lib/rke2lab/reports/diagnostic-report.adoc",
              adocReport.replace("'", "'\\''")))
          .build());
}

== Targeted Diagnostic Capture

**Principle:** Clean output when healthy, detailed diagnostics only on failure.

Implementation pattern:

[source,java]
----
public Stages systemd_adapter_probe_runs() {
  diagnostics.onProbeStart();

  try {
    result = ensureReachable(config, logger);
    diagnostics.onProbeSuccess(result);  // Clean: just mark success

  } catch (Exception e) {
    diagnostics.onProbeFailure(e);

    // Capture rich diagnostics ONLY on failure
    diagnostics.captureSystemdUnitStatus("rke2lab-dbus-tcp-system-bus", getSystemdUnitStatus(...));
    diagnostics.captureJournalLogs("rke2lab-dbus-tcp-system-bus", getJournalLogs(...));
    diagnostics.capturePortStatus(12434, checkPortListening(12434));
    diagnostics.suggestRemediation("Check socat installation", "Verify script exists");
  }

  return self();
}
----

The report stays concise on success, expands with context on failure.

== The doctor as a CONSULTED sub-step (its place in the ClusterSeed scenario map)

In the ClusterSeed vision (link:bdd.adoc#clusterseed-scenario-map[the scenario map]) the doctor plays NO
scenario of its own — it is not a root step, it orchestrates nothing. It is CONSULTED transversally by a
domain scion in trouble (systemd on a symptom, cluster on a failing phase, bbox on a refused row). Its
G/W/T is therefore a nested sub-step UNDER a scion's failing phase, never a top-level runbook node:

[listing]
----
  (nested under a scion's failing phase)
  WHEN the domain consults the doctor about a symptom (ConsultingService.consult)
  THEN the generalist admits the patient — the neutral Parcel projected as Patient, OSGi-side
    AND reads the medical record — Cellar.fetch(parcel), the visit blobs rebuilt inside the bundle realm
    AND returns a consultation: a @Scion("fruit") (the finding) + a @Scion("sowing") (verify next visit)
----

This is the ONE place the Cellar is READ (`fetch(Parcel)`) and the `fruit`/`sowing` scion roles are
produced (see link:../osgi/seed-broker-spec.adoc[the seed-broker spec] — Cellar + the split-by-role). The
projection `Parcel → Patient` is entirely OSGi-side; the host, and every calling scion, hold only neutral
gardening terms. The consultation grafts back as part of the calling scion's scion, so the operator sees
the diagnosis exactly under the phase that failed.
