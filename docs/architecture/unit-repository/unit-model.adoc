What a unit *is*. This is the deepest justification of the whole thesis: if a unit were only inert
data, git would suffice and OSGi would be unnecessary. A unit is a **living entity** — data plus
behavior — so its logic must be resolved and loaded. That is precisely what OSGi adds over git: the
living object model above the content store.

[NOTE]
.Why "unit"
====
The term is the bundle-equivalent for this system, deliberately chosen. OSGi names its repository
after its unit (*bundle* → bundle repository); ours is the **unit repository**. We do not reuse
"bundle" — it keeps its precise OSGi meaning in our vocabulary (a *handler* genuinely IS an OSGi
bundle: loadable bytecode), and overloading it would collide. We do not reuse "document" — it drags
the centralized content-repository baggage the thesis rejects, and connotes inert data, fighting the
living-entity redefinition. We do not reuse "resource" as the surface word — it collides with
Pulumi's `Resource` and with the OSGi `Resource` API. "Unit" is rke2lab's native word for the thing
(`ManifestsUnit`, `SystemdUnit` already Provide/Require and get resolved), and it *says* the thesis:
**a unit is mainly configuration AND logic** (a package, a script, a manifest) — that is data plus
behavior, exactly the living entity below. The generic supertype maps to OSGi's `Resource` (the
capability bearer, Core ch.6), never to `Bundle`.
====

== Unit = living entity, never inert data

In the lost system, data and logic were **not separated**: a unit is not inert structured data, it
is an entity in an object model (data plus behavior). To materialize a unit you must load the
bundles that give it its lifecycle and services. This unifies the last duality — **"run the app" and
"use a unit" are the SAME operation**: the runtime resolves a closure from the store and
instantiates a living entity.

Two levels are kept distinct, and that distinction is what saves the deduplication:

* **Object-model level: inseparable.** A unit = data plus behavior, one entity.
* **Storage/addressing level: distinct objects, joined by a requirement.** The data payload and the
  logic bundle are *separate* content-addressed objects, united by a Require-Capability. Otherwise N
  units of type X each embed a copy of the same code and the hash dedup collapses.
  Inseparability-at-use is kept *via the requirement edge*, without physical co-bundling.

[NOTE]
.Shipped vs design at this level
====
*SHIPPED in rke2lab:* the Felix resolver runs in the embedded framework; `ManifestsUniverse`
already turns a `ManifestsUnit` into a `UnitResource` (the capability-bearing supertype), so the
unit-as-resolvable-resource half of the thesis is real today.

*Still DESIGN:* the constitutive handler edge carried on real production units, the lens and
severance machinery, `uses:` extraction from concrete artifacts, and content-addressing of units
themselves.
====

== Anatomy

A unit is a content-addressed tree unit-node: a **manifest** (Provide/Require capabilities, the
`uses:` facet, the durability facet — and **always** the handler edge) plus an **optional inert data
payload** plus **hash-edges** to child units. Behavior is resolved via the handler edge, not
embedded.

== Recursive homogeneous composition — a unit can contain units

The hash-edges to child units are not a special "container type". A unit that contains units is a
unit, exactly as a folder that contains documents is a document. The containment is *recursive* and
*homogeneous*: the container is the same kind as the contained, at every depth. There is no
second-class aggregate, no separate "bundle vs unit" layer — there are only units, some leaf, some
containing.

This is the node homogeneity axiom (no special node types) applied one level down, INSIDE a node: no
special unit types. A leaf is a unit; a folder is a unit; a clinic that aggregates specialists is a
unit; a `HealthSystem` that holds the registry, the access policy, and the employed clinicians is a
unit; the node that serves them is itself described by units. What used to read as "a bundle is an
aggregator of units" is just this: a bundle is a unit whose payload is bytecode AND which may contain
others — the aggregator is not a different species, only a unit at a containing depth.

The payoff is the property the prior OBR-fronted document repository had by construction: because
EVERYTHING reduces to units, and a unit contains units, *resolution is total*. Loading a containing
unit pulls its closure — recursively all sub-units, including the code bundles they require to be
consulted. There is no point where "it leaves the DAG", except the kernel level-0 (the boot amount
that cannot load itself from a store it has not opened yet — see
link:node-and-resolution.adoc[node and resolution]). This is the self-hosting keystone: the app is a
DAG of units and its state is a DAG of units, so the model closes on itself.

== The handler edge is constitutive — the graph's orientation

A unit cannot exist in the oriented unit-graph **without** the edge to the capabilities required to
manipulate it. That edge is **what orients the graph** (= the resolution order); remove it and the
unit-node has no place, no resolution order — it is not a unit, it is content. So:

* **Unit** = a first-order entity in the oriented graph = ALWAYS carries the handler edge.
  Non-optional, constitutive. (The earlier "pure-data unit, extender optional" was a category error
  — deleted.)
* **Blob / payload** = inert content, NOT an autonomous unit — it has meaning only inside a unit,
  interpreted by that unit's handler. It is leaf content, not a graph unit-node.
* **Even the minimal opaque-content unit** requires its content-type handler — exactly OSGi's
  `osgi.content` / ContentNamespace. **No bare-data unit-node exists in the graph** so the unit graph
  is **connected by construction**: every unit has at least one outgoing handler edge.

This mirrors the node-level homogeneity axiom at the unit level: all units are the same kind (entity
plus handler edge), differing only by type/handler — no second-class "data" category. See
link:model-overview.adoc[the axiom].

== Binding the logic — the extender pattern, TWO orthogonal axes

Behavior binds via the **extender pattern** (Compendium §135.2 — what DS/Blueprint themselves use).
The crucial correction over the original sketch: a real felix.scr-style extender carries **ONE**
name. The earlier idea of a per-type extender name (`osgi.extender=unitrepo.type.X`) does not match
how felix.scr actually works — its extender contract is the single fixed name
`osgi.extender=osgi.component`, and the *type* travels out of band. The unified model therefore
keeps the handler edge as **two orthogonal axes**:

* **Axis (a) — the extender CONTRACT.** One fixed name, version-ranged. A handler bundle
  `Provide-Capability: osgi.extender; osgi.extender=unitrepo.handler; version=...`; a unit
  `Require-Capability` that same single name within a version range. This says only "an extender of
  the unitrepo kind, of a compatible version, must be present." It does NOT carry the type. This
  axis is **SHIPPED in rke2lab** as the providing half: `unitrepo-handler-spi` declares the
  `osgi.extender=unitrepo.handler` capability (version `1.0`) on the bundle carrying the
  `UnitHandler` SPI.
* **Axis (b) — the type WIRING.** A SEPARATE `unitrepo.type` namespace carries the per-type edge.
  The handler bundle `Provide-Capability: unitrepo.type; unitrepo.type=X`; the unit
  `Require-Capability: unitrepo.type; filter:=(unitrepo.type=X)`. This is what threads the per-type
  edge into the resolution graph, so "connected by construction" is **resolver-proven**: the
  resolver cannot satisfy a type-X unit unless a handler that provides `unitrepo.type=X` is in the
  universe.

Keeping the two apart is what lets the contract version independently of the type vocabulary, and
lets one extender contract govern an open set of types.

**Dedup is maximal**: one shared handler bundle, N units; logic lives once, content-addressed.
**Live property**: handler gone so type-X units go inert; handler reappears or upgrades so they are
re-handled. That is live re-resolution applied to *behavior*. Because rke2lab boots an embedded Felix
in production, handlers load as **bundles in that live framework** — there is no standalone or
framework-less loading path; the earlier "no running framework" loading mechanism is dropped.

== Lens plus severance — the read-time projection that hides

The transfer/ownership unit is the rooted directed closure (a git subtree). A **lens** is a
read-time projection over what a unit-node already holds. When materialized, a lens **severs** into a
*new independent DAG*: content-addressed, fully owned, self-sufficient, **with no back-edges** to the
source (like `git subtree split` — a new repo with its own root, not a pointer back).

**Severance is load-bearing — it is what makes hiding work.** If the lens kept edges into the hidden
parts of the source, a peer pulling the lens-closure would follow them and transitively pull the
source, defeating the purpose. A severed lens-DAG has no back-edges so hidden parts are GENUINELY
ABSENT, nothing to follow. Severance also frees the lens to be **generative**
(summary/abstract/rewrite): it is honest about being its own new thing by its own hash, not a
faithful view of the source.

Visibility is **holder-gated**: a unit-node advertises both the full subtree (S) and the lens (Y); a
local, non-propagating access policy decides which face a peer may resolve. This is the rke2lab
HealthSystem `GrantPolicy` joint — see link:../integration-atlas.adoc[the atlas].

Lens, severance, and holder-gating are **still DESIGN** in rke2lab — none of this is shipped yet.

== The master pattern — materialize as an immutable DAG

Lens and lockfile are the same move: **materialize a computation as an immutable,
content-addressed, independent DAG.** A lens is a frozen *projection*; a **lockfile-DAG is a frozen
*resolution*** (= `flake.lock`). Resolution stays emergent (each unit-node resolves fresh against who
is available); **pinning is opt-in** — freeze a lockfile-DAG for reproducibility or for the doctor's
"what ran then vs now". A Pulumi checkpoint is this pattern applied to *deploying*.

== uses: — agreement constraint in schema-name space

`uses:` protects transitive **agreement** on a shared dependency within one class-space — only what
shows through a capability's public face. The apparent contradiction with severance resolves by
distinguishing two name-spaces:

* a **content back-edge** says "fetch this to reconstruct/run me" — a closure link, in the
  **content-hash** space; severance cuts these;
* a `uses:` is **not** a content back-edge — it says "if you wire to me AND to schema-B, it must be
  the SAME schema-B my public face assumes." A conditional agreement constraint in the
  **schema-name** space (`SchemaRef`), revealing no hidden bytes.

So a severed lens carries `uses:` by **schema NAME**, never content hash — severance intact. `uses:`
is **always extracted from a concrete artifact** (bytecode for bundles; the frozen output for a lens,
at materialization; the resolved checkpoint for a stack), never hand-declared. A `uses:` conflict is
then a **diagnosable unmet need carrying its why** — the doctor's `ReferralReply`/`Assessment` shape
— not an explosion.

`uses:` extraction from concrete artifacts is **still DESIGN** in rke2lab.
