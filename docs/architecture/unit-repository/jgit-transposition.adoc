= JGit <-> unitrepo — model transposition
:toc: left
:toclevels: 3
:kroki-server-url: https://kroki.io

NOTE: This is *design*, folded into rke2lab. It records a chosen-but-unbuilt
substrate decision for the unit repository. As of this writing there is *no*
`ContentStore` and no unitrepo storage code in the reactor: JGit
(`org.eclipse.jgit`) is a dependency of `exec/seed-master` only, where it backs
`GitMetadataExtractor` and `EntryGatePolicyEnforcer`. Treat everything below as
the target shape of the storage substrate, not as something present today.

unitrepo is *inspired by* git's object model. This doc does the fidelity verification the design
calls for: do the principles our model EXPOSES match the principles git actually adopted — so
that JGit can sit underneath as the implementation substrate, decorrelated, with a thin
integration layer? It names where we deliberately diverge, where JGit does NOT help (correctly),
and records the decision that **a unitrepo unit IS a git tree** (option B below).

== Why this doc exists

The `ContentStore` unit — not yet built — is to be a content-addressed blob store. Rather than
hand-roll it, the design chooses to build it on JGit, reusing git's object machinery (addressed
objects, DAG, dedup, reflog, GC, fetch/clone). JGit is already a declared dependency of
`exec/seed-master` (used today in `GitMetadataExtractor` and `EntryGatePolicyEnforcer`), so this is
reuse of an already-present library, not a new third-party dependency — though the storage code
itself remains to be written.

The deeper point is **fidelity**: our exposed model is git-inspired, so it must apply git's own
principles. If it does, the JGit integration layer is thin (a mechanical mapping); if it diverged
arbitrarily, the layer would be impedance. This doc is that confirmation, plus the precedent (how
Eclipse/Google already solved the same decorrelation).

The organizing insight (already established in the model for `uses:` vs closure): our model lives
in **two orthogonal name-spaces** — a content-hash name-domain and a schema-name name-domain.
Everything that follows is read off this axis.

[cols="1,2,2",options="header"]
|===
| | content-hash name-space | schema-name name-space

| holds | hash-edges, closures, payloads, versions | requirements, `uses:`, capabilities, the handler edge
| who manipulates it | the **transport** (move a closure) | the **resolution** (decide what to move)
| severance | **cuts** (no back-edge) | **preserves** (by name)
| git equivalent | **YES** — fetch/clone, trees, commits | **NO** — the OSGi contribution, irreducibly ours
| JGit helps? | yes — plumbing | no — and correctly so (it is our layer, above)
|===

== The decision — a unitrepo unit IS a git tree (option B)

Two architectures were possible: (A) JGit as a *bare CAS* (a hash->bytes map, with our DAG modelled
only in the manifest layer above), or (B) **our units ARE git trees** — hash-edges = tree
entries, a Visit = a commit, a severed lens = `git subtree split`, a closure = git reachability.

**B is the chosen substrate** — chosen but unbuilt; no storage code realizes it yet. Rationale:

* **We already do the bottom-up reconstruction.** The doctor's medical record was reconstructed
  from Pulumi state — empirical proof that the system supports "rebuild our model from a DAG that
  is GIVEN." Ingesting a git DAG is the same parse (see the ingest section); B is not a bet, it is
  a gesture already exercised.
* **It realizes the thesis literally.** "Built the way git works" is only true if the DAG is
  *given* by git's tree/commit structure, not re-modelled above a hashmap. A makes the thesis
  hollow; B makes it structural.
* **Native git operations come as a bonus** — `fetch`/`pull`/`push`/`rebase`, dedup of unchanged
  subtrees, reflog, GC — all inherited rather than re-implemented.

Cost, accepted: units must serialize to canonical git trees, and the content hash becomes
git's (SHA-1 today, SHA-256 as JGit matures) — already framed as an implementation detail behind
`ContentStore`, which speaks `hash`/`bytes`/`unit`, never `ObjectId`.

**Latent tension this resolves (surfaced in review):** the spec's `ContentStore` (put/get/has
bytes) read like A, but the life-model says "migration = a pull = git clone," which presupposes
B. B reconciles them: the clone claim is backed by the substrate once it is built.

== Fidelity map — our exposed model vs git's principles

Verified against primary sources (git-scm book, JGit DFS package, JGit `ObjectDatabase` apidoc).
The check-mark = faithful (same principle); the warning = deliberate divergence (a resolved fork,
named).

[cols="2,2,1",options="header"]
|===
| git principle | unitrepo model | verdict

| content-addressed immutable objects; same content -> same hash -> dedup
| content-addressed units; lens/lockfile materialized immutable
| faithful

| blob = opaque content, non-autonomous (meaning only inside a tree)
| inert payload = leaf content, NOT a graph unit-node (meaning only inside a unit)
| faithful

| tree = named entries -> children (spatial DAG)
| unit subtree: manifest + hash-edges -> child units
| faithful (our unit IS a git tree)

| commit = snapshot (a tree) + parent chain (temporal DAG)
| Visit = a version (its resource subtree) + version chain
| faithful (Visit IS a commit)

| two orthogonal DAGs: tree (spatial) + commit-chain (temporal)
| "state = graph, history = time": resource subtree + checkpoint chain
| faithful — exact mapping

| Merkle DAG: a unit-node's hash covers its whole closure
| any tree unit-node is the self-identifying root of its sub-DAG
| faithful (verbatim)

| refs = mutable pointers into the immutable graph (the only mutable part)
| unit-node identity = peer-id + its SET of root hashes (evolves on re-resolution)
| faithful — this IS our refs layer (answers the spec's unit-node-identity question)

| reflog = bounded local journal of a ref's moves
| retention = local reflog (literally named after git)
| faithful

| GC by reachability: alive iff reachable FROM A REF
| alive-iff-required: alive iff required by a live need-closure
| divergence — same mechanism, different root-set (federated need-closures, not local refs)

| transport: pull the missing closure; clone = everything reachable
| pull-own, but SPARSE, requirement-driven replication (not whole graph)
| divergence — "deliberately un-git-like in replication"

| submodule/gitlink: pointer to content WITHOUT owning it; if source dies, objects lost
| serve-own-DAG, never proxy; acquisition is first-party pull-and-own
| divergence — we are STRICTER than git (no reference-without-ownership; the rejected proxy model)

| merge: three-way content merge of blobs, human-resolved (markers)
| conflict = incoherent closure; resolver REFUSES; diagnosed, not merged
| divergence — a different KIND of conflict (see the conflicts section)

| object model = substrate; porcelain above
| git object model = the `ContentStore` layer; OSGi resolution / living-entity = ABOVE
| faithful — the key stratification
|===

What we ADD above the store (git has no equivalent): the **constitutive handler edge** and the
**`uses:` edges in the schema-name name-space**. Both live ABOVE `ContentStore`, in
manifest/resolver semantics — at the store level they are just more hash-edges in an object;
their MEANING is interpreted by the layer above, exactly as a git tree does not "know" what a blob
means. So they do not break store-level fidelity.

== The precedent — JGit's `ObjectDatabase` SPI (decorrelation, proven)

JGit already implements the decorrelation, and makes it an explicit SPI. The abstract class
`org.eclipse.jgit.lib.ObjectDatabase` has essentially **three abstract methods** — `newInserter()`
(write), `newReader()` (read), `close()` — with `has(AnyObjectId)` / `open(AnyObjectId)` above
them. There are **two subclasses**: `ObjectDirectory` (on-disk: loose + packfiles) and
`DfsObjDatabase` (block-based, stream-oriented, for storing git objects off local disk — the
lineage of the database-backed backend Google used for hosted Gerrit).

The JGit DFS architecture states the property verbatim: *"this architecture allows implementers to
swap storage backends while keeping git object-model semantics consistent."* That is exactly our
thesis: **swap the storage backend without touching the object model.**

Lesson for `ContentStore`: its interface (`put`/`get`/`has`) is to be modelled almost exactly on
`ObjectDatabase`. Copy the discipline — **`ContentStore` speaks `hash`/`bytes`/`unit`, never
`ObjectId`/`RevWalk`**. JGit gives the precedent for the bottom half (store to object model); it
has nothing for the top half (object model to behaviour resolution), which is our contribution — so
design effort concentrates there. (Whether we plug in via a custom `ObjectDatabase` subclass or
consume `ObjectInserter`/`ObjectReader` directly is an implementation choice for the build plan;
the model commitment is only that units serialize as git trees.)

== Conflicts — a DIFFERENT kind, on purpose

Verified: git's conflict model is **blob-centric and textual** — a three-way merge
(base/ours/theirs as index stages 1/2/3), conflict markers in the working tree, **resolved by a
human editing text**. It is a *content merge*.

Our conflict is **not** that, and naming the difference prevents accidentally inheriting a model
that does not fit:

[cols="1,2,2",options="header"]
|===
| | git conflict | unitrepo conflict

| what | two overlapping edits of one blob | an INCOHERENT closure: `uses:` demands schema agreement, two providers break it
| name-space | content-hash (blob text) | schema-name name-space (`SchemaRef`), orthogonal to the hash
| detected | at merge, by region diff | at RESOLUTION, by the OSGi resolver (class-space consistency, Core 3.7.6)
| resolved by | human edits text, removes markers | the resolver REFUSES the wiring -> an unmet need that CARRIES ITS WHY (`ReferralReply`/`Assessment`)
| result | a merged blob | the unit-node STAYS on its coherent closure ("always safe in that state"); nothing is merged
|===

So: **git merges content; we REFUSE an incoherent composition.** Our conflict is a
constraint-satisfaction failure, not a textual overlap. It is not resolved by editing — it is
**diagnosed** (the doctor narrates the why) and the unit-node does not move.

JGit's merge machinery (`MergeStrategy`, three-way, index stages) operates on the object model,
BELOW our SPI. Our coherence lives ABOVE (resolver layer), like git porcelain. **We use JGit's
store, not its merge.** The `ObjectDatabase` precedent validates exactly this: the plumbing does
not know the semantics above it.

*Risk to avoid (named):* never present a `uses:` incoherence as a three-way merge with markers.
That would import git's blob-centric model into a name-space (schema names) where it is
meaningless. Our conflict is a `ReferralReply`, not a merge marker.

== Subtrees — git has three things; we chose deliberately

Verified mechanics confirm three distinct git notions, and validate our choices:

[cols="2,1,2,1",options="header"]
|===
| git mechanic (verified) | property | unitrepo side | JGit helps?

| object-model property: any tree is the self-identifying root of its closure (hash = identity of
  all reachable)
| Merkle
| oriented closure = the transfer/ownership unit; naming a root hash = fetch its closure
| yes — `RevWalk`/`TreeWalk` walk the closure; `ObjectReader` serves objects

| `git subtree split`: generates a NEW standalone history, subdir content becomes root, objects
  EMBEDDED/owned, NO back-edge
| severance
| materialized lens = a severed DAG (new root, no back-edges -> this is what makes hiding work) —
  verbatim `subtree split`
| yes — write the severed DAG = `ObjectInserter.insert` new trees/blobs; no ref to source

| submodule/gitlink (mode 160000): pointer WITHOUT ownership; objects in a separate store; if
  source dies, objects LOST
| reference-without-ownership
| REJECTED — the proxy model. We are STRICTER: pull-own, first-party acquisition, never a gitlink
| no — we do not use this mechanic
|===

The strong point: git itself *contrasts* subtree (owns) vs submodule (points), and notes that if a
submodule disappears, its objects are lost, not backed up in the superproject. **That is precisely
the danger the pull-own regime eliminates.** Our "subtree, never submodule" choice is not
arbitrary — git names the trap we avoid.

Concretely on our side: a "subtree" = the reachable closure of a root hash (the unit you pull and
own); a "lens" = a `subtree split` (new, severed DAG). JGit provides both primitives: `TreeWalk`
to READ a closure, `ObjectInserter` to WRITE the severed DAG.

== Transport — subsumed, not a hard problem

A natural worry: "transport does not really arise — we transfer DAGs at OUR level." Refined via the
two-name-space axis:

* the HARD part (decide WHAT to move) = **resolution** = ours; git has no notion of resolving a
  requirement (the OSGi contribution).
* the EASY part (move a named closure) = **transport** = lives in the content-hash name-space, and
  git does exactly this (`git fetch`/`clone`, JGit `Transport`).

So transport "does not arise" as a hard problem because the hard half is ours and git does not
touch it, while the easy half is solved by git (units are trees). The federation's
`pull-own` is then `git fetch` of a named root's closure, made SPARSE by resolution choosing the
root — the "sparse replication" divergence stays in OUR layer (which roots), git moves the closure
beneath it.

== The bottom-up gesture = the ingest parse (a unification)

"Reconstruct our model from a DAG coming from JGit (bottom-up)" is not a separate problem — **it is
the checkpoint ingest the spec already describes**, which says for Pulumi: *"the DAG is GIVEN by the
state model; we do not construct it, we parse structure already there."*

Bottom-up from JGit is the SAME gesture:

* the **content-hash name-space** is GIVEN by the git DAG (trees = units, entries = hash-edges,
  commits = versions) — `TreeWalk`/`RevWalk` render it natively;
* the **schema-name name-space** is PARSED from the manifest blobs (capabilities, handler edge,
  `uses:`).

So "ingest a git DAG" and "ingest a Pulumi checkpoint" are the same parse operation. A real
unification, not an analogy — and the empirical reason B is safe: we already did the
Pulumi side for the medical record.

== A note on the loading regime in rke2lab

The original transposition was framed against a "no framework" loading model. In rke2lab that no
longer holds: production boots an embedded Felix runtime, so loading is bundle-based and the
host consumes services from the OSGi registry. This doc is almost entirely about *storage* — the
`ContentStore` substrate and its fidelity to git's object model — and the object-model decision is
indifferent to the loader. The point of contact is only that, when the store and its resolver are
built, they live as OSGi bundles like the rest of the unit-repository machinery; the schema-name
resolution it sits beneath is itself the OSGi contribution. The storage substrate carries no
classloading concern of its own.
