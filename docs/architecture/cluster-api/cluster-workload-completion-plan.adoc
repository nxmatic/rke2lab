= Cluster Workload Completion Plan
:toc: left
:toclevels: 3

The remaining work to finish the master cluster's workload bring-up. seed-master's validation was
paused mid-way to rework its provisioning logic (the BDD-as-engine pipelines), so this is a live
FUTURE worklist, not a closed plan — it resumes with that rework. It captures what is still to do to
call the master fully operational, in a recommended (but reorderable) sequence.

== What still blocks a fully-operational master

* *Porch CRD absent* — `Repository`/`PackageVariant` resources (`gitops/porch-resources/*`) fail apply.
* *Flux Operator CRD absent* — `FluxInstance` (`gitops/flux-instance/*`) fails apply.
* *CAPN provider not configured* — `rke2lab-cluster-api-install.service` /
  `rke2lab-capn-provider-install.service` stay `inactive` (a systemd ordering bug: their prerequisite
  activates after `rke2lab.target` has settled; and `clusterctl.yaml` lacks the `incus` provider). The
  seed-master output shows them as `pendingDependencies`.

Known hygiene items to revisit once the workload set is stable: pods log `DNSConfigForming` (>3
nameservers in `/etc/resolv.conf`, kubelet trims silently); several `rke2lab-*-manifests.service` units
run after `rke2.target` has settled — unit ordering to revisit.

The component pattern is in place — what's left is bumping each operator into its layer.

== Phase 2 — close the CAPN gap (Stage B prerequisite)

Stage B (CAPI + CAPN + CAPRKE2) cannot start until the master cluster has the CAPN infrastructure provider configured. Today the `rke2lab-capn-provider-install.service` fails because `clusterctl config repositories` does not list `incus` (no `~/.cluster-api/clusterctl.yaml`).

=== 2.A — Foundation: install services + clusterctl.yaml

Two prerequisite work items before any `Machine` reconciles:

. *Materialize `clusterctl.yaml` at provisioning time.* Pulumi config (`rke2lab:capn.provider.url`, `rke2lab:capn.provider.version`) → templated by a host-side init script writing `/root/.cluster-api/clusterctl.yaml`. Drives `rke2lab-capn-provider-install.service` precondition green. Add CAPRKE2 in the same pass so `clusterctl init -i incus -c rke2 -b rke2` is one call.
. *Fix the systemd ordering bug.* `rke2lab-cluster-api-install.service` and `rke2lab-capn-provider-install.service` both have `Requires=` on a prerequisite that becomes active after `rke2lab.target`, so they get queued and dropped. Either propagate `WantedBy=` from the prerequisite, or restructure so both services are pulled in by their actual unblocker rather than by the target.

Validation: `pulumi up` with these fixes should land the seed-master output's `pendingDependencies` empty (currently shows the two services as `inactive`).

=== 2.B — Bring control-plane peers under CAPN

Once 2.A lands, the *first* CAPN-managed nodes are the missing bioskop control-plane peers (peer1, peer2, peer3) — not workers. They round out HA on the management cluster itself before any worker scale-out. Worker provisioning (worker1, worker2, nikopol) is a later phase.

Work items:

. *Define a `Cluster` resource for `bioskop`* targeting the existing master and the three peers. The seed-master output already publishes the handoff identity (`managementClusterName=bioskop`, `apiEndpoint=https://10.66.106.10:6443`, `kubeconfigRef`, etc.) — Stage B reads these to populate the Cluster spec.
. *Define `IncusMachine`+`RKE2ControlPlane`* (or equivalent CAPN+CAPRKE2 shapes) for peer1/peer2/peer3. They join via the kube-vip-fronted control-plane endpoint that's already up.
. *Validate end-to-end*: `kubectl get machines` shows the four control-plane Machines reconciling; `etcd` member list grows to 4; `kube-apiserver` is reachable through the VIP throughout. The bbox DHCP reservations for peer1/2/3 are already in place (the seed-master reconciles 12 reservations; only 1 is currently bound to a running instance).

Worker nodes (worker1, worker2) and external nodes (nikopol) are deferred to a later sub-phase — they need separate `MachineDeployment` shapes and a different bootstrap profile, and we want HA on the management plane before adding workload capacity.

== Phase 3 — automation: tracking and bumping upstream artifacts

Once Phase 1 lands we will have ≥4 `release-vX.Y.Z.yaml` files committed under `manifests/src/main/resources/upstream/`. Treat this as a versioned manifest of cluster components and automate the bump cycle.

Goals:

* Single source of truth for "what version of upstream operator X is the cluster running."
* Mechanical upgrade: replace the file, bump the Java string, review the YAML diff, ship.
* Visibility: PR review sees what changed in the upstream artifact alongside our integration changes.

Concrete workstream:

. *Inventory.* Author a `docs/upstream-tracked-components.adoc` listing every tracked upstream (Tekton operator, Flux operator, Porch, snapshot-controller-CRDs, …) with its current pinned version, source URL, and the layer that owns it.
. *Bumper script.* Small flake script (`bin/bump-upstream-component.sh <component>`): re-fetches the latest release artifact, writes the new YAML to a new versioned filename, prints the diff against the old one, leaves the Java string update to the human (one place, easy to grep).
. *CI guard.* Build asserts that every `release-*.yaml` referenced by Java code actually exists in `src/main/resources/upstream/`. Catches typos and orphaned files.
. *Renovate-style automation* (later): periodic check, opens a PR per component when a new upstream release exists.

== Phase 4 — build cluster-required binaries via nix

The flox runtime flake (`manifests/src/main/resources/runtime/flox/flake.nix`) already builds `flox-nri-plugin`, `kdns`, headplane stack from source. Same path applies to the rest of the operator binaries we currently consume as upstream container images.

Why bother: same reason flox-injected workloads beat per-image baking — single nix store across host and pods, byte-for-byte reproducibility through `flake.lock`, no registry dependency, fast iteration.

Candidates, ordered by leverage:

. *clusterctl* — currently shipped via `curl` from `rke2lab-cluster-api-install.service`. Move it to a flox env so version pinning matches the same flake.lock as everything else. Pairs naturally with Phase 2.A.
. *kube-vip* — single Go binary, easy to flake-build. Replace the upstream container with a flox-managed version. Lower priority now that the daemonset is healthy, but the leverage argument still holds.
. *Tekton operator* — Go-built, but more involved (multi-binary, embedded assets). Phase 4.B candidate after the simpler ones land.
. *Porch / Flux operator* — same shape as Tekton operator, evaluate after Phase 4.A pieces land.

Open question for each candidate: do we replace the **operator container image** referenced in the upstream release.yaml (transform hook in `UpstreamYamlInclusion` to swap the image tag), or do we build a **separate workload that calls the same controller code** (more work, more control)? For phase 4.A (clusterctl, kube-vip) the answer is "image swap." For Tekton/Porch it's likely "image swap" too, but the diff is bigger.

== Order of operations summary

Recommended execution order — respects what unblocks what, leaves room to skip:

. *Phase 2.A CAPN materialization + systemd ordering fix* — unblocks Stage B; the resume point.
. *Phase 2.B CAPN-managed control-plane peers (peer1/2/3)* — HA on the management cluster, follows immediately after 2.A.
. *Phase 1.1 Porch* — biggest single workload unblock (7 manifests). Same shape as Tekton. Independent of Phase 2; can run in parallel or after.
. *Phase 1.2 Flux Operator* — small follow-up; once Porch is in we have the core gitops surface.
. *Phase 2.C CAPN-managed workers (worker1/2) and nikopol* — after the control-plane is HA.
. *Phase 3 tracking + bumper script* — once the upstream inventory is non-trivial.
. *Phase 4 nix builds for clusterctl, then operator binaries* — opt-in, per-component. (kube-vip nix build was the original Phase 4.A but is now lower priority since the daemonset is healthy.)
