= Staged Post-Cluster Resources
:toc:
:toclevels: 3

== Overview

This document describes the **staged post-cluster resource pattern** — a solution for Kubernetes resources that cannot be synthesized during Stage A host-state preparation due to dependency cycles, but must exist in-cluster before Stage B workloads run.

=== Diagram Legend

Throughout this document, color coding indicates component ownership:

[cols="1,3"]
|===
| Color | Domain

| 🟢 Green
| Pulumi domain (Java) — Outputs, provider resources, resource lifecycle

| 🔵 Blue
| Systemd domain — Boot ordering, service dependencies, restart policies

| 🟡 Yellow
| Shell domain — kubectl apply, error handling (NO YAML authoring)

| 🟠 Orange
| Data contract — CDK8s-synthesized YAML manifests that decouple domains

| 🟣 Purple
| Kubernetes domain — Final in-cluster resources

| 🔴 Red
| Problem/cycle — Components that cannot work together directly
|===

**Problem**: Stage A provisions `/srv/host` (including manifests) BEFORE Pulumi provider resources are created. But some manifests need data FROM those provider resources (e.g., image fingerprint). This creates a chicken-and-egg cycle.

**Solution**: Defer the resource creation to a systemd oneshot unit that runs AFTER the cluster is up, applying a CDK8s-synthesized manifest written during Pulumi apply.

=== Requirements Checklist

Use staged post-cluster resources when ALL of the following conditions are true:

1. **The resource must exist in-cluster** (not just as a file in `/srv/host`)
2. **Stage B workloads depend on it** (controllers, operators, CRDs)
3. **It requires data from Pulumi resources** (Outputs that aren't available during host-state prep)
4. **It can be created after RKE2 starts** (doesn't need to exist for cluster bootstrap itself)

Common examples:

- ConfigMaps with provider-managed resource IDs or fingerprints
- Secrets containing generated credentials from cloud providers
- Custom resources that reference Pulumi-managed infrastructure

=== Anti-Patterns

DO NOT use this pattern when:

- **The manifest can be synthesized statically** — use CDK8s synthesis in the normal flow
- **The data is available before Pulumi resources are created** — pass it through `ManifestSynthesisRequest`
- **The resource isn't needed until much later** — create it in Stage B provisioning
- **It's needed for RKE2 bootstrap itself** — must be in `/srv/host/manifests/` (find another solution)

**Boundaries:**

- **🟢 Pulumi** knows about Outputs, provider resources, and when to trigger CDK8s synthesis
- **🔵 Systemd** knows about boot ordering, service dependencies, and restart policies
- **🟡 Shell** knows about kubectl apply and error handling (NO YAML serialization)
- **📦 YAML Manifest** is CDK8s-authored (same as all other manifests), just written late via Output.apply()
- **🟣 Kubernetes** is the final destination, agnostic to how the ConfigMap was created

**Key principle:** Shell scripts never author YAML. All manifest structure comes from CDK8s, even for staged resources.

=== Component Responsibilities

[cols="1,3"]
|===
| Component | Responsibility

| **Pulumi Program (ProviderStage)**
| Use `Output.all()` to combine resolved provider resource Outputs, call standalone CDK8s synthesis method with resolved values, write the resulting YAML manifest to `/srv/host/manifests/clusterapi/staged/`

| **Standalone CDK8s Synthesis**
| Direct use of CDK8s primitives (ApiObject, ApiObjectMetadata, JsonPatch) to create the ConfigMap. NOT the normal manifest unit machinery — staged synthesis is a separate entrypoint without ManifestSynthesisContext dependency

| **YAML Manifest File**
| CDK8s-synthesized Kubernetes manifest in `/srv/host/manifests/clusterapi/staged/`. Same structure as ImageStateConfigMapManifestUnit, just synthesized via standalone entrypoint

| **Systemd Unit**
| Oneshot service (+ optional timer) that runs after `rke2-server.service` and applies the manifest via `kubectl`

| **Bootstrap Script**
| Shell script that does `kubectl apply -f <manifest>`. NO YAML authoring, NO templating, NO JSON parsing — just applies the CDK8s-authored file
|===

**Architecture invariants:**
1. All YAML structure comes from CDK8s (no shell templating)
2. Staged synthesis uses CDK8s primitives directly (no context machinery that doesn't fit)
3. Shell scripts only do `kubectl apply`

== Architecture Decision: Standalone vs. Reusing Manifest Units

Before implementation, understand the key architectural choice:

**Should staged synthesis reuse the normal manifest unit code?**

**❌ NO — Use a standalone CDK8s entrypoint instead.**

**Why not reuse manifest units?**

The normal synthesis flow uses ManifestSynthesisContext which bundles:
- FloxDebugPolicy
- BootstrapIdentity (9 fields: clusterName, clusterId, clusterToken, ...)
- NetworkTopology
- ComponentVersions
- ImageState

Staged synthesis only needs:
- `clusterName` (1 field)
- Image data (5 fields: alias, fingerprint, checksum, project, remote)

Forcing staged synthesis through ManifestSynthesisContext creates **bad smell**:
- Dummy BootstrapIdentity with fake clusterId, clusterToken, nodeId values
- Empty NetworkTopology/ComponentVersions that aren't used
- ImageState wrapper when you already have the raw values
- AbstractManifestUnit.bootstrapIdentity() accessor that isn't needed

**Solution:** Standalone synthesis using CDK8s primitives directly (ApiObject, ApiObjectMetadata, JsonPatch). Same YAML structure, no machinery that doesn't fit.

**When to reuse manifest units:**
- Normal host-state synthesis flow (ManifestSynthesisService)
- Full context is available
- Multiple units share the same context

**When to use standalone synthesis:**
- Staged resources (this pattern)
- Only need a subset of context
- Outputs drive the synthesis

== Implementation Guide

=== Step 1: Identify the Dependency Cycle

Before implementing, verify you actually have a cycle:

1. What Pulumi resource Output do you need? (e.g., `image.fingerprint()`)
2. When does that Output resolve? (during Pulumi apply, after the resource is created)
3. When do you need the manifest? (before instance creation, during host-state prep)
4. Can you reorder the pipeline stages? (usually NO — host-state must come before provider resources)

If you can't break the cycle by reordering, proceed to staged creation.

=== Step 2: Synthesize the Manifest via CDK8s

**IMPORTANT**: Do NOT serialize YAML in shell scripts. All manifest authoring stays in CDK8s. The staged pattern only defers *when* the synthesis happens.

**Architecture Decision**: Use a **standalone CDK8s entrypoint**, not the normal manifest unit machinery. The ManifestSynthesisContext is designed for the host-state preparation flow and doesn't fit the staged use case.

Create a synthesis method that uses CDK8s primitives directly:

[source,java]
----
/**
 * Synthesize the image-state ConfigMap via CDK8s with resolved values.
 * Standalone entrypoint - does NOT use ManifestSynthesisContext.
 */
private String synthesizeImageStateConfigMapYaml(
    String clusterName,
    String imageAlias,
    String imageFingerprint,
    String imageBuildChecksum,
    String incusProject,
    String incusRemoteAddress) {

  // Create in-memory CDK8s app (temp dir for output)
  final Path tempDir = Files.createTempDirectory("cdk8s-staged-");
  final App app = new App(AppProps.builder().outdir(tempDir.toString()).build());
  final Chart chart = new Chart(app, "staged-resources");

  // Create ConfigMap directly using CDK8s primitives
  final Map<String, String> data =
      Map.of(
          "imageAlias", imageAlias,
          "imageFingerprint", imageFingerprint,
          "imageBuildChecksum", imageBuildChecksum,
          "incusProject", incusProject,
          "incusRemoteAddress", incusRemoteAddress);

  final ApiObject configMap =
      new ApiObject(
          chart,
          "configmap-image-state",
          ApiObjectProps.builder()
              .apiVersion("v1")
              .kind("ConfigMap")
              .metadata(
                  ApiObjectMetadata.builder()
                      .name(clusterName + "-image-state")
                      .namespace("capn-system")
                      .annotations(
                          Map.of(
                              "package", "clusterapi/image-state",
                              "description", "Stage A → Stage B image identity handoff"))
                      .build())
              .build());

  configMap.addJsonPatch(JsonPatch.add("/data", data));

  // Synthesize, read from disk, cleanup
  app.synth();
  final String yaml = Files.readString(tempDir.resolve("staged-resources.k8s.yaml"));
  // ... cleanup tempDir ...
  return yaml;
}
----

**Key insight:** Staged synthesis is a **separate entrypoint**, not a variant of normal synthesis. Don't force-fit ManifestSynthesisContext/AbstractManifestUnit when you only need CDK8s primitives. The structure matches ImageStateConfigMapManifestUnit but without the context dependency.
----

=== Step 3: Write the Manifest YAML During Pulumi Apply

In the appropriate pipeline stage (usually ProviderStage), synthesize the manifest and write it:

[source,java]
----
import com.pulumi.command.local.Command;
import com.pulumi.command.local.CommandArgs;

ProviderStage createImageStateConfigMap() {
  final Output<String> manifestYaml =
      Output.all(
              state.ensuredImageFingerprint,  // Output<String> from provider
              Output.of(config.imageAlias()),
              Output.of(imageProvider.buildChecksum()),
              Output.of(config.incusProject()),
              Output.of(config.incusRemote()))
          .applyValue(
              tuple -> {
                final String fingerprint = tuple.t1();
                final String alias = tuple.t2();
                final String checksum = tuple.t3();
                final String project = tuple.t4();
                final String remote = tuple.t5();

                // CDK8s synthesis with resolved values
                return synthesizeImageStateConfigMapYaml(
                    config.clusterName(), alias, fingerprint, checksum, project, remote);
              });

  // Write manifest to /srv/host/manifests/clusterapi/staged/
  final Path targetPath =
      state.localPaths.assetsRoot()
          .resolve("manifests/clusterapi/staged/image-state-configmap.yaml");

  new Command(
      "write-image-state-manifest",
      CommandArgs.builder()
          .create(
              manifestYaml.applyValue(
                  yaml ->
                      String.format(
                          "mkdir -p %s && cat > %s <<'EOF'\n%s\nEOF",
                          targetPath.getParent(), targetPath, yaml)))
          .triggers(List.of(manifestYaml))  // Re-run if manifest changes
          .build(),
      CustomResourceOptions.builder()
          .provider(state.providerContext.provider())
          .dependsOn(state.ensuredProject)
          .build());

  return this;
}
----

**Key differences from JSON approach:**

1. Calls `synthesizeImageStateConfigMapYaml()` instead of `toJson()`
2. Writes to `manifests/clusterapi/staged/` (manifest location, not data location)
3. File extension is `.yaml` (not `.json`)
4. The YAML is CDK8s-authored (same as all other manifests)

=== Step 4: Create the Bootstrap Script

Create a simple shell script that applies the CDK8s-synthesized manifest:

.seed-master/src/main/resources/.../rke2lab-cluster-api-image-state-apply.sh
[source,bash]
----
#!/usr/bin/env -S bash -exu -o pipefail

: "Load RKE2 environment for kubectl"
source <(flox activate --dir /var/lib/rancher/rke2)

MANIFEST_FILE="/srv/host/manifests/clusterapi/staged/image-state-configmap.yaml"

if [[ ! -f "${MANIFEST_FILE}" ]]; then
  echo "image-state manifest not found: ${MANIFEST_FILE}" >&2
  exit 1
fi

# Ensure namespace exists
kubectl get namespace capn-system >/dev/null 2>&1 || \
  kubectl create namespace capn-system

# Apply the CDK8s-synthesized manifest
kubectl apply -f "${MANIFEST_FILE}"

echo "image-state ConfigMap applied from ${MANIFEST_FILE}"
----

**Much simpler!** No JSON parsing, no YAML templating. Just `kubectl apply` of a CDK8s-authored manifest.

=== Step 5: Create the Systemd Unit

Create a systemd service unit that runs the script:

.rke2lab-cluster-api-image-state-apply.service
[source,ini]
----
[Unit]
Description=Apply Cluster API image-state ConfigMap
Documentation=file:///srv/host/docs/staged-post-cluster-resources.adoc
After=rke2-server.service
Before=cluster-ready.target
Wants=network-online.target
ConditionPathExists=/srv/host/manifests/clusterapi/staged/image-state-configmap.yaml

[Service]
Type=oneshot
RemainAfterExit=yes
Environment="CLUSTER_NAME=master"
ExecStart=/srv/host/systemd.d/systemd-scripts/rke2lab-cluster-api-image-state-apply.sh
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
----

**Key directives**:

- `After=rke2-server.service` — wait for cluster to be up
- `Before=cluster-ready.target` — block the ready gate until this completes
- `ConditionPathExists=` — skip if manifest file doesn't exist (preview mode, old image)
- `RemainAfterExit=yes` — mark as active after successful run (idempotent)

=== Step 6: Wire Into the Bootstrap Sequence

Ensure the systemd unit is:

1. Materialized into `/srv/host/systemd.d/` during host-state prep
2. Enabled via `systemctl enable` in the provisioning flow
3. Listed in the bootstrap dependency chain

If using a custom target like `cluster-ready.target`, make sure it's defined and the new unit is ordered before it.

== Troubleshooting

=== Manifest File Missing

**Symptom**: `ConditionPathExists` causes unit to skip

**Causes**:

- Pulumi apply didn't complete successfully
- File write command failed (check Pulumi logs)
- Path mismatch between Pulumi target and systemd `ConditionPathExists=`

**Fix**: Check `pulumi up` output for the file-write Command resource. Verify the path.

=== ConfigMap Apply Fails

**Symptom**: Systemd unit fails with kubectl error

**Causes**:

- RKE2 not fully ready (race condition)
- Namespace doesn't exist (script should create it)
- Invalid YAML in manifest (CDK8s synthesis failed)
- RBAC issue (shouldn't happen on master, but check)

**Fix**: Add retries to the script, or make the unit `Restart=on-failure` with `RestartSec=10s`.

=== Data is Stale

**Symptom**: ConfigMap has old fingerprint after image rebuild

**Causes**:

- Manifest file wasn't updated (Pulumi didn't detect change in Outputs)
- Systemd unit is `RemainAfterExit=yes` and didn't re-run

**Fix**: Force re-apply:

[source,bash]
----
systemctl reset-failed rke2lab-cluster-api-image-state-apply.service
systemctl restart rke2lab-cluster-api-image-state-apply.service
----

Or delete the old ConfigMap and restart the unit.

== Comparison to Alternatives

[cols="1,2,2"]
|===
| Approach | Pros | Cons

| **CDK8s Synthesis (normal flow)**
| Simple, type-safe, all manifests in one place
| Can't access Pulumi Outputs

| **Pulumi Kubernetes Provider**
| Native Pulumi resource, Output-aware
| Requires kubernetes provider configured AFTER instance is up; complicates Stage A

| **Staged Post-Cluster (this pattern)**
| Breaks the dependency cycle cleanly; all YAML still CDK8s-authored
| More moving parts (late synthesis + systemd unit + script)

| **Stage B Provisioning**
| Defers creation until Stage B tooling runs
| Stage B might need the data BEFORE its provisioning runs (chicken-and-egg at a different level)

| **Instance Config Keys**
| Simple key/value storage
| Incus config values are strings and have size limits; not structured data; requires reading via `incus config get` inside the instance

| **Cloud-Init User-Data**
| Standard VM initialization mechanism
