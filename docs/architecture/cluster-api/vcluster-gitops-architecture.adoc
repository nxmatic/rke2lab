**Status**: This document proposes the vCluster architecture for deploying applications using a management vCluster pattern.

**Implementation**: See link:vcluster-implementation-plan.adoc[vCluster Implementation Plan] for the complete phased implementation roadmap.

**Dependencies**:

* ✅ Phase 1 Complete: Master node + CAPI/Flux operators installed via Pulumi
* 📋 Phase 1.5-5 Planned: Implementation detailed in link:vcluster-implementation-plan.adoc[vCluster Implementation Plan]

**Key Architectural Decision**: Use a three-layer bootstrap approach where RKE2 auto-deploy handles infrastructure-critical components (Layer 1), Pulumi creates gitops-mgmt vCluster (Layer 2), and Flux manages all workloads (Layer 3). This enables complete reentrancy and testability while maintaining operational infrastructure dependencies.

== Document Overview

This document defines the architecture for Phase 4 of rke2lab: deploying applications in virtual clusters using a lightweight GitOps approach with Flux in a dedicated management vCluster.

== Overview

Phase 4 extends the rke2lab bootstrap system to provision and manage applications within vClusters. Rather than installing Flux in the core cluster (Option A) or duplicating Flux in every vCluster (Option B), we use **Option D**: a permanent `gitops-mgmt` vCluster that hosts Flux and manages both the parent cluster and all child vClusters.

**Key Innovation**: The `gitops-mgmt` vCluster uses the parent cluster's kubeconfig (via Secret) to apply manifests to the core cluster itself. This enables complete reentrancy: the cluster core is managed as if it were just another vCluster.

**Benefits**:

* **Mutualized**: One Flux (120MB) manages everything, not N × 120MB
* **Reentrant**: Can test a new version of the core in `gitops-mgmt-next` before promoting
* **Isolated**: Flux failure in `gitops-mgmt` doesn't crash the core (core still runs, just not managed)
* **Testable**: Standard workflow for validating upgrades before applying to production

== Problem Statement

=== Current State (Phase 1-3)

rke2lab implements:

* **Phase 1 COMPLETE**: Cluster API + Flux Operator installed via Pulumi (`seed-master/`)
* **Phase 2-3 IN PROGRESS**: `seed-peers/` module to provision peer nodes via CAPI
* **Architecture**: Pulumi → master node → CAPI/Flux → peers

=== Requirements for Phase 4

From conversation with Perplexity, need to replace heavy Porch/Flux/kpt stack (200-400MB) with lightweight solution for:

* Provisioning applications in vClusters (labs/teams)
* Deploying standard apps: Traefik, cert-manager, etc.
* Managing 1-5 vClusters (not hundreds)
* **Critical**: System must be reentrant — a lab vCluster should be able to test/deploy a new version of the cluster core

**Problems with current Porch/Flux/kpt**:

* 200-400MB RAM per installation + 10+ CRDs
* 10-minute Git sync delay
* Complex debugging (4+ commands to diagnose issues)
* Excessive complexity for small-scale use case

**Desired characteristics**:

* Lightweight (0-120MB acceptable)
* GitOps-native (auto-sync from Git)
* Simple debugging
* Multi-lab/multi-team support
* **Reentrant**: Can test core upgrades in isolation

== Architecture Decision Process

=== Options Explored

==== Option A: Centralized GitOps in Core (Initial Approach)

[source,text]
----
Cluster core (RKE2)
├── Namespace: flux-system
│   ├── source-controller (50MB)
│   ├── kustomize-controller (50MB)
│   └── notification-controller (20MB)
├── vCluster lab-1 (namespace: lab-1)
│   └── Apps deployed by core Flux
└── vCluster lab-2 (namespace: lab-2)
    └── Apps deployed by core Flux
----

**Advantages**:

* ✅ Single Flux to maintain
* ✅ 120MB total (vs 120MB × N)
* ✅ Centralized view of all deployments

**Disadvantages**:

* ❌ Core is a Single Point of Failure
* ❌ Cannot test new core version easily
* ❌ **Not reentrant**: How to bootstrap the core itself?
* ❌ Strong coupling: core problem impacts all labs

==== Option B: Distributed GitOps per vCluster

[source,text]
----
Cluster core (RKE2) - MINIMAL
├── vCluster lab-1 (namespace: lab-1)
│   ├── Namespace: flux-system
│   │   ├── source-controller (50MB)
│   │   ├── kustomize-controller (50MB)
│   │   └── notification-controller (20MB)
│   └── Apps deployed locally
├── vCluster lab-2 (namespace: lab-2)
│   └── Same: own Flux
└── vCluster core-next (test next core)
    └── Flux that deploys v2 of cluster core
----

**Advantages**:

* ✅ **Reentrant**: A lab can deploy/test new core
* ✅ **Complete isolation**: lab-1 problem doesn't affect lab-2
* ✅ **Dogfooding**: System can manage itself
* ✅ **Testing**: Test new core in disposable vCluster

**Disadvantages**:

* ❌ 120MB × N vClusters (600MB for 5 labs)
* ❌ N Flux installations to maintain/upgrade
* ❌ No centralized view (unless monitoring added)

==== Option C: Hybrid GitOps (Compromise)

[source,text]
----
Cluster core (RKE2)
├── Namespace: flux-system (LIGHTWEIGHT)
│   └── source-controller (50MB) - ONLY watches Git
├── vCluster lab-1 (namespace: lab-1)
│   ├── kustomize-controller (50MB) - Applies locally
│   └── Apps
├── vCluster lab-2 (namespace: lab-2)
│   └── Same: local controller
└── vCluster core-next (test next core)
    └── Full GitOps stack
----

**Advantages**:

* ✅ 50MB in core + 50MB × N (300MB for 5 labs)
* ✅ Partially reentrant
* ✅ Isolation for applies (local kustomize-controller)
* ✅ Centralized Git source (single source-controller)

**Disadvantages**:

* ⚠️ Intermediate complexity
* ⚠️ source-controller in core remains a Git SPOF

==== Option D: Flux in Management vCluster (SELECTED)

[source,text]
----
Bootstrap initial (Pulumi)
↓
Cluster core (RKE2) - NO FLUX IN CORE
├── vCluster: gitops-mgmt (namespace: gitops-mgmt) ← PERMANENT
│   ├── Flux complete (120MB)
│   ├── CAPI controllers (150MB)
│   └── Manages core itself via parent-cluster-kubeconfig Secret
├── vCluster: lab-1 (namespace: lab-1)
│   └── Apps (managed by gitops-mgmt Flux)
└── vCluster: lab-2 (namespace: lab-2)
    └── Apps (managed by gitops-mgmt Flux)
----

**Pattern**: A special `gitops-mgmt` vCluster is responsible for managing the core cluster.

**Advantages**:

* ✅ **Completely reentrant**: Core is managed like a lab
* ✅ **Testing**: Create `gitops-mgmt-next` to test new core
* ✅ **Rollback**: Return to `gitops-mgmt` v1 if problems
* ✅ **Perfect isolation**: Everything in vClusters
* ✅ **Mutualized**: One Flux manages everything (not N × 120MB)
* ✅ **Evolutive**: Can test Flux upgrades in gitops-mgmt-next

**Disadvantages**:

* ⚠️ 270MB in gitops-mgmt (120MB Flux + 150MB CAPI)
* ⚠️ Conceptually more complex than Option A
* ⚠️ Requires 3-layer bootstrap (see below)

**Decision**: Option D selected because it solves the reentrancy requirement while maintaining mutualization benefits.

== Migration Path from Phase 1-3

=== Current State (Post-Phase 3)

After Phase 1-3 completion, the cluster architecture is:

[source,text]
----
RKE2 Core Cluster
├── Namespace: flux-system (IN CORE)
│   ├── Flux Operator (installed by Pulumi)
│   ├── FluxInstance CR
│   └── Watching gitops/clusters/bioskop/ (if Phase 1 GitOps bootstrap complete)
├── Namespace: capi-system (IN CORE)
│   ├── CAPI core controllers (cluster-api-controller-manager)
│   └── Cluster CRs for peer provisioning
├── Namespace: capn-system (IN CORE)
│   ├── CAPN Incus provider (for LXC container provisioning)
│   └── Secret: bioskop-incus-identity (Incus API credentials)
├── Namespace: caprke2-system (IN CORE)
│   └── CAPRKE2 bootstrap provider (RKE2 cloud-init generation)
└── Peer nodes: peer1, peer2, peer3 (CAPI-managed, Incus containers)
----

**Key characteristic**: Flux and CAPI live **in the core cluster**. This is a **temporary arrangement** for Phase 1-3. They will migrate to a vCluster in Phase 4.

=== Why Migrate to gitops-mgmt vCluster?

The Phase 1-3 architecture has limitations:

* **Not reentrant**: Cannot test core cluster upgrades in isolation
* **Single point of failure**: Flux crash impacts the entire cluster
* **No upgrade testing**: Upgrading Flux/CAPI requires applying directly to production
* **Tight coupling**: Core cluster problems impact GitOps management

Moving Flux + CAPI into a dedicated vCluster solves these issues while maintaining the benefits of centralized management.

=== Phase 4 Transition Steps

**Step 1: Install vCluster Operator** (via manifests layer)

Add `VClusterOperatorLayer.java` to `manifests/` module, installed by `rke2lab-cluster-manifests.service`:

[source,java]
----
// manifests/.../layers/vcluster/VClusterOperatorLayer.java
public class VClusterOperatorLayer extends Construct {
    public VClusterOperatorLayer(Construct scope) {
        super(scope, "vcluster-operator");
        // Helm chart installation via CDK8s
        // Operator size: ~10MB
    }
}
----

**Step 2: Create gitops-mgmt vCluster** (via seed-master Pulumi)

Update `seed-master/` to create the management vCluster:

[source,java]
----
// seed-master/.../layers/vcluster/GitopsMgmtVClusterLayer.java
public class GitopsMgmtVClusterLayer {
    public GitopsMgmtVClusterLayer(Construct scope) {
        // Creates VCluster CR: gitops-mgmt
        // With init.manifests: Flux bootstrap YAML (vendored)
        // Result: vCluster with Flux pre-installed
    }
}
----

**Step 3: Inject parent-cluster-kubeconfig Secret**

Key innovation: Flux in the vCluster can manage the parent cluster:

[source,bash]
----
# Extract vCluster kubeconfig
vcluster connect gitops-mgmt -n gitops-mgmt --print > /tmp/gitops-mgmt-kubeconfig

# Inject parent cluster kubeconfig into vCluster
kubectl --kubeconfig=/tmp/gitops-mgmt-kubeconfig \
  create secret generic parent-cluster-kubeconfig \
  -n flux-system \
  --from-file=kubeconfig=$HOME/.kube/config
----

**Step 4: Bootstrap Flux in gitops-mgmt**

Connect Flux to the repository:

[source,bash]
----
flux bootstrap github \
  --kubeconfig=/tmp/gitops-mgmt-kubeconfig \
  --owner=nxmatic \
  --repository=rke2lab \
  --branch=main \
  --path=gitops/flux-system
----

**Step 5: Configure Kustomizations to use parent kubeconfig**

Create Kustomizations that apply to the **parent cluster**:

[source,yaml]
----
# gitops/vclusters/gitops-mgmt/flux/kustomizations.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: bioskop-core
  namespace: flux-system  # IN gitops-mgmt vCluster
spec:
  interval: 10m
  path: ./clusters/bioskop/core  # CAPI resources, etc.
  prune: true
  sourceRef:
    kind: GitRepository
    name: flux-system
  # KEY: Apply to parent cluster, not vCluster
  kubeConfig:
    secretRef:
      name: parent-cluster-kubeconfig
----

**Step 6: Move CAPI controllers to gitops-mgmt** (optional, can stay in core)

Two sub-options:

* **Option 6A**: Keep CAPI in core (simpler, manages physical infrastructure)
* **Option 6B**: Move CAPI to gitops-mgmt (full reentrancy, can test CAPI upgrades)

**Recommended**: Start with Option 6A (CAPI in core), migrate to 6B later if needed.

**Step 7: Suspend old Flux in core** (during transition)

Prevent conflicts during dual-Flux period:

[source,bash]
----
# Suspend old Flux Kustomizations in core
kubectl patch kustomization -n flux-system <name> \
  --type=merge -p '{"spec":{"suspend":true}}'

# After validating gitops-mgmt Flux works, delete old Flux from core
kubectl delete namespace flux-system  # In core cluster
----

**Step 8: Create lab vClusters**

With gitops-mgmt operational, create application vClusters:

[source,yaml]
----
# gitops/vclusters/labs/lab-1/vcluster.yaml
apiVersion: vcluster.loft.sh/v1
kind: VCluster
metadata:
  name: lab-1
  namespace: lab-1
spec:
  sync:
    toHost:
      pods:
        enabled: true
----

Flux in gitops-mgmt applies this to the parent cluster via `parent-cluster-kubeconfig`.

=== Migration Validation

**After each step, validate**:

1. **vCluster Operator**: `kubectl get crd vclusters.vcluster.loft.sh`
2. **gitops-mgmt vCluster**: `kubectl get vcluster -n gitops-mgmt`
3. **Flux in gitops-mgmt**: `vcluster connect gitops-mgmt && flux get all`
4. **Parent kubeconfig Secret**: `kubectl --kubeconfig=<vcluster> get secret parent-cluster-kubeconfig -n flux-system`
5. **Kustomizations apply to parent**: Check that Flux creates resources in parent, not vCluster
6. **Old Flux suspended**: Verify no reconciliation conflicts
7. **Lab vClusters created**: `kubectl get vcluster -n lab-1`

=== Rollback Plan

If Phase 4 migration fails:

1. **Suspend gitops-mgmt Flux**: `kubectl patch kustomization ...`
2. **Resume old Flux in core**: `kubectl patch kustomization --type=merge -p '{"spec":{"suspend":false}}'`
3. **Delete gitops-mgmt vCluster**: `kubectl delete vcluster gitops-mgmt -n gitops-mgmt`
4. **Investigate logs**: `kubectl logs -n gitops-mgmt <flux-pod>`

The core cluster remains operational throughout — Flux manages GitOps, but cluster itself is independent.

**Three Layers:**

1. **Layer 1** (Pulumi): Install vCluster Operator + create gitops-mgmt vCluster with Flux inside
2. **Layer 2** (Pulumi): Bootstrap Flux to GitHub + inject parent-cluster-kubeconfig Secret
3. **Layer 3** (Flux): Manage parent cluster via parent kubeconfig Secret

**Chicken-and-egg solved:** Pulumi creates the vCluster with Flux pre-installed via `init.manifests`, then bootstraps Flux to GitHub, then injects the Secret. From there, Flux manages the parent cluster as if it were external.

    participant Lab as lab-1 vCluster

    Op->>CDK8s: mvn -pl :seed-vclusters generate-resources
    CDK8s->>CDK8s: Generate VCluster CR + apps YAML
    CDK8s-->>Op: gitops/vclusters/lab-1/

    Op->>GitHub: git add gitops/vclusters/lab-1/<br/>git commit && git push

    Flux->>GitHub: Poll every 1m (default)
    GitHub-->>Flux: New commit detected

    Flux->>Flux: Reconcile Kustomization: vclusters
    Flux->>Flux: Read parent-cluster-kubeconfig Secret
    Flux->>Core: Apply VCluster CR: lab-1<br/>using parent kubeconfig

    Core->>VClusterOp: Reconcile VCluster CR
    VClusterOp->>Core: Create namespace: lab-1
    VClusterOp->>Lab: Create vCluster control plane pods
    VClusterOp-->>Core: VCluster ready

    Flux->>Core: Apply Traefik manifests to lab-1 namespace<br/>using parent kubeconfig
    Core->>Lab: Traefik pods start

    Lab-->>Op: lab-1 ready with Traefik
----

**Key Points:**

* **No Flux in lab-1**: Flux in gitops-mgmt manages lab-1 apps remotely
* **Git-driven**: Changes to `gitops/vclusters/lab-1/` auto-apply
* **Mutualized**: One Flux manages all labs

public class VClusterTemplate extends Construct {
    public VClusterTemplate(Construct scope, String id, String namespace, Map<String, String> apps) {
        super(scope, id);

        // VCluster CR
        ApiObject vcluster = new ApiObject(scope, id + "-vcluster", ApiObjectProps.builder()
            .apiVersion("vcluster.loft.sh/v1")
            .kind("VCluster")
            .metadata(ApiObjectMetadata.builder()
                .name(id)
                .namespace(namespace)
                .build())
            .build());

        vcluster.addJsonPatch(JsonPatch.add("/spec", Map.of(
            "sync", Map.of(
                "toHost", Map.of(
                    "pods", Map.of("enabled", true)
                )
            )
        )));

        // Apps (Traefik, cert-manager, etc.)
        if (apps.containsKey("traefik")) {
            new TraefikLayer(scope, id + "-traefik", namespace);
        }
        if (apps.containsKey("cert-manager")) {
            new CertManagerLayer(scope, id + "-cert-manager", namespace);
        }
    }
}

== Open Questions

=== Critical (must decide before implementation)

1. **CAPI placement decision**: Should CAPI controllers stay in core cluster (manages physical infrastructure) or move to gitops-mgmt vCluster (full reentrancy)?
   * **Recommendation**: Start with CAPI in core (Option 6A), migrate later if needed
   * **Rationale**: Physical infrastructure management feels more stable in core; vCluster overhead not justified initially

2. **Migration strategy**: How to transition Flux+CAPI from core to gitops-mgmt without downtime?
   * **Approach**: Dual-Flux period with old Flux suspended via `.spec.suspend: true`
   * **Validation**: Server-side dry-run of gitops-mgmt Kustomizations before suspending old Flux

3. **Bootstrap sequence**: Should gitops-mgmt vCluster creation be in seed-master (Pulumi) or seed-vclusters (CDK8s)?
   * **Recommendation**: seed-master Pulumi (Layer 1 bootstrap)
   * **Rationale**: gitops-mgmt is infrastructure, not an application. Pulumi ensures it exists before any GitOps loops start.

=== Important (can be deferred to post-Phase 4)

4. **VCluster lifecycle**: Should lab vClusters be ephemeral (auto-delete after N days)?
   * **Initial answer**: Manual lifecycle (no auto-delete). Add TTL controller later if needed.

5. **App catalog**: Predefined app sets (minimal, full, custom)?
   * **Initial answer**: Hardcode Traefik + cert-manager in seed-vclusters. Abstract to catalog in Phase 5.

6. **Resource limits**: What are the memory/CPU limits for gitops-mgmt and lab vClusters?
   * **Initial answer**: No limits initially. Monitor and tune based on observed usage.

=== Nice-to-have (future enhancements)

7. **Monitoring**: How to aggregate metrics/logs from gitops-mgmt + labs?
   * **Future work**: Centralized Prometheus + Loki with vCluster label selectors

8. **RBAC**: How to isolate lab-1 from lab-2 (NetworkPolicy, RBAC)?
   * **Initial answer**: Namespace isolation only. NetworkPolicy + RBAC in Phase 5 if multi-tenant requirements emerge.

9. **Upgrade testing automation**: Can gitops-mgmt-next creation/promotion be automated?
   * **Future work**: Tekton pipeline for "create test vCluster → validate → auto-promote on success"
