= vCluster GitOps Architecture — the workload GitOps control plane
:toc: left
:toclevels: 3

Each workload cluster runs its GitOps control plane (Flux) inside a permanent `gitops` vCluster that
manages the workload's own core via a `parent-cluster-kubeconfig` Secret, and drives its lab / sandbox
vClusters. This is *Option D, scoped to a workload and stripped of CAPI/CAPN*.

[IMPORTANT]
====
Read against the management/workload separation (see the anchor,
link:management-workload-topology.adoc[Management / Workload Topology]).

The earlier *Option D* put *two* things in the `gitops-mgmt` vCluster: (1) Flux managing its parent via
`parent-cluster-kubeconfig` (+ lab vClusters), and (2) CAPI/CAPN. The separation removes *only (2)* —
machine lifecycle moves to the dedicated management cluster. *(1) stays valid*: a workload cluster has
no CAPI/CAPN, so its `gitops` vCluster hosts only Flux.

Do not conflate the *two managements*: the **management cluster** (CAPI/CAPN/CAPRKE2, machine lifecycle,
a real separate cluster) and the per-workload **`gitops` vCluster** (Flux, GitOps of that workload).
The old single mutualised `gitops-mgmt` that managed *every* cluster (parent + peers via CAPI) is what
is superseded; the pattern itself lives on, once per workload, CAPI-free.
====

== Two managements — keep them separate

[cols="1,2,2,1",options="header"]
|===
| | Owns | Where | Tier

| *Management cluster* (`bioskop-mgmt`)
| machine lifecycle — CAPI + CAPN + CAPRKE2
| a real, separate cluster (cross-cluster reach)
| Tier 2

| *`gitops` vCluster* (one per workload)
| GitOps of the workload — Flux + `parent-cluster-kubeconfig`, drives lab/sandbox vClusters
| *inside* each workload cluster
| Tier 1
|===

A `gitops` vCluster hosts *only Flux* — never CAPI/CAPN. Hosting a vCluster in a workload never
re-introduces Cluster API into that workload: vClusters provision *pods* (a virtual control plane
sharing the workload's nodes), not machines, so they need no infrastructure provider.

== Why a vCluster for the workload's Flux (the Option-D benefits, retained)

Running the workload's Flux *inside* a `gitops` vCluster — rather than directly in the core's
`flux-system` — buys the original Option-D properties, now at the workload level:

* *Isolated* — a Flux failure is contained in the `gitops` vCluster; the workload core keeps running
  (just unreconciled).
* *Reentrant* — spin a `gitops-next` vCluster to test a Flux/GitOps upgrade before promoting.
* *Uniform* — the workload core is "managed like just another vCluster", via `parent-cluster-kubeconfig`.
* *Autonomous (Tier 1 preserved)* — that Flux still pulls from git and depends on no management cluster;
  the vCluster is only *where* Flux runs, not a new dependency.

The cost is a per-workload bootstrap (install the vCluster operator, create the `gitops` vCluster, seed
Flux in it) — the price of the isolation/reentrancy, versus running Flux directly in the core.

== What the `gitops` vCluster's Flux drives

* *the workload core* — addons/apps applied to its parent (the workload cluster) via
  `parent-cluster-kubeconfig`;
* *sandbox vClusters* — disposable, isolated API surfaces for *deployment testing* (try a manifest/app
  change without touching real namespaces, then delete the CR);
* *lab / tenancy vClusters* (optional, later) — isolated API surfaces for teams, same mechanism.

All of these are pods sharing the workload's nodes; none involve CAPI/CAPN.

GitOps loop. Inside the workload, the `gitops` vCluster's Flux pulls from git and manages the workload

== Two test scopes — which mechanism

[cols="1,2,2",options="header"]
|===
| You are testing | Mechanism | Where

| a *deployment / app* (manifests, an app version)
| a *sandbox vCluster* (pods, disposable), driven by the workload's `gitops` Flux
| inside the workload (Tier 1, no CAPI)

| the *workload's GitOps/Flux itself* (a Flux or config upgrade)
| a *`gitops-next` vCluster* — reentrant, promote-or-discard
| inside the workload (Tier 1)

| a *cluster / machine lifecycle* (RKE2 version, node config, CAPI upgrade)
| *function-of-git* — seed a `*-next` *real* cluster from a branch
| Tier 2, the management path (see the anchor, § _Function of git_)
|===
