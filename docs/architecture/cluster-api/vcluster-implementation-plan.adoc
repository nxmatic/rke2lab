= vCluster Implementation Plan — the workload `gitops` vCluster
:toc: left
:toclevels: 3

How to deliver the per-workload `gitops` vCluster (see
link:vcluster-gitops-architecture.adoc[vCluster GitOps Architecture]) under the management/workload
separation: the workload's Flux runs inside a permanent `gitops` vCluster, manages the workload core
via `parent-cluster-kubeconfig`, and drives sandbox/lab vClusters — *without CAPI/CAPN*.

[IMPORTANT]
====
Read against the anchor, link:management-workload-topology.adoc[Management / Workload Topology].

This is *Option D scoped to a workload, with CAPI/CAPN removed*. The old plan put Flux **and CAPI**
inside a single `gitops-mgmt` vCluster that managed one self-managed core and grew peers via CAPI. Under
the separation: CAPI/CAPN live only in the dedicated *management* cluster (machine lifecycle); each
workload's `gitops` vCluster hosts *only Flux*. No `seed-vclusters`-grows-peers module, no CAPI in the
vCluster. The rest of Option D — Flux-in-a-vCluster, `parent-cluster-kubeconfig`, reentrant upgrade
testing, lab/sandbox vClusters — is retained per workload. The full old plan is in git history.
====

== Scope — three pieces, all Tier 1, all inside a workload, no Cluster API

. the *vCluster operator* — a workload add-on, delivered like Flux;
. the *`gitops` vCluster* — permanent, hosts Flux, holds `parent-cluster-kubeconfig`;
. Flux *Kustomizations* that apply to the workload core (via that Secret) and drive sandbox/lab
  vClusters.

== Piece 1 — the vCluster operator as a Tier 1 add-on

One more manifest unit in the `manifests` module, same family as `FluxOperatorManifestsUnit` — a
`helm.cattle.io/v1` HelmChart, versioned from `ComponentVersions`:

[source,java]
----
public final class VClusterOperatorManifestsUnit extends AbstractManifestsUnit {

  public static final String MANIFEST_UNIT_ID =
      ManifestDomainCatalog.GITOPS + "/vcluster-operator";

  public VClusterOperatorManifestsUnit() {
    super(MANIFEST_UNIT_ID, List.of());
  }

  @Override
  protected void doSynthesize(final Construct scope, final ManifestsUnitContext context) {
    final String version =
        ManifestSynthesisContext.current().componentVersions().vclusterOperator();
    // helm.cattle.io/v1 HelmChart: chart=vcluster, repo=https://charts.loft.sh,
    // version=${version}, targetNamespace=vcluster-system, installCRDs
  }
}
----

It publishes with the `gitops` domain (see the anchor, § _Materialization consequences_):
`manifests.publish.gitops=true` on a workload brings the vCluster operator alongside Flux. It is
*never* published to the management cluster.

== Piece 2 — create the `gitops` vCluster and seed Flux in it

Per workload, at its initial bring-up (the workload's RKE2 auto-deploy / `gitops` domain):

. *Create the `gitops` vCluster* — a `VCluster` CR in namespace `gitops`, reconciled by the operator.
. *Seed Flux inside it* and *inject `parent-cluster-kubeconfig`* — a Secret in the vCluster's
  `flux-system` holding the *workload core's* kubeconfig, so Flux can apply to its parent:

[source,bash]
----
# inside the workload, once the gitops vCluster is Ready:
vcluster connect gitops -n gitops --print > /tmp/gitops.kubeconfig
flux bootstrap github \
  --kubeconfig=/tmp/gitops.kubeconfig \
  --owner=nxmatic --repository=rke2lab --branch=main \
  --path=gitops/workloads/<workload>/flux-system
kubectl --kubeconfig=/tmp/gitops.kubeconfig \
  create secret generic parent-cluster-kubeconfig \
  -n flux-system --from-file=kubeconfig=<workload-core-kubeconfig>
----

This is the per-workload bootstrap cost — the price of isolating Flux and enabling reentrant upgrade
testing, versus running Flux directly in the core's `flux-system`.

NOTE: There is *no* `parent-cluster-kubeconfig` pointing at a *management* cluster, and *no* CAPI in the
`gitops` vCluster. The parent here is always the *workload core*.

== Piece 3 — Flux Kustomizations (apply to the workload core)

Flux in the `gitops` vCluster applies to its parent (the workload core) via `parent-cluster-kubeconfig`,
and drives sandbox/lab vClusters:

[source,yaml]
----
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: workload-core
  namespace: flux-system            # IN the gitops vCluster
spec:
  interval: 10m
  path: ./workloads/<workload>/core # addons + apps
  prune: true
  sourceRef: { kind: GitRepository, name: flux-system }
  kubeConfig:
    secretRef: { name: parent-cluster-kubeconfig }   # apply to the workload core
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: sandboxes
  namespace: flux-system
spec:
  interval: 10m
  path: ./workloads/<workload>/sandboxes   # disposable VCluster CRs + test manifests
  prune: true
  sourceRef: { kind: GitRepository, name: flux-system }
  kubeConfig:
    secretRef: { name: parent-cluster-kubeconfig }
----

A sandbox is created by committing a `VCluster` CR under `sandboxes/`, tested against its isolated API
surface, and destroyed by deleting the CR (Flux prunes it). Lab/tenancy vClusters (optional, later) use
the same path pattern.

== The reentrancy split

* *deployment / app test* → a *sandbox vCluster* driven by this Flux (Tier 1, in-workload, disposable);
* *the workload's Flux/GitOps itself* → a *`gitops-next` vCluster* (copy the `gitops` config to a
  `gitops-next/` path with the new versions; Flux creates it; validate; promote by moving the versions
  into `gitops/`, or discard by deleting `gitops-next/`);
* *cluster / machine lifecycle* (RKE2 version, node config, CAPI upgrade) → *function-of-git*: seed a
  `<host>-mgmt-next` (or throwaway workload) *real* cluster from a branch. Tier 2 / management, no
  vCluster.

== Validation

* `VClusterOperatorManifestsUnit` synthesises a HelmChart; present on a workload
  (`manifests.publish.gitops=true`), *absent* from the management cluster.
* `kubectl --context <workload> get vcluster -n gitops` shows the `gitops` vCluster Ready; connecting to
  it, `flux get kustomizations` shows `workload-core` + `sandboxes` applied.
* `parent-cluster-kubeconfig` in the `gitops` vCluster points at the *workload core* (never a management
  cluster); no CAPI/CAPN controller runs anywhere in the workload.
* Committing a `VCluster` CR under `sandboxes/` makes Flux create the sandbox; deleting it prunes it.
