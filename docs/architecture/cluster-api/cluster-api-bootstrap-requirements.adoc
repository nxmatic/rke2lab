= Cluster API Bootstrap Requirements & Cleanup
:toc: left
:toclevels: 3

Plan for Phase 1 cleanup and flox environment architecture for cluster workloads.

== Overview

Declarative CAPI/CAPN/CAPRKE2 installation runs via manifest layers: the Cluster API Operator with
provider CRs, the Incus identity secret, the image-state ConfigMap (Stage A → Stage B handoff), the
Flux GitRepository + root Kustomization, and the SOPS age Secret are all in place as manifest units.

This document covers what remains: (1) remove the old imperative clusterctl-based installation, (2)
the flox-environment architecture for pod-level executable injection, (3) validating bootstrap with no
clusterctl dependency.

[IMPORTANT]
====
Read against the management/workload separation (see the anchor,
link:management-workload-topology.adoc[Management / Workload Topology]). Under the separation the
`cluster-api` domain (operator + provider CRs + Incus identity + image-state ConfigMap) publishes to
the *management* cluster *only* — that is where CAPI/CAPN/CAPRKE2 live. The `gitops` domain (Flux + the
vCluster operator) publishes to the *workload* clusters. Two consequences for the units below: the
`IncusIdentitySecretManifestUnit` becomes *per-remote* (one identity secret per bare-metal — bioskop +
nikopol — since CAPN drives two remotes), and the flox pod-injection architecture applies to *any*
cluster, not one named host. Porch is *descoped* (see
link:cluster-workload-completion-plan.adoc[Cluster Workload Completion Plan]).
====

== Architecture: Flox Environment Injection for Pods

=== Three-Tier Environment Model

**Goal**: Pods in any rke2lab cluster use flox-provided executables from nix store via annotation-based injection.

[mermaid]
----

    end

    subgraph BootstrapNode["Bootstrap Node (master host)"]

=== Tier 2: Bootstrap Node (Master Host)

**Components**:

- RKE2 server binary (installed by RKE2 install script)
- Nix store with flox environments
- Flox NRI plugin DaemonSet (existing pattern)

**DaemonSet responsibilities**:

- Materialize flox environments to `/srv/host/k8s-daemonset.d/runtime/flox/environment.d/`
- Update nix store on nodes
- Publish environment metadata via ConfigMap (nix store paths)

**Pattern**: Reuses existing flox NRI plugin architecture.

=== Tier 3: Cluster Workloads (Pods)

**NEW ARCHITECTURE**: Pods use flox annotations for executable injection.

**Annotation format**:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  annotations:
    flox.dev/environment: "fleet/k8s"  # or "fleet/keyhole"
spec:
  containers:
  - name: app
    image: alpine:latest  # minimal base image
    command: ["/nix/store/xxx-kubectl/bin/kubectl", "version"]
----

**Mutating admission webhook** injects:

1. **Volume mounts** - nix store read-only:
+
[source,yaml]
----
volumeMounts:
- name: nix-store
  mountPath: /nix/store
  readOnly: true
volumes:
- name: nix-store
  hostPath:
    path: /nix/store
    type: Directory
----

2. **Environment variables** - flox environment:
+
[source,yaml]
----
env:
- name: PATH
  value: "/nix/store/xxx-kubectl/bin:/nix/store/yyy-helm/bin:..."
- name: FLOX_ENV
  value: "fleet/k8s"
----

3. **Init container** (optional) - environment verification

**Webhook implementation** (future):

- Deployed in `flox-system` namespace
- Cluster-wide scope with opt-in annotation
- Reads ConfigMap for nix store paths (published by DaemonSet)
- Failure policy: Fail (missing tools should block pod creation)
- Certificate: cert-manager managed TLS

=== Environment Availability

**How environments reach nodes**:

1. Flox NRI plugin DaemonSet materializes environments to host
2. Nix store paths available for volume mounting
3. ConfigMap publishes environment metadata (paths, versions)
4. Webhook reads ConfigMap to inject correct paths

**Phase 1 scope**: Verify these environments exist and are suitable.

**Future work**: Implement webhook injection based on annotations.

== Remaining work

The near-term surface is the environment definition + removing the old imperative installation
(include fleet/keyhole in the operator environment; delete the imperative clusterctl systemd units;
decide the mesh/cicd domain toggles). Then two future tracks:

* *Environment availability* — materialize `fleet/k8s` + `fleet/keyhole` on nodes via the DaemonSet
  trampoline, publish their nix store paths in a ConfigMap, mount them by the existing flox-NRI-plugin
  volume pattern.
* *Mutating webhook* (the Tier-3 dynamic injection above) — an admission webhook reading the
  `flox.dev/environment` annotation and injecting the volumes + env vars, cert-managed, deployed in
  `flox-system`. Its design is in link:../patterns/flox-webhook-design.adoc[the flox webhook design].

== Benefits of Flox Injection Architecture

**Single source of truth**:

- Tool versions defined in flox environments
- No version drift between dev and cluster
- Update once, applies cluster-wide

**Minimal container images**:

- Base images (alpine, busybox) sufficient
- No need for kubectl/helm/etc in every image
- Smaller image sizes, faster pulls

**Consistent with existing patterns**:

- Reuses flox NRI plugin DaemonSet pattern
- Same nix store maintenance
- Unified environment management

**Easy updates**:

- Update flox environment
- Refresh DaemonSet
- All pods get new tool versions

**Developer experience**:

- Same tools locally and in-cluster
- Annotate pod, get tools
- No Dockerfile changes for new tools

== Open Questions

1. **Mesh domain at bootstrap?**
   - Tailscale provides cluster networking
   - **Answer**: Keep enabled, may be required

2. **CICD domain at bootstrap?**
   - Tekton needed for Phase 3
   - **Answer**: Keep enabled, lightweight operator

3. **Age key generation automation?**
   - Manual vs automated in seed-master
   - **Answer**: Keep manual (one-time setup, documented)

4. **Webhook namespace?**
   - flox-system vs kube-system
   - **Answer**: flox-system (separate from core K8s components)

5. **Failure policy?**
   - Fail vs Ignore for missing environments
   - **Answer**: Fail (missing tools should block pod creation)

== Success Criteria

The cleanup is done when no clusterctl remains in any flox environment and no imperative
cluster-api systemd units remain; fleet/keyhole is included in the operator environment; the manifests
module builds; the Cluster API operator installs declaratively with all provider CRs (Core,
Infrastructure, ControlPlane); and bootstrap completes with no clusterctl dependency.
