This document defines the architecture for the new `systemd-adapter` module and intentionally splits diagrams into small reviewable units.

IMPORTANT: current implementation is D-Bus-backed (`dbus-java` via `DbusSystemdStatusSnapshotProvider`).
Shell-backed probing is legacy and no longer the canonical runtime path.

== Runtime placement and Pulumi ownership

The `systemd-adapter` is designed to run on the master node itself (inside the management-cluster node runtime),
not on the operator workstation and not inside the Pulumi controlplane process.

Its architectural role is a node-local proxy/adapter boundary:

* reads systemd state locally from the master node (D-Bus via `org.freedesktop.systemd1`)
* exposes normalized HTTP status endpoints (`/status/systemd`, `/healthz/systemd`)
* provides the readiness signal consumed by Pulumi Stage A components

Pulumi owns orchestration of this component lifecycle during bootstrap:

* ensures the adapter unit is launched/verified early on the master node
* consumes adapter status endpoints for runtime/readiness decisions
* exports launch/readiness summaries as controlplane outputs

This keeps the contract clear: systemd introspection is local to the master node,
while Pulumi remains the external orchestrator and policy owner.

== Why split this architecture set

The adapter spans multiple concerns:

* bootstrap/runtime monitoring contract
* systemd state probing
* HTTP status surface consumed by operators and Pulumi
* deployment/runtime ownership boundaries

To keep reviews focused, each concern is diagrammed separately with one primary question per diagram.

=== 5) Port contract — the contract types

Review question: what crosses the host↔OSGi frontier, and does it stay free of host types?

The adapter's normalized surface is declared as `systemd-contract` types (an installed bundle
wired bundle-to-bundle inside the OSGi world, so neither side leaks its own config type across):

[cols="2,3",options="header"]
|===
| Port type | Contract

| `SystemdProbeRequest`
| The pure input crossing the readiness seam — `dbusHost`, `dbusPort`, `nodeName`, `imageBuilderHost`
  — a record with a normalizing canonical constructor (blank/absent fields fall back to `localhost` /
  `0` / `unknown`). It is COMPOSED OSGi-side by `SystemdAdapterScenario`, not filled by the flat host:
  the node's mDNS FQDN (`<cluster>-<node>.local`) and the `<cluster>-nixos` host DERIVE from the
  netplan `ClusterNetworkBlueprint` (a pure identity→topology function, the single source of network
  names), while `dbusPort` is a fixed systemd SERVICE constant — a port is not identity-derived, so it
  stays with the service, never in the blueprint. So no host config type crosses and no network host
  is hard-coded. The former fixed `localhost:0` marker survives only for an offline play.

| `SystemdRunbookInput`
| The systemd runbook trigger's input — one `@Amendment(FACET)` role, the stable cluster/node
  `Identity` the host contributes AMBIENT (mirroring the incus FACET). The scenario derives the
  network blueprint from that identity to compose the `SystemdProbeRequest` above, so the host names
  only the neutral identity (JSON on the FACET role), never a systemd or netplan type. `Optional` /
  EMPTY is the honest model of an unamended (offline) play — the scenario then falls to the marker.
|===

== Readiness — awaiting convergence, not a one-shot probe (2026-08)

`SystemdRuntimeProbe.awaitReady(request, budget)` is the systemd twin of the cluster's
`ClusterReadinessContact.awaitReady` (§ link:../osgi/cluster-edge-spec.adoc[cluster-edge-spec],
readiness-await). It does NOT snapshot the adapter once; it AWAITS convergence over the shared
`ReadinessAwait` driver (`osgi/runtime/readiness-await`): a two-tier `ReadinessBudget` — a CONNECT
deadline to reach the dbus-over-TCP endpoint (absorbing a cold boot), then a READY deadline to
converge once reachable. The edge opens ONE dbus connection, subscribes the manager's `JobRemoved`
signal, and wakes on each job completion to re-check the target's state rather than polling blind —
falling back to a bounded poll if no signal arrives. On the connect deadline it throws, surfaced as an
adapter-not-ready snapshot. This is what fixed the regression where a checkpoint probed DURING the grow
failed the instant the node was not yet up.

The budget is CONDITIONED by the grow's cold/warm `Growth` (§ link:../atlas/seed.adoc[atlas/seed], the
readiness beat): a WARM master gets a short fail-fast budget, a COLD bring-up the patient one. The
deadline VALUE lives in code (`@ReadinessDeadlines` on the scenario `@Test`, the visible default) and is
tuned per checkpoint from `rke2lab:readiness:` under the `systemd-adapter` checkpoint slug (§
link:../osgi/seed-broker-spec.adoc[seed-broker-spec], `ReadinessOverrides`).
