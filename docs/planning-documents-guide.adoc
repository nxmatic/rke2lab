== Overview

This guide helps navigate the multiple planning documents in rke2lab. As the project evolved, plans were refined and consolidated. This document explains which plans are active, which are superseded, and how they relate.

== Current Active Plans

=== 1. link:vcluster-implementation-plan.adoc[vCluster Implementation Plan] 📋 **PRIMARY PLAN**

**Status**: Active implementation roadmap

**Scope**: Phase 1.5 through Phase 6 (post-Phase 1 from original plan)

**Purpose**: Complete implementation roadmap for establishing gitops-mgmt vCluster pattern

**Use when**: You need concrete implementation steps, code examples, or validation criteria

**Key sections**:
* Three-layer bootstrap architecture (RKE2 auto-deploy → Pulumi → Flux)
* Phase 1.5: Refactor manifests/ to infrastructure-critical only
* Phase 2: Create gitops-mgmt vCluster with Flux
* Phase 3: Create seed-vclusters module
* Phase 4: Peer provisioning via Flux
* Phase 5: Lab vCluster deployment
* Phase 6: Upgrade testing pattern

**Supersedes**: Phase 2-4 sections in gitops-cluster-api-transition-plan.md

=== 2. link:vcluster-gitops-architecture.adoc[vCluster GitOps Architecture] 📐 **ARCHITECTURE REFERENCE**

**Status**: Architecture decisions and design analysis

**Scope**: Complete vCluster architecture with Option A/B/C/D analysis

**Purpose**: Understand WHY the architecture is designed this way

**Use when**: You need to understand architectural trade-offs, review design decisions, or see C4 diagrams

**Key sections**:
* Problem statement and requirements
* Four architecture options analyzed (A: centralized, B: distributed, C: hybrid, D: management vCluster)
* Decision rationale for Option D (selected)
* C4 diagrams (Context, Container, Component, Deployment, Sequence)
* Migration path from Phase 1-3
* Testing patterns

**Relationship to implementation plan**: Architecture plan provides the "why", implementation plan provides the "how"

=== Scenario 2: I need to understand why we chose gitops-mgmt vCluster

1. **Read**: link:vcluster-gitops-architecture.adoc#architecture-decision-process[vCluster Architecture - Decision Process]
2. **See**: Option A/B/C/D comparison with advantages/disadvantages

=== Scenario 3: I want to implement peer provisioning

1. **Read**: link:vcluster-implementation-plan.adoc#phase-4-peer-provisioning-via-flux[vCluster Implementation Plan - Phase 4]
2. **Reference**: link:gitops-cluster-api-transition-plan.md#phase-2-seed-peers-module-operator-driven-peer1[Original Plan - Phase 2] for CAPI patterns (still valid)

=== Scenario 4: I'm confused about which Flux to install where

1. **Read**: link:vcluster-implementation-plan.adoc#architecture-decision-three-layer-bootstrap[vCluster Implementation Plan - Three-Layer Bootstrap]
2. **Key point**:
   * Layer 1 (RKE2 auto-deploy): Flux**Operator** only (not FluxInstance)
   * Layer 2 (Pulumi): Creates gitops-mgmt vCluster, bootstraps Flux **inside** it
   * Layer 3 (Flux in gitops-mgmt): Manages everything via parent-cluster-kubeconfig

=== Scenario 5: What happened to Phase 2-3 from the original plan?

1. **Answer**: Merged into Phase 1.5-4 of vCluster Implementation Plan
2. **Why**: Skip "Flux in core" step, go directly to gitops-mgmt vCluster
3. **Benefit**: Simpler migration path, no need to move Flux later

== Common Questions

=== Q: Why are there multiple planning documents?

**A**: The project evolved. Initial plan (gitops-cluster-api-transition-plan.md) was written before vCluster architecture was fully designed. After architectural analysis, we decided to skip "Flux in core" and go directly to gitops-mgmt vCluster, requiring a revised implementation plan.

=== Q: Should I read all the plans?

**A**: No. Start with link:vcluster-implementation-plan.adoc[vCluster Implementation Plan] for implementation. Reference link:vcluster-gitops-architecture.adoc[vCluster GitOps Architecture] for design rationale. Original plan is historical context only.

=== Q: What if the plans conflict?

**A**: vCluster Implementation Plan takes precedence for Phase 1.5+. If you find conflicts, they should be resolved in favor of the implementation plan (as it's the most recent).

=== Q: Are Phase 2-3 from the original plan lost?

**A**: No, they're incorporated into the revised plan:
* Phase 2 (original) → Phase 1.5 (refactor) + Phase 4 (peers) in new plan
* Phase 3 (original) → Phase 3 (seed-vclusters) + Phase 4 (peers) in new plan

The work is preserved, just reorganized for better architecture.

=== Q: When should I update these plans?

**A**:
* After completing a phase: Update implementation plan with "✅ Complete" status
* After discovering architectural issues: Update architecture doc with lessons learned
* After making implementation changes: Update implementation plan steps
* Keep original plan as historical record (don't delete it)
